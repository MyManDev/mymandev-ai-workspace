# ADR 0014 review record

- Status: Review record for [ADR 0014](../decisions/0014-accounts-devices-and-invitations.md), which is Proposed.
- Date: 2026-10-28

This record keeps the research and the review behind ADR 0014. The ADR is authoritative; where this record and the ADR differ, the ADR applies.

The ADR was written from four research reports, checked by three independent reviews (security, consistency with the existing records and code, and desktop and operations feasibility), and revised. The sections below list the research findings with their sources, every review finding, the changes that were applied, the findings that were rejected with their reasons, and the claims that could not be verified.

Recommendations:

- Choose option C. The long-lived device credential is a key pair generated in the Electron main process with node:crypto, and the private key never leaves the device. The WebSocket authenticates by direct challenge-response in the first message, so no bearer secret ever travels on the socket. HTTP routes use short-lived opaque access tokens (32 bytes from crypto.randomBytes, base64url, stored only as SHA-256; for example 10 to 15 minutes, which is the PM's choice). A signed challenge mints them, so there is no refresh token and no rotation state.
- Amend ADR 0004:27 and packages/protocol/README.md:25 in the new ADR. A device credential becomes a registered public key, which is not a secret on the server. The 32-random-byte, SHA-256-hash rule continues to apply to access tokens and session IDs, challenges and nonces, sign-in transaction IDs and invitation tokens. ADR 0004 is Accepted, so this needs an explicit PM answer.
- Store `key_algorithm` (text CHECK) next to the public key on `devices` (additive migration per ADR 0013). v0 accepts exactly one algorithm. Recommended: Ed25519 (deterministic, fixed 32-byte key and 64-byte signature encodings, no DER versus IEEE-P1363 pitfalls). ES256/P-256 stays reserved for future Secure Enclave or TPM keys. Alternative: start with ES256 so that a later hardware key needs no new algorithm.
- Signed input: domain-separated and length-unambiguous, for example the UTF-8 lines 'mymandev-auth-v0', purpose ('ws' or 'http-token' or 'sign-in'), audience (the API origin the client connected to), base64url nonce, connectionId or challengeId, deviceId, protocolVersion. A signature for one purpose or server can then never be accepted for another, and a malicious relay server is rejected because the audience does not match.
- Gateway protocol (M2-01, under P-48). On open, the server sends auth.challenge {nonce (32 random bytes), connectionId, supported protocol versions} and starts an auth timer (for example 10 s, unref'd). Before success, exactly one auth.response frame is accepted; a second frame, any other frame or a frame larger than a small pre-auth limit closes the connection. No frame reaches decodeClientEvent or onEvent before success. Verify the signature first, then the revocation state: unknown device or bad signature closes with a generic 44xx auth_failed; a valid signature from a revoked device gets device_revoked so the real device stops retrying. On success the server sends auth.ok and builds a new frozen context of an AuthenticatedConnectionContext type with non-null identity; bindIdentity accepts only that type, mirroring the UnverifiedEvent/VerifiedEvent brands.
- Use codes in the 4000-4999 private range for auth_failed, auth_timeout, device_revoked and connection_replaced (exact numbers are M2-01's decision; ADR 0009 codes are provisional, P-24). The desktop never reconnects automatically after device_revoked or auth_failed. It reconnects with backoff after 1001 or 1006.
- Revocation while connected. The revoke transaction sets devices.revoked_at and revokes the device's access tokens. After commit, the server closes every socket of that device from a Map<DeviceId, Set<WebSocket>> registry with device_revoked, then terminates it after the grace period. Fan-out to a connection also checks its revocation flag. Keep ADR 0006's per-event revoked check, and add a periodic sweep (for example every 60 s) as a backstop. Use PostgreSQL LISTEN/NOTIFY only when the API runs more than one instance.
- Allow only one live authenticated connection per device; a newer connection replaces the older one with connection_replaced and an audit record. The desktop keeps a single connection in the main process. A cloned private key then shows up as connection flapping, which partly replaces the clone detection that refresh-token rotation would have given.
- Lost device. Any signed-in device of the same person can list and revoke the person's devices. A person without another device signs in with GitHub on a new device and revokes the lost one there, so GitHub account security is the recovery root (recommend GitHub 2FA in the docs). Revoking stops agents hosted on that device (ADR 0006). The UI must tell the person to rotate the AI provider credentials that stay on the lost device, because the cloud cannot. Notify the person's other devices when a new device registers.
- Expire devices after inactivity using the existing devices.last_seen_at column (for example 180 days, PM decision). This follows the RFC 9700 §4.14.2 idea of inactivity expiry without any rotating client state. Update last_seen_at at most once per connection or once per hour, not on every event.
- Desktop storage (desktop owner, M2-02/M1-04 shared contract). Export the private key as PKCS#8 DER, base64 it, encrypt it with safeStorage.encryptStringAsync, and write it to a file under app.getPath('userData') with an atomic write (temp file plus rename). Load it with decryptStringAsync and rewrite it when shouldReEncrypt is true. Do not use the synchronous safeStorage API, which is removed in Electron 46, and do not use keytar, which is archived. Code-sign macOS builds so the Keychain does not prompt on every update.
- Linux without a secret service: detect it (basic_text on the sync backend name; the async-provider detection has to be verified on real Linux) and by default keep the key in memory only, which means signing in again on each launch. Offer an explicit opt-in to 'remember this device without OS protection'. The desktop owner decides the UX; the ADR records the rule.
- Sign-in binding (coordinate with the OAuth-flow part of the ADR). Generate the device key before opening the system browser and send the public key, platform and label in sign-in start. The cloud API holds the GitHub client secret and does the PKCE S256 code exchange. Completion goes back to the initiating device through a loopback redirect (127.0.0.1, any port), and that device presents a signature over the sign-in transaction ID. Do not complete sign-in by polling alone, and do not use the GitHub device flow for the desktop. Use the GitHub token only to read the account identity once, then discard it.
- Rate-limit unauthenticated WebSocket connections and auth attempts per remote address, cap pre-auth connections globally, and never log auth frames, challenges or Authorization headers. Keep serializeRequest header-free as it is now.
- Keep Sec-WebSocket-Protocol for version advertisement only (for example 'mymandev.v0', as ADR 0006 consequences suggest for M2-01), never for credentials. With challenge-response a server nonce cannot travel in the handshake header anyway.
- Tests to require in the implementation: auth timeout closes; a frame before auth closes and never reaches onEvent; a wrong signature, wrong audience, wrong purpose, a reused nonce and an unknown device all close with the same generic code; a revoked device with a valid signature gets device_revoked; revoking a connected device closes its socket and stops fan-out; a second connection replaces the first; bindIdentity rejects a mismatched deviceId or actor and writes an audit record; an expired or revoked HTTP access token returns 401.

Open questions:

- PM: accept amending ADR 0004 and the protocol README so that a device credential becomes a registered public key (options A/C), or keep the 32-byte bearer device credential (option B)?
- PM: Ed25519 (simpler, software-only) or ES256/P-256 (allows a later Secure Enclave or TPM key without a new algorithm) as the single v0 algorithm?
- PM: access-token lifetime for HTTP, device inactivity expiry (last_seen_at threshold), and the auth timeout value. All three are judgment calls; no source prescribes them.
- PM: should a new device registration need approval from an existing device of the same person? It resists GitHub account takeover, but it makes recovery harder when the only device is lost.
- PM: GitHub sign-in reads identity once and discards the token, so the server cannot see when someone revokes the app's GitHub authorization or when GitHub suspends the account. Is that acceptable, or should the server keep a GitHub token or re-check identity periodically?
- Unverified: how Electron's async safeStorage fallback behaves on Linux without a secret service, and whether getSelectedStorageBackend() reports it. This needs a test on a Linux desktop without gnome-keyring or kwallet (for example a bare i3 session or a container) before the desktop storage rule is final.
- Unverified: whether GitHub prompts again or approves silently when a person who already authorized the app opens an attacker-supplied authorize URL. This determines how strongly the sign-in completion must be bound to the initiating device.
- Does the M2 HTTP API need access tokens at all, or can everything after sign-in run over the authenticated WebSocket, leaving HTTP only for sign-in start and completion? That would remove the session table from M2.
- Desktop owner: confirm that the WebSocket client and key handling live in the Electron main process (M1-04/M2-02), and agree on the IPC surface the renderer gets. This is an authentication contract and therefore a shared boundary per OWNERSHIP.md.
- When does the API run more than one instance? That decides whether revocation broadcast via PostgreSQL LISTEN/NOTIFY, and a shared challenge store for the HTTP token endpoint, are needed in M2 or later.
- Unverified: whether TLS channel binding (tls-exporter, through Node's exportKeyingMaterial) is usable behind the planned TLS termination. If not, audience binding in the signed input is the practical substitute.

Recommendations:

- Q1, person model: do NOT create placeholder `users` rows. A user who already has a `users` row from another workspace would then have two rows, and every RESTRICT foreign key (messages, agents, grants) would have to be merged. Instead, restructure `workspace_members` into the 'person' table and keep its name. Columns: `id` (new protocol brand `MemberId`, server-generated UUIDv7, primary key), `workspace_id`, `user_id` NULL (null means a predefined person not yet claimed), `display_name` (1 to 64 characters, ADR 0005 text rule, workspace-scoped), `role` (owner, admin, member), `added_by_user_id`, `created_at`, `updated_at`, `claimed_at`, `removed_at`, `removed_by_user_id`. Constraints: CHECK `(user_id IS NULL) = (claimed_at IS NULL)`; CHECK `role <> 'owner' OR user_id IS NOT NULL`; CHECK `(removed_at IS NULL) = (removed_by_user_id IS NULL)`; a partial unique index on (workspace_id, user_id) WHERE user_id IS NOT NULL AND removed_at IS NULL (one active person per account per workspace); a partial unique index on (workspace_id) WHERE role = 'owner' AND removed_at IS NULL (at most one owner); unique (id, workspace_id) as a composite foreign-key target; an index on user_id. 'Active member' (ADR 0006 reference binding, ADR 0008 `isGrantActive`) becomes: a row with this workspace_id and user_id where removed_at IS NULL. `messages`, `agents`, `agent_runs` and `permission_grants` keep referencing `users`, so history stays attributed after removal. `devices` stays account-level and needs no change for this flow. `workspaces.created_by_user_id` stays a historical fact; ownership lives in `role`. With #15, `users` gains `github_user_id bigint UNIQUE NOT NULL` (the durable ID) and `github_login text` (display only, refreshed at every sign-in, not unique). No production database exists, so the migration loses no data. It still changes an M1-03 table, which is a shared boundary, so the ADR must list it for the Project Manager.
- Q2, invitation table `workspace_invitations`: `id` (UUIDv7); `workspace_id`; `member_id` with a composite foreign key (member_id, workspace_id) -> workspace_members(id, workspace_id); `token_hash bytea UNIQUE NOT NULL` with CHECK `octet_length = 32`; `created_by_user_id`; `created_at`; `expires_at NOT NULL` with CHECK `expires_at > created_at AND expires_at <= created_at + interval '7 days'`; optional `pinned_github_user_id bigint`; `accepted_at`, `accepted_by_user_id`, `accepted_device_id` with a composite foreign key (accepted_device_id, accepted_by_user_id) -> devices(id, user_id); `revoked_at`, `revoked_by_user_id`. Paired-null CHECKs, plus a CHECK that an invitation is not both accepted and revoked. A partial unique index on (member_id) WHERE accepted_at IS NULL AND revoked_at IS NULL allows one live invitation per person; issuing a new one revokes the previous one in the same transaction, because an expired row keeps the slot, as with grants.
- Q2, token rules: 32 bytes from crypto.randomBytes, base64url, behind a fixed prefix (for example `mmdi_`, 48 characters in total) so that secret scanning and the desktop paste field can recognize it. A CRC32 checksum is optional. Store only the SHA-256 hash; a fast unsalted hash is fine at 256 bits of entropy and allows an indexed lookup (ADR 0004). Show the code once at creation; it can never be shown again, so a lost code is reissued. Only the owner or an admin creates or revokes invitations, and only for a person who is unclaimed and not removed. Default and maximum lifetime 7 days (GitHub's value, for a developer audience), minimum 1 hour; Slack and Tailscale use 30 days, which is too long for a token bound to a person. Redemption needs a signed-in device session. It runs in one transaction: a conditional UPDATE consumes the invitation (WHERE token_hash matches, not accepted, not revoked, expires_at > now(), and the pin matches if set), then `UPDATE workspace_members SET user_id, claimed_at WHERE id = $m AND user_id IS NULL AND removed_at IS NULL`, which must affect exactly one row; if the user is already an active member, the transaction rolls back with `already_member`. Add a preview endpoint that does not consume the code and returns the workspace name, the person's display name, the inviter's display name and GitHub login, and the expiry, so the joiner confirms before claiming. The code travels only in POST bodies (`POST /v0/invitations/preview` and `/accept`), never in a path or query. Responses carry `Cache-Control: no-store`. Every failure returns one client code, `invitation_invalid`; the server logs the specific reason with the invitation ID and never logs the code.
- Q2, delivery and P-48: in v0 the only carrier of the secret is a copyable code that the person pastes into the desktop 'Join a workspace' screen. The creator sends it through any channel they like; the server cannot send email, because sign-in requests no email scope. This meets P-48 completely and does not depend on registering a URL scheme. Never put the code in a custom-scheme URL or a query string: RFC 8252 §8.1 shows that another app can intercept the scheme, and on Windows and Linux Electron receives the URL as a command-line argument that Windows event 4688 can log in plain text. A one-click link can come later as an option: `https://mymandev.com/join#<code>`, served as a static page with no third-party scripts, `Referrer-Policy: no-referrer`, a strict CSP, and `history.replaceState` to remove the fragment. The page offers 'copy code' and an 'open app' link that carries nothing secret. The ADR must call this a deliberate, documented exception to P-48, because the fragment stays in browser history. How deep links are handled belongs to the desktop owner (M0-03, M1-04).
- Q2, containing a leaked code: on every claim, notify the owner and all admins (realtime when online, otherwise listed at their next sign-in) with the claimer's verified GitHub login, and let them remove the person in one step. Offer an optional pin: if the inviter enters the invitee's GitHub login, the server resolves it to the durable numeric ID (`GET /users/{username}`) when the invitation is created, and only that account can redeem it. GitHub does the same for email invitations, which only an account with that verified email can accept.
- Q3, join requests (Matrix 'knock' model): table `workspace_join_requests` with `id`, `workspace_id`, `requester_user_id`, `requested_display_name` (1 to 64 characters, ADR 0005 text rule), `created_at`, `expires_at` (+7 days), `decided_at`, `decided_by_user_id`, `decision` (approved, denied or withdrawn), and `member_id` once approved. A partial unique index allows one pending request per (workspace_id, requester_user_id). Sending a request needs a GitHub-signed-in device. The owner or an admin approves on their own authenticated device; approval creates a new member with role member in the same transaction, and the approver may edit the display name. Approvers always see the requester's verified GitHub login next to the self-chosen display name, because Matrix notes that display names enable impersonation. v0 has no free-text note: a note is a spam and phishing channel, and Matrix recommends not displaying the knock reason by default. Before approval the requester sees nothing about the workspace: no name, no people, no member count, no projects.
- Q3, abuse limits (proposed values, to be tuned): one pending request per user per workspace; at most 5 pending requests per user overall and 10 new requests per user per 24 hours; at most 50 pending requests per workspace; a 24-hour cooldown after a denial; pending requests expire after 7 days. For invitations: at most 50 live invitations per workspace and 100 created per workspace per 24 hours (GitHub allows 50 a day for new organizations); preview and accept limited to 10 failures per 15 minutes per user. Key the limits by the authenticated user ID with @fastify/rate-limit `keyGenerator`, because trustProxy is false and IP-based limits wait for the deployment decision. Use the in-memory store while there is one instance and Redis once there are several. A per-workspace block list (Matrix 'ban') and a setting to switch join requests off are follow-ups, not v0.
- Q3, guessing workspace IDs: guessing an ID is infeasible (at least 42, and normally about 73, random bits behind the timestamp) and, with per-user limits, has no practical value. The design must still not rely on it (RFC 9562 §8), and it does not, because a request only creates something an approver must accept. Recommend accepting that a workspace's existence can be revealed: answer `workspace_not_found` for unknown or archived IDs so that typos surface, and never reveal anything beyond existence. The creation time inside the UUIDv7 is visible to anyone who has the ID; accept this as P-08 did for user IDs.
- Q4, minimal roles for v0: `owner` (exactly one), `admin` and `member`. The owner and admins: define, rename and remove unclaimed people; create and revoke invitations; approve and deny join requests; remove members. Admins cannot remove the owner or other admins. Owner only: promote and demote admins, transfer ownership, archive the workspace. Members: see the workspace, leave it, and edit their own display name. Roles never imply a capability (ADR 0005 and ADR 0008); an admin cannot grant capabilities on another person's agent, and the P-44 composite foreign key already enforces this. Recommend that ordinary members cannot approve: Linear's paid plans and Tailscale restrict this to admins, and GitHub limits owners. The UI should encourage at least one admin besides the owner, so that approval is not blocked when the owner is offline (GitHub recommends two owners).
- Q5, removing a person (by the owner or an admin, or leaving on one's own): one transaction sets `removed_at` and `removed_by_user_id`; revokes the person's live invitation if the person is unclaimed; revokes unaccepted invitations that the removed person created as an admin; sets `agents.disabled_at` on their agents in the workspace's projects; and explicitly revokes their active grants with `revoked_at` and `revoked_by_user_id` set to the remover. The explicit revocation keeps an audit trail and frees the unique slot; `isGrantActive` already treats these grants as inactive. The server drops the removed user's workspace subscriptions on open connections; the per-event membership check (ADR 0006) is the backstop. Messages, runs, grants and the member row stay, since nothing is hard-deleted; the UI shows 'former member'. Rejoining creates a new member row through a new invitation or a join request, so the old period stays in history.
- Q5, removing a device: the owning user revokes it from any other signed-in device, or after signing in with GitHub on a new device (signing in again is the recovery path). This sets `devices.revoked_at`; consider adding `revoked_by_user_id`. The device credential stops working immediately, the server closes that device's connections, and agents hosted on it are disabled; their grants become inactive through `isGrantActive`. A revoked device never comes back: a reinstall gets a new server-issued device ID. Workspace admins cannot revoke another user's device, because devices belong to the account, not the workspace; they remove the person instead.
- Q5, ownership: the owner cannot be removed and cannot leave until they transfer ownership (Tailscale has the same rule). A transfer is one transaction: the target, an active claimed member, becomes owner and the old owner becomes admin; the partial unique index guarantees a single owner. v0 has no self-service recovery when the owner loses their GitHub account. Record a manual operator procedure as an open item, and rely on admins to keep the workspace running.
- Q5, runs still in progress when their agent is disabled, their device is revoked or their owner is removed: the server can stop accepting their events, but it cannot end them, because ADR 0007 allows later transitions only from the host device. The ADR must either change ADR 0007 so the server can emit `-> cancelled` with a system actor and a reason such as `member_removed` or `device_revoked`, or record that such runs stay non-terminal until M3. This is a protocol change and needs a decision.
- Q6, what a workspace ID allows: nothing without sign-in. With a signed-in device it allows exactly one thing: `POST /v0/workspaces/{workspaceId}/join-requests` with a requested display name. It never reveals the name, people, projects or member count, never selects or claims a person, and never subscribes to events. Every other route that takes a workspace ID checks active membership first. A non-member gets the same 404 as for a workspace that does not exist (the same pattern as ADR 0007's rule for unknown run IDs). The workspace ID is only routing data in REST paths and envelopes, never a credential. Because the ID is public, it may appear in URLs.
- Process and contracts: (a) Run membership commands (create person, invite, revoke, preview, accept, request, approve, deny, remove, leave, transfer) as REST endpoints authenticated by the device credential from the #15 design, not as WebSocket client events. The server announces changes as server-originated events in M2, which means new event types (a protocol change; M2-01 owns the WebSocket protocol). (b) Add the brands `MemberId`, `InvitationId` and `JoinRequestId` in packages/protocol/src/ids.ts and a `WorkspaceMember` entity ({id, workspaceId, displayName, userId | null, role}). This is a shared boundary that needs the desktop owner's agreement. (c) The desktop join screen accepts either an invitation code (claim) or a workspace ID (request); the desktop owner designs the UI. (d) For v0 the who and when columns on members, invitations and join requests serve as the audit trail; a general audit table comes later. (e) Suggested implementation issues: schema migration (members, invitations, join requests, users GitHub columns); protocol brands and entity; invitation endpoints; join request endpoints; removal, transfer and revocation effects; ADR 0007 server cancellation; desktop join UI (desktop owner); and M2-05 using the invitation path between two devices.

Open questions:

- What does 'another approved person' in the #14 decision mean: any active member, or only someone given an approver role (admin)? The recommendation assumes owner plus admin; if it means every member, the roles collapse to owner and member, and any compromised member account can admit others.
- Is claiming a predefined person strictly invitation-only, or may an approver, when approving a join request, attach the requester to an existing unclaimed person ('approve as Ali')? This would be as secure as an invitation, but it differs from the literal decision that 'claiming a predefined person needs a single-use, expiring invitation'.
- Should invitations be optionally pinned to a GitHub account in v0? Pinning needs a server call to GitHub (`GET /users/{username}`; I did not check its unauthenticated rate limit for this ADR) to resolve the login to the durable ID. Without pinning, a leaked code works for any GitHub account until it is used or expires.
- Should v0 offer only a copyable code (strict P-48), or also an https link with the code in the fragment (a documented exception, because the fragment stays in browser history)? Custom-scheme deep links must never carry the code; whether to add a scheme at all is for the desktop owner.
- For an unknown or archived workspace ID, should a join request return `workspace_not_found` (better for typos; reveals only existence) or the same response as a valid ID (better against enumeration, but a typo stays silent)?
- Is 7 days the right default and maximum for invitation lifetime (GitHub uses 7 days; Slack and Tailscale 30; Discord's API, by third-party sources, a 24-hour default with a 7-day maximum), or should the default be shorter, for example 72 hours?
- How is a workspace recovered when the owner's GitHub account is lost or deleted and no admin exists? Is a manual operator procedure acceptable, and what identity check would it use?
- Does an ownership transfer need the recipient to accept it, or does it take effect immediately with a notification?
- Who sets and edits a member's display name: the creator's name for a predefined person, the joiner's choice, or both? May members rename themselves? Should the verified GitHub login always be shown next to it?
- When the server disables agents (member removed, device revoked), should ADR 0007 gain a server-originated `-> cancelled` transition with a system actor in M2, or should runs in progress stay non-terminal until M3?
- Is restructuring `workspace_members` (surrogate key, nullable `user_id`, role) acceptable as an M1-03 schema change? No production database exists. And which names: keep `workspace_members` with `MemberId`, or rename to `workspace_people` with `PersonId`?
- Rate limiting: the in-memory store is enough for one API instance, but keying by IP depends on the deployment and proxy setup, which is not decided; for now, limits are keyed by the authenticated user. When does a shared store (Redis) become necessary?
- Does v0 need a per-workspace block list (Matrix 'ban') and a setting to switch join requests off, or are the per-user caps and the cooldown after a denial enough until abuse shows up?
- Not verified: the official Discord invite defaults (the official pages failed to load); Tailscale's single-owner and device-deletion rules (search summaries only); Notion invite-link reset behavior (search snippets only); and whether GitHub's API lets the server resolve a login to an ID without a user token under the expected load.

- Options for the OAuth flow. (a) Authorization code with PKCE through the system browser and a loopback redirect to the desktop. The code is exchanged on the API, because only the API holds the client secret, and the desktop receives a single-use, PKCE-bound login code that it exchanges by POST. (b) The OAuth device flow. Present key-pair credentials as a rejected or later option that would amend ADR 0004. Recommendations:

- Register one GitHub App for sign-in, separate from any repository access. Give it zero repository, organization and account permissions; do not request email unless a concrete need appears (data minimization). Keep expiring user tokens on, leave the device flow disabled, and register exactly one HTTPS callback (for example https://api.mymandev.com/v1/auth/github/callback) with wildcard matching off. Turn on the webhook URL with a secret so `github_app_authorization` events arrive. Reasons over an OAuth App: the revocation webhook, the 2026 profile-only consent screen, fine-grained permissions, and no coarse `repo` scope.
- Add repository access later through a second GitHub App, installed per account or organization with selected repositories, or not at all if Git keeps using the person's local credentials on the device (M1-05). Never add repository permissions to the sign-in app: that would change every sign-in consent screen, and a leaked sign-in secret would then expose repositories.
- Flow (recommended): the cloud API is a confidential client of GitHub and acts as a small authorization server for the desktop. Step 1: the desktop main process creates a code_verifier and a state (32 random bytes each, base64url), listens on 127.0.0.1 port 0 (host passed explicitly) at path /callback, and opens the system browser with shell.openExternal on `https://<api>/v1/auth/github/authorize?code_challenge=<S256>&code_challenge_method=S256&redirect_uri=http://127.0.0.1:<port>/callback&state=<state>`, built from a fixed base. Step 2: the API validates redirect_uri exactly (scheme http, host 127.0.0.1 or [::1], port 1024 to 65535, path /callback, no query or fragment), stores a login transaction with a 10-minute lifetime, and redirects to GitHub with its own client_id, its exact HTTPS callback, a new server state and its own PKCE pair. Step 3: on the GitHub callback the API consumes the transaction once, exchanges the code with client_secret, code_verifier and redirect_uri, calls GET /user, and takes `id`, `login`, `name` and `avatar_url`. Step 4: the API drops the GitHub token, issues a MyManDev one-time code (32 random bytes, SHA-256 stored, about 60 seconds, single use, bound to the desktop challenge and redirect_uri), and redirects with 302 to http://127.0.0.1:<port>/callback?code=...&state=.... Step 5: the desktop checks state, closes the listener, shows a 'return to the app' page, and POSTs { code, code_verifier, redirect_uri, device: { label, platform } } to /v1/auth/token. The API answers with { userId, deviceId, deviceCredential } in the response body.
- Do not use the device flow, polling, or a custom URL scheme for sign-in. Polling with an ID that the initiator holds can be phished in the same way as device codes, because GitHub skips consent for returning users. Custom schemes need packaging-time registration and can be claimed by other apps. If loopback is ever blocked, fall back to having the user paste the one-time code from the browser page into the app, not to polling.
- Never accept a GitHub access token from a client as proof of identity. If a token path is ever added (for example the device flow for a CLI), the API must first check the token with POST /applications/{client_id}/token and then read /user itself.
- Key the account on GitHub's numeric user ID in a provider-neutral table, for example `user_identities (user_id -> users, provider text CHECK in ('github'), provider_subject text or github_user_id bigint, login, avatar_url, created_at, last_sign_in_at)` with UNIQUE (provider, provider_subject). Validate the numeric ID as a positive safe integer. Treat login and avatar as display caches refreshed on each sign-in, never for authorization or lookup. Pre-fill `users.display_name` from the GitHub `name` only if it passes the ADR 0005 text rule and the 1 to 64 length; otherwise use `login`. The table is an additive migration (P-38) and leaves room for the later non-GitHub method.
- Device credential per ADR 0004: 32 random bytes, SHA-256 stored, one per device row, revocable on its own through `devices.revoked_at`. Because the desktop is a public client, RFC 9700 section 2.2.2 applies: rotate the credential (for example on each successful WebSocket authentication, with a short grace window for the previous value) and treat reuse of a rotated value as theft, which revokes that device. Add an idle timeout and an absolute lifetime that requires a new GitHub sign-in; the numbers are a Project Manager decision. A device keypair with a signed challenge (sender-constrained) is the later hardening option.
- Transport per P-48: REST sends `Authorization: Bearer <deviceCredential>`; WebSocket authentication is the first message after connect (M2-01), and the server fills ConnectionContext.identity only after verification. Store the credential on the desktop with safeStorage.encryptStringAsync. On Linux, warn the person when getSelectedStorageBackend() returns `basic_text`. On revocation, close that device's open sockets. bindIdentity already rejects revoked devices for every event.
- GitHub account lifecycle. Rename: no action needed, because the account is keyed on the numeric ID; refresh the cached login at the next sign-in. Revoked authorization (`github_app_authorization`): verify X-Hub-Signature-256, find the user by `sender.id`, and apply the Project Manager's policy (recommended: revoke all of that user's device credentials, so they must sign in again). Deletion or suspension: GitHub sends no signal, so the absolute credential lifetime bounds exposure; a later option is an occasional server-side check of the account. Never resolve invitations or memberships by login. If an invitation targets a GitHub account, store the numeric ID resolved when the invitation is created.
- Keep secrets out of the repository and out of the desktop. GITHUB_CLIENT_ID, GITHUB_CLIENT_SECRET and GITHUB_WEBHOOK_SECRET go through apps/api loadConfig (ADR 0010), with placeholders only in .env.example. The desktop needs no GitHub client ID at all, only the API base URL. Use separate GitHub Apps for production and development or staging, each with its own secret and callback; contributors register their own development app.
- Login transactions and codes follow ADR 0004 hashing: hash the GitHub state and the MyManDev code. Keep the server's GitHub PKCE verifier readable only for the transaction's lifetime and delete it on use or expiry; state this exception in the ADR. Rate-limit the authorize and token endpoints. Handle GitHub's limit of 2,000 token requests per hour with a clear 'try again later' response.
- Write the auth contract as a shared boundary first: the endpoint shapes, the loopback callback contract (path, parameters, close page) and the error codes. Then the API (Project Manager) and the desktop (the desktop owner) can be built independently, as OWNERSHIP.md requires for 'authentication contracts'.
- Before accepting the ADR, verify by experiment: (a) the API-to-loopback 302 in current Chrome, Edge, Firefox and Safari, including the Local Network Access behavior; (b) whether GitHub delivers `github_app_authorization` for a user who authorized but never installed the app; (c) whether DELETE /applications/{client_id}/token on our own sign-in token triggers that webhook, which decides between revoking the GitHub token right away and letting it expire after 8 hours; (d) the GitHub App consent screen with zero permissions.

Open questions:

- P-48 exception: does the Project Manager accept that a single-use MyManDev code (about 60 seconds, bound to PKCE, delivered only to a 127.0.0.1 redirect) appears in a URL query string, together with the unavoidable GitHub code on our HTTPS callback? The alternative is a paste-the-code fallback with no URL.
- Policy when a person revokes the GitHub App authorization: revoke all of their device credentials right away (recommended), require a new sign-in only at the next credential rotation, or only record the event?
- Device credential lifetime: idle timeout and absolute lifetime before a new GitHub sign-in is required (for example 30 and 90 days). Is rotation with reuse detection required in M2, or is a device keypair (sender-constrained) wanted from the start?
- Re-sign-in on the same installation: does it create a new DeviceId and revoke the old one, or keep the DeviceId (agents and messages reference host_device_id and sender_device_id)?
- Does the cloud ever need GitHub repository access (a second GitHub App), or does Git keep using each person's local credentials on the device only (M1-05)? This decides whether a second app exists at all.
- Is any email needed (notifications, invitations), or is identity limited to the numeric ID, login, name and avatar? Requesting email adds an account permission and personal data.
- Claiming a predefined person (#14): if the joiner already has a MyManDev user, is a 'person' a global user row that gets linked, or a profile scoped to the workspace? This decides whether accounts are merged or linked.
- Invitation token delivery under P-48: a deep link, a URL fragment, or a code pasted into the app? Is an invitation optionally bound to a GitHub account (by numeric ID) in addition to the predefined person?
- Should the production API accept sign-ins from fork builds of the open-source desktop app? It cannot reliably tell them apart, so this is about terms and support, not security.
- Unverified platform behavior: Chrome Local Network Access and top-level redirects to loopback, the Windows Firewall prompt for a listener bound only to 127.0.0.1, GitHub App loopback port handling (documented only for OAuth apps), and the token state of a suspended GitHub account.
- Hosting prerequisite: the recommended flow needs the API reachable over public HTTPS (callback and webhook). ADR 0010 currently keeps API_HOST on loopback until authentication exists, so the deployment task and this ADR are linked.

## Applied in the revision

- security/blocker (ConsentFix phishing of the loopback flow): verified on the Push Security ConsentFix page and RFC 9700 section 2.1.1. Rewrote the phishing threat (the prize is a MyManDev device, not a public profile). Added a __Host- attempt cookie that binds GitHub's callback to the browser that started the attempt, an API confirmation page with the GitHub login and a pairing code derived from code_challenge, a sign-in code that is minted only after Continue and reaches the loopback listener only in an auto-submitted form POST (never in a URL), and tests (callback without cookie fails; no code before confirmation). Rejected the paste-a-code alternative.
- security/major (copied key persists): the device key is now replaced at every GitHub sign-in (old-key and new-key signatures, swap in the same transaction, the desktop keeps the old key until the new one authenticates). Specified connection_replaced behavior (no auto reconnect, warning, two actions) and rewrote the threat text: on Windows (DPAPI) and with an unprotected Linux file the key can be copied, not only used while malware runs.
- security/major (stolen laptop with GitHub web session): a revocation with reason lost starts a 7-day registration lock that only another active device can lift; the desktop tells the person to end GitHub sessions, change the password, and rotate provider credentials; tests added to the REST issue. Presented under P-55.
- security/major (new device has full authority): applied parts (2), (3) acceptance, and (4): a device younger than 72 hours cannot offer ownership or promote admins; ownership transfer needs the target's acceptance within 7 days and the owner can withdraw; the takeover threat no longer claims that older devices win.
- security/major and consistency/major (unclaimed admin): an unclaimed person is always a member (CHECK), only the owner promotes and only a claimed person, demotion revokes the admin's live invitations in the same transaction, owner and admins can list live invitations with their creators; tests added.
- security/major, consistency/major, feasibility/major (database growth, per-address limits behind a proxy, GitHub token budget): sign-in attempts, sign-in codes and access tokens moved to API memory and the two tables dropped (verified ADR 0011: no DELETE); global caps before authentication; per-address limits valid only when the API is reached directly or after P-63 sets trustProxy (verified app.ts trustProxy false); per-device limit on access tokens; 20 active devices and 10 registrations per account per 24 hours; workspace creation limit; token-exchange counter with a warning and sign_in_unavailable.
- security/major and feasibility/major (Linux memory-only mode breaks the device model): replaced with a passphrase-encrypted key file (scrypt and AES-256-GCM from node:crypto) and an explicit unprotected-file choice; an installation that loses its key names its previous device, which the server revokes as replaced; the Linux rule stays open until the verification issue names the fallback API (verified: Electron documents getSelectedStorageBackend only in the synchronous section and no detection for the asynchronous fallback).
- security/minor (app visibility): verified on GitHub docs that a private app can be authorized only by members of the owning organization. Added public (Any account), no authorization during installation, no setup URL, and that installations grant nothing and installation events are ignored.
- security/minor (proxy logs and token exchange in URL): verified GitHub docs describe the exchange as query parameters. The exchange now sends parameters in a form-encoded body, GitHub response bodies are never logged, the proxy rule is a condition of P-63, and log-capture tests cover failed and timed-out exchanges. Body acceptance by GitHub is added to the verification list.
- security/minor (removal and runs): removal also cancels every unfinished run the removed person requested on other members' agents; the desktop stops local execution on device_revoked, removal, and server cancellation; the record states that a stolen or hostile device cannot be stopped from the cloud.
