# ADR 0016: Desktop toolchain and Electron security baseline

- Status: Accepted (2026-11-01)
- Date: 2026-11-01
- Decided by: Project Manager

## Context

M0-03 (#3) establishes the Electron application shell in `apps/desktop`: a development entry point, a React renderer, TypeScript, a minimal shell with a screen structure, and integration with the shared workspace tooling. The product screens (M0-04, #6), the local runtime and its IPC (M1-04, #22), repository inspection (#23), and packaging (#17) build on it.

Earlier decisions constrain the toolchain:

- [ADR 0001](0001-internal-packages-export-typescript-source.md): workspace packages export TypeScript source. The renderer uses `moduleResolution: "bundler"` at the renderer language level (ES2024), and Electron main and preload code that imports a workspace package is bundled.
- [ADR 0002](0002-node-test-runner.md): a bundled workspace may use Vitest in its own `devDependencies`, matched to its Vite version, with `"test": "vitest run"`. Tests use dependency injection instead of module mocks.
- [ADR 0003](0003-zod-runtime-validation.md): the renderer runs under a strict Content Security Policy without `eval`.
- [ADR 0014](0014-accounts-devices-and-invitations.md), "Storage and transport on the device": the main process takes the single-instance lock before it touches the device key, and the renderer gets narrow IPC results only. Its dependency policy leaves the Electron version policy to M0-03.

Facts checked on 2026-11-01:

- Electron 45.0.0 was released on 2026-10-21 and is 14 days old on 2026-11-04. The newest Electron 44 release that was at least 14 days old on 2026-11-01 was 44.9.0, released on 2026-10-17.
- Electron 42 and later have no install script; Electron 41 still downloaded its binary in a `postinstall` script. The npm package ships a `checksums.json` with the SHA-256 of every release archive and downloads the binary on first use: through its `install-electron` command, its `electron` command, or a `require("electron")` from Node.js. The archive is checked against `checksums.json`, which the lockfile's integrity hash covers. `ELECTRON_SKIP_BINARY_DOWNLOAD`, which the old `postinstall` script read, is read by neither Electron nor `@electron/get` any more.
- The macOS binary in the Electron release archive has only an ad-hoc signature. `codesign -dv` reports `flags=0x20002(adhoc,linker-signed)`, `Signature=adhoc`, `TeamIdentifier=not set`, and `Sealed Resources=none`, and `codesign --verify --deep --strict` fails with "code has no resources but signature indicates they must be present". The signature therefore proves nothing about the origin of the binary. Code signing is part of packaging (#17).
- GHSA-jr5w-w6x2-84p9 (high, published 2026-10-23) affects Electron 44 releases before 44.9.1, which was released on 2026-10-20: without the fix, a certificate issued through compromised eMudhra intermediates is accepted for TLS connections. Apps that make no network connections are not affected. `npm audit` reports it for 44.9.0.

## Options considered

| Area             | Option                                                         | Result                                                                                                                                                                                                                              |
| ---------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bundler          | electron-vite with Vite                                        | One configuration for the main process, the preload script, and the renderer; a development server with hot reload for the renderer, and with `--watch` a rebuild and restart of the main process; no packaging, so #17 stays open. |
|                  | Electron Forge with its Vite plugin                            | Build and packaging in one tool; it would decide the packaging of #17 now.                                                                                                                                                          |
|                  | Vite for the renderer, a separate bundler for main and preload | Two toolchains and a hand-written development process.                                                                                                                                                                              |
| Screen structure | A router library                                               | URL-based navigation, which needs hash routing or a scheme handler that answers every route with `index.html`, and which the navigation guard would have to allow.                                                                  |
|                  | A typed screen state with a reducer                            | No dependency; the screens are a union type, and switching screens is a pure function that tests cover.                                                                                                                             |
| Tests            | Vitest in `apps/desktop`                                       | Runs `.tsx` tests with the same transform as the build (ADR 0002).                                                                                                                                                                  |
|                  | `node:test`                                                    | No `.tsx`.                                                                                                                                                                                                                          |
| Render tests     | `react-dom/server` in the Node.js environment                  | No new dependency; checks the rendered markup.                                                                                                                                                                                      |
|                  | jsdom or happy-dom                                             | A DOM emulation library as a new dependency; needed only once tests click through components.                                                                                                                                       |

## Decision

1. Electron, with this version policy: the desktop uses the newest supported major version whose exact release is at least 14 days old. Patch releases follow the same 14-day rule. A security release does not wait: as for every dependency, the 14-day cooldown applies to version updates only ([WORKSPACE.md, "Dependency updates"](../../development/WORKSPACE.md#dependency-updates)). The shell starts on Electron 44: the Project Manager approved 44.9.0, and the shell uses 44.9.1 instead, the first Electron 44 release that fixes GHSA-jr5w-w6x2-84p9; it was 12 days old on 2026-11-01. The move to Electron 45 is a separate pull request once a 45 release is 14 days old, from 2026-11-04.
2. electron-vite with Vite bundles three targets into `apps/desktop/out/`, which the root `.gitignore` and the root ESLint ignores already cover:
   - the main process from `src/main` as an ES module (the workspace sets `"type": "module"`);
   - the preload script from `src/preload` as CommonJS (`index.cjs`), because a sandboxed preload script cannot be an ES module;
   - the renderer from `src/renderer/index.html`.
3. Packages that the bundles contain, including workspace packages, are `devDependencies` of `@mymandev/desktop`. electron-vite leaves every package listed in `dependencies` out of the main and preload bundles and loads it from `node_modules` at runtime (its `build.externalizeDeps` default), which ADR 0001 rules out for workspace packages. `dependencies` stays empty until a package must be loaded at runtime, for example a native module; how such a package ships is part of #17.
4. React 19 for the renderer. `react` and `react-dom` are `devDependencies`, because the renderer bundle contains them.
5. No router library. The shell keeps a typed screen state: `ScreenId` is a union of the screen names, and `shellReducer` switches screens ([`screens.ts`](../../../apps/desktop/src/renderer/screens.ts)). The Project Manager delegated this choice. A router can be added when the application needs deep links or a history.
6. Vitest for the desktop tests, in the Node.js environment, without DOM emulation. Render tests use `renderToString` from `react-dom/server`. Code that touches Electron is kept thin; the logic it uses (window options, the navigation guard, the renderer URL, the guards, and the `app://` scheme) is in plain functions that take minimal interfaces, and tests call them with fakes (ADR 0002).
7. The security baseline of the shell:
   - Every window runs its renderer with `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false` (also in workers and subframes), `webSecurity: true`, `allowRunningInsecureContent: false`, `webviewTag: false`, and `navigateOnDragDrop: false`, set explicitly. Developer tools are on only when the application is not packaged (`devTools: !app.isPackaged`) ([`window.ts`](../../../apps/desktop/src/main/window.ts)).
   - Every web contents gets `installContentsGuards` ([`guards.ts`](../../../apps/desktop/src/main/guards.ts)): `window.open` is denied; `will-navigate`, `will-frame-navigate`, and `will-redirect` to a URL outside the application are prevented ([`navigation.ts`](../../../apps/desktop/src/main/navigation.ts)): with the built files, only `app://renderer/index.html` itself, without a query, is navigable, and other `app://` paths are not; with the development server, any URL on its origin; `will-attach-webview` is prevented; and Bluetooth device selection is cancelled.
   - Every session gets `installSessionGuards` once: the default session after `ready`, and every session created later through `app.on("session-created")`, so that a future partition is covered too. The permission request handler answers false, the permission check handler and the device permission handler return false, HID, serial, and USB device selection is cancelled, and `will-download` is prevented, so no download starts. Without a check handler, Electron grants permission checks, so `Notification.permission` read "granted" in the renderer.
   - The main process takes the single-instance lock first (ADR 0014). A second instance quits and the first one shows its window.
   - The built renderer loads from `app://renderer/index.html`, not from a `file:` URL ([`app-protocol.ts`](../../../apps/desktop/src/main/app-protocol.ts)). The scheme `app` is registered with `protocol.registerSchemesAsPrivileged` before the `ready` event as `standard` and `secure`, with no other privilege, and handled with `protocol.handle`. The handler serves only files inside `out/renderer/`: methods other than GET and HEAD get 405; another host, credentials, a port, invalid percent-encoding, a missing file or a directory, a file whose real path after symbolic links is outside the real path of `out/renderer/`, and a path segment that after percent-decoding is empty, ends with a dot or a space (which Windows drops; this also covers `.`, `..`, and `...`), is a Windows device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`, with or without an extension, in any case), or contains `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`, or a control character get 404. Every response, errors included, carries the production Content Security Policy as a `Content-Security-Policy` header and `X-Content-Type-Options: nosniff`; files also carry the Content-Type of their extension. The page's origin is `app://renderer`, so `'self'` in the Content Security Policy means exactly these files, and the navigation guard compares scheme, host, and port with this URL.
   - A packaged application always loads its built files and ignores `ELECTRON_RENDERER_URL`. During development, that variable must be an http URL on a loopback host.
   - The preload script exposes one object, `window.desktop`, through `contextBridge` ([`desktop-bridge.ts`](../../../apps/desktop/src/shared/desktop-bridge.ts)). It holds only the Electron version until M1-04 adds the typed IPC interface.
   - The production Content Security Policy is defined once, in [`content-security-policy.ts`](../../../apps/desktop/src/shared/content-security-policy.ts): `default-src 'none'`, and only `'self'`, the page's own origin, for scripts, styles, images, and fonts. No `unsafe-inline`, no `unsafe-eval`, no remote origin, and no network connection from the renderer. The main process sends it as a header with every `app://` response, and the renderer's Vite plugin ([`config/csp.ts`](../../../apps/desktop/config/csp.ts)) writes it into the meta element of `index.html` in builds and on the development server. The source `index.html` holds `default-src 'none'`, so a page that missed that step stays blocked. For `electron-vite dev`, the plugin also creates a nonce for each start of the development server, adds it to `script-src` and `style-src` for the inline scripts and styles that the server injects, and allows `connect-src 'self'` for the hot reload WebSocket.
8. Repository inspection (#23) reads Git with the system `git` through `execFile`, without a shell, using read-only commands, and watches files with `fs.watch`. No Git library is added.
9. CI does not download the Electron binary and does not launch Electron. `npm ci`, the type check, the tests, and `npm run build -w @mymandev/desktop` need no binary; the Check workflow runs the build on Linux, Windows, and macOS. Electron 42 and later download nothing during `npm ci`, so `ELECTRON_SKIP_BINARY_DOWNLOAD` is not needed, and the workflows do not set it; the Project Manager's goal, no download and no launch in CI, holds without it. Tests that launch Electron come later. Packaging, code signing, and Electron fuses stay with #17; see the open items below.
10. The desktop `dev` script runs `install-electron` before `electron-vite dev`. It downloads the binary once, checks it against the SHA-256 in `checksums.json`, and returns at once when the binary is present. Because the macOS binary is only ad-hoc signed, the integrity of the binary rests on that SHA-256, which comes from the npm package and is covered by the lockfile's integrity hash.

## Consequences

- The shell runs an Electron release with the fix for GHSA-jr5w-w6x2-84p9, before sign-in (#94) and the WebSocket client (#26) open TLS connections. `npm audit` no longer reports the advisory.
- The first `npm run dev -w @mymandev/desktop` downloads the Electron archive for the platform (about 130 MB on macOS) into the Electron cache. A clean `npm ci` downloads nothing.
- electron-vite does not minify by default; the renderer bundle is about 570 KB and is loaded from disk.
- If `ELECTRON_RUN_AS_NODE` is set in the environment, as some shells and tools do, Electron runs as plain Node.js and the main process fails to import `BrowserWindow`. The desktop README says to unset it.
- Electron takes its application name from `package.json`. Without a `productName`, it is `@mymandev/desktop`, which also names the application data folder that a development run creates. See the open question below.
- Built files load from `app://renderer`, as Electron's security checklist recommends, instead of `file:`, where `'self'` would cover other local files. The renderer's origin `app://renderer` is not an http or https origin, so the API's WebSocket Origin check would reject it (P-02); ADR 0014 places the cloud connection in the main process, which sends no Origin header.
- Permission checks now return false. A later feature that needs a web permission, for example notifications, changes the guard and its test.
- The screen state replaces a router. M0-04 extends `SCREEN_IDS` and the screens; a screen that needs parameters adds them to the state.
- Update of 2026-11-01 (#22): applied under the Project Manager's rule to apply the recommended option. `window.desktop` now also holds the runtime API of the typed IPC contract, `getStatus` and `subscribeStatus`; the object stays frozen and holds no `ipcRenderer` and no generic invoke, and the main process checks the sender and the arguments of every call ([apps/desktop/README.md, IPC contract](../../../apps/desktop/README.md#ipc-contract)). The main process imports zod, at the exact version of `@mymandev/protocol`, as a `devDependency` of `@mymandev/desktop`, because packages that the bundles contain are `devDependencies` (Decision, item 3). This meets the intent of [ADR 0003](0003-zod-runtime-validation.md)'s rule that every workspace importing zod declares it as a `dependency`: one exact version and one hoisted copy, with zod carried in the main process bundle. The preload script and the renderer import only zod's types. The text above is unchanged.
- Update of 2026-11-01 (#23): repository inspection (Decision, item 8) is refined, without a new dependency, for the Project Manager's review. Git is started by its absolute path from an absolute folder of `PATH`, because Windows looks up a program name alone in the child's working folder, here the repository, first. The environment holds no `GIT_` variable from outside and only the absolute folders of `PATH`, and sets `GIT_OPTIONAL_LOCKS=0`, `GIT_NO_LAZY_FETCH=1`, and an empty `GIT_ALLOW_PROTOCOL`, so a partial clone fetches nothing on any Git version. Every command gets `-c core.fsmonitor=`, `-c core.useBuiltinFSMonitor=false`, `-c protocol.allow=never`, and `-c protocol.<name>.allow=never` for `ssh`, `git`, `file`, `http`, `https`, and `ext`, and `git status` turns off the programs of every configured filter driver, the one with an empty name included, and does not enter submodules, because a repository's own configuration, and files it includes, can name programs that `git status` runs; a test with the real `git` shows that a plain `git status` runs them and the inspection does not. Git 2.15 or later is required, checked with `git version`, because `GIT_OPTIONAL_LOCKS` exists since then; the ownership check (`safe.directory`) needs Git 2.35.2 or later. How a packaged application finds Git (on macOS, the Finder's short `PATH` leads to the `/usr/bin/git` stub) is left to #17. A folder inside a working tree is refused, not widened to its top level. A mount is identified by an in-memory mount ID, not a protocol `RepositoryId`, and mounts are not stored; storing them and the remote URL in the data model ([ADR 0013](0013-m1-data-model.md)) need a persistence decision ([apps/desktop/README.md, Repositories](../../../apps/desktop/README.md#repositories)). The text above is unchanged.
- Update of 2026-11-02: the Project Manager decided the data folder, one of the open items below. The application keeps its local data in a folder named `MyManDev` in Electron's `appData` path (`%APPDATA%\MyManDev` on Windows, `~/Library/Application Support/MyManDev` on macOS, `~/.config/MyManDev` on Linux), not in a folder named after the application name. The main process sets it as the `userData` path before anything reads it, and then takes the single-instance lock, which Chromium keeps in that folder ([apps/desktop/README.md, Local data](../../../apps/desktop/README.md#local-data)). The application name and the application ID stay with #17. The text above is unchanged.
- Update of 2026-11-02: the Project Manager decided the Dependabot groups, one of the open items below, as recommended. `.github/dependabot.yml` groups `react` with `react-dom`, and Vite with Vitest, `@vitejs/plugin-react`, and electron-vite, for major, minor, and patch updates, because these packages work only at matching versions ([docs/development/WORKSPACE.md, Dependency updates](../../development/WORKSPACE.md#dependency-updates)). The text above is unchanged.

## Dependency policy

- Electron: the newest supported major version whose exact release is at least 14 days old; patch releases follow the 14-day rule; security releases do not wait; exact pin; a `devDependency` of `@mymandev/desktop`; a major update in its own pull request.
- electron-vite 6, Vite 8, `@vitejs/plugin-react` 6, and Vitest 5: exact pins, `devDependencies` of `@mymandev/desktop` only. Vitest and the React plugin stay matched to the Vite major version; update them together.
- React 19 and `react-dom` 19 at the same exact version, with `@types/react` and `@types/react-dom` 19: exact pins, `devDependencies`.
- `@types/node` for Node.js 24, at the same exact version as the other workspaces.
- Not added: a router library, jsdom or happy-dom, a Git library, and Electron Forge.
- Install scripts: none of these packages has one, so the lockfile's `"hasInstallScript": true` entries stay the four of [ADR 0011](0011-drizzle-sql-migrations.md). Native code arrives as prebuilt binaries: Rolldown and Lightning CSS in optional per-platform packages, and `@electron-internal/extract-zip`, which Electron uses to unpack its archive, with the binaries of every platform in one package. The Electron binary itself is downloaded on first use, as described above.

- M0-03 acceptance checks on macOS, 2026-11-01: `npm run build -w @mymandev/desktop` succeeded; `npm run dev -w @mymandev/desktop` started the main process and the renderer, and the renderer connected to the development server without a policy violation; `electron-vite preview` loaded the built files under the production policy. The first runs used Electron 44.9.0 and loaded the built files from `file:`; after the move to 44.9.1 and to `app://renderer`, both runs were repeated with the same results. In addition, in both runs `Notification.permission` and `navigator.permissions.query` for notifications reported "denied", and a `file:` navigation was blocked. In the preview, the page loaded from `app://renderer/index.html`; the stylesheet came back with 200 and `text/css`, and script requests for `assets/missing.js`, `..%2fmain%2findex.js`, `%2e%2e%2f%2e%2e%2fpackage.json`, `..%5cmain%5cindex.js`, and `../../main/index.js` (which the browser sends as `/main/index.js`) came back with 404. The changes of the second security review (the policy header on every `app://` response, navigation limited to `app://renderer/index.html`, the download guard, the guards for every session, and the Windows name rules) were verified by the tests and the build only, where the built `index.html` carries the full policy: Electron was not launched for them, because the Project Manager was using the Mac and every Electron window takes the focus. With the binary removed, the build, the type check, and the tests passed without a download. The darwin-arm64 archive of Electron 44.9.1 matched its SHA-256 in `checksums.json`: `ff597552c9c7b0b16c39a7fb93a346ee7148afbd372ebcf0c18415482c49fbea`.
