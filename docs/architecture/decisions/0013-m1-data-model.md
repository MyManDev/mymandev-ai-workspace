# ADR 0013: M1 data model conventions and the M1-03 tables

- Status: Accepted (2026-10-28)
- Date: 2026-10-27
- Decided by: Project Manager

## Context

Issue #21 lists users, devices, projects, repositories, agents, conversations, messages, permission grants, and agent runs. Identities must match the protocol ([ADR 0004](0004-uuidv7-identifiers.md) to [ADR 0008](0008-capability-vocabulary-v0.md)). Permission grants depend on M1-06. Users and devices depend on the account model decision (#15). Destructive migrations are out of scope. Database entities consumed by desktop and cloud are a shared boundary.

## Options considered

- PostgreSQL enums, or `text` with CHECK constraints (recommended, because enum changes are awkward inside the single migration transaction of Drizzle).
- A generic soft-delete column, or explicit lifecycle columns (recommended: `archived_at`, `disabled_at`, `revoked_at`, `removed_at`, and `deleted_at`, where each has a meaning).
- Database-generated or application-supplied IDs (recommended: application, [ADR 0004](0004-uuidv7-identifiers.md)).

## Decision

Conventions for every table:

- `uuid` primary keys supplied by the application; no default. ID columns carry the protocol brands (`UserId`, `DeviceId`, and so on), so assigning one ID kind to another column is a compile error.
- `timestamptz` everywhere; `created_at DEFAULT now() NOT NULL`; `updated_at` on mutable entities, maintained by the data layer ([ADR 0011](0011-drizzle-sql-migrations.md)).
- Foreign keys `ON DELETE RESTRICT`. Nothing is hard-deleted in M1.
- Ownership rules that span tables are composite foreign keys, not only application checks. A composite key targets a composite unique key on the parent, for example `devices (id, user_id)`. PostgreSQL's default `MATCH SIMPLE` skips the check when an optional column is null, which is the intended behaviour for optional repositories and for the author column that is not used.
- Vocabularies as `text` with a CHECK that matches the protocol constant, proven by a test.
- Length CHECKs that match the protocol limits for human-entered text. The character rule of [ADR 0005](0005-workspaces-contain-projects.md) stays in the protocol, because PostgreSQL regular expressions have no `\p{...}` classes.
- Explicit snake_case column names; TypeScript property names in camelCase.
- Production target: PostgreSQL 18, matching the PGlite used in tests.

Update of 2026-10-29 (#74), following ADR 0015 (P-79, P-82): a `provider_connections` table (`id`, `host_device_id` -> devices, `created_at`, `removed_at`; unique (`id`, `host_device_id`)) holds connection metadata, never a credential. `permission_grants` gains `provider_connection_id` -> provider_connections and `host_device_id`; the scope CHECK requires exactly one of `repository_id` and `provider_connection_id`, the latter exactly for `provider.use`; the second partial unique index is per (agent, capability, provider connection); (`grantee_agent_id`, `host_device_id`) -> agents (`id`, `host_device_id`) and (`provider_connection_id`, `host_device_id`) -> provider_connections (`id`, `host_device_id`) keep a `provider.use` grant on a connection of its agent's host device. `permission_grants.id` is typed as `PermissionGrantId`. The text above is unchanged.

The message sequence is allocated per conversation in the insert transaction: the writer increments `conversations.last_seq` with an `UPDATE ... RETURNING` and inserts the message with the returned number. The number a client sees therefore reveals nothing about other conversations or workspaces. A global identity column would: the gaps between two messages would show how many messages other workspaces wrote in between. The `UPDATE` locks the conversation row until the transaction ends, so concurrent writers to one conversation are serialized; different conversations do not wait for each other. The first message writer (M2-03) adds the allocation as a database package function. Event sequences in M2 follow the same rule (per workspace or per run, never global).

## Consequences

- One grant row grants exactly one capability. There is no wildcard, role, or level column, so the data model cannot express an inferred capability.
- The database rejects rows that mix owners, devices, and projects: an agent on a device of another user, a grant or run in another project than its agent, a grant or run on a repository of another project, a grant by a user who does not own the agent, and a message from a device that does not belong to its author.
- An expired grant still occupies the unique slot until it is revoked, because an index predicate cannot use `now()`. M1-06 decides whether re-granting revokes the expired row first or extends it; `isGrantActive` treats it as inactive either way.
- Server ordering of messages comes from `seq` within a conversation, never from client time.
- A device retry of the same message hits the unique (`sender_device_id`, `client_event_id`) index and fails with 23505 instead of creating a duplicate.
- Adding authentication columns later (#15) is an additive migration.
- If M1-06 changes the grant shape after M1-03 is merged, that is a new migration, possibly a destructive one. Hence P-34.
