# ADR 0007: Agent run lifecycle v0

- Status: Accepted (2026-10-28)
- Amended by [ADR 0014](0014-accounts-devices-and-invitations.md)
- Date: 2026-10-27
- Decided by: Project Manager

## Context

Agents run on their host device. Other members see run progress. The state machine must be the same in the protocol, on the server, and in the database, and terminal states must stay terminal.

## Options considered

- One `awaiting_input` state for both "waiting for a permission approval" and "waiting for a human answer" (recommended), or two states. Two states add a protocol change for every new reason to wait.
- Retry as a new run (recommended) or as a transition back from `failed`. A transition back would make terminal states non-terminal.

## Decision

| From              | Allowed next states                                  |
| ----------------- | ---------------------------------------------------- |
| (created, `null`) | `queued` (emitted by the server only)                |
| `queued`          | `running`, `failed`, `cancelled`                     |
| `running`         | `awaiting_input`, `completed`, `failed`, `cancelled` |
| `awaiting_input`  | `running`, `failed`, `cancelled`                     |
| `completed`       | none (terminal)                                      |
| `failed`          | none (terminal)                                      |
| `cancelled`       | none (terminal)                                      |

- A retry is a new run with a new `RunId`, linked through `correlationId`.
- Creating a run is a server command (M2). The server allocates the `RunId` ([ADR 0004](0004-uuidv7-identifiers.md)), stores the run, and emits `null -> queued` with a `system` actor and `deviceId: null`. A device never sends a creation transition; `decodeClientEvent` rejects `previousState: null` with `not_allowed_from_device`.
- Every later transition comes from the agent's host device, with the actor `{ kind: "agent", agentId }` matching `payload.agentId` (`invalid_actor` otherwise). The server accepts it only if the run exists in the event's workspace with that agent ([ADR 0006](0006-event-envelope-v0.md), reference binding), `previousState` equals the stored state (optimistic concurrency), and `canTransition()` allows it. The server answers an unknown run ID with the same rejection as a run in another workspace, so a device cannot probe which run IDs exist.
- A cancel request from another member is a command. Commands are out of scope for v0.
- The database stores `state` with a CHECK constraint on the six values and a second CHECK: `finished_at` is set exactly when the state is terminal (M1-03).

## Consequences

- The protocol enforces the transition rule inside the payload schema, so every decoder rejects an illegal transition.
- Retries keep a clean audit trail: one run never moves from `failed` back to `running`.

## Dependency policy

No new dependency.

- Update of 2026-11-24 (#35), following the defaults of 2026-11-24 on #35 until the Project Manager decides: the agent's host device runs its runs with a supervisor in the desktop main process. It picks up the unfinished runs of the open project whose agent it hosts and that is not disabled, one run of an agent at a time, the oldest first. A queued run that cannot run on the device (no executor for its provider kind, or a provider connection that is not one of the device's) fails at once with a reason; otherwise the device sends `queued -> running` and reports the outcome as `completed` or `failed`. A run interrupted on the host (a restart, a crash, a lost connection) is reported `failed`; a run stopped because a grant became inactive or the sign-in ended is reported `cancelled` (#55, decision of 2026-11-19). There is no resume: a retry is a new run. The host's reasons are codes of the desktop, sent as plain `reason` text, not a protocol list. As part of the default for a queued run that cannot run on the device, and also a default until the Project Manager decides, a queued run without a provider connection, which only the development seed creates, is left queued; every other queued run that cannot run fails at once, also before the provider adapters (#30, #31) register an executor. Whether the device checks `provider.use` before `queued -> running` is still open. The text above is unchanged.
- Update of 2026-11-25 (#35, #55). Decided by the Project Manager in D13: before `queued -> running`, the host device checks `provider.use` for the run's provider connection with its permission enforcement point, immediately before each send of the start, and a run whose agent has no active grant of `provider.use` on that connection (`no_grant`) fails at once with the host reason `provider_use_denied`; it does not stay queued. Also decided by the Project Manager on 2026-11-25: every other denial before a start (a denial of the sign-in, or a check that cannot be made, for example an unusable grant store, an invalid clock, or an enforcement point that fails) leaves the run queued; it does not start and is checked again later, after the next change of the grants or the next reload of the runs. As implementation details of the desktop, not decisions: the check is made again once the server acknowledged the start and before the run executes, because the grants may change while the start is on its way, and a denial then ends the run, which is already `running`, with the mapping for a running action that is checked again after a change of the grants (a grant that is no longer active is `cancelled` with `grant_inactive`, a denial of the sign-in is `cancelled` with `signed_out`, and a check that cannot be made is `failed` with `grant_check_unavailable`, accepted by the Project Manager on 2026-11-25, #55); and a grant created moments before a run can still lose the race to the device's next read of its grants, and the run then fails with `provider_use_denied`. The check comes after the run's provider connection and executor are found, so a run without an executor for its provider kind still fails with `no_executor` first. This answers the question that the previous update left open. The text above is unchanged.
