# @mymandev/database

The PostgreSQL baseline: the Drizzle schema of the M1 tables and of the account, device key, membership, and audit tables, the SQL migrations, a migration command, typed connection handling, and errors that never carry query data. The decisions behind it are recorded in [ADR 0011](../../docs/architecture/decisions/0011-drizzle-sql-migrations.md), [ADR 0012](../../docs/architecture/decisions/0012-pglite-database-tests.md), [ADR 0013](../../docs/architecture/decisions/0013-m1-data-model.md), and [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md).

No application uses this package yet. The cloud API imports its query functions and types from `@mymandev/database` with the first feature that stores data (M2).

## Local PostgreSQL 18

Development and production use PostgreSQL 18. Install it natively, for example with the installer from postgresql.org on Windows, Postgres.app or Homebrew `postgresql@18` on macOS, or the PostgreSQL packages of your Linux distribution. Docker is not required.

### Roles

The database uses two roles:

- `mymandev_migrator` owns the database and the schema. Only `npm run db:migrate` connects as this role, through `DATABASE_MIGRATION_URL`.
- `mymandev_app` is the role of the application (from M2, through `DATABASE_URL`). It gets `CONNECT` on the database and `SELECT`, `INSERT`, and `UPDATE` on tables, and nothing else: no `DELETE` or `TRUNCATE`, because nothing is hard-deleted; no `CREATE` and no temporary tables; and no access to the `drizzle` schema that records the applied migrations.

PostgreSQL lets every role connect to a new database and create temporary tables in it. The script below removes these defaults, so apart from superusers only the two roles can connect.

Run this once per server in `psql` as a superuser. How to start `psql` as a superuser depends on the installation:

- Windows installer: `psql -U postgres`, with `C:\Program Files\PostgreSQL\18\bin` on `PATH`, or with the full path to `psql.exe` in that folder.
- macOS with Homebrew: `psql -d postgres`. Homebrew makes your macOS user the superuser; it creates no `postgres` role.
- macOS with Postgres.app: the bundled `/Applications/Postgres.app/Contents/Versions/latest/bin/psql -d postgres`, which connects as your macOS user.
- Linux distribution packages: `sudo -u postgres psql`. The default `pg_hba.conf` lets only the `postgres` operating system user connect as `postgres`.

Use real passwords from a password manager or secret store instead of `change-me`:

```sql
CREATE ROLE mymandev_migrator LOGIN PASSWORD 'change-me';
CREATE ROLE mymandev_app LOGIN PASSWORD 'change-me';
CREATE DATABASE mymandev OWNER mymandev_migrator TEMPLATE template0 ENCODING 'UTF8';
REVOKE ALL ON DATABASE mymandev FROM PUBLIC;
GRANT CONNECT ON DATABASE mymandev TO mymandev_app;
\c mymandev
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
ALTER DEFAULT PRIVILEGES FOR ROLE mymandev_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE ON TABLES TO mymandev_app;
```

The database must use the UTF8 encoding: the unique index of project names (#155) lowers names with the built-in `pg_c_utf8` collation, which exists only in a UTF8 database, so migration `0009_project_keys` fails in any other. `TEMPLATE template0 ENCODING 'UTF8'` asks for it whatever the encoding of `template1`; with a server locale whose character set is not UTF-8, also add `LOCALE 'C.UTF-8'` or another UTF-8 locale. PGlite and the `postgres:18` image of the Database workflow use UTF8.

The same privileges are tested on PGlite (`src/schema.test.ts`), where `ALTER DATABASE ... OWNER TO` replaces `CREATE DATABASE` and the roles have no passwords. The Database workflow (`.github/workflows/database.yml`) runs this script on a PostgreSQL 18 server in CI, applies the migrations twice, runs `db:compare`, and checks that the application role is refused everything listed above.

### Apply the migrations

Copy [`.env.example`](.env.example) to `packages/database/.env` and put the migration role's password into the URL. `.env` is ignored by Git; never commit it. The file works the same in PowerShell, `cmd.exe`, and Git Bash. A `DATABASE_MIGRATION_URL` set in the environment wins over the file.

```text
DATABASE_MIGRATION_URL=postgres://mymandev_migrator:<password>@127.0.0.1:5432/mymandev?sslmode=disable
```

Then, from the repository root:

```sh
npm run db:migrate -w @mymandev/database
```

The command prints "Migrations applied." and exits with 0. A second run applies nothing. Without a URL it prints "DATABASE_MIGRATION_URL is not set." and exits with 1; Node.js also prints ".env not found. Continuing without it." when the file does not exist.

### Connection URLs

`checkDatabaseUrl` checks every URL before it is used, and the URL is never printed, because it contains the password:

- The scheme is `postgres:` or `postgresql:`.
- `sslmode` is absent, `disable`, or `verify-full`. The pg driver treats `prefer`, `require`, and `verify-ca` differently from libpq, and `no-verify` skips certificate checks, so these values are rejected, and so is `uselibpqcompat`.
- With `NODE_ENV=production`, `sslmode=verify-full` is required.
- The URL is percent-encoded: no spaces, and every `%` starts an escape such as `%40`. Encode special characters in the password this way.
- No query parameter appears twice.

pg parses the URL again on its own. It takes the last value of a repeated parameter, and it re-encodes a URL with a space or a stray `%` before parsing it, so without the last two rules it could connect with other settings than the ones that were checked, for example `sslmode=verify-full&sslmode=disable`.

`createDatabase` creates a pg connection pool with a connection timeout of 5 seconds (pg waits forever by default), a statement timeout of 30 seconds (configurable per connection), and an idle-in-transaction timeout of 60 seconds. The two server timeouts are sent as session parameters; PGlite ignores them, so their effect is verified only on a real server.

### Smoke test without PostgreSQL

The production path (pg pool, advisory lock, node-postgres migrator) can be tried without installing PostgreSQL, with `pglite-server` from `@electric-sql/pglite-socket` run through `npx`. Use two terminals.

Terminal 1, from the repository root. npx lists the packages it would install and asks first; answer only after checking the list. Stop the server with Ctrl+C before you close the terminal; on Windows, the `node` process can otherwise keep listening. `netstat -ano | findstr 54329` (Windows) or `lsof -i :54329` (macOS, Linux) prints nothing once the port is free.

```sh
npx -p @electric-sql/pglite-socket@0.2.12 -p @electric-sql/pglite@0.5.9 pglite-server --port 54329
```

Terminal 2: set `DATABASE_MIGRATION_URL` in `packages/database/.env` to this line, then run the migration twice. If the file already holds the URL of your local PostgreSQL, keep a copy of that line first. Both runs print "Migrations applied." and exit with 0. Afterwards, put your previous line back, or delete the file if you created it only for this test.

```text
DATABASE_MIGRATION_URL=postgresql://postgres:postgres@127.0.0.1:54329/postgres?sslmode=disable
```

```sh
npm run db:migrate -w @mymandev/database
```

`pglite-server` binds to `127.0.0.1` and keeps its database in memory. Never add `@electric-sql/pglite-socket` to a `package.json`: its exact-version peers make npm install a second PGlite copy, which breaks `drizzle-orm/pglite`, and it resets pooled connections after a second error on the same connection.

## Migrations

- Migrations are generated from the schema in `src/schema/` and committed as SQL in `migrations/` together with `migrations/meta/`:

  ```sh
  npm run db:generate -w @mymandev/database -- --name <name>
  ```

- Always check that a new SQL file was written. drizzle-kit asks in the terminal about ambiguous changes such as renames. In a non-interactive shell it prints an error, writes nothing, and still exits with 0. Generate such migrations in an interactive terminal, or write them by hand with `drizzle-kit generate --custom`.
- A merged migration is never edited. Hand-written SQL goes into a `--custom` migration.
- Generated files are never reformatted. drizzle-kit writes SQL with tabs and without a final newline; the root `.editorconfig` keeps editors from changing `migrations/**`, and the root `.prettierignore` excludes `migrations/meta/`.
- `npm run db:check -w @mymandev/database` checks the migration folder for consistency. Running `db:generate` without changes prints "No schema changes, nothing to migrate".
- `src/migrations.test.ts` fails when the journal timestamps do not strictly increase, because the migrator silently skips a migration that is older than the last applied one. If it fails after merging `develop`, delete the branch's new migration and generate it again.
- The migrator runs all pending migrations in one transaction, so statements that cannot run in a transaction, such as `CREATE INDEX CONCURRENTLY`, are not possible. Vocabularies therefore use `text` with a CHECK constraint, not PostgreSQL enums.
- Migrations run as a separate deployment step, never when the API starts. Deployments install with `npm ci --omit=dev`; `db:migrate` needs only drizzle-orm and pg, so drizzle-kit and its build tools never reach a server.
- drizzle-kit adds the new constraints of a changed table after the foreign keys of new tables. A new composite foreign key whose target is a new unique constraint on an existing table therefore fails. Generate the unique constraint first, then the foreign key as a second migration, as `0003_account_tables` and `0004_account_tables_member_keys` do; both stay generated, and the pending migrations still run in one transaction.
- A destructive change starts with a hand-written `--custom` guard migration that stops with a clear message when the affected tables hold rows. Because all pending migrations run in one transaction, the guard also stops the migrations after it. `0002_account_tables_guard` stops the account tables migrations (ADR 0014) on a database with a row in `users`, `devices`, or `workspace_members`.

## Reset a local database

The account tables migrations (ADR 0014) need a database without users, devices, or workspace members: `devices` gains required key columns and `workspace_members` a new primary key, and neither has an honest default. No production database exists. On a local database that holds such rows, `db:migrate` stops with "The account tables migrations (0003, 0004) need a database without users, devices, or workspace members" and changes nothing. Drop and recreate the database, then migrate again.

In `psql` as a superuser, connected to the `postgres` database (see [Roles](#roles) for how to start it). The roles stay; only the database is replaced:

```sql
DROP DATABASE mymandev WITH (FORCE);
CREATE DATABASE mymandev OWNER mymandev_migrator TEMPLATE template0 ENCODING 'UTF8';
REVOKE ALL ON DATABASE mymandev FROM PUBLIC;
GRANT CONNECT ON DATABASE mymandev TO mymandev_app;
\c mymandev
REVOKE CREATE ON SCHEMA public FROM PUBLIC;
ALTER DEFAULT PRIVILEGES FOR ROLE mymandev_migrator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE ON TABLES TO mymandev_app;
```

`WITH (FORCE)` closes open connections to the database first. Then, from the repository root:

```sh
npm run db:migrate -w @mymandev/database
```

PGlite test databases and `pglite-server` keep their data in memory, so they need no reset.

## Rules for code in this package

- Use only the SQL-like core query builder: `select`, `insert`, `update`, `delete`, and joins. Do not use `relations()` or `db.query`, which Drizzle 1.0 replaces.
- Every query function runs its statements through `withDatabaseErrors`. A failed Drizzle query throws an error whose message and stack contain the SQL text and every parameter value; `withDatabaseErrors` replaces it with a `DatabaseError` that carries only the SQLSTATE `code` and the `constraint` name.
- Schema files import from `@mymandev/protocol` only with `import type` (ID brands and literal unions), so drizzle-kit loads them without running protocol code. ID columns carry the protocol brands, so a `DeviceId` cannot be written into a `UserId` column.
- CHECK vocabularies (capabilities, run states, platforms, roles, key algorithms, revocation reasons, join request decisions, identity providers) are literal SQL. A test compares them with the protocol constants, so a change on one side fails until the other side follows. The audit vocabularies, which only the server uses, are constants in this package (`AUDIT_ACTIONS`, `AUDIT_REASONS` in `src/audit-vocabulary.ts`), compared the same way. The range of `workspaces.max_unclaimed_members` (1 to 500) is literal SQL as well, and a test checks it against the protocol's `UNCLAIMED_MEMBER_LIMIT`.
- Public keys and SHA-256 hashes are lowercase hexadecimal `text` with the CHECK `^[0-9a-f]{64}$`. No table holds sign-in attempts, sign-in codes, or access tokens.
- `updated_at` is set by `.$onUpdate(() => new Date())` on updates made through Drizzle. An update in raw SQL must set it itself.
- Where a CHECK compares `created_at` with a time the application sets, as the invitation expiry does, the writer sets both from the same instant. The default `now()` is the start of the database transaction, not the application's clock. Durations in CHECKs use hours (`interval '168 hours'`), because adding days follows the session time zone and a day across a daylight saving change has 23 or 25 hours.
- Foreign keys use `ON DELETE RESTRICT`; nothing is hard-deleted. Ownership rules that span tables are composite foreign keys, listed in [ADR 0013](../../docs/architecture/decisions/0013-m1-data-model.md) and [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md).
- Constraint errors carry the SQLSTATE: `23505` unique, `23514` check, `23503` missing parent, `23001` delete of a referenced row.

## Transactions

- `revokeDevice(db, input)` revokes a device in one transaction (ADR 0014, "Revocation, sign-out, and recovery"): it sets `revoked_at` and `revocation_reason`, disables the agents that the device hosts, revokes the active grants on the device with the account as `revoked_by_user_id` (ADR 0015, P-77), moves the unfinished runs of those agents to `cancelled` with the reason `device_revoked` (P-60), and writes a `device.revoked` audit record. Inside another transaction it runs as a savepoint, so a sign-in can revoke the replaced device in its own transaction. A device that does not exist, belongs to another account, or is already revoked is left unchanged and the result says `revoked: false`. The result lists the disabled agents, the revoked grants, and the cancelled runs, each in the order of their IDs, so that the caller can close the device's socket and send the run events after the commit. Each cancelled run (`CancelledRun`) carries what the server's `agent.run.state_changed` event needs: the run, its agent, its project and the project's workspace, its repository and correlation ID or null, its state before the cancellation (`queued`, `running`, or `awaiting_input`), and the reason code stored with it (`device_revoked`). After the device, the agents, the grants, and the runs are each read and locked `FOR NO KEY UPDATE`, the lock that their update takes, in the order of their IDs, and exactly those rows are updated (`src/cascade.ts`, shared with the removal of a person, so the two cannot deadlock); PostgreSQL checks a row that changed while it waited for the lock again, so an agent, a grant, or a run that a concurrent transaction already changed is neither reported nor changed again.

- `recordGitHubRevocation(db, { subject, deliveryId, now })` records GitHub's revocation webhook in one transaction (ADR 0014, P-54): it finds the account whose GitHub identity has `subject`, the numeric sender ID as decimal text, never the login; writes a `github.authorization_revoked` audit record without an actor, with the account as the subject and `deliveryId` as `github_delivery_id`; locks the account's row with `FOR NO KEY UPDATE`, the lock of the API's sign-in, so the two serialize; and sets `users.sign_in_required_at` to the latest of its current value, `now`, and one millisecond after the `last_sign_in_at` of each of the account's devices that are not revoked, so that it never moves backward. Each device counts at most 60 seconds past `now`, so a last sign-in in the future, after a jump of the clock, cannot keep the account from signing in for longer. Every sign-in that committed before the revocation must therefore be repeated, whatever times the two requests took before their transactions (#115; a decision applied on 2026-11-01 under the Project Manager's rule to apply the recommended option). The devices stay registered. A delivery ID that is already recorded changes nothing (`changed: false`); the insert waits for a concurrent one with the same ID. A sender without an account, or whose identity was erased, gets the audit record without a subject and `userId: null`. The result also lists the account's devices that are not revoked, so that the API can drop their access tokens after it closes the account's sockets.

- `requireSignIn(db, { userId, now })` locks the account's row and sets `users.sign_in_required_at` in one transaction by the same rule, without an audit record, and returns the account's devices that are not revoked. The API calls it after a sign-in committed while the webhook recorded a revocation of its GitHub identity that the webhook's own lookup may have missed, such as for an account that the sign-in created (#115).

- `createWorkspace(db, { userId, deviceId, name, displayName, maxUnclaimedMembers, now })` creates a workspace in one transaction (ADR 0014, "People and roles" and "Limits"): it locks the account's row, so that concurrent creations of one account are counted one after another; counts the workspaces whose `created_by_user_id` is the account and whose `created_at` lies within 24 hours before `now`; and at 10 returns `created: false` with `retryAfterMs`, the time until the oldest of them leaves the window, without writing anything. Otherwise it inserts the workspace with `max_unclaimed_members` set to `maxUnclaimedMembers`, or 500 when it is omitted (outside 1 to 500 the CHECK fails), and the creator's person as the claimed `owner` named `displayName`, both with `created_at` set to `now`, writes a `workspace.created` audit record with the account and the device as the actor and the workspace as `workspace_id` and subject, and returns the workspace with the person as a `WorkspaceMembership` of the protocol. Inside another transaction it runs as a savepoint, so the API checks the actor in the same transaction first.

- `defineMember`, `renameMember`, `removeMember`, `leaveWorkspace`, `promoteMember`, and `demoteMember` (`src/people.ts`) change the people of a workspace, each in one transaction (ADR 0014, "People and roles" and "Removal and ownership"). Each takes the acting account and its device, recorded as the actor of the audit record, the workspace, and `now`. Each first locks the acting account's active person and the target person `FOR NO KEY UPDATE` in one statement, in the order of their IDs, so that two changes of the same people wait for each other and cannot deadlock; PostgreSQL checks a row that changed while it waited again, so an actor removed in the meantime is not found. A refusal writes nothing and names its reason: `not_member` (the account is not an active member, also when the workspace does not exist), `not_found` (the workspace has no person with that ID), `forbidden`, or `conflict`. Inside another transaction each runs as a savepoint, so the API checks the actor in the same transaction first.
  - `defineMember(db, { workspaceId, userId, deviceId, displayName, now })` lets only the owner and admins define a person, unclaimed and with the role `member`, the account as `added_by_user_id`, and `created_at` set to `now`, and writes a `member.defined` audit record. It returns the person as the protocol's `WorkspaceMember`. After the acting person it locks the workspace row `FOR NO KEY UPDATE` and counts the active unclaimed people (no account, not removed); when they already reach `workspaces.max_unclaimed_members`, it refuses with `rate_limited` and writes nothing (Project Manager decision of 2026-11-02). The result carries no wait, because no time frees a place: only removing or claiming one of them, or a higher limit, does.
  - `setUnclaimedMemberLimit(db, { workspaceId, userId, deviceId, maxUnclaimedMembers, now })` lets only the owner change `workspaces.max_unclaimed_members`; an admin or a member is `forbidden`. After the acting person it locks the workspace row, as `defineMember` does, so that the two count one after another, and refuses a value below the number of active unclaimed people with `conflict`. It sets the value and `updated_at` and writes a `workspace.unclaimed_member_limit_changed` audit record with the workspace as the subject and no value, because the audit table holds IDs and vocabularies only (P-61). The value in force changes nothing and writes nothing (`changed: false`). A value above 500 fails the CHECK.
  - `renameMember(db, { workspaceId, memberId, userId, deviceId, displayName, now })` lets every active member rename their own person and the owner and admins rename an unclaimed person; another claimed person is `forbidden`, and a removed person is `conflict`. It writes a `member.renamed` audit record.
  - `removeMember(db, { workspaceId, memberId, userId, deviceId, now })` removes a person by the roles table of ADR 0014: the owner removes any person except the owner, and an admin removes unclaimed people and claimed people with the role `member`. Every other combination is `forbidden`: a member's removal, an admin's removal of the owner or of another admin, and anyone's removal of their own person, who leaves instead. A removed person is `conflict`. It writes a `member.removed` audit record and removes the person as described below.
  - `leaveWorkspace(db, { workspaceId, userId, deviceId, now })` lets the account's own person leave: an admin or a member. The owner cannot leave and transfers ownership first (`forbidden`); an account that is not an active member is `not_member`. It writes a `member.left` audit record and removes the person as described below, with the leaving account as the remover.
  - A removal and a departure are one transaction (ADR 0014, "Removal and ownership"; P-60; ADR 0015, P-77). It sets `removed_at` and `removed_by_user_id`, and clears an ownership offer to the person, because only an active person can hold one. It revokes the person's own invitation and the invitations that the person's account created in the workspace, each neither accepted nor revoked, also an expired one (as in the unique index of one live invitation per person), with the remover as `revoked_by_user_id` and an `invitation.revoked` audit record with the reason `member_removed` for each. For a claimed person it also disables the account's agents in the workspace's projects, revokes their active grants, also expired ones never revoked, with the remover as `revoked_by_user_id`, and moves to `cancelled`, with the reason `member_removed`, `finished_at` set, and `previousState` reported, the unfinished runs in the workspace's projects that run on those agents or that the account requested on another member's agent. Nothing outside the workspace changes, and nothing is deleted: the person row, its runs, grants, and invitations stay with their attribution, and an account that rejoins claims a new person. The grant revocations write no audit record, because the audit vocabulary has no grant action (P-61; grant events are P-80). The result (`MembershipEnd`) names the person and the account that had claimed it (null for an unclaimed person) and lists the revoked invitations, the disabled agents, the revoked grants, and the cancelled runs (`CancelledRun`, as for a device revocation), each in the order of their IDs, for what the API sends after the commit.
  - The database refuses a removed owner too: the CHECK `workspace_members_owner_removal_check` (migration `0005_owner_never_removed`; the Project Manager's decision in the #93 issue comment of 2026-10-30) allows `removed_at` only on a person whose role is not `owner`, so a bug cannot leave a workspace without an owner. The migration has no guard that checks the rows first: no application path could write an owner with `removed_at`, because removing a claimed person was refused before #93 and `0002_account_tables_guard` required empty tables. Should a database hold such a row anyway, `db:migrate` fails with `23514` and rolls back every pending migration. An erasure that archives a workspace makes its owner's person a `member` first and then removes it ("Operator commands"), so only an archived workspace has no owner.
  - A removal that waits for a concurrent claim of an unclaimed person decides on the person as claimed: it removes the person that the claim attached to the account, with the account's agents, grants, and runs and the account frame, because the roles table allows the owner and an admin to remove a claimed `member`. Before #93 such a removal answered `conflict`.
  - `promoteMember(db, { workspaceId, memberId, userId, deviceId, now })` makes an active, claimed `member` an `admin` and writes a `member.promoted` audit record. Only the owner, from a device whose `created_at` lies more than `DEVICE_TOO_NEW_MS` (72 hours, ADR 0014, "Lifetimes") before `now`; a device exactly 72 hours old or younger, or a device that the account does not have, is `device_too_new`. `created_at` never changes, so the device is read without a lock.
  - `demoteMember(db, { workspaceId, memberId, userId, deviceId, now })` makes an active `admin` a `member`, from any of the owner's devices, and writes a `member.demoted` audit record. In the same transaction it revokes the invitations that the admin's account created in the workspace, each neither accepted nor revoked, also an expired one, as a removal does, with the owner as `revoked_by_user_id` and an `invitation.revoked` audit record with the reason `creator_demoted` for each, and returns their IDs in order.
  - For both, anyone but the owner, and a change of the owner's own role, which changes only by transfer, is `forbidden`, so nobody changes their own role. The device age is decided after the role and before the person's state. A removed person, an unclaimed person, who is always a member, a promotion of an admin, and a demotion of a member are `conflict`.

- `offerOwnership`, `acceptOwnershipOffer`, and `withdrawOwnershipOffer` (`src/ownership.ts`) offer the ownership of a workspace, accept the offer, and withdraw it, each in one transaction (ADR 0014, "People and roles", "Removal and ownership", and "Lifetimes"). They take the same actor as the people functions. The offer is `ownership_offered_at` on the target's row: the CHECK `workspace_members_ownership_offer_check` keeps it on an active, claimed person who is not the owner, and the unique index `workspace_members_ownership_offer_key` keeps at most one per workspace. An offer lives `OWNERSHIP_OFFER_LIFETIME_MS` (7 days); from then on it is no offer, and `workspaceView` no longer shows it. Nothing sweeps an expired offer: the owner's next offer or withdrawal, or the target's acceptance, clears it, and only then, without an audit record (Project Manager decision of 2026-11-01). Each first locks, `FOR NO KEY UPDATE` in one statement and in the order of their IDs, the acting account's active person, the active owner, the person that holds the offer, and the person that a new offer names, so a transfer locks both people before it changes either. Inside another transaction each runs as a savepoint.
  - `offerOwnership(db, { workspaceId, memberId, userId, deviceId, now })` lets only the owner offer, from a device older than `DEVICE_TOO_NEW_MS`, as for a promotion; a device exactly that old or younger is `device_too_new`, decided after the role and before the person's state. Anyone else, and an offer to the owner's own person, is `forbidden`; an unknown person is `not_found`; a removed or unclaimed person, and a workspace with a live offer, to this person or another, are `conflict`. A refusal writes nothing. It clears an expired offer first, sets `ownership_offered_at` to `now`, and writes an `ownership.offered` audit record. It returns the offer as the protocol's `OwnershipOffer`, the target's account, and the expired offer it replaced as `ended` (`EndedOwnershipOffer`: the person, the account, the reason `expired`, and its expiry as `endedAt`), or null. A statement that waited for the owner's row does not see an offer that another device of the owner made meanwhile to a third person, so it reads the offers again under the owner's lock and answers `conflict` for one.
  - `acceptOwnershipOffer(db, { workspaceId, userId, deviceId, now })` lets the target accept the live offer from any of its devices: it makes the owner an `admin` and then the target the `owner`, in two statements in this order, so that `workspace_members_active_owner_key` never sees two owners, clears the offer, and writes an `ownership.transferred` audit record with the target as the subject. It returns the former owner's person and account and the target's person, so that the server tells both accounts. The owner is `forbidden`, and so is any other person while the offer names someone else. Without a live offer it is `conflict`; an expired offer to the acting person is cleared, returned as `ended`, and committed with the refusal. The CHECK that the owner is never removed holds afterwards: the former owner is an admin, whom the new owner may remove.
  - `withdrawOwnershipOffer(db, { workspaceId, userId, deviceId, now })` lets the owner withdraw the live offer from any of the owner's devices: it clears the offer, writes an `ownership.offer_withdrawn` audit record with the target as the subject, and returns it as `ended` with the reason `withdrawn` and `now`. Anyone else is `forbidden`. Without a live offer it is `conflict`; an expired offer is cleared, returned as `ended` with the reason `expired`, and committed with the refusal. An offer that another device of the owner makes while the withdrawal waits for the owner's row is not withdrawn: the withdrawal decides as if it came first, and the offer stays until the next withdrawal, because withdrawing it would need its row locked out of the order of IDs.
  - A removal and a departure of the target clear the offer, as described above; a demotion of the target keeps it, because ADR 0014 lets the owner offer ownership to a member too.

Lock order: a transaction that changes the people of a workspace locks the account (`users`), then the device (`devices`), as `lockActor` in the API does, then the people (`workspace_members`) in the order of their IDs, then the invitations (`workspace_invitations`). Creating and revoking an invitation lock the person before the invitation as well, and creating one locks the workspace row (`workspaces`) after the people and before the invitations, for the counts of the workspace; defining a person and changing the limit of unclaimed people lock the acting person and then the workspace row, for the count of the active unclaimed people; accepting an invitation locks the invited person before it consumes the invitation and claims the person. Join requests (`workspace_join_requests`) follow the people: the account, the device, the people in the order of their IDs, then the join request rows, several in the order of their IDs, then the workspace row only where the counts of the workspace or its pause need it. Creating a request locks the account, the account's open request row in the workspace, and then the workspace row; approving, denying, blocking, and unblocking lock the acting person and then the request; denying all locks the acting person and then the pending requests of the workspace in the order of their IDs; pausing and resuming lock the acting person and then the workspace row; withdrawing locks only the request after the account and the device. A removal and a departure lock the acting person and the removed person, then the invitations they revoke, then the agents, the grants, and the runs, each in the order of their IDs. A demotion locks the owner's person and the admin's, then the invitations it revokes, in the same way. An ownership offer, its acceptance, and its withdrawal lock only people, in one statement in the order of their IDs, and each holds the owner's row, so offers are made one after another. An operator's erasure (`eraseAccount`) locks the account's identity before the account, as the sign-in does, and the account's join requests before its people, and after its people the workspaces that the account owns: their unclaimed people, their pending join requests, their workspace rows, their projects and repositories, and their open invitations; "Operator commands" below describes why. The invitations that the removed or demoted person created name other people, whom the removal or the demotion does not lock. Every other change of an invitation locks the invited person, and its acting person, before it touches that person's invitations, of which at most one is neither accepted nor revoked; it waits for the people that the removal or the demotion holds only when it acts as the remover, the owner, or the removed or demoted person, and then before it holds an invitation. So the two cannot wait for each other in a cycle. A demotion locks no join request row either, so an approval, a denial, or another action of the approvers on join requests by the admin whom it demotes waits for it, or makes it wait, at the people, and is then decided on the new role. A removal locks no join request row and no workspace row (its audit record takes only the key-share lock of a foreign key, which the `FOR NO KEY UPDATE` of a pause or a resume does not wait for), and no action of the approvers on join requests (approving, denying, blocking, unblocking, denying all, pausing, or resuming) locks an invitation, agent, grant, or run. So the two share only the people that they lock first, in the order above: such an action by the person whom a removal removes, or by its remover, waits for it or makes it wait at that step. An approval's insert of the new person may wait for a removal of an earlier person of the same account, through the unique index of one active person per account, but the removal never waits for the approval. A device revocation locks its device and then the agents, the grants, and the runs in the same way, and an operator's `disableAccount` locks the account and then the grants in the same way (`src/cascade.ts`), so a removal and either of them lock shared rows in the same order. So no two of these transactions wait for each other. Each step binds its IDs as one array parameter (`idIn`, `= any($1::uuid[])`), so no list of IDs reaches PostgreSQL's limit of 65,535 parameters per statement.

A future writer that inserts an agent, a grant, or a run (#75, M3) must lock the person of each account it attaches the row to before the insert: the agent's owner, and for a run also the requester, in the order of their IDs, `FOR SHARE` or stronger, and check that each is still active. A removal holds the person `FOR NO KEY UPDATE`, which `FOR SHARE` waits for and `FOR KEY SHARE` does not. So either the removal commits first and the writer finds the person removed, or the insert commits first and the removal sees the new row; otherwise a removal could miss an agent, a grant, or a run that a concurrent insert added. The person lock comes after the account and the device and before the agents, grants, and runs, as in the order above.

- `createInvitation` and `revokeInvitation` (`src/invitations.ts`) change the invitations of a workspace, each in one transaction (ADR 0014, "Invitations" and "Limits"). They take the same actor and give the same refusals as the people functions, and first lock the acting person and the invited person in the same way, so that every change of a person's invitations waits for every other change of that person. Inside another transaction each runs as a savepoint.
  - `createInvitation(db, { workspaceId, memberId, userId, deviceId, tokenHash, lifetimeSeconds, now })` lets only the owner and admins invite an unclaimed person; a claimed or removed person is `conflict`. After the people it locks the workspace row `FOR NO KEY UPDATE`, so that concurrent creations in one workspace are counted one after another, and returns `rate_limited` with `retryAfterMs`, without writing anything, when the workspace has 50 live invitations (neither accepted, revoked, nor expired at `now`), not counting the one of the invited person, or 100 whose `created_at` lies within 24 hours before `now`. `retryAfterMs` is the time until the live invitation that expires first expires, or until the oldest of the 24 hours leaves the window; the later of the two when both limits are reached. It revokes the person's invitation that is neither accepted nor revoked, also an expired one, with the account as `revoked_by_user_id` and an `invitation.revoked` audit record with the reason `replaced`; inserts the new invitation with `tokenHash`, the SHA-256 hash of the code that the caller made, so that the code never reaches the database, `created_at` set to `now`, and `expires_at` `lifetimeSeconds` later (7 days when omitted; outside 1 hour to 7 days the CHECK fails); and writes an `invitation.created` audit record. It returns the protocol's `Invitation`, whose creator is the acting person, and the ID of the invitation it replaced.
  - `revokeInvitation(db, { workspaceId, invitationId, userId, deviceId, now })` lets only the owner and admins revoke a live invitation: it sets `revoked_at` and `revoked_by_user_id` and writes an `invitation.revoked` audit record without a reason. An invitation that the workspace does not have is `not_found`; one that is accepted, revoked, or expired is `conflict`.

- `acceptInvitation(db, { tokenHash, userId, deviceId, now })` (`src/invitations.ts`) consumes an invitation code and claims its person in one transaction, at the connection's isolation level, PostgreSQL's default READ COMMITTED (ADR 0014, "Invitations"). It takes the SHA-256 hash of the code, never the code. It finds the invitation by the hash in whatever state; an unknown hash is `invitation_invalid`. An account that is already an active member of the invitation's workspace is `already_member` before anything is consumed. An archived workspace is `invitation_invalid` with the reason `workspace_archived`, whatever the invitation's state; this is a second line of defense, because the erasure that archives a workspace revokes its invitations too. Then it locks the invitation's person `FOR NO KEY UPDATE`, which it read without a lock because the person of an invitation never changes; consumes the invitation with a conditional update, only if the hash matches and the invitation is neither accepted, nor revoked, nor expired at `now`, recording `accepted_at`, `accepted_by_user_id`, and `accepted_device_id`; and claims the person only if it is still unclaimed and not removed, with `claimed_at` set to `now`. When either update changes no row, the transaction rolls back and the result is `invitation_invalid` with the reason (`InvitationFailure`): `unknown`, `used`, `revoked`, `expired`, `member_removed`, or `member_claimed`; the last two happen only to data written outside these functions, because removing a person revokes its invitation and claiming one consumes it. A unique violation of `workspace_members_active_user_key`, when the account claimed another person of the workspace concurrently, rolls back too and is `already_member`. PostgreSQL checks a row that a concurrent transaction changed again before it updates it, so of two acceptances of one code only the first claims the person, and the second is `used`. A claim always takes the invited person, a new row, so an account that was removed rejoins as a new person and its earlier person stays. It writes an `invitation.accepted` and a `member.claimed` audit record with the account and the device as the actor, and returns the workspace with the claimed person as a `WorkspaceMembership`. Inside another transaction it runs as a savepoint, so the API checks the actor in the same transaction first. A refusal carries the invitation's ID, if the hash names one, so that the API can log it with the reason.

- The join request functions (`src/join-requests.ts`; ADR 0014, "Join requests", "Limits", "Lifetimes", and "What a workspace ID allows") each run in one transaction, as a savepoint inside another. A request is pending while it has no decision and its `expires_at` lies after `now`; a request past its expiry is not pending even before it is marked (Project Manager decision of 2026-11-01): it is not returned as the pending request, counts toward no limit, is not listed for the approvers, and cannot be approved, denied, blocked, or withdrawn (`conflict`).
  - `createJoinRequest(db, { workspaceId, userId, deviceId, displayName, now })` decides in this order, and a refusal writes nothing: a workspace that does not exist or is archived is `workspace_not_found`; an active member is `already_member`; the account's pending request in the workspace is returned unchanged with `created: false`, also while requests are paused (awaiting the Project Manager's confirmation); a paused workspace or a block in force (`decision = 'blocked'` without `unblocked_at`) is `join_requests_closed`; and the limits of ADR 0014 are `rate_limited` with `retryAfterMs`, the latest of the times at which each reached limit ends: 24 hours after the account's latest denial in the workspace, 5 pending requests of the account until the first of them expires, 10 requests of the account created within 24 hours until the oldest leaves the window, and 50 pending requests in the workspace until the first of them expires, rounded up to the next full hour, so that the answer does not tell when another account asked; the waits of the account's own limits stay exact. Otherwise it marks the account's earlier request in the workspace that is past its expiry but unmarked as `expired`, with `decided_at` set to its `expires_at` and no audit record, and only then inserts the new request with the requested display name, the device, `created_at` set to `now`, and `expires_at` 168 hours later, and writes a `join_request.created` audit record. It locks the account's row first, so that the requests of one account are counted one after another, then the account's open row in the workspace, so that it waits for an approval of that row and then sees the new person, then the workspace row, so that the requests of one workspace are counted one after another and a pause is seen.
  - `listOwnJoinRequests(db, { userId, now })` returns the account's requests as `OwnJoinRequestListItem`s of the protocol, the most recently created first, at most `MAX_ANSWER_LIST_ITEMS`: a block as `denied`, and a request without a decision past its expiry as `expired` with its `expires_at` as `decidedAt`, the value that marking it stores too.
  - `withdrawJoinRequest(db, { joinRequestId, userId, deviceId, now })` lets the requester withdraw a pending request: it sets `decision` to `withdrawn` with `decided_at` and `decided_by_user_id` and writes a `join_request.withdrawn` audit record in the request's workspace. A request of another account is `not_found`, as one that does not exist; one that is no longer pending is `conflict`.
  - `listJoinRequests(db, { workspaceId, userId, now })` returns the approvers' view, the protocol's `JoinRequest`: the pending requests, then the blocks in force, each the most recently created first, at most `MAX_ANSWER_LIST_ITEMS`, with the requester's GitHub login, the time it was last verified (`user_identities.last_sign_in_at`), and the creation date of the GitHub account. Only the owner and admins: a member is `forbidden`, an account without an active person `not_member`. A pending request is left out when its requester is already an active member of the workspace, because approving it could only answer `already_member`, and when the requester's identity was erased, because the approvers could not tell who asks. A block in force stays listed, also of an erased account, which then has no requester.
  - `approveJoinRequest(db, { workspaceId, joinRequestId, userId, deviceId, displayName, now })` and `denyJoinRequest(db, { workspaceId, joinRequestId, userId, deviceId, now })` lock the acting person as the people functions do, then the request `FOR NO KEY UPDATE`, and refuse with `not_member`, `not_found` (a request that the workspace does not have), `forbidden` (a member), or `conflict` (a request that is no longer pending), in this order. PostgreSQL reads a request that a concurrent decision or withdrawal changed again after the lock, so only the first of them finds it pending. An approval of a requester who is already an active member is `already_member`, and the request stays pending. Otherwise it inserts a new claimed person of the requester with the role `member`, the approver's `displayName` or else the requested name, the approver as `added_by_user_id`, and `created_at` and `claimed_at` set to `now`, so a requester who was removed earlier rejoins as a new person; sets the request's `decision` to `approved` with the new person as `member_id`; and writes a `join_request.approved` and a `member.claimed` audit record with the approver as the actor. A unique violation of `workspace_members_active_user_key`, when the requester claimed another person concurrently, rolls back and is `already_member`. A denial sets `decision` to `denied` and writes a `join_request.denied` audit record. Both return the requester's account, which the API sends the decision to.
  - `blockJoinRequest(db, { workspaceId, joinRequestId, userId, deviceId, now })` locks and refuses as a denial does, sets `decision` to `blocked` with `decided_at` and `decided_by_user_id`, writes a `join_request.blocked` audit record, and returns the requester's account, which the API sends the decision to as `denied`. Until the block is lifted, a new request of the account in the workspace is `join_requests_closed`; the requester sees the request as `denied`.
  - `unblockJoinRequest(db, { workspaceId, joinRequestId, userId, deviceId, now })` locks the acting person, then the request `FOR NO KEY UPDATE`, and refuses with `not_member`, `not_found`, `forbidden`, or `conflict` (a request that is not blocked, or whose block was already lifted), in this order. It sets `unblocked_at` and `unblocked_by_user_id` and writes a `join_request.unblocked` audit record; the decision stays `blocked`. The account can ask again at once, because only a `denied` decision starts the 24-hour wait.
  - `denyAllJoinRequests(db, { workspaceId, userId, deviceId, now })` lets only the owner and admins deny every pending request of the workspace: a member is `forbidden`, an account without an active person `not_member`. After the acting person it locks the pending requests `FOR NO KEY UPDATE` in the order of their IDs, so it never waits for a transaction that waits for it, and PostgreSQL leaves out a request that a concurrent decision or withdrawal changed meanwhile. It denies each as a denial of one request does, also the requests that the approvers' list leaves out, and writes one `join_request.denied` audit record per request (Project Manager decision of 2026-11-01). A request past its expiry stays as it is. It returns the denied requests with their accounts, in the order of their IDs, and an empty list when nothing was pending.
  - `pauseJoinRequests(db, { workspaceId, userId, deviceId, now })` and `resumeJoinRequests(db, { workspaceId, userId, deviceId, now })` let only the owner and admins set or clear `workspaces.join_requests_paused_at`, with `updated_at`, and refuse with `not_member` or `forbidden`. They write a `join_requests.paused` or `join_requests.resumed` audit record with the workspace as the subject, and return `changed: false`, writing nothing, when the workspace already is in that state. A pause has no expiry and keeps the pending requests: they can still be approved, denied, blocked, or withdrawn, and a requester who asks again gets the pending request back (awaiting the Project Manager's confirmation). The update locks the workspace row after the acting person; a new request locks the same row, so it is either stored before the pause or sees it.

- The project functions (`src/projects.ts`; #155, Project Manager decisions of 2026-11-02) each run in one transaction, as a savepoint inside another. A project's name is unique among the workspace's projects that are not archived, compared without regard to case: the unique index `projects_active_name_key` on (`workspace_id`, `lower(name collate "pg_c_utf8")`) where `archived_at` is null (migration `0009_project_keys`) decides it, so that two concurrent writers cannot both pass. `lower` with the built-in `pg_c_utf8` collation applies Unicode's simple lowercase mapping, the same on every PostgreSQL 18 server whatever its locale: `App` and `APP` clash, and so do `Ärger` and `ÄRGER`, while `Straße` and `STRASSE` do not. A unique violation of that index rolls back the function's transaction and is `conflict`; the outer transaction goes on. Before the index, the migration archives the projects of every archived workspace that are not archived yet, with the workspace's `archived_at`, because an erasure before #155 gave them all the same placeholder name without archiving them. The same migration adds the unique index `conversations_project_kind_key`, one `project` conversation per project, and the index `projects_created_by_user_id_created_at_idx` for the count of an account's creations. Creating and renaming a project write no audit record: they are not administrative actions of ADR 0014, and the audit vocabulary has no project action. The functions take names that the protocol normalized (`normalizeProjectName`: Unicode NFC, without white space at the start and the end) and store and compare them as given. The CHECK `projects_name_nfc_check` (`name is nfc normalized`, in the same migration) refuses a name that is not in NFC with `23514`, whatever the writer; the trimming has no CHECK, so every caller must trim too, as the API's request schema does.
  - `createProject(db, { workspaceId, userId, name, now })` lets any active member create a project; an account without an active person is `not_member`. It locks the account's row, so that the creations of one account are counted one after another, then the acting person as the people functions do, then the workspace row `FOR NO KEY UPDATE`, so that the creations of one workspace are counted one after another. It refuses with `rate_limited` when the workspace holds `MAX_ACTIVE_PROJECTS_PER_WORKSPACE` (100) projects that are not archived, with `retryAfterMs: null`, because no time frees a place, and then when the account created `MAX_NEW_PROJECTS_PER_DAY` (20) projects, in any workspace, whose `created_at` lies within 24 hours before `now`, with `retryAfterMs` until the oldest of them leaves the window. It inserts the project with `name`, the account as `created_by_user_id`, and `created_at` and `updated_at` set to `now`, and its `project` conversation, the project's chat, with the same account and time and no title, and returns the protocol's `WorkspaceProject`, with the acting person as `createdByMemberId`.
  - `listProjects(db, workspaceId)` returns the workspace's projects that are not archived as the protocol's `WorkspaceProject`, the oldest first (`created_at`, then the ID), at most `MAX_ANSWER_LIST_ITEMS`. The table records the creating account, and `createdByMemberId` is that account's person in the workspace, as `listInvitations` finds an invitation's creator: its active person, which holds the account's right to rename, or else its most recently removed one, whose ID stays valid because person rows are never deleted. Invariant: the creating account of every project has a person in the project's workspace, because `createProject` inserts a project only for the acting account's active person and nothing deletes a person. A project written otherwise, without such a person, makes `listProjects` throw for the whole workspace ("Invariant broken: ..."), so the API answers `500` instead of a list without a creator; a writer of projects other than `createProject` must keep the invariant. The caller checks membership first.
  - `renameProject(db, { workspaceId, projectId, userId, name, now })` lets the account that created the project, also after it left and joined again, the owner, and admins rename it. It locks the acting person, then the workspace row, as `createProject` does, then the project, each `FOR NO KEY UPDATE`, so that every writer of a workspace's project names holds its workspace row and they run one after another: two renames that swap two names could otherwise each wait for the other's entry in the unique index, a deadlock. It refuses with `not_member`, `not_found` (a project that the workspace does not have), `forbidden`, or `conflict` (an archived project), in this order. The name in force, exactly as stored, changes nothing (`changed: false`); otherwise it sets `name` and `updated_at`.
  - An erasure that archives a workspace (see "Operator commands") also sets `archived_at` on its projects, keeping an earlier time, because every project of such a workspace gets the same placeholder name, which the unique index allows only among archived projects.

- The chat functions (`src/chat.ts`; #27, Project Manager decisions of 2026-11-02) post to and read a project's chat, its `project` conversation, which `createProject` creates. Any active member of the project's workspace posts and reads; posting to an archived project or workspace is refused, and an archived project's history stays readable. Since migrations `0010_chat_author_member` and `0011_chat_author_member_keys`, a person's message names both the account (`author_user_id`) and the account's person in the workspace (`author_member_id`), because an account that leaves and joins again gets a new person and the protocol names a message's author by person: the CHECK `messages_author_member_check` sets `author_member_id` exactly when `author_user_id` is set, so an agent's message names neither, and the composite foreign key `messages_author_member_user_fk` (`author_member_id`, `author_user_id`) -> `workspace_members` (`id`, `user_id`) keeps the person the author account's, as `messages_sender_device_user_fk` keeps the device. Its target is the new unique constraint `workspace_members_id_user_id_key`, generated in the first of the two migrations, as the section "Migrations" asks. That the person is one of the project's workspace is the writer's rule, because a message records its conversation, not its workspace. The event ID's key, unique per sending device and event ID (`messages_sender_device_client_event_key`), already existed (ADR 0013). Migration `0011_chat_author_member_keys` adds the CHECK without filling `author_member_id` in, because no writer of messages existed before: on a local database that holds a person's message, `db:migrate` stops at `messages_author_member_check` (`23514`) and, as all pending migrations run in one transaction, changes nothing. Reset the database as described in "Reset a local database", then migrate again.
  - `postChatMessage(db, { actor: { workspaceId, userId, deviceId }, projectId, eventId, body, now })` posts in one transaction, as a savepoint inside another. It locks the account's active person in the actor's workspace `FOR SHARE`, the lock that `src/people.ts` asks of a writer that attaches a row to a person, and without one refuses with `not_member`, also for a workspace that does not exist. Then, before any state of the project, it looks for a message that the device already stored with `eventId`: the account's own message in the actor's workspace is returned as it is stored with `duplicate: true`, even when the body differs or its project or workspace was archived since, and nothing is written; one in another workspace, or a message of an agent hosted on the device (the key is per device, whoever the author), is `conflict`. Then it locks the project `FOR SHARE` and refuses a project that the workspace does not have, also one of another workspace, with `not_found`, and an archived project or workspace with `conflict`. It numbers the message with `UPDATE conversations SET last_seq = last_seq + 1 ... RETURNING` and inserts it with the account, the person, the device, the event ID, and `now` as `created_at`, and returns it as the protocol's `ChatMessage` (author `{ kind: "member", memberId }`, `seq`) with `duplicate: false`. The update and the insert run as a savepoint: when a concurrent post of the same device and event ID committed first, the insert fails the unique index, the savepoint rolls the number back too, and the result is the stored message as above, so no number is lost. A removed member is `not_member` also for an event ID that it stored before.
  - `listChatMessages(db, { actorUserId, projectId, beforeSeq, limit })` returns one page of the history, the answer of `GET /projects/:projectId/messages`: the newest first by `seq`, with `beforeSeq` only lower numbers, at most `limit`, from 1 to `CHAT_HISTORY_PAGE.max` (100); a limit outside that range or a `beforeSeq` that is not a positive integer throws a `RangeError`, the caller's mistake, because the API's query schema already bounds both. A project that does not exist and one whose workspace the account is not an active member of, removed members included, give the same `not_found`. The membership check and the page run in one read-only transaction at `REPEATABLE READ`, so both see one snapshot; inside another transaction it runs as a savepoint. A message keeps its author's person after the person was removed, and an agent's message shows `{ kind: "agent", agentId }`. No writer sets `deleted_at` yet; a deletion decides how the history shows a deleted message.
  - Lock order: the acting person (`workspace_members`), then the project (`projects`), then the conversation (`conversations`), after the account and the device that `lockActor` in the API locks first. A removal holds the person `FOR NO KEY UPDATE`, which the post's `FOR SHARE` waits for, so either the removal commits first and the post is `not_member`, or the post commits first and the removal comes after the message. The posts of one person do not wait for each other at the person. The project's `FOR SHARE` makes an erasure that archives the project, which locks it `FOR NO KEY UPDATE` after the people and the workspace rows, wait for the post or be seen by it. The `UPDATE` of `last_seq` holds the conversation until the transaction ends, so the posts of one chat are numbered one after another, without a gap and without a number twice, and the posts of different chats do not wait for each other. The unique constraint on (`id`, `user_id`) makes `user_id` a key column of `workspace_members` for row locks: claiming a person, the only update of `user_id`, now takes `FOR UPDATE`, which also waits for the key-share locks of foreign-key checks; every writer that inserts a row referring to a person locks that person first, so this adds no wait in practice.

- The agent activity functions (`src/agent-activity.ts`; #28, Project Manager decisions of 2026-11-02) record the run transitions that an agent's host device sends and read a project's agents and runs. Migration `0012_agent_run_keys` adds the unique constraints `agent_runs_id_agent_id_key` (`id`, `agent_id`) and `agent_runs_id_repository_id_key` (`id`, `repository_id`), the targets of the transition log's composite foreign keys, generated before the table as the section "Migrations" asks, and the partial index `agent_runs_project_id_finished_at_idx` on (`project_id`, `finished_at`, `id`) where `finished_at` is set, for a project's most recently finished runs. Migration `0013_agent_run_transitions` adds the transition log `agent_run_transitions`: one row per accepted transition, with the run, the agent, the sending device, the device's event ID, and what the relayed event carries besides the run's workspace, which the run's project names: the payload's `repository_id`, `previous_state`, `state`, and `reason` as sent, null where the event had none, the event's `occurred_at`, `correlation_id`, and `causation_id`, and the server's time as `created_at`. So a transition sent again gets exactly the event that was relayed. Unique (`device_id`, `event_id`) (`agent_run_transitions_device_event_key`) is the idempotency key per device that ADR 0006 asks for; the CHECK `agent_run_transitions_transition_check` holds exactly the transitions that `canTransition` allows from a state, never a creation; `reason` has 1 to 500 characters when set; (`run_id`, `agent_id`) -> agent_runs (`id`, `agent_id`) keeps the run the agent's, (`agent_id`, `device_id`) -> agents (`id`, `host_device_id`) keeps the device the agent's host, and (`run_id`, `repository_id`) -> agent_runs (`id`, `repository_id`) keeps a sent repository the run's. The server's own transitions, a run's creation and its cancellations, have no row. The new unique constraints make `agent_id` and `repository_id` key columns of `agent_runs` for row locks; no writer changes them.
  - `recordRunTransition(db, { actor: { workspaceId, userId, deviceId }, agentId, runId, repositoryId, eventId, previousState, state, reason, occurredAt, correlationId, causationId, now })` records one transition in one transaction, as a savepoint inside another, and returns the relayed `agent.run.state_changed`: every field as the device sent it, an optional field it did not send absent, and `deviceId: null` (ADR 0006, update of 2026-11-02). It decides in this order, as the protocol README's refusal table has it: it locks the account's active person in the actor's workspace `FOR SHARE`, and without one refuses with `not_member`, on which the API closes the connection; it looks for a transition that the device already recorded with `eventId`, and answers one in the actor's workspace with its stored event and `duplicate: true`, before any state of the agent or the run, also when the event sent again differs or the run moved on, and one in another workspace with `conflict`; it locks the agent `FOR SHARE` and refuses an agent that does not exist or is not in the actor's workspace with `not_found`, and an agent of the workspace that the device does not host or that another account owns with `identity_mismatch`, on which the API closes the connection and writes an audit record; it locks the run `FOR NO KEY UPDATE`, the lock that its update takes, and refuses a run that does not exist or is not the agent's, also one of another workspace, and a `repositoryId` that is not the run's repository, with `not_found`; and it refuses a disabled agent, an archived project or workspace, a transition that `canTransition` refuses, and a run whose stored state is not `previousState` with `conflict`, unless the device recorded the event ID meanwhile, as below. Then it sets the run's `state`, `state_reason` (the reason, or null), `started_at` (`now`, the first time the run becomes `running`), and `finished_at` (`now` for a terminal state) with one `UPDATE ... WHERE id = runId AND state = previousState`, and inserts the log row, both as a savepoint. A concurrent transition of the same run makes this one wait at the run's lock and then decide on the state that the other left: the stored event if the other had the same device and event ID, and `conflict` otherwise. When a concurrent transition of the same device and event ID on another run committed first, the insert fails the unique index, the savepoint rolls the run's update back, and the result is the stored event. A device revocation is the API's check (`lockActor`); the revocation disables the device's agents in its own transaction, so a transition after it is `conflict`. The API passes the authenticated connection's device, never the event's `deviceId`, and `new Date(event.occurredAt)`, which keeps the protocol's millisecond precision. The API must handle the run events of one connection one after another, in the order in which they arrive: a device sends `queued -> running` and then `running -> completed` without waiting, and the second, run concurrently with the first, would read the run before the first committed and be `conflict`.
  - `listProjectAgents(db, { actorUserId, projectId })` returns the project's agents, disabled ones included, the answer of `GET /projects/:projectId/agents`: the oldest first, at most `MAX_ANSWER_LIST_ITEMS`, each with its ID, project, name, owner's person (`ownerMemberId`), and `disabledAt`, and never its host device, read like the runs below in one read-only `REPEATABLE READ` transaction. The table records the owning account; `ownerMemberId` is that account's active person in the project's workspace, or else its most recently removed one, as `listProjects` finds a project's creator. Invariant: every agent's owner has a person in its project's workspace, because a writer of agents attaches the agent to its owner's active person; an agent written otherwise makes the list throw ("Invariant broken: ...").
  - `listProjectRuns(db, { actorUserId, projectId })` returns the answer of `GET /projects/:projectId/runs`: every unfinished run, the most recently created first, at most `MAX_ANSWER_LIST_ITEMS`, and the `RECENT_FINISHED_RUNS` (50) most recently finished runs, the most recently finished first, ties to the higher run ID, each with its agent, project, repository, state, `reason` (the run's `state_reason`), `createdAt`, and `finishedAt`. The membership check and both lists are read in one read-only `REPEATABLE READ` transaction, from one snapshot, so a run that finishes meanwhile is listed once.
  - Both lists answer any active member of the project's workspace, also for an archived project, and give the same `not_found` for a project that does not exist and one whose workspace the account is not an active member of, removed members included.
  - Lock order: the acting person (`workspace_members`), then the agent (`agents`), then the run (`agent_runs`), after the account and the device that `lockActor` in the API locks first. A removal holds the person `FOR NO KEY UPDATE`, which the transition's `FOR SHARE` waits for, so either the removal commits first and the transition is `not_member`, or the transition commits first and the removal cancels the run from its new state. A device revocation and a removal lock the agents before the runs `FOR NO KEY UPDATE` (`src/cascade.ts`), which the transition's `FOR SHARE` on the agent waits for, and the other way round, so either the cancellation commits first and the transition finds the agent disabled, `conflict`, or the transition commits first and the cancellation starts from its new state. The transitions of one agent do not wait for each other at the agent; the run's `FOR NO KEY UPDATE` holds it until the transaction ends, so of two concurrent transitions of one run the second waits and then is `conflict`, or gets the stored event when it has the same device and event ID.

## Queries

Device authentication and the WebSocket gateway of the API use these (ADR 0014, "Device key and authentication" and "Revocation, sign-out, and recovery"; ADR 0006, identity binding):

- `deviceRow(db, deviceId)` reads a device with its current key and its account's state, a `DeviceAccessRow`: the account, the public key, `revoked_at`, `signed_out_at`, `last_sign_in_at`, and the account's `disabled_at` and `sign_in_required_at`. A device that does not exist gives `undefined`.
- `deviceRows(db, deviceIds)` reads the same rows for many devices, as a map by device ID, with one query per 500 IDs; the gateway's sweep re-checks every open connection with it. A device that does not exist is missing from the map.
- `isActiveMember(db, { workspaceId, userId })` says whether the account is an active member of the workspace: whether `activePersonOf` finds a claimed person whose `removed_at` is empty. A workspace that does not exist gives `false`.
- `activePeopleOf(db, memberships)` finds the active person of each pair of a workspace and an account, with one query per 500 pairs, as a map from the workspace to the accounts and their person IDs; the gateway's sweep re-checks the workspace subscriptions of every open connection with it (#110). A pair whose account is not an active member is missing, also when the workspace does not exist.
- `markDeviceSeen(db, { deviceId, now })` sets `devices.last_seen_at`, when a connection authenticates, and `devices.first_authenticated_at` if it is empty.
- `markDeviceAuthenticated(db, { deviceId, now })` sets `devices.first_authenticated_at` if it is empty, before the API issues an access token. The column records when the device first proved its key under its device ID; while it is empty, and for 7 days after the registration, a new-device sign-in with the same key repeats the registration (#153). Migration `0014_device_first_authenticated` adds it and sets it to the creation time of every device that existed before, because nothing records whether those were used.
- `markDevicesSeen(db, { deviceIds, now })` sets `devices.last_seen_at` of many devices whose connections are still open, with one update per 500 IDs. A revoked device is left unchanged. A device row that another transaction holds is skipped (`FOR NO KEY UPDATE SKIP LOCKED`): the update never waits for a locked row, so it cannot deadlock with a sign-in or a revocation.
- `writeConnectionAudit(db, { action, userId, deviceId, subjectId, now })` writes a `connection.replaced` or `event.identity_mismatch` audit record with the connection's account and device as the actor. It never writes `workspace_id`, which is a foreign key, because the workspace of a refused event is unverified; the event ID goes into `subject_id`.

The workspace routes of the API use these (ADR 0014, "People and roles" and "What a workspace ID allows"). They return the protocol's `WorkspaceMember` for each person: the identity is the account's GitHub identity, its `verifiedAt` is `user_identities.last_sign_in_at`, and it is null for an unclaimed person and after erasure.

- `activePersonOf(db, { workspaceId, userId })` returns the account's active person in the workspace, its ID and role, or `undefined` when the account is not an active member, also when the workspace does not exist, so that the API answers both alike.
- `listWorkspaces(db, userId)` returns the workspaces that the account is an active member of, each with the account's own person, the most recently claimed first, at most `MAX_ANSWER_LIST_ITEMS`.
- `workspaceView(db, { workspaceId, now })` returns the workspace, all its people including former members, `join_requests_paused_at`, `max_unclaimed_members`, and the ownership offer while it is younger than 7 days at `now`, or `undefined` when the workspace does not exist. The caller checks membership first. The people are cut to `MAX_ANSWER_LIST_ITEMS` in an order that keeps the active owner and the target of the offer and in which unclaimed people never push out claimed ones: active people first, the owner, then the target, then the other claimed people, then the unclaimed people, each the most recently created first; then former members, the most recently removed first. ADR 0014 set no limit on the people that the owner and admins define, so an admin could otherwise have defined 1,000 unclaimed people and pushed every claimed member out of the view (applied on 2026-11-01 under the Project Manager's rule). Since the Project Manager's decision of 2026-11-02, a workspace holds at most `max_unclaimed_members` active unclaimed people, 500 at most, so they fill at most half of the view.
- `listInvitations(db, { workspaceId, userId, now })` returns the live invitations of the workspace, those neither accepted, revoked, nor expired at `now`, as the protocol's `Invitation`, the most recently created first, at most `MAX_ANSWER_LIST_ITEMS`. Only the owner and admins: a member is `forbidden`, and an account that is not an active member is `not_member`. The table records the creator's account; `createdByMemberId` is that account's active person in the workspace, which it has because removing a person or demoting an admin revokes the invitations they created (#93), and otherwise its most recently removed person. No code and no hash leaves the database.
- `previewInvitation(db, { tokenHash, userId, now })` returns what an invitation code claims, without consuming it or writing anything: the workspace's name, the display name of the person, the inviter, and the expiry, as the protocol's `PreviewInvitationResponse`. The inviter is the person of the invitation's creator in the workspace, its active person or else its most recently removed one, as in `listInvitations`, with the GitHub login and the time it was last verified. It decides as `acceptInvitation` does: `already_member` first, for an active member of the invitation's workspace in whatever state the invitation is, and otherwise `invitation_invalid` with the same reasons, `workspace_archived` for an archived workspace among them, and `inviter_unknown` when the creator has no person or no GitHub identity in the workspace. `acceptInvitation` needs no inviter and still takes such a code; the API README records why this is deliberate.

## Operator commands

An operator disables, enables, or erases an account with the application role in `DATABASE_URL`:

```sh
npm run db:account -w @mymandev/database -- disable <user ID>
npm run db:account -w @mymandev/database -- enable <user ID>
npm run db:account -w @mymandev/database -- erase <user ID> --confirm
```

The arguments are checked before the command connects (`src/account-command.ts`): an unknown action, a user ID that is not a UUIDv7, a missing or extra argument, and `--confirm` on `disable` or `enable` print the usage and exit with 1. `erase` without `--confirm` says what it would do and exits with 1, because an erasure cannot be undone. After the transaction, a refusal exits with 1 (`src/account-command.ts`): an erasure of an account that owns a workspace with another active member who has an account, or that does not exist, and enabling an erased account. Every other outcome exits with 0, also "no change": a second disable, enable, or erasure.

- `disableAccount` sets `users.disabled_at`, so every authentication of the account fails, and revokes in the same transaction the active grants of the agents that the account owns, with the account as `revoked_by_user_id` (ADR 0014; ADR 0015, P-77 and P-78). It locks the grants in the order of their IDs, as a removal does, and returns them in that order.
- `enableAccount` clears it. No grant is restored; the person grants again what their agents need. An erased account is refused (`erased: true`) and stays disabled, without an audit record: `enableAccount` locks the account's identity `FOR SHARE` first, in the order of the sign-in and the erasure, so it waits for an erasure that runs and then sees it.
- Both write an audit record (`account.disabled`, `account.enabled`) without an actor, and change nothing when the account does not exist or is already in that state.
- `eraseAccount(db, { userId, now })` (`src/account-erasure.ts`) erases a person's data on request in one transaction (ADR 0014, "Data model", P-62). It refuses an account that is the `owner` of a workspace in which another active, claimed person remains, and names those workspaces in the order of their IDs, because the owner is never removed (`workspace_members_owner_removal_check`): ownership is transferred to that person first. A workspace that the account owns without such a person is archived instead (the Project Manager's decision of 2026-11-02); unclaimed and removed people do not count. An account that does not exist, or has no GitHub identity, which the sign-in always creates with the account, is `not_found`; an account whose identity is erased is `already_erased`, and nothing changes, so a second erasure is harmless. Otherwise it:
  - sets `user_identities.erased_at` and clears `subject`, `login`, and `account_created_at`; no synthetic subject is written, so the former GitHub ID never matches a sign-in again, and a later sign-in with it creates a new account;
  - replaces `users.display_name`, the display names of every person of the account, removed ones included, and the requested display names of every join request of the account with the placeholder "Former user" (`ERASED_DISPLAY_NAME`), the labels of every device of the account, revoked ones included, with "Former device" (`ERASED_DEVICE_LABEL`), and the names of every agent that the account owns, disabled ones included, with "Former agent" (`ERASED_AGENT_NAME`), because a label or a name can hold personal data, such as "Ayla's work laptop" (the Project Manager's decision of 2026-11-02); and sets `users.disabled_at`, keeping an earlier time;
  - withdraws each pending join request of the account, with the account as `decided_by_user_id` and a `join_request.withdrawn` audit record, and marks a request past its expiry without a decision `expired`, with its `expires_at` as `decided_at`, as the account's next request would; so no request of an erased account can be approved. A block keeps its decision and its `unblocked_at`, and a pause of a workspace is not changed;
  - archives each workspace that the account owns without another active, claimed person: it sets `workspaces.archived_at` and `updated_at`; revokes the workspace's invitations that are neither accepted nor revoked, also expired ones, with the account as `revoked_by_user_id`, as a removal revokes them; denies the pending join requests of other accounts in it, with the account as `decided_by_user_id`, so their requesters see `denied`; and makes the owner's person a `member`, which the removal below then removes, so that `workspace_members_owner_removal_check` holds. It replaces the names that the owner wrote in the workspace with fixed placeholders: the workspace's name with "Archived workspace" (`ARCHIVED_WORKSPACE_NAME`), the names of its projects with "Archived project" (`ARCHIVED_PROJECT_NAME`) and of their repositories with "Archived repository" (`ARCHIVED_REPOSITORY_NAME`), and the display names of its unclaimed people, removed ones included, with "Former user" (`ERASED_DISPLAY_NAME`); the rows and their links stay, and every placeholder fits the length CHECK of its column. It also sets `archived_at` on the workspace's projects, keeping an earlier time, so that their common placeholder name meets the unique index of project names (#155) only among archived projects. A former member's person keeps the name of its own account. It writes `workspace.archived` with the workspace as the subject, and `invitation.revoked` and `join_request.denied`, each with the reason `account_erased`; the role change has no audit record of its own. An archived workspace has no owner, and only an archived workspace may have none: nobody with an account is active in it, so every membership check refuses it, and its unclaimed people, former members, and join requests past their expiry stay as they are. A join request to it is `workspace_not_found`, and an invitation code of it `invitation_invalid` (`workspace_archived`). `listWorkspaces` and `workspaceView` need no check of their own: the first starts from the account's active people, the API checks membership before the second, and no account has an active person in an archived workspace. Nothing of it is deleted, and nothing brings it back;
  - removes each active person of the account with the removal of `removeMember` (`removePerson` in `src/people.ts`), with the account itself as `removed_by_user_id` and `revoked_by_user_id` (the Project Manager's decision in the #93 issue comment of 2026-10-30), the former owner's person of an archived workspace too: it revokes the invitations that the account created, disables the account's agents, revokes their grants, and cancels the runs with `member_removed`, workspace by workspace, and writes `member.removed` with the reason `account_erased`;
  - revokes every device of the account that is not revoked with the reason `account_erased`, through `revokeDevice`, which disables the agents, revokes the grants, and cancels with `device_revoked` the runs on the device that no removal reached;
  - writes `account.erased` with the account as the subject.

  Every audit record of an erasure has no actor, as an operator's has none (the Project Manager's decision of 2026-11-01). Nothing is deleted: messages, runs, grants, invitations, workspaces, devices, agents, and person rows keep their attribution to the account's ID. Before anything else, every erasure takes one transaction-level advisory lock with a fixed key (`pg_advisory_xact_lock`), so two erasures run one after another: otherwise two erasures of accounts that share workspaces could lock the runs that each requested on the other's agents in opposite orders, because each takes the workspaces in the order of its own person IDs. Lock order: the account's identity `FOR UPDATE` first, as the API's sign-in locks it before the account, then the account, its devices, revoked ones included, its join requests, and its people, removed ones included, each in the order of their IDs. Then, for the workspaces that the account owns, each in the order of their IDs: (1) their unclaimed people, removed ones included; (2) the pending join requests of other accounts in them; (3) the workspace rows; (4) the pending join requests once more; (5) their projects, then the repositories of those projects; (6) their invitations that are neither accepted nor revoked. Only then does it decide whether to archive or to refuse. After the archive's writes come the agents that the account owns, in the order of their IDs, for their names, and then what each removal and each device revocation lock (`src/cascade.ts`): every agent that those lock is already held, so the order agents, then grants, then runs holds for the erasure as a whole. The join requests come before the people, unlike in an approval, so that an approval that holds a request of the account commits its new person before the erasure reads the people; an approval locks no person of the requester, so the two cannot wait for each other. The unclaimed people come with the people, before the workspace rows and the invitations, because the people functions and the invitations lock the people before a workspace row, and an acceptance locks its person before its invitation; a writer that holds an unclaimed person could wait only for the account's own person, as its actor, and every request of the account in the API locks the account first (`lockActor`), which the erasure holds. The requests of an owned workspace come before its row, as in every writer of join requests: a requester whose clock already counts its request as expired, while the erasure's earlier `now` does not (the command takes `now` before it waits for the advisory lock), holds that request and then waits for the workspace row, and the erasure waits for it before it holds the row. They come once more after the row: a new request locks the row before it stores the request, so the second pass finds every request that was stored before the erasure held the row, and a new request that waits for the erasure at the row then finds the workspace archived. Nothing else writes projects or repositories yet; a future writer locks them after the people and the workspace row, a project before its repositories. The erasure decides whether another active, claimed person remains only after it holds the workspace's unclaimed people and open invitations: an acceptance that holds its person first makes the erasure wait for its commit and then see the new person, so the erasure refuses; an acceptance that comes later waits at its person and then finds its invitation revoked. An approval or a new invitation needs an active owner or admin of the workspace, which is either the account's person, which the erasure holds from the start, or another person, who stops the archive anyway. One rare cycle remains, which PostgreSQL ends by aborting one of the two transactions: a workspace that the account owns can hold a pending request of the account itself, made before it became a member there, and a pending request of another account with a lower ID; the erasure holds the first from the account's own join requests and waits for the second, while another admin's `denyAllJoinRequests` holds the second and waits for the first. That admin is an active, claimed person, so the erasure would be refused anyway. A sign-in that waits for the erasure finds no identity and creates a new account; a request of the account in the API checks the account inside its transaction (`lockActor`), waits, and is refused.

- The command runs outside the API, which learns of an erasure only from the database, as of a disable. The API closes the account's open connections at its next sweep, within 60 seconds, with `device_revoked`, which ends their subscriptions. The account's access tokens stay in the API's memory until they expire, within 15 minutes, but stop working at once, because every request checks the device, and a revoked device never comes back. The other members get no `workspace.member.removed` and no `agent.run.state_changed` for the cancelled runs; they see the change when they next load the workspace.

Decided by the Project Manager on 2026-11-02, after these were open here: an erasure replaces the device labels and agent names, which the person chose, with fixed placeholders, because a label or a name can hold personal data that ADR 0014 did not list; and an erasure archives a workspace whose owner is the erased account when no other active, claimed person remains, instead of refusing, because there is nobody to transfer its ownership to, and replaces the names that the owner wrote in it. The Project Manager also decided on 2026-11-02 that the archive's audit records keep the reason `account_erased`; that the requesters whose join requests the archive denies get no live notice, because the command runs outside the API, and see `denied` in `GET /join-requests`; and that there is no command that restores an archived workspace.

## Development seed

The test source of M2 (#28, D2; ADR 0007, update of 2026-11-02): until #35 adds a route that creates runs, a development-only command creates an agent hosted on the developer's device, with runs in `queued`, which the desktop's development switch then moves through allowed transitions as the agent. It connects with the application role in `DATABASE_URL`, like the API:

```sh
MYMANDEV_DEV_SEED=1 npm run db:dev-seed -w @mymandev/database -- <device ID> <project ID> [--runs <n>]
```

In PowerShell, set `$env:MYMANDEV_DEV_SEED = "1"` first. Before it connects, the command (`src/dev-seed-command.ts`) refuses, with exit code 1 and without printing the URL: arguments other than a device ID and a project ID, both UUIDv7, and an optional `--runs` from 1 to 20 (3 by default); an environment without `MYMANDEV_DEV_SEED=1`, an explicit opt-in that no server sets; `NODE_ENV=production`; a `DATABASE_URL` that `checkDatabaseUrl` refuses; and a database that is not on this computer: the URL's host must be `localhost`, an IPv4 address in 127.0.0.0/8 in its usual dotted form (`net.isIPv4`), or `::1`, and the URL must not name a host in its query, which pg would connect to instead. After it connects, it also refuses a server that took the connection on another address than a loopback one (`host(inet_server_addr())`, null for a Unix-domain socket), so that a name that resolves elsewhere cannot pass. Every server database, the production one among them, is reached over the network, so the host decides without a marker in the database itself; a tunnel that forwards a local port to a server defeats this rule, and the opt-in is the second guard against it.

`seedDevAgent(db, { deviceId, projectId, runs, now })` (`src/dev-seed.ts`) then creates, in one transaction, an agent named "Test agent" in the project, owned by the device's account and hosted on the device, and the runs of it in `queued`, requested by the same account, without a repository, one millisecond apart. It refuses a device that does not exist or is revoked, a project that does not exist, a device whose account is not an active member of the project's workspace, and an archived project or workspace, and writes nothing then. It locks the device `FOR SHARE`, then the account's active person `FOR SHARE`, as `src/people.ts` asks of a writer that inserts an agent or a run, then the project `FOR SHARE`. The package index does not export it, so the API cannot call it; only the command and the tests import it. The command prints the agent ID and the run IDs.

transition and a device revocation of its device, in either order, and a transition that waits for a removal of its agent's owner, that run at the same time. The erasure's race tests also check which table the waiting transaction waits for (`pg_locks`). On PGlite they are skipped. The role test always uses its own PGlite instance; the Database workflow checks the same privileges on the server.

```sh
DATABASE_TEST_URL="postgres://postgres:<password>@127.0.0.1:5432/postgres?sslmode=disable" npm test -w @mymandev/database
```

The command above needs Git Bash on Windows; in PowerShell, set `$env:DATABASE_TEST_URL` first.

`db:compare` checks that the migrations create the same columns, constraints, indexes, and triggers on a PostgreSQL server as on PGlite. Run it after `db:migrate`; it reads `DATABASE_MIGRATION_URL` and needs the devDependencies. It always compares with PGlite, also when `DATABASE_TEST_URL` is set.

## Not included

API endpoints and query functions for these tables (each API issue of ADR 0014, #87 to #93, adds its own), the application connection (`DATABASE_URL`, M2), authentication, the permission check (M1-06), a purge job for old rows (P-62), and production database hosting.
