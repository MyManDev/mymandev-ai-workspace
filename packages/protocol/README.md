# @mymandev/protocol

Protocol v0: the shared contract between the desktop application and the cloud API. It defines the identities, the entities, the event envelope, the WebSocket frames that are not events, the agent run lifecycle, the capability vocabulary, the account, device, authentication, and membership contract, the workspace subscriptions, presence, chat messages, and event refusals of the realtime connection, and the chat history and agent activity routes, with zod schemas that validate untrusted input at runtime.

The protocol is a shared boundary. It changes only by agreement between the Project Manager and the desktop owner; see [OWNERSHIP.md](../../docs/process/OWNERSHIP.md). The decisions behind it are recorded in [ADR 0003 to ADR 0008 and ADR 0014](../../docs/architecture/decisions/README.md).

## Consumer rules

- Import only from `@mymandev/protocol`. Never import a file path inside this package.
- A device decodes what the server sends, events and frames, with `decodeServerMessage`. It refuses what only a device sends (`auth.response`, the workspace subscription requests, and `chat.message.send`) as `unknown_type`, and an event with a `deviceId` as `invalid_actor`, because the server sends every event with a null device; the decoded event's type, `ReceivedServerEvent`, says so.
- The server decodes what a device sends with `decodeClientFrame` before `auth.ok` and with `decodeClientMessage` after it. `decodeClientMessage` decodes events with `decodeClientEvent`, which rejects what only the server may originate (a `system` actor, `deviceId: null`, a run creation, and `SERVER_ONLY_EVENT_TYPES`) with `not_allowed_from_device`. Treat the result as `UnverifiedEvent` until the server's identity binding (M2) has bound its actor, device, and referenced IDs to the authenticated connection. Never cast it to `ProtocolEvent` or to a verified type.
- Decoding results are `{ ok: true, event }` or `{ ok: false, code }`. Unknown fields are stripped at every level, and the input is never mutated. The server rejects an event it cannot decode and reports the error to the sender; a device drops and logs it. Nobody processes part of an event, and the server never relays an event it could not validate.
- Under a strict Content Security Policy, the desktop renderer sets `z.config({ jitless: true })` before this package is evaluated: in a module that imports zod at the same exact version ([ADR 0003](../../docs/architecture/decisions/0003-zod-runtime-validation.md)) and that the renderer entry imports before anything that imports `@mymandev/protocol`. zod reads the setting when a schema is created, and this package creates its schemas when it is evaluated, so `enableJitlessValidation()` called after the import does not affect them. Without the setting, validation still works when code generation is blocked, because zod falls back, but zod's code generation probe is reported as a CSP violation.
- Human-entered text (`displayName`, `label`, `name`, run `reason`, chat message `body`) is always rendered as text, never as markup.
- `newId` and `newUuidV7` generate identifiers, never secrets. An ID is not a capability, and a UUIDv7 reveals its creation time.
- The server generates every entity ID, including run IDs. A device generates only event IDs.
- The capability names are defined here and nowhere else. This package exports no capability check; grant checks belong to `@mymandev/permissions`.
- Change the protocol only by agreement. Protocol version 0 is pre-stable: peers must run the same version, and any other version is rejected as `unsupported_version`.

## Credentials and device authentication

These rules follow [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md), which changes the secret rule of [ADR 0004](../../docs/architecture/decisions/0004-uuidv7-identifiers.md) (P-10, P-51).

- A device credential is a registered public key, not a stored secret. Each device holds an Ed25519 key pair; the private key never leaves the device, and the server stores only the raw 32-byte public key as 64 lowercase hexadecimal characters. `isDevicePublicKey` also refuses a non-canonical encoding and the keys of small order (`ED25519_WEAK_PUBLIC_KEYS`), for which a signature can be forged without the private key and some `node:crypto` builds accept it; the API checks it before it registers a key.
- Sign-in codes (`mmdc_`), access tokens (`mmda_`), invitation codes (`mmdi_`), and the sign-in cookie are 32 bytes from `crypto.randomBytes`, encoded as base64url. The codes carry their prefix and are 48 characters long, so secret scanning and the desktop recognize them. Only SHA-256 hashes are kept: invitation codes in the database, the others in API memory. The codes travel only in request bodies or the `Authorization` header, and the cookie only in the `Cookie` header; none of them appears in a URL or a log.
- The API's PKCE verifier for GitHub is the one exception to hashing: it is kept readable, and only in API memory, while a sign-in attempt lives.
- Nonces, PKCE states, verifiers, and challenges are 32 bytes as 43 base64url characters; a signature is 64 bytes as 86 base64url characters. Every encoding is the canonical one without padding that `Buffer.toString("base64url")` writes, and any other form is refused before verification.
- A device signs the UTF-8 bytes of `deviceAuthInput(...)`, never a string it builds itself. The input names its purpose (`ws`, `http`, or `sign-in`), the API's public origin as the audience, the nonce or sign-in code, the device, and what the signature binds to, so a signature never counts for another purpose, server, or connection. The audience is the origin of the API base URL as a URL parser writes it, with a DNS name or a dotted IPv4 address as the host, and must equal `API_PUBLIC_ORIGIN` exactly; the API's configuration refuses an origin that fails `isDeviceAuthAudience`, and `deviceAuthInput` throws for any value outside its format. Signing and verification use `node:crypto` in the desktop main process and in the API.
- `pairingCode(codeChallenge)` gives the 6 digits that the desktop and the API's confirmation page both show for one sign-in. It is not secret.
- The loopback listener checks the `state`, never the `Origin` header, which browsers send as `null` for the API's form POST (#67).

## WebSocket authentication and close codes

These rules follow [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md), "Device key and authentication", and the gateway of `@mymandev/api` applies them (#89).

- After the upgrade the server sends `auth.challenge` with a fresh nonce, the connection ID, and `protocolVersion`. The device answers with exactly one `auth.response`, signed over `deviceAuthInput` with the purpose `ws`, within `WS_AUTH_TIMEOUT_MS` (10 seconds). The server answers `auth.ok` with the user ID, the device ID, and the sign-in expiry, `SIGN_IN_LIFETIME_MS` (30 days) after the device's last sign-in. Only then may the device send events and the workspace subscription frames. A connection that is open at the expiry may stay open for `SIGN_IN_GRACE_MS` (24 hours) more; the server then closes it with `sign_in_required`.
- Before `auth.ok` the device sends nothing else: a binary frame, a frame over `MAX_AUTH_FRAME_BYTES` (1 KiB, measured on the raw frame before the JSON is parsed), a frame that is not JSON or that `decodeClientFrame` refuses, any frame other than `auth.response`, and a second frame close the connection with `protocol_violation`.
- A device decodes `auth.challenge` with `decodeServerMessage`. A challenge with another protocol version gives `unsupported_version` there, so the device knows that the versions differ before it answers.
- The close reason is the key of `WS_CLOSE_CODES`. A code is never reused, and new codes follow in order.

| Code | Reason                | When                                                                                                                   | What the desktop does                                                                                                                                                             |
| ---- | --------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 4000 | `auth_failed`         | Unknown device, bad signature, or disabled account.                                                                    | Does not reconnect. Shows the error and offers a sign-in.                                                                                                                         |
| 4001 | `auth_timeout`        | No `auth.response` within 10 seconds.                                                                                  | Reconnects with backoff.                                                                                                                                                          |
| 4002 | `device_revoked`      | A valid signature from a revoked device.                                                                               | Does not reconnect. Stops local execution, deletes the key, and creates a new key pair before the next sign-in.                                                                   |
| 4003 | `sign_in_required`    | A valid signature, but the device signed out, its last sign-in is older than 30 days, or GitHub reported a revocation. | Does not reconnect. Shows an in-app prompt with a "Sign in with GitHub" button. It never opens the browser on its own.                                                            |
| 4004 | `connection_replaced` | A newer connection of the same device authenticated.                                                                   | Does not reconnect on its own. Warns that the device key is in use in another installation and offers two actions: remove this device and register again, or reconnect here once. |
| 4005 | `protocol_violation`  | Before authentication: a frame that breaks the rules above.                                                            | Does not reconnect on its own and shows an error. When the protocol versions differ, it asks the person to update.                                                                |
| 4006 | `key_replaced`        | After authentication: a newer sign-in of the device replaced the key that signed.                                      | Reconnects at once with its new key and shows nothing. A copy of the old key then fails with `auth_failed`.                                                                       |

Decided by the Project Manager on 2026-10-31 (#89), as ADR 0014 leaves these details to the first change that needs them:

- A frame that breaks the rules before authentication closes with `protocol_violation` (4005), a new code after 4004.
- A connection whose key a newer sign-in of the device has replaced closes with `key_replaced` (4006), so that the desktop reconnects with its new key instead of offering a sign-in.
- Above the cap of 200 unauthenticated connections, the API answers the handshake with `429`, `rate_limited`, and `Retry-After` before the upgrade, so no close code is needed for it.
- `devices.last_seen_at` is written when a connection authenticates, and at most every 5 minutes while it stays open.

## Accounts and errors

- Inside a workspace, a user is always shown through their person row (`WorkspaceMember`): the person's display name and the GitHub login of its identity, in a monospace font with the time it was last verified, also for a removed person, who is shown as a former member. The account's own display name appears only on the account's own screens. A GitHub login is display data and never identifies an account.
- Every HTTP error answer has the body `{ statusCode, error, message, code }`. `code` is one of `API_ERROR_CODES`. A code that the API raises itself comes with its status from `API_ERROR_STATUS`. An error without its own code, such as a framework error, keeps its status and gets `genericApiErrorCode(status)`, so `bad_request` can come with another 4xx status (for example `413`) and `internal_error` with another 5xx status. `error` and `message` are the status text, never an input value: show the person the text for `code`.
- A route that names a workspace answers a non-member with `404` and `not_found`, exactly as for a workspace that does not exist. Only a join request answers an unknown workspace with `workspace_not_found`.
- An action that the caller's role does not allow answers `403` with `forbidden`; an action that conflicts with the current state, such as a second ownership offer, answers `409` with `conflict`; and an ownership offer or a promotion from a device younger than 72 hours answers `403` with `device_too_new`.

## Membership routes

These rules follow [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md) (People and roles, Invitations, Join requests, Limits, Removal and ownership, What a workspace ID allows). `MEMBERSHIP_ROUTES` fixes the paths, and `MEMBERSHIP_ROUTE_ERRORS` fixes every error code that each route can answer.

- Every route needs an access token. Only `GET` and `POST` are used, every path parameter is an ID filled in with `routePath`, and no route takes a query.
- Every path under `/workspaces/:workspaceId` checks active membership first, and a non-member gets `404` with `not_found`, as for a workspace that does not exist. The only action that a workspace ID allows a non-member, a join request, is therefore outside that path: `POST /join-requests` takes the workspace ID in its body, and the requester withdraws at `/join-requests/:joinRequestId/withdraw`. An invitation code names its own workspace, so preview and accept are under `/invitations`.
- An invitation code travels only in the bodies of `POST /invitations/preview` and `POST /invitations/accept`, and appears once, in the answer that creates it. These three answers carry `Cache-Control: no-store`. The list of live invitations never carries a code.
- A route with a response schema answers `200` with that body. Every other route answers `204` without a body, and the caller reads the new state from the workspace view, the lists, or the server's workspace events (M2-01).
- Every route can answer `bad_request`, `unauthorized`, `rate_limited`, and `internal_error`. Beyond those, `forbidden` means that the caller's role does not allow the action, and `conflict` that the target is not in the state the action needs: a removed person, an invitation or a request that is no longer live or pending, a person who is already claimed, a second ownership offer, or a limit of unclaimed people below their number. The limits that count live or pending items (50 live invitations or 50 pending join requests per workspace, 5 pending requests per person, and the workspace's limit of active unclaimed people) and the 24-hour wait after a denial answer `429` with `rate_limited` and `Retry-After`, like every other limit.
- Unknown fields are stripped, as everywhere in this package ([ADR 0003](../../docs/architecture/decisions/0003-zod-runtime-validation.md)), so a client cannot set a role, an account, or a note by adding a field.
- Every list in an answer (workspaces, people, invitations, join requests, and the device list of #97) holds at most `MAX_ANSWER_LIST_ITEMS` (1,000) items, as ADR 0003 usage rule 3 asks (Project Manager decision of 2026-10-29). The maximum lies far above every count limit of ADR 0014, so raising one of those limits with use (P-64) never breaks an older client. The people of a workspace with its former members, and the devices with the revoked ones, can grow beyond it over time; the API then sends the most recent items, until pagination exists.

What the answers show:

- The workspace view holds every person of the workspace, unclaimed, active, and former, so that history stays attributed; when join requests were paused, or null; how many active unclaimed people the workspace may hold (`maxUnclaimedMembers`); and the live ownership offer (the target's `memberId`, `offeredAt`, and `expiresAt`), or null. The schema checks that every person belongs to the workspace, that exactly one active owner exists, and that an offer names an active, claimed person who is not the owner.
- A live invitation shows the person it claims and its creator as `createdByMemberId`, which the desktop shows through the creator's person row. The creator is always an active member, because removing a person or demoting an admin revokes the invitations they created.
- A preview shows what ADR 0014 lists and nothing more: the workspace name, the display name of the person that the code claims, the inviter's display name in the workspace with their identity (the GitHub login and when it was last verified), and the expiry.
- The requester's own view of a join request holds only what they sent: its ID, the workspace ID, the requested display name, and when it was created and expires. It says nothing about the workspace. `GET /join-requests` adds how each request ended (`decision` and `decidedAt`, null while pending) from `OWN_JOIN_REQUEST_DECISIONS`: `approved`, `denied`, `withdrawn`, or `expired`. A block is shown as `denied`; a new request after a block answers `join_requests_closed`, as for a pause. A request past its `expiresAt` is shown as `expired` with `decidedAt` equal to `expiresAt`, whether or not the server has marked it. The list holds the most recent requests first.
- The approver's view of a join request adds the requester's identity: the GitHub login, when it was last verified, and the creation date of the GitHub account (`accountCreatedAt`). It lists the pending requests and the blocked requests whose block is in force, with `decision` and `decidedAt`. Its requester is null only after the account's data was erased, never on a pending request.

Decisions that ADR 0014 leaves open, settled here:

- A pause of join requests has no expiry: it ends only by hand, with `POST /workspaces/:workspaceId/join-requests/resume`. Pausing a paused workspace or resuming one that is not paused changes nothing. A pause keeps the pending requests; denying them all is a separate action.
- An ownership offer past its 7 days is no offer: the workspace view does not show it, accepting or withdrawing it answers `conflict`, and the owner can make a new one. How the stored offer is cleared stays with the API and the database (#86).
- Every person renames their own person; the owner and admins rename unclaimed people; nobody renames another claimed person. Nobody removes the owner, and the owner cannot leave: both answer `forbidden`. A person leaves with `leave`, not by removing their own person.
- The creator of a workspace and a requester send the display name of their person; the desktop fills it in with the account's display name. An approver may replace the requested name.
- `POST /invitations/preview` also answers `already_member` for an account that is already an active member of the workspace, so the join screen can say so before accepting.

Decided by the Project Manager on 2026-11-02, beyond ADR 0014:

- A workspace limits how many active unclaimed people it holds: people without an account who are not removed. `UNCLAIMED_MEMBER_LIMIT` fixes the range, from 1 to 500. The creator may send `maxUnclaimedMembers` with `POST /workspaces`; the server applies 500 when it is omitted. The workspace view shows the limit in force.
- Only the owner changes the limit, with `POST /workspaces/:workspaceId/unclaimed-member-limit`, to any value from 1 to 500. An admin or a member gets `forbidden`, like every other owner-only route, and a value below the number of active unclaimed people gets `conflict`. Sending the limit in force again changes nothing. No event reports a change; the members read it from the workspace view.
- Defining a person in a workspace that holds as many active unclaimed people as its limit answers `429` with `rate_limited` and `Retry-After`, as the other limits that count items do. No time frees a place, only removing or claiming one of them or a higher limit, so the desktop shows the limit instead of retrying on its own.

Decided by the Project Manager on 2026-11-01 (#92), as ADR 0014 leaves these details open:

- The requester learns the decision from `GET /join-requests`, which lists the account's own requests, and from the account frame `account.join_request_decided`, which reaches the account's open connections after an owner or admin approves or denies a request. Its `decision` is `approved` or `denied`; a block is sent as `denied`. A withdrawal and an expiry send no frame. Like every account frame, it reaches only open connections, so the desktop reads the list after `auth.ok`.
- A pending request whose `expiresAt` has passed no longer counts as pending, also before the server marks it `expired`: it is not returned as the pending request, it counts toward no limit, it is not in the approvers' list, and it can no longer be approved, denied, or withdrawn (`conflict`).
- "Deny and invite instead" needs no route of its own: the desktop denies the request and then creates an invitation for one of the unclaimed people.

Decided by the Project Manager on 2026-11-02 (#93), so that every device of both people learns of an ownership transfer (ADR 0014, "Removal and ownership"):

- The account frame `account.ownership_transferred` reaches every open connection of the previous owner's account and of the new owner's account, also one that subscribed to nothing. It carries the workspace ID, the two people (`previousOwnerMemberId`, now an admin, and `ownerMemberId`, now the owner), which are never the same, and `transferredAt`. The workspace's subscribers still get the `workspace.ownership.transferred` event. Like every account frame, it reaches only open connections, so the desktop reads the workspace view after `auth.ok`.

## Project routes

These rules follow #155 and the Project Manager's decisions of 2026-11-02. `PROJECT_ROUTES` fixes the paths, and `PROJECT_ROUTE_ERRORS` fixes every error code that each route can answer. The general rules of the membership routes above hold for them too: an access token, only `GET` and `POST`, every path parameter an ID, no query, unknown fields stripped, `200` with a body or `204` without one, and the common codes `bad_request`, `unauthorized`, `rate_limited`, and `internal_error`.

| Route                                                      | Who                                     | Body   | Answer                                                                      | Codes beyond the common ones         |
| ---------------------------------------------------------- | --------------------------------------- | ------ | --------------------------------------------------------------------------- | ------------------------------------ |
| `GET /workspaces/:workspaceId/projects`                    | member                                  |        | the projects that are not archived, the oldest first, each with its creator | `not_found`                          |
| `POST /workspaces/:workspaceId/projects`                   | member                                  | `name` | the new project with its creator                                            | `not_found`, `conflict`              |
| `POST /workspaces/:workspaceId/projects/:projectId/rename` | the project's creator, the owner, admin | `name` |                                                                             | `not_found`, `forbidden`, `conflict` |

Events, which only the server sends, with a `system` actor and `deviceId: null`, to the workspace's subscribed connections after the commit, as it sends the membership events:

| Event                       | Payload                                                         |
| --------------------------- | --------------------------------------------------------------- |
| `workspace.project.created` | `project`: `id`, `workspaceId`, `name`, and `createdByMemberId` |
| `workspace.project.renamed` | `projectId` and `name`                                          |

Decided by the Project Manager on 2026-11-02 (#155):

1. Any active member of a workspace may create a project in it.
2. Version 0 creates, lists, and renames projects. The project's creator, the workspace owner, and admins may rename it; anyone else gets `forbidden`. Archiving comes later, because under P-77 it must revoke grants.
3. A name has 1 to 100 characters, as the database check says, and is unique among the workspace's projects that are not archived, compared without regard to case. A clash answers `conflict`.
4. A workspace holds at most 100 projects that are not archived, and an account creates at most 20 projects in 24 hours. Both answer `429` with `rate_limited` and `Retry-After`, like the limit of unclaimed people (#141).
5. Creating a project creates its `project` conversation, the project's chat, in the same transaction (#27, D1).

Decided by the Project Manager on 2026-11-02, after the first review of #155:

1. The event names `workspace.project.created` and `workspace.project.renamed` are confirmed, and so is the erasure that archives the projects of a workspace it archives.
2. A project name is normalized before it is checked and stored, on creation and on rename: to Unicode NFC, then without white space at the start and the end (`normalizeProjectName`), so that names that look the same are the same. The 1 to 100 characters count the normalized name. Workspace and person names stay as they are sent.
3. The right to rename a project follows the account that created it: a creator who leaves the workspace and joins again as a new person may rename it again.
4. The answers and `workspace.project.created` name the project's creator as `createdByMemberId` (`WorkspaceProject`).

Settled here, as the decisions above leave them open:

- The paths lie under `/workspaces/:workspaceId`, like the membership routes, so the membership check covers every project route before anything else, and a project ID that the workspace does not have, also one of another workspace, answers the same `not_found` as an unknown one. The rename follows `.../members/:memberId/rename`.
- The events are named `workspace.project.created` and `workspace.project.renamed`, not `project.created` and `project.renamed` as #155 writes (confirmed above): ADR 0006 requires three parts, `<domain>.<entity>.<past_tense>`, and a type of two parts is a frame (`FRAME_TYPE_PATTERN`), which no decoder accepts as an event. They are the project lifecycle events that decision 3 of #110 below left to an issue about the projects API. `workspace.project.created` carries the whole project and `workspace.project.renamed` sets one value, so the resynchronization below applies to them as to the membership events.
- A name follows the text rule of ADR 0005 for single-line text (`displayText(LIMITS.name)`), as a workspace's name, after it is normalized. The request schemas parse to the normalized name, so the server stores and compares only normalized names: `Cafe` with a combining acute accent and `Café` with the composed letter are one name, and so are `App` and `App` sent with a space before and after it, and a name of only white space is empty and refused with `bad_request`. Trimming removes what `String.prototype.trim` counts as white space or a line terminator at the start and the end, among them the tab, CR, LF, U+2028, and U+FEFF; inside a name, a control or format character such as these is still refused by the text rule. A name may be sent with up to 1,000 characters, so that a name of 100 characters fits in a decomposed form or with white space around it; longer text is refused before it is normalized. The answers and the events carry names as stored, so they need no normalization. "Without regard to case" is Unicode's simple lowercase mapping, as PostgreSQL's `lower` applies it with the built-in `pg_c_utf8` collation, the same on every server: `App`, `app`, and `APP` clash, and so do `Ärger` and `ÄRGER`; `Straße` and `STRASSE` do not, and spaces count. The database's unique index decides, so a desktop that checks a name before it sends it still handles `conflict`.
- The 24 hours count every project that the account created, in all its workspaces together. A refused creation does not count. The limit of 100 projects in a workspace ends with no time, only when a project is archived, so its `Retry-After` is 24 hours, as for unclaimed people; the 20 creations end when the oldest of them leaves the 24 hours. A limit is decided before the name, so a creation at a limit answers `rate_limited` whatever its name.
- Renaming a project to its name in force, after normalization, changes nothing and sends no event; a change of case alone is a new name. An archived project is not listed, cannot be renamed (`conflict`), and leaves its name free. Today only the erasure of an owner's account archives projects, with the workspace it archives.
- Creating and renaming a project write no audit record: they are not administrative actions of ADR 0014, and its audit vocabulary has no project action.

- `createdByMemberId` is the creating account's active person in the workspace, and the account's most recently removed person while it has none, as `createdByMemberId` of an invitation is. So a creator who left and joined again is named by the new person, which holds the right to rename the project (decision 3 above), and the desktop offers the rename when `createdByMemberId` is the account's own person or the account's role is owner or admin. A creator who left is named by the former person, an ID that stays valid because person rows are never deleted, and is shown through that row as a former member. The person that created the project is not kept apart from the account: after a rejoin the project names the new person, as the rights do. `workspace.project.created` names the person that created the project, which is that account's active person at that moment.

## Workspace subscriptions, presence, and chat

These rules follow #110 and the Project Manager's decisions of 2026-11-01, confirmed on 2026-11-02 (below). Storing chat messages, their authorization, and the history route belong to #27, whose contract is in the next section; the gateway of `@mymandev/api` applies the rules of this section (#129). The protocol is a shared boundary: the desktop owner reviews this contract when they start work (ADR 0014, P-67).

Frames after `auth.ok`:

| Frame                         | From   | Fields                              | Meaning                                                                                                                                                                                                           |
| ----------------------------- | ------ | ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspace.subscribe`         | device | `workspaceId`                       | Asks for the workspace's events and presence. Subscribing again keeps one subscription and gets a fresh `workspace.subscribed`, also when the connection is at the subscription cap.                              |
| `workspace.unsubscribe`       | device | `workspaceId`                       | Ends the subscription. Answered with `workspace.unsubscribed` also when the connection was not subscribed.                                                                                                        |
| `workspace.subscribed`        | server | `workspaceId`, `onlineMemberIds`    | The subscription is live. `onlineMemberIds` is the presence snapshot: each online person once, the subscriber's own person included, at most `MAX_ANSWER_LIST_ITEMS`; everyone else is offline.                   |
| `workspace.subscribe_refused` | server | `workspaceId`, `code`               | `not_found` for an unknown workspace and for one that the account is not an active member of, alike; `too_many_subscriptions` when the connection holds as many as the server allows.                             |
| `workspace.unsubscribed`      | server | `workspaceId`, `reason`             | The subscription ended: `requested` by the device, or `membership_ended` when the person was removed or left (`account.removed_from_workspace` also reaches the account).                                         |
| `presence.changed`            | server | `workspaceId`, `memberId`, `status` | A person of a subscribed workspace became `online` or `offline`.                                                                                                                                                  |
| `event.refused`               | server | `eventId`, `code`                   | The server refused an event that this connection sent, stored and relayed nothing, and keeps the connection open: `not_found`, `conflict`, or `rate_limited` (next section). Sent only to the sending connection. |

Events:

| Event                     | From                                                                                                                                                                                                              | Payload                                                                                  |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `chat.message.send`       | a device only, with the person's `user` actor and its device ID                                                                                                                                                   | `projectId`, `body`                                                                      |
| `chat.message.created`    | the server only, with a `system` actor and `deviceId: null`                                                                                                                                                       | `message`: `id` (`MessageId`), `projectId`, `seq`, `author`, `body`, `createdAt`         |
| `agent.run.state_changed` | the server with a `system` actor and `deviceId: null` when it creates or cancels a run; otherwise the agent's host device with the `agent` actor and its device ID, which the server relays with `deviceId: null` | `runId`, `agentId`, optional `repositoryId`, `previousState`, `state`, optional `reason` |

Decided by the Project Manager on 2026-11-01:

1. Subscribing is explicit. A connection receives a workspace's events and presence only while it is subscribed to the workspace with `workspace.subscribe`, and only while its account is an active member. The server answers each subscribe and unsubscribe with a frame, in the order they arrived.
2. Presence is per person, `online` or `offline`, and never stored. A person is online while at least one connection of its account is subscribed to the workspace; an unclaimed person is always offline. The server sends a snapshot in `workspace.subscribed` and then `presence.changed` for every change of a person's status, not for each device. No subscription or presence frame names a device: device data is shown only to its own account.
3. A project event is an event scoped to a project, such as a chat message or a run. It goes to every subscribed connection of the workspace; the server does not filter by project. Project lifecycle events wait for an issue about the projects API.
4. #110 defines the chat events `chat.message.send` and `chat.message.created`. Storing them and the history route belong to #27.
5. M2 has no server sequence number. The device reloads the workspace over HTTP after every `workspace.subscribed`, also after a reconnect.

Settled here, as the decisions above leave them open:

- Frame names: `workspace.subscribe`, `workspace.unsubscribe`, `workspace.subscribed`, `workspace.subscribe_refused`, `workspace.unsubscribed`, and `presence.changed`. Their codes come from `WORKSPACE_SUBSCRIBE_REFUSAL_CODES`, `WORKSPACE_UNSUBSCRIBE_REASONS`, and `PRESENCE_STATUSES`.
- Resynchronizing (decision 5): the device starts its HTTP reload only after `workspace.subscribed`, and buffers the workspace's events from that frame until the reload answers. Then it applies the buffered events in order on top of the reloaded state. The HTTP answer carries no event IDs, so the order matters: an event committed after the server read the state can arrive over the connection before the HTTP answer, and applying the older answer over it would lose it. An event that the reloaded state already contains changes nothing, because every event sets the state it reports: `workspace.member.defined` and `workspace.member.claimed` carry the full person, the other membership events set one value, and a run state change sets the run's state. Chat messages are deduplicated by message ID. Presence is not part of the HTTP view: the snapshot and `presence.changed` apply at once.
- Before `auth.ok`, `decodeClientFrame` answers a subscription frame with `unexpected_frame`, so the rule that only `auth.response` may come first is unchanged. After `auth.ok`, `decodeClientMessage` answers `auth.response` with `unexpected_frame`.
- `chat.message.send` is a device's command event: a request that the server may refuse. It keeps the Project Manager's name, an exception to the past-tense rule of ADR 0006; the fact is `chat.message.created`. The Project Manager confirmed the exception on 2026-11-02; it is recorded as updates in ADR 0006. The server never relays it, and a device refuses it from the server by its type (`CLIENT_ONLY_EVENT_TYPES`). Its event ID is the idempotency key that the database keeps as `client_event_id`, so a resent event with the same ID creates no second message.
- Before #27 stores or relays a message, the server's `bindIdentity` must also bind the `projectId` of `chat.message.send` to the event's workspace (ADR 0006, reference binding). Today it checks the device, the user, and active membership only.
- `chat.message.created` is server-originated like the membership events, with a `system` actor and `deviceId: null`. It is the null `deviceId` that keeps the sender's device ID from other members; the message itself is always attributed to its author, `author`, a person shown through their person row or an agent (#27). The server sets `causationId` to the ID of the `chat.message.send`, so the sending device can replace its pending copy.
- The events name the project, not a conversation: a project has one chat in M2, and the server finds the conversation that holds it. A conversation ID waits until a project can have more than one.
- The message `body` follows the text rule of ADR 0005 with two exceptions, the line feed and the tab (`multilineText`, `SAFE_MULTILINE_TEXT_PATTERN`); the carriage return and every other control character stay refused, so the desktop sends a line break as a line feed. The exceptions hold for chat message bodies only; the Project Manager confirmed them on 2026-11-02, and they are recorded as updates in ADR 0005. It holds 1 to `LIMITS.messageBody` (16,000) code points, which equals the database CHECK, because zod and `char_length` both count code points. The largest `chat.message.send` that `JSON.stringify` writes is about 64,500 bytes, and the largest `chat.message.created`, with its `seq` and `author`, about 64,600 bytes, both just under `MAX_FRAME_BYTES` (64 KiB), the largest frame that the server accepts after authentication; a larger body or a larger envelope needs a larger frame limit.

Confirmed by the Project Manager on 2026-11-02 (#110):

- the two exceptions above: the name `chat.message.send` (ADR 0006) and the line feed and the tab in chat message bodies (ADR 0005);
- the limits of the gateway: 50 subscriptions per connection, after which `workspace.subscribe` answers `too_many_subscriptions`, a heartbeat every 30 seconds, and 1 MiB of data waiting to be sent per connection.

Still open:

- whether erasing an account's data also removes the bodies of its chat messages; today an erasure keeps them and their attribution (#27).

## Chat history, refused events, and agent activity

These rules follow the Project Manager's decisions of 2026-11-02 on #27 (project chat) and #28 (agent activity). Storing messages and run transitions, and serving the routes, belong to the database and API parts of those issues. The desktop owner reviews these additions together with the rest of this contract (ADR 0014, P-67).

Decided by the Project Manager on 2026-11-02 (#27, #28):

1. The server answers an event from a device that it refuses with `event.refused`, sent only to the sender, and the connection stays open. Protocol violations still close it (below). The codes are `not_found`, `conflict`, and `rate_limited` (`EVENT_REFUSAL_CODES`), a closed list that is complete before protocol version 1. The values of the send limit behind `rate_limited` are decided with the API part of #27.
2. A `chat.message.send` whose event ID the server already stored for the sending device gets the stored message again: a `chat.message.created` sent only to the sending connection, with `causationId` set to that event ID, and never to the workspace again.
3. A chat message names its author as `{ kind: "member", memberId }` or `{ kind: "agent", agentId }` (`ChatMessageAuthorSchema`). Servers of M2 send only `member`. The database keeps the author's person as `author_member_id` (ADR 0013).
4. `chat.message.created` and the history carry the message's `seq`, its number in the project's chat, from 1.
5. `GET /projects/:projectId/messages?beforeSeq=&limit=` returns the history, the newest first, 50 messages by default and at most 100 (`CHAT_HISTORY_PAGE`). The desktop loads the newest page when a chat opens and again after each `workspace.subscribed`.
6. In M2, the agent activity events are `agent.run.state_changed` only. A development-only database command seeds an agent hosted on the developer's device and runs in `queued`, and a development-only switch of the desktop main process moves them through allowed transitions as the agent, over the real connection. No production route creates runs before #35 (ADR 0007).
7. Two read routes return a project's agents and its unfinished and recent runs, which the desktop reloads after each `workspace.subscribed`. The agent list does not show the host device to other accounts.
8. The server stores an accepted transition from the agent's host device and relays it to the workspace's subscribers with every field unchanged (`id`, `occurredAt`, `actor`, `correlationId`, `causationId`, and `payload`) except `deviceId`, which is null, so that other members never see the host device's ID. `decodeServerMessage` accepts that form and refuses every event from the server that carries a `deviceId` (`invalid_actor`); `decodeClientMessage` refuses the relayed form from a device (`not_allowed_from_device`).
9. The server records every accepted transition with its device and event ID, which are unique together, in a transition log that the database part of #28 adds. A transition whose device and event ID are already recorded gets the relayed `agent.run.state_changed` again, sent only to the sending connection, and is never applied twice. The sending connection gets its own relayed transition, its acknowledgement, also when it is not subscribed to the workspace.
10. A transition for a disabled agent gets `event.refused` with `conflict`, and the connection stays open: it is a race with the person who disabled the agent, not an attack.

Update of 2026-11-03 (#27, API part): the values of the chat send limit, applied under the Project Manager's rule of 2026-11-02 and recorded in the [API's README](../../apps/api/README.md#project-chat): at most 15 `chat.message.send` in any 10 seconds and 600 in an hour per account, all its devices and workspaces together; a send above either gets `event.refused` with `rate_limited`, the connection stays open, and the device may send the same event ID again later. 15 of the largest `chat.message.created` stay under the server's 1 MiB backpressure limit of a connection. The limit counts per account, not per device, so that more devices give an account no more room; the protocol is unchanged. Whether run transitions (#28) count too is decided with that part.

Applied as defaults unless the Project Manager decides otherwise (#27, #28):

- Any active member of the project's workspace may post to the project's chat and read its history, agents, and runs.
- Posting to an archived project or workspace is refused with `conflict`; the history of an archived project stays readable.
- A reused event ID returns the stored message, also when the body differs: the event ID is the idempotency key.
- The sending connection gets the `chat.message.created` of its message, or the refusal, also when it is not subscribed to the workspace.
- The server stores each accepted run transition before it relays it, with one update that applies only while the run is still in `previousState`.

What the server does with an event from a device that it does not accept:

| Case                                                                                                                                                                                                                                                                | Answer                                                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `decodeClientMessage` refuses the message, or the frame is binary, not JSON, or over `MAX_FRAME_BYTES`.                                                                                                                                                             | Closes the connection, with the codes that the [API's README](../../apps/api/README.md) lists. |
| The event's `deviceId`, or a `user` actor's `userId`, is not the connection's; or an `agent` actor names an agent of the workspace that another device hosts.                                                                                                       | Closes the connection with `identity_mismatch`, and the server audits it (ADR 0006).           |
| The account is not an active member of the event's workspace.                                                                                                                                                                                                       | Closes the connection with `not_a_member`.                                                     |
| The device or the account may no longer act: a revoked device, a sign-out or an expired sign-in, a disabled account, or a replaced key.                                                                                                                             | Closes the connection with its code from `WS_CLOSE_CODES`.                                     |
| The device sent more events than the send limit allows.                                                                                                                                                                                                             | `event.refused` with `rate_limited`.                                                           |
| A `chat.message.send` whose event ID the server already stored for the sending device. Checked before the state of the project and the workspace, so a message stored before an archive is still answered.                                                          | The stored message in a `chat.message.created`, to the sending connection only.                |
| An `agent.run.state_changed` whose device and event ID the server already recorded.                                                                                                                                                                                 | The relayed transition again, to the sending connection only.                                  |
| The event names a project, an agent, a run, or a repository that does not exist, or that is not in the event's workspace; a run of another agent than the event's `agentId`; or a `repositoryId` that is not in the agent's project or is not the run's repository. | `event.refused` with `not_found`.                                                              |
| What the event names exists, but is not in the state that the event needs: a run whose stored state is not `previousState`, an archived project or workspace, or a disabled agent.                                                                                  | `event.refused` with `conflict`.                                                               |

- `event.refused` carries only the refused event's ID and a code from `EVENT_REFUSAL_CODES`. A project, an agent, a run, or a repository that does not exist and one of another workspace get the same `not_found`, as ADR 0007 and ADR 0014 ask, so that a device cannot probe which IDs exist.
- A device chooses its event IDs, and the server de-duplicates by device and event ID (ADR 0006). The relayed event has no device, so a receiver never de-duplicates relayed run events by event ID alone; it does not need to, because a run event sets the run's state. A repeated `chat.message.created` changes nothing, because chat messages are deduplicated by message ID.

Routes (#27, #28):

- Every route needs an access token. A project that does not exist and a project of a workspace that the account is not an active member of both answer `404` with `not_found`.
- The paths start with the project, as the Project Manager chose for the history: a project ID names its workspace, so a workspace in the path would only add another case that must answer the same `404`. `CHAT_ROUTES` and `AGENT_ROUTES` fix them, and `CHAT_ROUTE_ERRORS` and `AGENT_ROUTE_ERRORS` fix their codes. Every route can answer the common codes of the membership routes: `bad_request`, `unauthorized`, `rate_limited`, and `internal_error`.
- Unlike the membership routes, the history takes a query. Its values are strings in plain decimal form, without a sign, a leading zero, or an exponent (`ChatHistoryQuerySchema`).

| Route                               | Who    | Query                                                                | Answer                                                  | Codes beyond the common ones |
| ----------------------------------- | ------ | -------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------- |
| `GET /projects/:projectId/messages` | member | optional `beforeSeq`; optional `limit`, from 1 to 100, 50 by default | one page of the history, the newest first               | `not_found`                  |
| `GET /projects/:projectId/agents`   | member |                                                                      | the project's agents                                    | `not_found`                  |
| `GET /projects/:projectId/runs`     | member |                                                                      | the unfinished runs and the most recently finished runs | `not_found`                  |

What the answers show:

- The history holds messages of one project, each message ID once, the newest first by `seq`. With `beforeSeq`, it holds only messages with a lower `seq`. A page with fewer messages than its `limit` is the oldest; the device asks for the next older page with the lowest `seq` it holds as `beforeSeq`. The schema cannot see the request, so the device checks that every `seq` is lower than the `beforeSeq` it sent, that the page holds at most the `limit` it sent, and that every message belongs to the project of the path.
- An agent shows its `id`, `projectId`, `name`, its owner's person as `ownerMemberId`, shown through the person row also after the owner was removed, and `disabledAt`, null while it is enabled. Disabled agents are listed too, so that their runs stay attributed. The list shows the host device to no account today, so other accounts never see it (#110); a field that tells the owner's own devices which agents they host can be added later as an optional field, without a new protocol version. The owner is named by person, because inside a workspace a user is always shown through their person row.
- The runs come in two lists. `unfinishedRuns` holds every unfinished run (`queued`, `running`, or `awaiting_input`), up to `MAX_ANSWER_LIST_ITEMS`, the most recently created first. `finishedRuns` holds the most recently finished runs, the most recently finished first: the server sends `RECENT_FINISHED_RUNS` (50), and the schema accepts up to `MAX_ANSWER_LIST_ITEMS`, so that raising the server's count never breaks an older desktop. "Recent" is a number of runs, not a time, so the answer stays bounded however busy the project is. A run shows its `id`, `agentId`, `projectId`, `repositoryId` or null, `state`, the `reason` of its last state change or null, `createdAt`, and `finishedAt`, which is set exactly when the state is terminal.
