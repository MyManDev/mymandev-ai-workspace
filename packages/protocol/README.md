# @mymandev/protocol

Protocol v0: the shared contract between the desktop application and the cloud API. It defines the identities, the entities, the event envelope, the WebSocket frames that are not events, the agent run lifecycle, the capability vocabulary, and the account, device, authentication, and membership contract, with zod schemas that validate untrusted input at runtime.

The protocol is a shared boundary. It changes only by agreement between the Project Manager and the desktop owner; see [OWNERSHIP.md](../../docs/process/OWNERSHIP.md). The decisions behind it are recorded in [ADR 0003 to ADR 0008 and ADR 0014](../../docs/architecture/decisions/README.md).

## Consumer rules

- Import only from `@mymandev/protocol`. Never import a file path inside this package.
- A device decodes events that the server sends with `decodeEvent`.
- The server decodes events that a device sends with `decodeClientEvent`. It rejects what only the server may originate (a `system` actor, `deviceId: null`, and a run creation) with `not_allowed_from_device`. Treat the result as `UnverifiedEvent` until the server's identity binding (M2) has bound its actor, device, and referenced IDs to the authenticated connection. Never cast it to `ProtocolEvent` or to a verified type.
- Decoding results are `{ ok: true, event }` or `{ ok: false, code }`. Unknown fields are stripped at every level, and the input is never mutated. The server rejects an event it cannot decode and reports the error to the sender; a device drops and logs it. Nobody processes part of an event, and the server never relays an event it could not validate.
- Under a strict Content Security Policy, the desktop renderer sets `z.config({ jitless: true })` before this package is evaluated: in a module that imports zod at the same exact version ([ADR 0003](../../docs/architecture/decisions/0003-zod-runtime-validation.md)) and that the renderer entry imports before anything that imports `@mymandev/protocol`. zod reads the setting when a schema is created, and this package creates its schemas when it is evaluated, so `enableJitlessValidation()` called after the import does not affect them. Without the setting, validation still works when code generation is blocked, because zod falls back, but zod's code generation probe is reported as a CSP violation.
- Human-entered text (`displayName`, `label`, `name`, run `reason`) is always rendered as text, never as markup.
- `newId` and `newUuidV7` generate identifiers, never secrets. An ID is not a capability, and a UUIDv7 reveals its creation time.
- The server generates every entity ID, including run IDs. A device generates only event IDs.
- The capability names are defined here and nowhere else. This package exports no capability check; grant checks belong to `@mymandev/permissions`.
- Change the protocol only by agreement. Protocol version 0 is pre-stable: peers must run the same version, and any other version is rejected as `unsupported_version`.

## Credentials and device authentication

These rules follow [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md), which changes the secret rule of [ADR 0004](../../docs/architecture/decisions/0004-uuidv7-identifiers.md) (P-10, P-51).

- A device credential is a registered public key, not a stored secret. Each device holds an Ed25519 key pair; the private key never leaves the device, and the server stores only the raw 32-byte public key as 64 lowercase hexadecimal characters. `isDevicePublicKey` also refuses a non-canonical encoding and the keys of small order (`ED25519_WEAK_PUBLIC_KEYS`), for which a signature can be forged without the private key and some `node:crypto` builds accept it; the API checks it before it registers a key.
- Sign-in codes (`mmdc_`), access tokens (`mmda_`), invitation codes (`mmdi_`), and the sign-in cookie are 32 bytes from `crypto.randomBytes`, encoded as base64url. The codes carry their prefix and are 48 characters long, so secret scanning and the desktop recognize them. Only SHA-256 hashes are kept: invitation codes in the database, the others in API memory. The codes travel only in request bodies or the `Authorization` header, and the cookie only in the `Cookie` header; none of them appears in a URL or a log.
- The API's PKCE verifier for GitHub is the one exception to hashing: it is kept readable, and only in API memory, while a sign-in attempt lives.
- Nonces, PKCE states, verifiers, and challenges are 32 bytes as 43 base64url characters; a signature is 64 bytes as 86 base64url characters. Every encoding is the canonical one without padding that `Buffer.toString("base64url")` writes, and any other form is refused before verification.
- A device signs the UTF-8 bytes of `deviceAuthInput(...)`, never a string it builds itself. The input names its purpose (`ws`, `http`, or `sign-in`), the API's public origin as the audience, the nonce or sign-in code, the device, and what the signature binds to, so a signature never counts for another purpose, server, or connection. The audience is the origin of the API base URL as a URL parser writes it, with a DNS name or a dotted IPv4 address as the host, and must equal `API_PUBLIC_ORIGIN` exactly; the API's configuration refuses an origin that fails `isDeviceAuthAudience`, and `deviceAuthInput` throws for any value outside its format. Signing and verification use `node:crypto` in the desktop main process and in the API.
- `pairingCode(codeChallenge)` gives the 6 digits that the desktop and the API's confirmation page both show for one sign-in. It is not secret.
- The loopback listener checks the `state`, never the `Origin` header, which browsers send as `null` for the API's form POST (#67).

## WebSocket authentication and close codes

These rules follow [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md), "Device key and authentication", and the gateway of `@mymandev/api` applies them (#89).

- After the upgrade the server sends `auth.challenge` with a fresh nonce, the connection ID, and `protocolVersion`. The device answers with exactly one `auth.response`, signed over `deviceAuthInput` with the purpose `ws`, within `WS_AUTH_TIMEOUT_MS` (10 seconds). The server answers `auth.ok` with the user ID, the device ID, and the sign-in expiry, `SIGN_IN_LIFETIME_MS` (30 days) after the device's last sign-in. Only then may the device send events.
- Before `auth.ok` the device sends nothing else: a binary frame, a frame over `MAX_AUTH_FRAME_BYTES` (1 KiB, measured on the raw frame before the JSON is parsed), a frame that is not JSON or that `decodeClientFrame` refuses, any frame other than `auth.response`, and a second frame close the connection with `protocol_violation`.
- A device decodes `auth.challenge` with `decodeServerMessage`. A challenge with another protocol version gives `unsupported_version` there, so the device knows that the versions differ before it answers.
- The close reason is the key of `WS_CLOSE_CODES`. A code is never reused, and new codes follow in order.

| Code | Reason                | When                                                                                                                   | What the desktop does                                                                                                                                                             |
| ---- | --------------------- | ---------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 4000 | `auth_failed`         | Unknown device, bad signature, or disabled account.                                                                    | Does not reconnect. Shows the error and offers a sign-in.                                                                                                                         |
| 4001 | `auth_timeout`        | No `auth.response` within 10 seconds.                                                                                  | Reconnects with backoff.                                                                                                                                                          |
| 4002 | `device_revoked`      | A valid signature from a revoked device.                                                                               | Does not reconnect. Stops local execution, deletes the key, and creates a new key pair before the next sign-in.                                                                   |
| 4003 | `sign_in_required`    | A valid signature, but the device signed out, its last sign-in is older than 30 days, or GitHub reported a revocation. | Does not reconnect. Shows an in-app prompt with a "Sign in with GitHub" button. It never opens the browser on its own.                                                            |
| 4004 | `connection_replaced` | A newer connection of the same device authenticated.                                                                   | Does not reconnect on its own. Warns that the device key is in use in another installation and offers two actions: remove this device and register again, or reconnect here once. |
| 4005 | `protocol_violation`  | Before authentication: a frame that breaks the rules above.                                                            | Does not reconnect on its own and shows an error. When the protocol versions differ, it asks the person to update.                                                                |

Decided by the Project Manager on 2026-10-31 (#89), as ADR 0014 leaves these details to the first change that needs them:

- A frame that breaks the rules before authentication closes with `protocol_violation` (4005), a new code after 4004.
- Above the cap of 200 unauthenticated connections, the API answers the handshake with `429`, `rate_limited`, and `Retry-After` before the upgrade, so no close code is needed for it.
- `devices.last_seen_at` is written when a connection authenticates; part B of #89 adds an update every 5 minutes for an open connection.

## Accounts and errors

- Inside a workspace, a user is always shown through their person row (`WorkspaceMember`): the person's display name and the GitHub login of its identity, in a monospace font with the time it was last verified, also for a removed person, who is shown as a former member. The account's own display name appears only on the account's own screens. A GitHub login is display data and never identifies an account.
- Every HTTP error answer has the body `{ statusCode, error, message, code }`. `code` is one of `API_ERROR_CODES`. A code that the API raises itself comes with its status from `API_ERROR_STATUS`. An error without its own code, such as a framework error, keeps its status and gets `genericApiErrorCode(status)`, so `bad_request` can come with another 4xx status (for example `413`) and `internal_error` with another 5xx status. `error` and `message` are the status text, never an input value: show the person the text for `code`.
- A route that names a workspace answers a non-member with `404` and `not_found`, exactly as for a workspace that does not exist. Only a join request answers an unknown workspace with `workspace_not_found`.
- An action that the caller's role does not allow answers `403` with `forbidden`; an action that conflicts with the current state, such as a second ownership offer, answers `409` with `conflict`; and an ownership offer or a promotion from a device younger than 72 hours answers `403` with `device_too_new`.

## Membership routes

These rules follow [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md) (People and roles, Invitations, Join requests, Limits, Removal and ownership, What a workspace ID allows). `MEMBERSHIP_ROUTES` fixes the paths, and `MEMBERSHIP_ROUTE_ERRORS` fixes every error code that each route can answer.

- Every route needs an access token. Only `GET` and `POST` are used, every path parameter is an ID filled in with `routePath`, and no route takes a query.
- Every path under `/workspaces/:workspaceId` checks active membership first, and a non-member gets `404` with `not_found`, as for a workspace that does not exist. The only action that a workspace ID allows a non-member, a join request, is therefore outside that path: `POST /join-requests` takes the workspace ID in its body, and the requester withdraws at `/join-requests/:joinRequestId/withdraw`. An invitation code names its own workspace, so preview and accept are under `/invitations`.
- An invitation code travels only in the bodies of `POST /invitations/preview` and `POST /invitations/accept`, and appears once, in the answer that creates it. These three answers carry `Cache-Control: no-store`. The list of live invitations never carries a code.
- A route with a response schema answers `200` with that body. Every other route answers `204` without a body, and the caller reads the new state from the workspace view, the lists, or the server's workspace events (M2-01).
- Every route can answer `bad_request`, `unauthorized`, `rate_limited`, and `internal_error`. Beyond those, `forbidden` means that the caller's role does not allow the action, and `conflict` that the target is not in the state the action needs: a removed person, an invitation or a request that is no longer live or pending, a person who is already claimed, or a second ownership offer. The limits that count live or pending items (50 live invitations or 50 pending join requests per workspace, 5 pending requests per person) and the 24-hour wait after a denial answer `429` with `rate_limited` and `Retry-After`, like every other limit.
- Unknown fields are stripped, as everywhere in this package ([ADR 0003](../../docs/architecture/decisions/0003-zod-runtime-validation.md)), so a client cannot set a role, an account, or a note by adding a field.
- Every list in an answer (workspaces, people, invitations, join requests, and the device list of #97) holds at most `MAX_ANSWER_LIST_ITEMS` (1,000) items, as ADR 0003 usage rule 3 asks (Project Manager decision of 2026-10-29). The maximum lies far above every count limit of ADR 0014, so raising one of those limits with use (P-64) never breaks an older client. The people of a workspace with its former members, and the devices with the revoked ones, can grow beyond it over time; the API then sends the most recent items, until pagination exists.

What the answers show:

- The workspace view holds every person of the workspace, unclaimed, active, and former, so that history stays attributed; when join requests were paused, or null; and the live ownership offer (the target's `memberId`, `offeredAt`, and `expiresAt`), or null. The schema checks that every person belongs to the workspace, that exactly one active owner exists, and that an offer names an active, claimed person who is not the owner.
- A live invitation shows the person it claims and its creator as `createdByMemberId`, which the desktop shows through the creator's person row. The creator is always an active member, because removing a person or demoting an admin revokes the invitations they created.
- A preview shows what ADR 0014 lists and nothing more: the workspace name, the display name of the person that the code claims, the inviter's display name in the workspace with their identity (the GitHub login and when it was last verified), and the expiry.
- The requester's own view of a join request holds only what they sent: its ID, the workspace ID, the requested display name, and when it was created and expires. It says nothing about the workspace.
- The approver's view of a join request adds the requester's identity: the GitHub login, when it was last verified, and the creation date of the GitHub account (`accountCreatedAt`). It lists the pending requests and the blocked requests whose block is in force, with `decision` and `decidedAt`. Its requester is null only after the account's data was erased, never on a pending request.

Decisions that ADR 0014 leaves open, settled here:

- A pause of join requests has no expiry: it ends only by hand, with `POST /workspaces/:workspaceId/join-requests/resume`. Pausing a paused workspace or resuming one that is not paused changes nothing. A pause keeps the pending requests; denying them all is a separate action.
- An ownership offer past its 7 days is no offer: the workspace view does not show it, accepting or withdrawing it answers `conflict`, and the owner can make a new one. How the stored offer is cleared stays with the API and the database (#86).
- Every person renames their own person; the owner and admins rename unclaimed people; nobody renames another claimed person. Nobody removes the owner, and the owner cannot leave: both answer `forbidden`. A person leaves with `leave`, not by removing their own person.
- The creator of a workspace and a requester send the display name of their person; the desktop fills it in with the account's display name. An approver may replace the requested name.
- `POST /invitations/preview` also answers `already_member` for an account that is already an active member of the workspace, so the join screen can say so before accepting.

Still open: how a requester learns the decision on a join request (no route lists an account's own requests), and whether an expired request that is not yet marked counts as pending; the lists carry `expiresAt`.

```sh
npm run typecheck -w @mymandev/protocol
npm test -w @mymandev/protocol
```
