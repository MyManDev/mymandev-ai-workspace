# @mymandev/desktop

The desktop application: an Electron shell with a React renderer. It shows the product UI skeleton with placeholder content, the status of the local runtime in the main process, the local Git repositories mounted on this device, the sign-in of this installation, and the account's workspaces and projects, which the renderer reads through a typed IPC contract. The decisions behind it are recorded in [ADR 0016](../../docs/architecture/decisions/0016-desktop-toolchain.md).

## Start locally

From the repository root, after `npm ci`:

```sh
npm run dev -w @mymandev/desktop
```

The first start downloads the Electron binary for your platform (about 130 MB on macOS) and checks it against the SHA-256 checksums that the Electron npm package ships. Later starts reuse it. electron-vite then builds the main process and the preload script, starts the Vite development server on `http://localhost:5173`, and opens the application window. A change in the renderer reloads in place. A change in the main process or the preload script takes effect after a restart; electron-vite's `--watch` option (`npm run dev -w @mymandev/desktop -- --watch`) rebuilds and restarts them on change instead. Stop it with Ctrl+C.

Some shells and tools set the environment variable `ELECTRON_RUN_AS_NODE`. With it, Electron runs as plain Node.js, and the start fails with "The requested module 'electron' does not provide an export named". Unset it before `npm run dev`, for example with `unset ELECTRON_RUN_AS_NODE` on Linux and macOS, or `Remove-Item Env:ELECTRON_RUN_AS_NODE` in PowerShell.

## Screens

The renderer shows the product UI skeleton (M0-04): the main screens, so that later work has a defined place for its content. The screens show placeholder content; the sidebar shows the account's [workspaces](#workspaces) and the selected workspace's projects, and the repository side panel shows the [mounted repositories](#repositories). Nothing runs an agent; the main process connects to the cloud API once a device is signed in ([Connection](#connection)).

The screens are a typed state, not routes ([ADR 0016](../../docs/architecture/decisions/0016-desktop-toolchain.md)): [`src/renderer/screens.ts`](src/renderer/screens.ts) lists them, and `shellReducer` switches between them. A workspace contains projects ([ADR 0005](../../docs/architecture/decisions/0005-workspaces-contain-projects.md)), so the shell shows either a workspace screen or a screen of the open project.

| Screen        | Belongs to    | Shows                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `home`        | the workspace | A hint to open a project, and the [account panel](#account): sign in with GitHub, also in another browser, the pairing code, the signed-in login with "This is not me", and the passphrase of a device key that needs one.                                                                                                                                                                                          |
| `about`       | the workspace | The product name and the Electron version.                                                                                                                                                                                                                                                                                                                                                                          |
| `chat`        | a project     | The message list with two placeholder messages, and the message composer, which is disabled.                                                                                                                                                                                                                                                                                                                        |
| `tasks`       | a project     | A placeholder.                                                                                                                                                                                                                                                                                                                                                                                                      |
| `decisions`   | a project     | A placeholder.                                                                                                                                                                                                                                                                                                                                                                                                      |
| `permissions` | a project     | The permission screen shell after [ADR 0015](../../docs/architecture/decisions/0015-capability-and-permission-contract-v0.md), with a placeholder section each for the agent, the repository files (`repo.read`, `repo.write`), Git (`git.commit`, `git.push`), the terminal (`terminal.execute`), the AI provider (`provider.use`), and the granted permissions. The presentation rules of ADR 0015 follow in #77. |

- The header shows the product name, the status of the connection to the cloud API, and the local runtime status on every screen.
- The sidebar, a `nav` landmark named "Workspace", lists the workspace screens, the account's workspaces, and the selected workspace's projects, from the [workspace state](#workspaces) of the main process (`window.desktop.workspaces`). `App` subscribes to the state while it is mounted, and every state dispatches `replace-projects`, also when the shown view stays the same, for example after a rename. A workspace is a button; the selected one is marked, and another one switches with `select`. On `too_soon`, a calm fixed text below the workspaces asks to wait a moment, and the selection stays. A switch clears the text first and then shows the text of its answer, if any; only the latest switch's answer counts, and a newer workspace state clears the text. Creating workspaces and projects stays with #95.
- Every switch goes through `switchWorkspace` ([`src/renderer/workspace-view.ts`](src/renderer/workspace-view.ts)). That is where the person will be asked before a switch while chat messages wait to be sent; it is not built yet. The main process's chat service detects the waiting messages: the chat IPC of a later part makes `workspaces.select` and `openProject` answer `{ outcome: "waiting", count }`, and an optional `{ discardWaiting: true }` argument repeats the switch (see [IPC contract](#ipc-contract)).
- The workspace logic is a plain controller, `createWorkspaceSidebar` in the same file, so that it is tested without a DOM: `start` subscribes and returns the function that ends the subscription, `openProjectChanged` reports the open project and drops the previous answer, and `select` switches. `App`'s `useWorkspaces` only calls it from its effects.
- Each state of the workspaces has its own fixed text: without the bridge or when the main process refuses the subscription "Workspaces are not available.", before the first state "Checking the workspaces.", `signed_out` "Workspaces appear once this device is signed in and ready." (true for every cause: no sign-in, a key that loads or waits for its passphrase, or a build without a server address), `loading` "Loading the workspaces." or, while the selected workspace loads (on the first load and after a switch), "Loading the projects.", `ready` without workspaces "No workspaces yet.", workspaces listed but none selected "Select a workspace to see its projects.", `ready` without projects "No projects yet.", and `unavailable` a fixed sentence for its problem, with the workspaces and projects that were loaded before and no "No projects yet.". The problem and the switch text share one `role="status"` paragraph below the workspaces, which is always rendered, empty when there is nothing to say, so that a screen reader announces a new text; the switch text is not shown while `signed_out`. No ID is shown. Workspace and project names are rendered as text, take their direction from their content (`dir="auto"`), and wrap when they are long.
- The shell reports its open project, or null, to the main process at the start and after every change (`openProject`), because the main process closes its open project when the page reloads. `openProject` refuses only with `not_found`, which closes the project in the shell too and shows the home screen; a failed call keeps it, and so does the answer to a report that a newer one replaced.
- A project screen adds the project navigation, a `nav` landmark named "Project" with chat, tasks, decisions, and permissions, and the side panel, an `aside` landmark with the project's agents (placeholder) or the mounted repositories. The side panel stays as it is when another project screen or another project is shown. A mount is not linked to a project yet, so every project shows the same mounted repositories.
- The shown screen is marked with `aria-current="page"`, and the selected workspace and the open project with `aria-current="true"`. Every navigation item is a button, so the keyboard reaches all of them, and a control focused with the keyboard shows a focus outline.
- The side panel is chosen with tabs (`role="tablist"`, `aria-selected`). Only the selected tab is in the tab order; the arrow keys, Home, and End select another tab and move the focus to it.
- The actions are `show-screen`, `open-project`, `show-panel`, and `replace-projects`. The reducer refuses a project screen or a side panel while no project is open, an unknown project, and an unknown screen, panel, or action, and then returns the same state object. A first view that is not valid, for example one whose project does not exist, shows the home screen. Two projects with the same ID are refused, by `createShellState` and by `replace-projects`, which also validates the shown view again, so a view whose project is gone shows the home screen. Projects that equal the shown ones return the same state object.

The styling is a placeholder. [`src/renderer/styles.css`](src/renderer/styles.css) reads colors, fonts, spacing, radii, borders, and the column widths from custom properties on `:root`; colors are written nowhere else. The theme follows the system setting (`prefers-color-scheme`), and a `data-theme` attribute of `light` or `dark` on the root element overrides it, so that the visual design can add a theme setting. The selected item has a background, a bold label, and a bar in the accent color, and in forced colors an underline. The visual design (#122) replaces these tokens and adds the base components. The Content Security Policy allows no inline styles, so styling stays in the stylesheet and never uses a `style` attribute.

## Local runtime

The local runtime ([`src/main/runtime.ts`](src/main/runtime.ts)) is a service in the main process. It starts when the application is ready and stops before the application quits: the first `will-quit` waits until the stop has settled, and the application then quits again ([`src/main/runtime-lifecycle.ts`](src/main/runtime-lifecycle.ts)). Its state is `stopped`, `starting`, `running`, `stopping`, or `failed`, and its `revision` grows by one with every change. A start or stop hook that rejects, throws, or takes longer than 5 seconds moves it to `failed`, so a quit waits at most about two hook timeouts: a start that is still running, then the stop. `stop` also runs the stop hook of a `failed` runtime, so that a start that failed or timed out can clean up, and the application stops a `failed` runtime before it quits as well. The runtime is a placeholder: its hooks do no work, open no network connection, and touch no file. Later milestones add their work there, for example agent execution (M3). The shell header shows the state, for example "Local runtime: Running".

## Local data

The application keeps its local data in a folder named `MyManDev` inside the system's per-user application data folder, Electron's `appData` path ([`src/main/data-folder.ts`](src/main/data-folder.ts)):

| System  | Folder                                                              |
| ------- | ------------------------------------------------------------------- |
| Windows | `%APPDATA%\MyManDev`                                                |
| macOS   | `~/Library/Application Support/MyManDev`                            |
| Linux   | `~/.config/MyManDev`, or `$XDG_CONFIG_HOME/MyManDev` when it is set |

The name is `DATA_FOLDER_NAME` in [`src/shared/product.ts`](src/shared/product.ts). The Project Manager fixed it on 2026-11-02, and it does not follow the product name, "MyManDev AI Workspace", or the application name. Without it, Electron would name the folder after the application name, which comes from `package.json` and is `@mymandev/desktop`, and renaming the folder after a release would need a data migration. Development runs before this change used that folder; it is no longer used and can be deleted.

The main process sets the folder as Electron's `userData` path as its first step, before anything reads it: it creates the folder when it is missing (on Linux and macOS for its owner only), sets the path, and then takes the single-instance lock, which Chromium keeps in that folder. The sessions keep their data (cookies, caches, and local storage) there too, because Electron's `sessionData` path follows `userData`. A development run and a built application use the same folder. On macOS and Linux, the [device key](#device-key) is stored in it as well. On Windows, where `%APPDATA%` roams, ADR 0014 places the device key in the local, non-roaming application data folder instead, so that a roaming profile does not copy it to another machine: `%LOCALAPPDATA%\MyManDev`, whose name is `LOCAL_DATA_FOLDER_NAME` in [`src/shared/product.ts`](src/shared/product.ts). It is fixed like the data folder's name, because renaming it after a release would lose the device key.

## Device key

The device key store ([`src/main/device-key/`](src/main/device-key/)) keeps the Ed25519 device key of [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md) in the main process (P-51, P-56). It is the first of four parts of #94. The [account](#account) loads it at startup and the [sign-in flow](#sign-in-flow) uses it; the [session](#session) (part 3) adds the access tokens, sign-out, removal at the API, and the device states, and is not wired in yet. The renderer gets nothing from it but its state.

- **Key.** `node:crypto` generates the key pair ([`signing-key.ts`](src/main/device-key/signing-key.ts)). The private key stays inside the store. A `DeviceKey` has two members: `publicKey`, the raw 32-byte key of RFC 8032 as 64 lowercase hexadecimal characters, the form the API stores, and `sign(input)`. `sign` signs only the UTF-8 bytes of the input that `deviceAuthInput` from `@mymandev/protocol` builds, and returns the 64-byte signature as 86 base64url characters. An input outside the protocol's format throws before anything is signed. A logged or serialized key shows its public key only. The private key is held as a `KeyObject` in memory, as the 10-second WebSocket handshake needs it without a prompt.
- **Folder.** On Windows, `%LOCALAPPDATA%\MyManDev` ([`key-folder.ts`](src/main/device-key/key-folder.ts)). A `LOCALAPPDATA` that is missing, empty, relative, or without a drive is an error (`local_data_folder_missing`), never a fallback to the roaming folder. On macOS and Linux, the [data folder](#local-data). A missing folder is created, on Linux and macOS for its owner only (0700).
- **Files.** `device-key.json` holds the newest key, which is tried first. `device-key.previous.json` holds the key that it replaced, until one authentication with the newest key succeeds. Every write goes to a new temporary file in the same folder (`<name>.<16 hexadecimal characters>.tmp`), created exclusively with mode 0600 on Linux and macOS, flushed, closed, and renamed over the file ([`atomic-file.ts`](src/main/device-key/atomic-file.ts)). The exclusive create fails when the name exists, also as a symbolic link, so a write never follows a link, and a file at that name that the write did not create is left alone. Every rename is flushed before the operation resolves: on Linux and macOS through the folder, and on Windows, which cannot flush a folder, by opening the renamed file again for writing and flushing it. These flushes are best effort. A failed write deletes its temporary file and leaves the old file as it was. A temporary file left by a stopped process is deleted at the next `load` or `delete`.
- **Protection.** Windows uses DPAPI, macOS the Keychain, and Linux kwallet or libsecret, through Electron's `safeStorage`, and only its asynchronous API: `isAsyncEncryptionAvailable`, `getSelectedStorageBackend`, `encryptStringAsync`, and `decryptStringAsync`. The synchronous API is deprecated and removed in Electron 46; a test checks that no file of the store names it.
  - On Windows and macOS only the system protects a key. When it cannot, for example after a denied or locked Keychain, `create` fails with `system_protection_unavailable`, and the screens tell the person. A passphrase or an unprotected key is refused there (`system_protection_required`). A key file protected by a passphrase or unprotected is `corrupt` there: the store never writes one, so someone else placed it, and no replacement may inherit its lower protection.
  - On Linux the system protects a key only when that is confirmed, and the check fails closed. `getSelectedStorageBackend` must report `gnome_libsecret`, `kwallet`, `kwallet5`, or `kwallet6`. `basic_text`, a fixed key that protects nothing, `unknown`, which it reports before the application is ready, or any other value does not count. That backend names the store of the synchronous API, and the asynchronous encryptor can still fall back to Chromium's fixed key when the secret service cannot be reached. So `systemProtection` also encrypts a probe, and every system-protected key file is checked before it is written: a ciphertext that does not start with the ASCII prefix `v11` (Chromium writes `v10` for its fixed key) counts as no confirmed secret service and is never written. Neither this prefix rule nor the backend behavior under the asynchronous API is verified on a real Linux desktop yet; part 4 of #94 checks them by hand (#67). A wrong guess only makes the person choose a passphrase, which is the safe direction. `load` does not check the prefix, so that a later Electron with another format does not strand stored keys.
  - Without confirmed system protection, a Linux key is encrypted with a passphrase that the person enters, or, after a warning and an explicit choice, stored unprotected with mode 0600. Both are refused while the system can protect the key (`system_protection_available`). `systemProtection` reports with `fallbackAllowed` whether this choice exists, which is true on Linux only. There is no memory-only mode.
- **Passphrase.** scrypt (N = 2^17, r = 8, p = 1; 128 MiB, in the thread pool) derives an AES-256-GCM key from the passphrase, normalized to NFC. A passphrase has 1 to 1024 characters and must be well-formed text: a lone UTF-16 surrogate would become U+FFFD in UTF-8, so different passphrases would derive the same key. Each file has a random 16-byte salt and a random 12-byte nonce. The header is authenticated as additional data. A wrong passphrase is refused as `wrong_passphrase`; AES-GCM cannot tell it from a changed file. While a key protected by a passphrase is held, the derived key stays in memory, so a replacement at a sign-in does not ask for the passphrase again; it adds no exposure, because the private key is in memory as well.
- **Startup.** `load` decrypts the stored keys once and holds them. The caller awaits it before any connection to the API opens, so that no prompt of the operating system runs inside the 10-second WebSocket handshake. `status` reports `passphraseRequired` when a key file that is not loaded yet, the current or the previous one, needs the passphrase. When `decryptStringAsync` reports `shouldReEncrypt`, the file is encrypted again and rewritten. On Linux it is not rewritten once the system no longer confirms a secret service, or when the new ciphertext does not start with `v11`, so that it is never downgraded to the fixed key. A rewrite that fails keeps the old file, which still decrypts, and does not stop the start.
- **Replacement.** ADR 0014: every GitHub sign-in replaces the key, and the previous key is kept until one authentication with the new key succeeds, with the new key tried first. `replace` generates a new key and stores it with the system's protection whenever the system can protect it, so a Linux key protected by a passphrase or unprotected moves up when a secret service appears. The previous key keeps its protection until `confirmReplacement` deletes it, so a start in between still asks for its passphrase. Only while the system cannot protect keys does the new key keep the protection of the current key: a passphrase key reuses the passphrase, and an unprotected key needs `acceptsUnprotectedKey: true` again, which the UI passes only after the warning again (`unprotected_not_accepted` otherwise). A system-protected key that the system can no longer protect is not replaced (`system_protection_unavailable`). `replace` first renames the current file to the previous file, then writes the new file, and resolves after both are on disk, so the sign-in sends the new public key only after it is stored. It returns both keys, so that an existing device can sign the same sign-in input with each. If the process stops between the two steps, `load` makes the previous key current again: the new key was never handed out. A failed write renames the previous file back. While a previous key is kept, `replace` is refused (`replacement_pending`). The caller first learns, by authenticating, which key the API holds. `confirmReplacement` then deletes the previous key (the new key authenticated). `abandonReplacement` renames the previous key back over the new one (the previous key authenticated, so the API never registered the new key). A key that the store drops signs nothing more (`key_retired`).
- **Delete.** `delete` removes the previous file, then the current file, and the temporary files, whether the key is loaded or not, for a removal that the API confirmed, `device_revoked`, or a lost key such as a forgotten passphrase.
- **Errors and logs.** The store never logs. Its errors are `DeviceKeyError`s whose message is fixed per code ([`errors.ts`](src/main/device-key/errors.ts)), so no passphrase, key, or file content reaches a message. A damaged file is `corrupt`, and so is a key file protected by a passphrase or unprotected on Windows or macOS. A file of a later format version is `newer_format`, so that an older version of the application does not call it damaged. Neither is deleted on its own.
- **Electron.** [`system.ts`](src/main/device-key/system.ts) connects the store to `safeStorage`, `process.env`, `process.platform`, and the `userData` path. It is created only after the application is ready, in the instance that holds the single-instance lock, so two instances never share one key.

The functions of the store (`createDeviceKeyStore` in [`store.ts`](src/main/device-key/store.ts)) run one after the other, in the order they were called:

| Function             | Does                                                                                                                                                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `systemProtection`   | `{ available: true }`, or `available: false` with `encryption_unavailable`, `no_secret_service`, or `secret_service_unconfirmed`, and `fallbackAllowed`, which is true on Linux only.                                                         |
| `hasKey`             | Whether a key file exists, readable or not.                                                                                                                                                                                                   |
| `status`             | `{ protection: "none" }`, or the protection (`system`, `passphrase`, `unprotected`) with `loaded`, `replacementPending`, and `passphraseRequired`, without decrypting.                                                                        |
| `load`               | Decrypts the stored keys once (with `{ passphrase }` for a passphrase key) and resolves with `{ current, previous }`, or null without a key.                                                                                                  |
| `keys`               | The keys held, or null.                                                                                                                                                                                                                       |
| `create`             | Generates and stores a key: `{ kind: "system" }`, or on Linux only `{ kind: "passphrase", passphrase }` or `{ kind: "unprotected", acceptsUnprotectedKey: true }`.                                                                            |
| `replace`            | Stores a new key, with the system's protection whenever it is available, and keeps the current one as the previous key; resolves with both. `{ acceptsUnprotectedKey: true }` renews an unprotected key while the system cannot protect keys. |
| `confirmReplacement` | Deletes the previous key.                                                                                                                                                                                                                     |
| `abandonReplacement` | Makes the previous key current again and deletes the new one.                                                                                                                                                                                 |
| `delete`             | Deletes every key file.                                                                                                                                                                                                                       |

The key file is one line of JSON. It holds the private key as PKCS#8 DER and nothing else: no public key, which is derived again, and no device ID. Binary values are base64url without padding.

| `protection`  | Fields after `format` (`"mymandev-device-key"`), `version` (`1`), and `protection`                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `system`      | `ciphertext`: the output of `encryptStringAsync` for the base64 of the PKCS#8 DER.                                                                                  |
| `passphrase`  | `kdf` (`"scrypt"`), `n`, `r`, `p`, `salt` (16 bytes), `cipher` (`"aes-256-gcm"`), `nonce` (12 bytes), `tag` (16 bytes), and `ciphertext`, the encrypted PKCS#8 DER. |
| `unprotected` | `pkcs8`: the PKCS#8 DER.                                                                                                                                            |

A file with an extra or a missing field, a value that is not canonical base64url or has the wrong length, or a scrypt cost outside N = 2^14 to 2^18 (a power of two), r = 8, p = 1 is refused as `corrupt`.

Not verified yet, because the tests use a fake `safeStorage`: the real DPAPI, Keychain, kwallet, and libsecret, `shouldReEncrypt` from a real system, which API reports the Linux fallback under the asynchronous API and whether the `v11` prefix rule holds there (#67), and whether flushing a renamed file on Windows makes the rename durable. The last part of #94 checks them by hand on Windows, macOS, and Linux.

## Repositories

The repository side panel mounts local Git repositories and shows them read-only (M1-05, #23): each with its folder name and path, its branch (or "Detached at" and the commit, or "no commits yet"), its upstream with the commits ahead and behind, a change summary (conflicted, staged, not staged, untracked; an untracked folder counts once), and its remotes. File changes refresh what it shows. Nothing writes to the repository or its files ([ADR 0016](../../docs/architecture/decisions/0016-desktop-toolchain.md), Decision, item 8).

- **Mount.** "Add a repository" asks the main process, which opens its own folder dialog (one existing folder; no files, no new folder) ([`src/main/repository-ipc.ts`](src/main/repository-ipc.ts), [`src/main/repository-system.ts`](src/main/repository-system.ts)). The renderer never sends a path, and only one dialog is open at a time. The main process checks the folder with `git rev-parse` ([`src/main/git-inspector.ts`](src/main/git-inspector.ts)) and refuses, with a message in the panel: a folder that is not in a Git repository; a folder inside a repository that is not its top-level folder, which is refused rather than widened to the top level, so a mount never covers more than the selected folder; a Git directory or a bare repository, which has no working tree; a repository that Git does not trust because it belongs to another user (`safe.directory`, which is never overridden); a repository that is already mounted (also through a link or, on Windows, in another case); more than 16 repositories; a path longer than 4,096 characters; and a missing Git or one older than 2.15. A linked worktree and a submodule mount like any working tree.
- **Identity.** A mount is identified by a mount ID, a random UUID that the main process creates. It lives in memory only: mounts are not stored and are gone after a restart. It is not a protocol `RepositoryId` and never leaves the device; linking a mount to a project's registered repository needs the cloud API and device storage. The path stays on the device as well ([ADR 0013](../../docs/architecture/decisions/0013-m1-data-model.md)).
- **Git.** The main process runs the system `git` with `execFile`, never a shell, without a console window, with a timeout (10 seconds, 30 for `git status`), an output limit (1 MiB, 16 MiB for `git status`), and `SIGKILL` when either is exceeded ([`src/main/git-process.ts`](src/main/git-process.ts)). Git is started by its absolute path, found in an absolute folder of `PATH`: on Windows, a program name alone is also looked up in the working folder, which would be the repository. Only `git.exe` is used there; a `git.cmd` would need a shell. The commands are `version` (once for each Git found), `rev-parse` (mount), `config -z --name-only --get-regexp "^filter\."`, `remote -v`, and `status --porcelain=v2 --branch -z --untracked-files=normal --ignore-submodules=all`.
- **Git version.** The inspection needs Git 2.15 or later, because `GIT_OPTIONAL_LOCKS`, which keeps `git status` from writing the index, exists since then. An older Git, or one whose `git version` cannot be read, is refused with a message ("The installed Git is too old") before any command runs in a repository. Every other protection works on Git 2.15 and later: `GIT_NO_LAZY_FETCH` exists only since Git 2.44, so `GIT_ALLOW_PROTOCOL` and the `protocol` settings stop a lazy fetch on older versions. The ownership check (`safe.directory`), which refuses a repository that belongs to another user, exists only since Git 2.35.2: an older Git mounts such a repository, with the same read-only protections.
- **Read-only.** The environment holds only `PATH`, with its absolute folders only, the home and configuration folders, and on Windows the system folders, never a `GIT_` variable from outside, plus `GIT_OPTIONAL_LOCKS=0` (`git status` does not refresh or write the index), `GIT_NO_LAZY_FETCH=1` and an empty `GIT_ALLOW_PROTOCOL` (a partial clone fetches no missing object: no transport is allowed, so neither `core.sshCommand` nor a remote helper runs), `GIT_TERMINAL_PROMPT=0`, no pager, and `LC_ALL=C`. No configured program runs, also when the repository's own configuration, or a file it includes with `include` or `includeIf`, names one: every command gets `-c core.fsmonitor=` (empty, which turns it off on every Git version), `-c core.useBuiltinFSMonitor=false` (Git for Windows 2.33 to 2.35), `-c protocol.allow=never`, and `-c protocol.<name>.allow=never` for `ssh`, `git`, `file`, `http`, `https`, and `ext`, which a repository's own `protocol.<name>.allow=always` cannot override, and `git status` gets `-c filter.<name>.clean=`, `smudge=`, `process=`, and `required=false` for every filter driver in the configuration, the driver with an empty name (`[filter ""]`, selected by the attribute `filter=`) included, so a filter such as Git LFS does not run either. A driver name that cannot be written as a `-c` option stops the status with a message. Submodules are not entered, because `git status` would run Git again with the submodule's own configuration, so their changes are not counted. No read-only command runs a hook, and the index is never written, so `core.hooksPath` is not changed.
- **What is shown.** The porcelain v2 output is parsed with NUL separators, so paths with spaces, non-ASCII characters, and line breaks are counted correctly ([`src/main/git-status.ts`](src/main/git-status.ts)). The user information, the query, and the fragment of a remote URL with a scheme, which can hold a token, are removed (`https://user:token@host/x?private_token=y` becomes `https://host/x`). When a `?` or `#` comes before the last `@` of the address, the host Git connects to and the end of a password are unclear (`https://host?u=a@evil.example` connects to `host`), so everything after the scheme is shown as "(address hidden)". Control, format, and line separator characters in names, paths, branches, and URLs are replaced with U+FFFD, and long values are shortened to the contract's limits.
- **Watching.** Each mount watches its working tree with `fs.watch`, recursively (on Linux too, with Node.js 20 or later), or its top-level folder alone where recursive watching is not available ([`src/main/repository-watcher.ts`](src/main/repository-watcher.ts)). Changes in the Git directory count for HEAD, the index, and refs, but not for the object store, the reflogs, or lock files. A Git directory outside the working tree, as in a linked worktree or a submodule, is watched without its subfolders. A burst of changes refreshes the status once, 300 ms after the last change and at the latest 2 seconds after the first, and never runs two `git status` at once for a repository ([`src/main/repositories.ts`](src/main/repositories.ts)). If watching fails, the panel says "Not watching for file changes", and the status is read once more. Unmounting a repository and quitting the application close its watchers and cancel its running Git commands. Watchers never keep the process alive.

Known limits:

- Changes in ignored folders, such as a build output or `node_modules`, also refresh the status. The debounce keeps that to one `git status` per burst and at most one every 2 seconds while the changes go on, but the status is read again although it cannot have changed.
- The filter drivers are read with one command and turned off in the next. A program that edits the repository's configuration between the two could add a driver that runs; that needs code already running on the device as the user.
- Git writes `(detached)` for a detached HEAD in the porcelain output, so a branch that is really named `(detached)` is shown as a detached HEAD.

## Sign-in listener

The values of a sign-in attempt and the loopback listener ([`src/main/sign-in/`](src/main/sign-in/)) implement steps 1 and 6 of "Sign-in" in [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md) in the main process (P-50, P-56). They are part 2a of #94; the [sign-in flow](#sign-in-flow) (part 2b) starts them. These rules are part of the authentication contract and are reviewed with the desktop owner when they start work (P-67).

- **Attempt.** `createSignInAttempt()` ([`attempt.ts`](src/main/sign-in/attempt.ts)) creates a PKCE verifier and a state of 32 random bytes each, from `node:crypto`, as 43 base64url characters; the S256 code challenge (`codeChallengeS256`: the SHA-256 hash of the verifier's ASCII bytes as base64url); and the pairing code, which `pairingCode` of `@mymandev/protocol` computes from the challenge, so the desktop and the API's confirmation page show the same six digits. Each value is checked with `Base64Url32BytesSchema`. The verifier is not enumerable, so logging the attempt or turning it into JSON leaves it out; it leaves the main process only in the body of `POST /auth/sign-in`.
- **Authorize URL.** `authorizeUrl({ apiOrigin, codeChallenge, redirectUri, state, signIn })` builds `<API origin>/auth/github/authorize` with `code_challenge`, `code_challenge_method=S256`, `redirect_uri`, and `state`. A first sign-in (`{ kind: "first" }`) adds `prompt=select_account`. A repeated sign-in (`{ kind: "repeated", login }`) adds `login` with the GitHub login of the device's account. After `device_account_mismatch` (`{ kind: "after_account_mismatch", login? }`) it adds `prompt=select_account`, and `login` when the person chose to sign in as the account that the installation holds. The origin must pass `isDeviceAuthAudience` and use `https`, or `http` only on `127.0.0.1` or `localhost`, the same rule as the API's `API_PUBLIC_ORIGIN`; which of them a build may use is decided by [`api-origin.ts`](src/main/api-origin.ts), which also holds this check. The query is checked with `GitHubAuthorizeQuerySchema`. Both checks run before the URL is built, so the API never gets a query that it would refuse; an error names the field, never its value. None of these values is secret.
- **Listener.** `startSignInListener({ state })` ([`listener.ts`](src/main/sign-in/listener.ts)) listens with `node:http` on `127.0.0.1`, passed explicitly, and port 0, so the system chooses a free port. It resolves with `{ redirectUri, port, wait, cancel, close }`; `redirectUri` is `http://127.0.0.1:<port>/callback`, checked with `LoopbackRedirectUriSchema`.
- **The valid request.** Only `POST /callback` is accepted, with exactly one `Host` header equal to `127.0.0.1:<port>`, exactly one `Content-Type` of `application/x-www-form-urlencoded` (a parameter such as `charset` is allowed), a body of at most 1,024 bytes, and exactly the fields `code` and `state`, or `error` and `state`, each once and in the format of `LoopbackCallbackBodySchema`, with the expected state. The size is checked from `Content-Length` before the body is read, and again while a chunked body arrives. The state is compared in constant time, with `timingSafeEqual` over SHA-256 hashes. The `Origin` header, which the browsers checked in #67 send as `null`, and the `Referer` header are never read.
- **Every other request** gets `404` with the body "Not Found", and the listener keeps listening: another method, path, or request target, a query string, a missing or repeated `Host` header or another value, another content type, a larger body, another state, another set of fields, a value outside the protocol's format, and a request after the listener ended. A request that Node.js cannot parse (`clientError`), whose headers are too large, or that keeps sending past the header or request timeout, and a request with an unknown `Expect` header (`checkExpectation`), get the same 404 instead of Node.js's own 400, 431, 408, or 417; when Node.js has no response object, the listener writes the 404 to the socket itself. Only when an answer has already started on the connection is the connection closed without another one.
- **Result.** `wait()` resolves once and never rejects: `{ kind: "code", code }` with the sign-in code; `{ kind: "error", error }` with the error that the API's page posts (`access_denied`, `sign_in_failed`, `unsupported_account`, or `sign_in_unavailable`; another error code in the protocol's format counts as `sign_in_failed`); `{ kind: "cancelled" }` after `cancel()` or `close()`; or `{ kind: "timed_out" }` after 10 minutes, the lifetime of the API's attempt. The `code` property is not enumerable, so `console.log` and `JSON.stringify` of the result leave it out.
- **Closing.** The listener stops listening after the valid request, after `cancel()`, or after 10 minutes, and closes every open connection. After the valid request it first lets its answer go out, for at most 1 second; then it closes every connection that is still open. `close()` cancels and resolves once the port is released.
- **Connections.** Each connection carries one request (`maxRequestsPerSocket` 1): Node.js drops a request pipelined behind it before it reaches the listener, and the first answer closes the connection (`Connection: close`), so the 503 that Node.js prepares for the dropped request is never sent. A connection ends after 10 seconds without activity (`socket.setTimeout`), without an answer, so a request that stalls in the middle of its headers or body usually ends this way. A request that keeps sending, but whose headers or body take longer than 10 seconds in total, gets the 404 and is closed when Node.js next checks the header and request timeouts, once a second (`connectionsCheckingInterval`), so within about 11 seconds. There is no cap on the number of connections (no `maxConnections`): a cap would let a local process that holds every slot, and reopens each one as soon as it closes, keep the browser's request out for the whole attempt. A process of the same user is outside the threat model, because it could stop the application anyway, and the timeouts bound how long each connection lives.
- **Answers.** The page after the valid request is fixed text that repeats nothing from the request and loads nothing: no script, style, image, or link. Every answer of the listener, the 404 included, closes its connection and sends `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Content-Security-Policy: default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`.
- **Logs.** The listener never logs. The optional `onError` receives a fixed message when the server reports an error after it started, never a request value.

The tests ([`attempt.test.ts`](src/main/sign-in/attempt.test.ts), [`listener.test.ts`](src/main/sign-in/listener.test.ts)) cover the formats of the verifier, the state, and the challenge (with the example of RFC 7636 appendix B), the pairing code, and the authorize URL against `GitHubAuthorizeQuerySchema` for each kind of sign-in, with refused origins, redirect URIs, states, challenges, and logins. For the listener, they send raw HTTP requests and show that it binds to `127.0.0.1` only (the arguments of `listen`, the bound address, and a refused connection on `::1`); that it answers 404 to a wrong method, path, request target, `Host` header, content type, state (also a well-formed one that differs, which only the comparison refuses), set of fields, or format, and still accepts the valid request afterwards; the same 404 with the security headers for a request that Node.js cannot parse and for an unknown `Expect` header; the size limit with and without `Content-Length`; that it closes, with every open connection, after the valid request, a cancel, or the 10-minute timer (an injected timer), and that the port is then released (a new connection is refused); that a request pipelined behind another one is dropped unread, that a request pipelined behind the valid one and a connection in the middle of a request do not hold back `close`; the idle timeout of every connection, the end of a silent connection, of unfinished headers, of an unfinished body, and of a body that trickles in (with a short injected timeout); that the valid request gets through while 20 other connections are held open in the middle of their headers, and that there is no connection cap; the headers and content of every answer; and that nothing secret reaches the console, `onError`, or a logged result.

## Sign-in flow

The sign-in flow ([`src/main/sign-in/flow.ts`](src/main/sign-in/flow.ts)) joins the [device key](#device-key), the device record, the attempt, and the [listener](#sign-in-listener) into steps 1, 6, and 7 of "Sign-in" in [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md), in the main process. It is part 2b of #94. The [account](#account) (part 2c) creates it and starts it on the person's action. These rules are part of the authentication contract and are reviewed with the desktop owner when they start work (P-67).

- **API origin.** [`api-origin.ts`](src/main/api-origin.ts) decides the API origin, the audience of every signature (ADR 0014, "Configuration"). `resolveApiOrigin({ isPackaged, env })` takes `app.isPackaged`: a packaged build uses `PRODUCTION_API_ORIGIN` and never reads the environment, and a development build (`npm run dev`) reads `MYMANDEV_API_ORIGIN`. Hosting (#96) has not chosen the production origin, so `PRODUCTION_API_ORIGIN` is null, and a packaged build answers a sign-in with `api_origin_unset`. `isApiOrigin` accepts an origin that passes `isDeviceAuthAudience` and uses `https`, or `http` only on `127.0.0.1` or `localhost`, the same rule as the API's `API_PUBLIC_ORIGIN`; [`attempt.ts`](src/main/sign-in/attempt.ts) uses the same check. A packaged build also requires `https`, because the loopback `http` origins are for development and tests only. Another value is `api_origin_invalid`, and the result never repeats it.
- **Device record.** [`device-record.ts`](src/main/device-record.ts) keeps the device ID, the user ID, the GitHub login, the display name, `signInExpiresAt`, and the device's public key of the last successful sign-in in `device-record.json`, next to the key files in the key's folder (on Windows `%LOCALAPPDATA%\MyManDev`, never the roaming folder), because the device ID belongs to that key. The file is versioned JSON (`version: 1`) without a secret, written with the key store's atomic write. `read()` resolves with `none`, `record`, or `corrupt`: unreadable JSON or UTF-8, another version, an unknown or missing field, a value outside the protocol's format, or a file larger than 4 KiB is corrupt and never trusted.
- **New or existing device.** `createSignInFlow(dependencies).start(options?)` decides from the record and the key store. A record and a loaded key make an existing device. A record without a key file is a lost key: a new device that names the record's device as `previousDeviceId`, which the API revokes as `replaced`. A record whose public key is not the loaded key's, with no replacement pending, is a lost key too: a confirmed key always sits next to a record that names it, so that key belongs to a new device whose registration got no clear answer. While the registration marker (below) names it, it is sent again as a new device that names the record's device (#153); otherwise it is deleted and a new device names the record's device again, with a new key. Without any record, a key file that the registration marker names is sent again in the same way; any other leftover key file is deleted first and a new device is registered. A corrupt record next to a key file answers `record_unreadable` and keeps the key, because the key may still be the key of a device that the API knows (for example after a downgrade that cannot read a newer record); an explicit reset is a later option. The [session](#session) (part 3), which confirms a pending replacement by authenticating, writes the record again with the new public key before it confirms, so the next sign-in does not treat the new key as a lost key. A corrupt record without a key file is not used, and a new device is registered. A record with a key that is not loaded yet answers `key_not_loaded`, and a key replacement that is still pending answers `replacement_pending` while the record names the previous key: an authentication must first learn which key the API holds (the [session](#session)), and neither key is deleted. When the record already names the new key, the application stopped between the record write and the confirmation after a `200`, so the replacement is confirmed and the device signs in as itself.
- **Registration marker.** `device-registration.json` ([`registration-marker.ts`](src/main/sign-in/registration-marker.ts)) holds the public key of a new device whose registration got no clear answer and the time of its first attempt, `{ version: 1, publicKey, at }`, next to the record and the key files and written the same way; it holds no secret, and a file outside the format is corrupt, reported, and dropped (#153). The flow writes it right after it created a new device's key and before it sends the request, so that a stop of the application during the request keeps the key too. The API answers a new device whose key already belongs to an active device of the same account with that device, so the next attempt sends the same key again, with a new code and as a new device, instead of deleting it: a lost answer then leaves one device on the account, and the account's other devices are not told of it twice. The key is sent again only while it is the loaded key, no record names it, no replacement is pending, and the marker's first attempt is less than 7 days ago (`REGISTRATION_RESEND_MS`); a resend keeps that time. The API accepts a repeat for the same 7 days, and only of a device that never authenticated, so a repeat after a lost answer always meets it. A marker file that exists but cannot be read stops an attempt that would delete a key (`record_unreadable`), because the key may be one that the API holds; an attempt that deletes no key goes on. Seven days cover an outage of the API or a person away for a week; after that, a key that never had a clear answer is not kept, and the flow falls back to deleting it and registering a new key. A time in the future means that the clock went back, and a key that is not loaded cannot sign, so neither is sent again. The key is never used with a device ID: it is sent as a new device, the record's device is named only as `previousDeviceId`, and a `200` that names that device is `unexpected_response` and writes nothing. A `200` writes the record as usual and then drops the marker; a `record_not_saved` keeps it, so that after a restart the key is sent again and the API answers with the same device. A certain refusal deletes the key and the marker, and every uncertain outcome and a cancel keep both. A marker that this attempt does not send again (expired, about another key, or about the key that a record names) is dropped when the attempt starts. The marker is not one of the [session notes](#session): the session reads those once, writes them alone, and drops them when no record names the key, which is when the marker matters, and the flow cannot use the session. The flow and the session both open stores over the key's folder, so both can read it.
- **Start.** The flow creates the attempt, starts the listener, and builds the authorize URL: `login` from the record on a repeated sign-in, `prompt=select_account` on a first sign-in, and both after `device_account_mismatch`. Before the listener starts, it checks that the key of this attempt can be stored: a new device's key with the system's protection (the default), or the replacement of a key that the system protects, needs the key store's `systemProtection`, or the sign-in does not start (`system_protection_unavailable`), so that the person does not finish the browser's part only for the key to fail. On Windows and macOS the system's key storage must work, for example an unlocked Keychain; on Linux a secret service must be confirmed, until the screens offer the passphrase choice. A key that a passphrase protects, or an unprotected one, follows the store's own rules. It opens the URL with `openExternal` and resolves with the pairing code, `cancel`, and `outcome`. When the browser does not open, or opening it takes longer than 10 seconds (`OPEN_EXTERNAL_TIMEOUT_MS`), it also returns the URL with `SIGN_IN_URL_WARNING`, a fixed text that says the address must not be shared (#149). With the option `openBrowser: false`, for a person who completes the sign-in in another browser (#175), the flow starts the attempt in the same way but does not call `openExternal`, and returns the URL with the same warning at once; the attempt is still bound to the browser that opens the URL first. One attempt runs at a time (`already_running`). `start` never rejects; a sign-in that cannot start resolves with `started: false` and a `failed` outcome. The option `onCallback` is called once, right after the listener accepted the valid request (a code or a posted error), before the key changes and before `POST /auth/sign-in`, so that the window can come to the front then (step 6); it is not called after a cancel or the timeout, and an error that it throws is ignored. `reset()` forgets what the flow keeps between attempts, the unsaved record and the account mismatch, when the installation forgets its account ("This is not me"); while an attempt runs it changes nothing and returns false.
- **Request.** Only when the listener delivers a code does the key change. A new device calls `keyStore.create` (the system's protection by default), or takes the loaded key that the registration marker names, and signs the `sign-in` input with that key (`newKeySignature`). If the key to send again is no longer the key held, the outcome is `key_changed` and nothing is sent or deleted. An existing device calls `keyStore.replace()` and signs the same input with the previous key (`currentKeySignature`) and the new key (`newKeySignature`). If the previous key is then not the key that the record names, the key store changed during the attempt: the replacement is abandoned, nothing is signed or sent, and the outcome is `key_changed`. The audience is the API origin, and the device ID is null for a new device. The label is `suggestedDeviceLabel` of the platform ("Windows computer", "Mac", or "Linux computer"), never the host name, unless the caller passes one. The flow posts the code, the verifier, the redirect URI, and the registration with the injected `fetch` to `<origin>/auth/sign-in` as JSON, with `redirect: "error"`, and stops waiting after 30 seconds. It reads at most 64 KiB of the answer (`MAX_ANSWER_BYTES`): a larger `Content-Length` is refused before reading, and the stream is cancelled once it passes the limit.
- **Answers.** A `200` whose body passes `SignInResponseSchema` (for an existing device, with the same device ID) writes the record with the new public key, a second time if the first write fails, and only then confirms the replacement, because the answer proves that the API holds the new key; so a confirmed key never sits next to a record that names the previous key. If both writes fail, it answers `record_not_saved`, an existing device keeps the replacement pending with both keys, and the record is kept in memory; the next attempt writes it before anything else, so the registered key is never taken for a leftover (a restart loses it). A `4xx` whose body passes `ApiErrorBodySchema` with the same status is a refusal of the API, but not every refusal proves that the API did not commit. When the connection fails after the commit, `net.fetch` or a proxy can send the same request again, and only the answer to that copy arrives. The API answers such a copy with `409` and `sign_in_code_used` while it keeps its record of the code, for a minute after the first copy ended (#152). That record lives in API memory only: a copy that reaches a restarted API gets `auth_failed`, because the API takes the sign-in code before every other check, and the route's limit can refuse a copy with `rate_limited` first. No other refusal can answer a copy of a request that committed. The API's request timeout answers `408` only after 30 seconds, when the flow has already stopped waiting, so `SIGN_IN_REQUEST_TIMEOUT_MS` must not exceed it. These three codes (`UNCERTAIN_REFUSAL_CODES`) answer `uncertain_refusal` with the code as `apiError` and are handled like no answer, for a new device too. An `auth_failed` or `rate_limited` that refused the request itself, or a `sign_in_code_used` after an earlier copy that a later check refused, is handled the same way, so an existing device then answers `replacement_pending` until the [session](#session) learns which key the API holds. `auth_failed` stays in the list for the restarted API; whether it can leave is a separate decision. Every other refusal means that the API did not commit: the replacement is abandoned, or a new device's key is deleted, and the outcome is `refused`. After `device_revoked` the key and the record are deleted. After `device_account_mismatch` the outcome carries the login of the account that the installation holds, and the next attempt adds `prompt=select_account`. A `5xx` (`server_error`) may come after the API committed, for example after its transaction or when the commit acknowledgement was lost, so it is handled like no answer. When no answer arrives (a network error, the timeout, or a cancel during the request), on a `5xx`, on an uncertain refusal, or when the answer is not the API's, nothing is undone: an existing device keeps the replacement pending, and the [session](#session) resolves it by trying the new key first. A new device keeps its new key and its registration marker, and the record of a lost key stays as it was; the next attempt within 7 days sends the same key again and gets the device that the API registered, or registers it now (see above). Without the marker, after 7 days, or when the key is not loaded, the next attempt deletes that key and registers a new device with a new key. If the uncertain request did commit, the API offers no way to learn the ID of the device that it registered, and no installation holds that device's key then. The device is never revoked on its own: after its sign-in expiry (30 days) it only requires a new sign-in, which nothing can sign. Until the person removes it from another device, it is listed among the account's devices and counts toward the account's 20 active devices; it also counted toward the 10 new devices per 24 hours, and the account's other devices were told of it as a new device.
- **Outcome.** `signed_in` with the account, `newDevice`, and the `login` to show with the "this is not me" path (#149); `cancelled`; `timed_out`; `listener_error` with `access_denied`, `sign_in_failed`, `unsupported_account`, or `sign_in_unavailable`; `refused` with the API's error code, never one of `UNCERTAIN_REFUSAL_CODES`; or `failed` with a fixed reason from `SIGN_IN_FAILURE_REASONS`, with `key_store_failed` the code of the store's `DeviceKeyError` as `keyError` when it raised one (for example `system_protection_unavailable`, when the protection went away while the browser was open), and with `uncertain_refusal` the API's code as `apiError`. An error that the flow did not expect is `unexpected`, never `key_store_failed`.
- **Secrets.** The flow never logs or returns the code, the verifier, a signature, or a key. The optional `onError` receives fixed messages only.
- **Electron.** [`sign-in/system.ts`](src/main/sign-in/system.ts) passes `net.fetch`, which follows the system proxy settings, `shell.openExternal`, `app.isPackaged`, `process.env`, and the platform, with the key store, the device record store, and the registration marker store of the caller, so that the flow and the [account](#account) use one record store over the key's folder. It stays thin and is only type-checked.

The tests ([`flow.test.ts`](src/main/sign-in/flow.test.ts), [`registration-marker.test.ts`](src/main/sign-in/registration-marker.test.ts), [`device-record.test.ts`](src/main/device-record.test.ts), [`api-origin.test.ts`](src/main/api-origin.test.ts)) use a temporary folder, the real key store with a fake `safeStorage`, the real record store, a fake `fetch`, a fake `openExternal`, injected timers, and the real listener, to which they deliver the code with an HTTP `POST` with the right `Host` header and a form body. They cover a new device (the request, its signature, and the record), an existing device (both signatures verify over the same input, and the key is confirmed on `200`), a lost key (`previousDeviceId`), a leftover key without a record, a corrupt record, a key that is not loaded and a pending replacement, a key store that changed during the attempt (`key_changed`, nothing sent), each class of answer (abandon on a `4xx` with `sign_in_required`, `conflict`, or `bad_request`; pending on `auth_failed`, `rate_limited`, and `sign_in_code_used`, also when a fake API with single-use codes committed the request and the `fetch` delivered it twice, so that only the copy's `409` with `sign_in_code_used` arrived, or, after a restart of the API between the copies, its `auth_failed`, where both keys stay on disk; pending on a `5xx` with an error body, a network error, the request timeout, a cancel during the request, and an answer that is not the API's; a new device's key and the old record kept on a `5xx`, `auth_failed`, `rate_limited`, and `sign_in_code_used`, a first sign-in's key kept on `sign_in_code_used`, and the same key sent again next time; delete on `device_revoked`; and `prompt` after `device_account_mismatch`), the 64 KiB answer limit with and without `Content-Length`, the second record write and the unsaved record written by the next attempt, a corrupt record next to a key (also of another version) and without one, `openExternal` that fails, rejects, or does not finish in time, `openBrowser: false` (no browser and no timer, the URL with the warning, a sign-in completed through that URL, and one attempt at a time), the early refusal when the system cannot protect a new key or the key to replace (also on Linux without a secret service, but not after the choice of a passphrase), a key whose protection went away while the browser was open (`key_store_failed` with `keyError`), `onCallback` (before the request, for a posted error, never after a cancel or the timeout, and one that throws), `reset` (no `prompt` and no unsaved record afterwards, and nothing while an attempt runs), an error that the flow did not expect (`unexpected`), cancel, the listener's timeout and a posted error, the origin rules (a packaged build refuses the loopback `http` origins), the registration marker (written before the request with the key and the time; the same key sent again with and without `previousDeviceId`, keeping the first time; deleted with the key on a certain refusal; sent again until 7 days and not after, nor with a time in the future; dropped when it names another key or the record's key, or is corrupt; a restarted store sends a loaded key again and deletes one that is not loaded; a `record_not_saved` followed by a restart gets the same device; kept on a cancel before and after the code; `key_changed` when the key changed during the attempt; no record with the replaced device's ID; the old behavior when the marker cannot be written, and `record_unreadable` with the key kept when it cannot be read), the record's and the marker's round trip and every kind of corrupt file, and that no code, verifier, signature, or private key reaches an outcome or a message, and no private key the record file.

## Account

The account service ([`src/main/account.ts`](src/main/account.ts)) starts the [sign-in flow](#sign-in-flow) from the application (part 2c of #94) and wires in the [device session](#session) (part 3): the device state, sign-out, removing this device, and the device list. It runs in the main process; the renderer shows its status in the account panel of the home screen ([`src/renderer/AccountPanel.tsx`](src/renderer/AccountPanel.tsx)), a placeholder until the screens of #95.

- **Startup.** [`index.ts`](src/main/index.ts) creates the service in the instance that holds the single-instance lock and registers its handlers before the first window loads. When the application is ready, `initialize` opens the [device key store](#device-key) and one device record store over the key's folder, which the flow shares ([`src/main/account-system.ts`](src/main/account-system.ts)), loads the key once, creates the [device session](#session) over the same key store and record store ([`session/system.ts`](src/main/session/system.ts)), and then reads the record. Until then the key state is `loading`. The session is created once the load has settled, also for a key that waits for its passphrase (the session then reports `key_not_loaded`); a session that cannot be created makes the device state `unavailable`, and its actions are refused as `not_signed_in`. A key store that cannot be opened makes the device state `unavailable` too. After the first status, `initialize` calls the session's `refresh`, which retries a pending removal, and then `reportSignOut` when a sign-out has not reached the API yet. An unlock refreshes the session too, without waiting for it. Such a background refresh uses the key and may write the record when the API answers, so every action of the person (sign-in, sign-out, removal, the device list, and "This is not me") takes the service's lock first and then waits for it, and checks the account again afterwards. The action is delayed rather than refused, because the refresh is not the person's doing and the first click after a start would otherwise fail for as long as an offline request takes; other actions answer `busy` meanwhile. The whole startup counts as background work, from the key's load until the startup refresh has ended, so an action in the gap between the loaded key and the refresh waits too. A sign-in that was cancelled while it waited ends as `cancelled` without starting the flow or opening the browser. A key that a passphrase protects (Linux) waits as `passphrase_required`; a key that cannot be used reports `unreadable`, `corrupt`, `newer_format`, `local_data_folder_missing`, or `failed`, and blocks the sign-in.
- **Signed in.** The installation is signed in when the device record exists. The status then holds the record's GitHub login, display name, and device ID, and nothing else. A corrupt record, or one that cannot be read, counts as signed out; a sign-in then follows the flow's own rules.
- **Sign-in.** Only the renderer's "Sign in with GitHub" and "Use another browser" start a sign-in, and the main process limits how often a start can open the browser: a start within 3 seconds (`SIGN_IN_START_COOLDOWN_MS`) of the last one that opened it, or offered its URL, is refused as `too_soon`, so that even a renderer that misbehaves cannot open the browser in a loop. A start that did not get as far as the browser does not count. One runs at a time (`busy`), and only with a key that is ready (`key_not_ready`). The status moves from `starting` to `waiting` with the pairing code, and with the authorize URL and `SIGN_IN_URL_WARNING` when the browser did not open (#149). The panel shows the URL in a read-only field with a button that selects it: the session denies every web permission, the clipboard included, so the person copies it themselves. Cancel ends the attempt, also while it is starting. A sign-in whose key the system cannot protect does not start, before the browser opens (`system_protection_unavailable`). The flow is created once, before the first sign-in, and kept: what it keeps in memory (an unsaved record, the prompt after an account mismatch) carries over to the next attempt until "This is not me" resets it.
- **Another browser.** The application cannot choose a browser, and the API binds an attempt to the browser that opened its address (the attempt's cookie), so a person whose default browser holds another GitHub account asks for the address instead (#175). `startSignIn({ browser: "other" })` starts the flow with `openBrowser: false`: the default browser does not open, and the status is `waiting` with the authorize URL and `SIGN_IN_URL_WARNING`, as when the browser did not open, and with `browser: "other"` where a browser that did not open has `browser: "default"`. The main process decides this; the renderer only asks. The cooldown, `busy`, and the key checks apply unchanged, and a start that offered its URL counts for the cooldown. The panel offers "Use another browser" next to "Sign in with GitHub", with the same conditions, and while a sign-in waits in the browser that opened; not while it starts, while it completes, or when its URL is already shown. While a sign-in waits, the panel first cancels it, because its address is bound to the opened browser, waits for its outcome, and starts the new one only when that outcome is `cancelled`. For a waiting sign-in it enables the button only 3 seconds (`ANOTHER_BROWSER_DELAY_MS`) after it saw the sign-in wait, no sooner than the cooldown allows a new start, so that the cancel does not end the waiting sign-in only for the new start to be refused as `too_soon`. While the sign-in that the person asked for starts, the panel says that it prepares the address instead of opening the browser. Above an address with `browser: "other"`, it asks the person to copy the address into the browser that they want to sign in with, also when the panel is shown again; above one with `browser: "default"`, it says that the browser did not open.
- **Session around the sign-in.** The service calls the session's `signInStarted` before every `start` of the flow and `signInFinished` with every outcome, also of a start that did not get as far as the browser and of a flow that could not be created (`failed` with `unexpected`), so that the session never resolves a pending replacement while a sign-in may still register the new key, and starts the grace period of an uncertain sign-in. When `start` answers `replacement_pending`, the service calls `authenticate`, which resolves the replacement as far as the API's answers allow (the new key confirmed, the replacement abandoned after the grace period, or both keys deleted as lost), and reads the key store. Only when the store no longer holds a replacement, and the person did not cancel meanwhile, does the flow start once more, still within the same action; its answer is shown as it is, even a second `replacement_pending`, so the service never loops. An authentication without a clear answer, during the grace period, or after a first refusal of both keys leaves the replacement, and the outcome stays `replacement_pending`.
- **Outcome.** The outcome becomes a fixed code (`SIGN_IN_OUTCOME_CODES`) with a fixed message in the renderer ([`src/renderer/account-view.ts`](src/renderer/account-view.ts)). The flow's kinds and reasons map one to one, `uncertain_refusal` and `key_changed` included; `uncertain_refusal` says that the server's answer does not show whether the sign-in was completed and that it is safe to start again, and the API's code (`apiError`) is not passed on. `key_store_failed` with the store's `system_protection_unavailable` becomes `system_protection_unavailable`, like the flow's early refusal; an API error code without its own entry becomes `refused` (the flow reports the codes of `UNCERTAIN_REFUSAL_CODES`, `auth_failed`, `rate_limited`, and `sign_in_code_used`, as `uncertain_refusal`), a page error without one `sign_in_failed`, and `unexpected` or any other reason or kind `failed`. `label_invalid` and `already_running` cannot happen here and are `failed` too. After `device_account_mismatch` the code carries the login of the account that the installation holds. After every outcome the record is read again, so that, for example, a device that the flow deleted after `device_revoked` shows as signed out.
- **Window.** As soon as the browser posted to the listener (a code or a page error), the flow's `onCallback` brings the main window to the front, on macOS by making the application active (ADR 0014, "Sign-in", step 6), before `POST /auth/sign-in` is sent. The status moves to `completing` until the answer; the panel offers no cancel then, because a cancel during the request leaves the API's answer unknown. A callback that arrives before `start` has returned still shows `completing`, and a late callback of an earlier attempt changes nothing. A cancel or the 10-minute timeout leaves the window where it is.
- **Device state.** The status's `device` follows the session's state as a fixed code (`DEVICE_STATES`, [`src/main/account-session.ts`](src/main/account-session.ts)): `starting`, `no_device`, `signed_in`, `signed_out` or `sign_out_report_pending`, `sign_in_required`, `auth_failed`, `account_mismatch`, `key_lost`, `key_not_loaded`, `unavailable`, `removal_pending`, `removed`, or `revoked`. The session's account (user ID, sign-in expiry) is not passed on. After a change the record and the key's replacement are read again; `removed` and `revoked` sign the account out at once instead, because the session publishes them before it deletes the key and the record, and they also reset the flow, so that an unsaved record of the gone device does not come back. The panel shows a fixed message per state and offers "Sign in with GitHub" without an account and in every state that needs a sign-in (signed out, `sign_in_required`, `auth_failed`, `account_mismatch`, `key_lost`, `removed`, `revoked`).
- **Revoked.** When the device state moves to `revoked`, the service calls `stopLocalExecution` before it publishes, which is right after the session published `revoked` and before it deletes the key (ADR 0014: a revoked device "stops local execution"). [`index.ts`](src/main/index.ts) passes an explicit no-op: the local runtime is a placeholder that executes nothing yet, and stopping it would only leave it stopped with no way back after the next sign-in; the local runtime tasks (terminal, process, and agent execution) stop their work there.
- **Sign-out (P-65).** `account:sign-out` calls the session's `signOut`: the device, its key, and its record stay, and the key is not used until the next GitHub sign-in, which is then a repeated sign-in of the same device. The result is `signed_out` when the API confirmed it and `pending` when it learns it later (the device state is `sign_out_report_pending` until then, and the next start reports it). The panel offers sign-out only while the device is `signed_in`, and the service refuses it as `removal_pending` while a removal waits for the API, because the session would end the removal that the person confirmed.
- **Remove this device.** `account:remove-device` first asks in a native dialog (`REMOVE_DEVICE_CONFIRMATION`: the login, "Remove this device", and "Keep" as the default and the cancel button), then calls the session's `removeDevice`, which notes the removal and revokes the device with the reason `removed`. The key and the record are deleted only after the API confirmed it (`removed`, and the flow is reset); without a clear answer the result is `pending`, the device state is `removal_pending` also after a restart, and the next start or another removal retries it. A signed-out device is refused as `signed_out`, and a key that waits for its passphrase as `key_not_loaded`, before the confirmation, because neither removal can happen.
- **Device list.** `account:list-devices` calls the session's `listDevices` (`GET /devices`) and passes on each device's ID, label, platform, last seen time, sign-in expiry, revocation time, and the API's `current` flag, which marks this installation's device; nothing secret, and no field that the protocol adds later. The panel lists them after "Show devices". The list takes the service's lock like the other actions, a list within 2 seconds of the last one is refused as `too_soon` (`LIST_DEVICES_COOLDOWN_MS`), and a list whose account changed while it was on its way (for example after the session found the device revoked) is dropped as `not_signed_in`.
- **Action results.** Sign-out, removal, and the list are refused as `busy` while a sign-in is open, the key is loading, or another action runs, as `not_signed_in` without an account or a session, and the list as `too_soon` within its cooldown. A failure of the session becomes a fixed code (`DEVICE_ACTION_FAILURES`): its reasons one to one, the API codes `sign_in_required`, `auth_failed`, `device_revoked`, `device_account_mismatch`, and `rate_limited`, `refused` for another API code, and `failed` for anything else.
- **This is not me.** After a sign-in, the panel names the GitHub login that the device is signed in to and offers "This is not me" (#149). The button only asks the main process, which confirms in a native dialog (`dialog.showMessageBox`, with the login, "Remove from this installation", and "Keep" as the default and the cancel button), like the folder dialog of the repositories; `cancelled` deletes nothing. It is the only confirmation: a renderer that misbehaves cannot answer it, and a second one in the page would only repeat it. The native dialog says that the device is removed from that account first only when it is signed in with a usable key and the server can be reached, and otherwise stays listed there. The main process then removes the device at the API through the session's `removeDevice` where it can, and forgets the account locally whatever the API answered: it deletes the device record and the registration marker, resets the flow (`reset`), deletes the key, and refreshes the session. The API removal comes first because it needs the key, which signs the access token request, and the record, which names the device; after the local delete nothing could sign for the device. Its failure (offline, signed out, a key that waits for its passphrase, a refusal, an error) never stops the local part, so the account never stays on the installation because the API could not be reached, and the removal itself deletes files only after the API confirmed it, so it cannot bring the account back either. The result `forgotten` says with `removedAtServer` whether the API confirmed the removal; when it did not, the panel says that the device stays registered to that account, without a usable key, until its 30-day sign-in ends or the account removes it from another device. A removal that the session noted as pending ends with the local delete. The record goes first, because a record without a key would make the next sign-in name this device as its previous device. A key without a record is deleted by the next sign-in unless the [registration marker](#sign-in-flow) names it, so the marker goes right after the record: otherwise a key whose delete fails would be sent again for the forgotten account (#153). A marker that cannot be deleted is reported and does not stop the rest; once the key is gone, it names no key. The reset comes right after the record, before the key: if the key delete then fails, the flow no longer holds a record that its next attempt would write back (after a `200` whose record could not be saved), so the account cannot return. It works in every key state but `loading`, also for a key whose passphrase is not known (then local only).
- **Passphrase.** The passphrase is the only secret that crosses IPC, from the renderer to the main process, in `account:unlock-key`. It goes to the key store's `load`; the service keeps no copy, and no status, result, or message holds it. A wrong passphrase is refused as `wrong_passphrase`, and the field is cleared after every attempt. After a wrong passphrase, the next unlock waits 1 second, and each further wrong one doubles the wait up to 30 seconds (`unlockDelayMs`); an unlock during the wait, also with the right passphrase, is refused as `too_soon` without asking the key store. A success clears the count.
- **Connection.** The [connection client](#connection) of #26 uses two functions of the service, in the main process only. `signWebSocketChallenge` returns the session's `auth.response` frame, or nothing: while a key replacement is pending, it authenticates once, which resolves the replacement, and signs again. `deviceRefused(code, deviceId)` passes a close reason (`auth_failed`, `device_revoked`, or `sign_in_required`) to the session's `deviceRefused` and follows the state it answers, so that `device_revoked` stops local execution as above; when the session fails, `device_revoked` still stops it. Neither is an IPC channel, and neither is an action of the person: they take no `operation` lock and never wait for a background refresh, so a handshake never makes the person's action answer `busy`, and a revocation applies at once; the session orders its own use of the key and the files. Only the authentication for a pending replacement, which sends requests, is left out while an action, a sign-in, or a background refresh runs; the connection then backs off and tries again.
- **Workspace reads.** `readWorkspaceData(name, params, query?)` sends one of six fixed `GET` reads of the allowlist in [`src/main/api-reads.ts`](src/main/api-reads.ts) for #27 and #28, in the main process only: no IPC channel and no bridge member reach it, and chat messages are sent over the connection. The reads are the account's workspaces (`GET /workspaces`, capped at 2 MiB), a workspace view (`GET /workspaces/:workspaceId`, 1 MiB), its projects (512 KiB), a page of a project's chat history (`beforeSeq`, and `limit` from 1 to 50, always sent; 4 MiB), its agents (1 MiB), and its runs (4 MiB). Each answer is read up to its cap and parsed with the protocol's response schema; every other route keeps the 512 KiB default. The caps hold the largest answers that the protocol's limits allow, with room to spare; the runs' cap holds about 900 finished runs, so a server that sends more than that needs a desktop with a larger cap. A name off the allowlist, or a parameter or a query outside its format, is refused as `failed` before anything is sent, also when a caller's types do not hold at runtime. A read is not an action of the person: it takes no `operation` lock and never makes an action answer `busy`. While a sign-in, a sign-out, "This is not me", a device removal, or an unlock runs, it answers `unavailable` without a request, and the caller tries again later. During the startup and a background refresh, which may report a sign-out or retry a removal with the key, it waits for the refresh to end without the lock and then checks again, so a read right after a start is delayed rather than refused (decided on 2026-11-05). The actions do not wait for a read that is on its way. Instead, a counter (`accountChanges`) goes up when one of those actions begins and when the published account, the key's state, or the device changes (except a device that becomes signed in); a read takes it before its request, and the data of its answer is dropped as `unavailable` when it changed, also when the action has ended before the answer arrives, for example a sign-out that started and finished while the read was on its way. A failure carries no data and is answered as it is, also when the read's own refusal changed the device (for example `sign_in_required` answers `not_signed_in`). An answer is also dropped when no device is signed in any more (`not_signed_in`) or another one is (`unavailable`). The failures are a closed set (`WORKSPACE_READ_FAILURES`): `not_signed_in` (also for a signed-in device whose key is not usable: it waits for its passphrase, it is lost, or it serves only a pending removal; the caller reads `status().deviceKey` to tell an unlock from a sign-in), `not_found`, `rate_limited` (the caller waits a fixed time; `Retry-After` is not read), `unavailable`, and `failed` (an answer too large or outside its schema, or another refusal). The checks that a schema cannot make, such as a page's `seq` below its `beforeSeq`, stay with the [chat timeline](#chat-timeline).
- **Secrets.** The status, the results, and the device list hold no sign-in code, verifier, signature, key, or token; the flow and the session never hand them over, and the contract drops unknown keys. Messages are fixed text.

Not in this part: choosing a passphrase or an unprotected key for a new Linux key without a secret service, which needs the flow's `newKeyProtection` (until then such a sign-in does not start); resetting a key whose passphrase is forgotten while the installation is signed out; and the screens of #95.

## Session

The device session ([`src/main/session/`](src/main/session/)) is part 3 of #94: access tokens, the pending key replacement, the device states, sign-out, removing this device, the device list, and the signature of the WebSocket challenge, in the main process ([ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md), "Device key and authentication", "Revocation, sign-out, and recovery", and "Storage and transport on the device"; P-56, P-65). The [account service](#account) creates it after the key's load, refreshes it at startup, tells it about every sign-in, and passes its state, sign-out, removal, and device list on to the IPC and the panel; the WebSocket client of #26 uses its signature. These rules are part of the authentication contract and are reviewed with the desktop owner when they start work (P-67).

- **Access tokens.** `createDeviceSession(dependencies)` ([`session.ts`](src/main/session/session.ts)) mints a token with `POST /auth/challenge` and `POST /auth/access-token`. The device key signs the `http` input: the API origin as the audience, the nonce, the device ID from the record, and the challenge ID. The token stays in the session's memory, and no function returns it. It is used until one minute before its 15 minutes end, counted from before the request that minted it on both the device's monotonic clock and its wall clock: the monotonic clock may stop while the computer sleeps, and the wall clock may jump. A difference between the clocks of the device and the API does not matter; `expiresAt` is not read. One mint runs at a time, and concurrent callers share it. `request` sends a request with the token. A `401` drops the token, mints one new token, and sends the request once more; when the new token cannot be minted, the failure names the API's reason (`auth_failed`, `device_revoked`, or `sign_in_required`), and a second `401` answers `unauthorized`. A removal noted while the first request was on its way stops that retry before the new token (`removal_pending`).
- **Requests.** [`api-call.ts`](src/main/session/api-call.ts) sends every request with the injected `fetch`, `redirect: "error"`, `cache: "no-store"`, and `credentials: "omit"`, only to a URL whose origin is the API origin (else nothing is sent, and the token never leaves for another host), stops waiting after 30 seconds, and reads at most 512 KiB of the answer by default, because the device list may hold up to 1,000 devices; a request may name its own cap (`maxAnswerBytes`), as the [workspace reads](#account) do. The session's `request` may also take a `query`, encoded with `URLSearchParams` after the filled path, which stays on the API origin. Only a `4xx` whose body passes `ApiErrorBodySchema` with the same status is a certain answer. A network error, the timeout, a `5xx`, and an answer that is not the API's are uncertain and change nothing on the device.
- **Pending replacement.** While the record names the previous key, the session tries the new key first. A token proves that the API holds the key that signed, and so do `sign_in_required` and `device_revoked`, which the API answers only after it verified the signature. If that is the new key, the record is written with the new public key (a second time if the first write fails), and only then is the replacement confirmed, the rule of the sign-in flow; when the record cannot be written, the replacement stays pending (`record_not_saved`). If the new key gets `auth_failed`, the previous key is tried with a new challenge, and if it authenticates, the replacement is abandoned, except during the grace period of an uncertain sign-in (below). If both get `auth_failed`, one round proves nothing: the API answers `auth_failed` also for a challenge that it lost (challenges live in its memory, so a deploy loses them) and to a resent copy of an access token request that it already answered. So the session notes the time, keeps both keys, answers `auth_failed`, and asks nothing more on its own for 10 minutes (`LOST_KEY_WAIT_MS`); `refresh` lets the person retry earlier, and a round in that time deletes nothing. The time is noted in the session notes, so a restart does not start the count again: a person whose device does not work is likely to restart the application, and the lost-key path must still be reachable. A token or `sign_in_required` for either key in between proves that the API holds a key, so it ends the first refusal, also during the grace period below; and a first refusal older than a day (`KEYS_REFUSED_MAX_AGE_MS`) says nothing about the API now, so the next refusal starts the wait again. Only a round at least 10 minutes, and less than a day, after the first one that refuses both keys again, the new key first, makes the installation treat them as lost (decided on #94): it publishes `key_lost` first, deletes both keys through the key store, and keeps the record, so the next sign-in takes the flow's lost-key path and registers a new device that names the record's device as `previousDeviceId`. A sign-out marker names only keys that are then gone, so it is deleted; a corrupt one stays until a sign-in. An uncertain answer in any round, or a refused challenge such as `rate_limited`, changes nothing, and no further key is tried after it; `sign_in_required` and `device_revoked` keep their meaning in every round. While a sign-in runs (from `signInStarted` until `signInFinished`), a pending replacement is not resolved (`sign_in_running`), because the sign-in may still register the new key. A record that already names the new key confirms the replacement when it is read, as in the sign-in flow.
- **Grace period of an uncertain sign-in.** The API can commit a `POST /auth/sign-in` well after the flow stopped waiting (its statement timeout applies to each statement). So after every outcome of the sign-in flow other than `signed_in` and `refused` (for example `no_answer`, `server_error`, `uncertain_refusal` with any of its codes, `record_not_saved`, or `cancelled`), a pending replacement gets a grace period of 10 minutes (`REPLACEMENT_GRACE_MS`) from that outcome. During it, a token of the previous key is used, but both keys stay, and every mint tries the new key first; a late commit of the new key is then confirmed as usual. Only after it does the previous key abandon the replacement. The time is in the session notes, so a restart keeps the grace period. A pending replacement that the session sees without a noted outcome, for example after a stop during the request, gets its grace period from then; a later outcome of an attempt that sent nothing keeps the first time. So for up to 10 minutes after an uncertain sign-in, unless the new key authenticates first, a new sign-in answers `replacement_pending` (the flow does not replace a key while one is pending), and the WebSocket challenge is not signed (`replacement_pending`); HTTP requests work with the previous key's token.
- **Device states.** `state()` and `onChange(listener)` give the account service a small state: `starting`, `no_device`, `key_lost`, `unavailable`, `key_not_loaded`, `signed_in`, `signed_out` (with `reportPending`), `sign_in_required`, `auth_failed`, `account_mismatch`, `removal_pending`, `removed`, or `revoked`, with the account from the record where there is one (device ID, user ID, login, display name, and sign-in expiry, no key). `key_lost` is a record without its device's key: the key file is gone, the loaded key is not the record's device's key, or both keys of a pending replacement were refused twice, 10 minutes apart; it follows from the files, so it holds after a restart too. `removal_pending` follows from the session notes, so it holds after a restart too. After `device_revoked` the session publishes `revoked` first, so that the caller stops local execution, then deletes the key, then the record (the record stays when the key could not be deleted), then the sign-out marker. `sign_in_required` and `auth_failed` keep the key and the record; the session then asks the API nothing until `refresh` or a sign-in, except to resolve a pending replacement, which the next sign-in needs. `signInFinished` with `refused` and `device_account_mismatch`, or that code in any answer of the API, moves to `account_mismatch` with the login from the record, and a failure carries the login as `deviceLogin`. The device itself is unchanged, so the person can sign in as that login and then remove the device. `deviceRefused(code, deviceId)` applies a close reason of the WebSocket the same way, for the device that the connection authenticated as; a refusal for another device, for example a late `device_revoked` from a connection of a device that this installation no longer holds, is ignored.
- **Sign-out (P-65).** `signOut` drops the tokens and writes the sign-out marker before it calls `POST /auth/sign-out`, with the cached token while it is still valid, or else with a new token that is used for nothing else. The device, its key, and its record stay. From then on `request`, `removeDevice`, and `signWebSocketChallenge` answer `signed_out` without asking the API, also after a restart, and so does `authenticate`, except that it still resolves a pending replacement, which the next sign-in needs (see the marker below). While offline, `signOut` resolves with `pending`, the state shows `reportPending`, and `reportSignOut` reports it later. `sign_in_required` in answer to the report counts as reported, because the API then takes the key only after a new sign-in. A `401` to the report gets one new token.
- **Sign-out marker.** `device-sign-out.json` ([`sign-out-marker.ts`](src/main/session/sign-out-marker.ts)) sits next to the record and the key files (on Windows `%LOCALAPPDATA%\MyManDev`) and is written with the key store's atomic write: `{ version: 1, publicKeys, reported }`. It is a file, not memory, because the sign-out must survive a restart, which is neither a GitHub sign-in nor a report. It names the public keys that the device held when the person signed out. Every GitHub sign-in stores a new key, so a key that the marker does not name was made by a sign-in after the sign-out: the marker is deleted by a read that finds none of its keys held, and when a key that it does not name authenticates. `signInFinished` with `signed_in` relies on that rule too, so a sign-out made while that sign-in ran, which names the sign-in's new key, holds; it deletes only a corrupt marker. Any other outcome of the sign-in flow leaves it, `failed` with `uncertain_refusal`, `key_changed`, or `record_not_saved` included: after an uncertain answer the replacement stays pending, the marker still names the previous key, and only an authentication with the new key proves that the sign-in committed. A corrupt or unreadable marker names every key (fail closed) until a sign-in. When the file cannot be written, the sign-out holds in memory until the application quits, and `onError` says so. While signed out, the key signs only to report the sign-out and to resolve a pending replacement that the next sign-in needs; a token minted with a key that the marker names is used only for the report.
- **Remove this device.** `removeDevice` first notes the removal in the session notes, then revokes the device with `POST /devices/:deviceId/revoke` and the reason `removed`. Only after the API confirmed it are the key, the record, the marker, and the notes deleted, and the state is `removed`. Without a clear answer it resolves with `pending`, and the key stays. While the removal is noted, also after a restart, the state is `removal_pending`, and the key serves only the removal: `request`, `listDevices`, `authenticate`, and `signWebSocketChallenge` answer `removal_pending` without asking the API (ADR 0014 shows an offline removal as pending). `refresh`, which the application calls at start, and another `removeDevice` retry it. A refusal of the revoke itself, for example `conflict`, ends the pending removal and keeps the key; a refusal of the token (`auth_failed`, `sign_in_required`, `rate_limited`) leaves it pending. A sign-out or a sign-in ends a pending removal, because the person chose that instead. It is refused while signed out, because the API takes no request of a signed-out device: the person signs in first.
- **Session notes.** `device-session.json` ([`session-notes.ts`](src/main/session/session-notes.ts)) sits next to the sign-out marker and is written the same way: `{ version: 1, removal, uncertainSignIn, keysRefused }`, each null or naming the device ID or the public keys that it is about, with a UTC time for the last two. One small strict file holds the three, because each must survive a restart, the record belongs to the sign-in flow, and the marker has its own meaning; it holds no secret. The session reads it once (this instance holds the single-instance lock, so only it writes the file), keeps only the notes about the device and the keys that the installation holds, and deletes the file when every note is empty. The times use the wall clock, the only clock that survives a restart. A time later than now, for example after the clock was set back, counts as now and is rewritten, so a note can never wait for a date in the future. While the application runs, a wait also needs the monotonic clock to have advanced, so a wall clock that jumps forward ends no wait early; a clock that moves back, or a computer that sleeps, only makes a wait longer. The one-day limit of a first refusal uses the larger age instead: a first refusal is too old as soon as either clock says so, so days that the computer slept through count, also while the application runs. A corrupt file is reported and not used; it then loses a pending removal, a grace period, and the first refusal time, which only makes the person retry the removal or wait again.
- **Device list.** `listDevices` calls `GET /devices` and returns the devices parsed with `DeviceListResponseSchema`.
- **Late answers.** An answer of the API can arrive long after the session read the files, for example while "This is not me" deletes the record and the key. Before a token or `sign_in_required` changes anything, the session reads the record again; when it is gone, names another device, or the key store no longer holds the keys that signed, it writes, confirms, and abandons nothing and answers `no_device`, so a late answer never writes an account back. `removeDevice` notes the removal inside the key queue, after a mint or a sign-out report that runs, and sends the revoke outside it.
- **WebSocket.** `signWebSocketChallenge(challenge)` returns the `auth.response` frame for the WebSocket client of #26: the `ws` input with the nonce and the connection ID of `auth.challenge`, signed with the current key ([`websocket-auth.ts`](src/main/session/websocket-auth.ts)). It sends no request, so it fits into the 10-second handshake. It is refused while signed out, while a removal is pending, after `sign_in_required` or `auth_failed`, and while a replacement is pending (`replacement_pending`); `authenticate` resolves the replacement first. The frame is the only value of the session that carries a signature.
- **Secrets.** No result, state, or message holds a token, a signature (except that frame), or a key. The optional `onError` receives fixed messages only, and the session never logs.
- **Electron.** [`session/system.ts`](src/main/session/system.ts) passes `net.fetch`, which follows the system proxy settings, `app.isPackaged`, `process.env`, the key folder, the platform, and the record store that the account service and the flow use. It stays thin and is only type-checked.
- **Known limits.** A corrupt sign-out marker names every key, so after a sign-in that committed while it was corrupt the device stays signed out until the next `signed_in` outcome deletes it (fail closed). A sign-out needs the key to be loaded (`key_not_loaded` otherwise), because the marker names the public keys that it holds. A corrupt session notes file loses a pending removal: no key is deleted, the device simply stays, and the person can request the removal again.

The tests ([`session.test.ts`](src/main/session/session.test.ts), [`session-notes.test.ts`](src/main/session/session-notes.test.ts), [`sign-out-marker.test.ts`](src/main/session/sign-out-marker.test.ts), [`api-call.test.ts`](src/main/session/api-call.test.ts), [`websocket-auth.test.ts`](src/main/session/websocket-auth.test.ts)) use a temporary folder, the real key store with a fake `safeStorage`, the real record and marker stores, injected timers, an injected monotonic clock and wall clock, and a fake API with the rules of the API's device routes: a single-use challenge, the signature checked before the device state, every signature verified with `node:crypto`, and tokens that a sign-out or a revocation ends. They cover minting and its signed input, the cache until shortly before the end, one mint for concurrent callers and for concurrent `401`s, the retry after a `401` and its limit, and the reason of the new token's failure. For the pending replacement: the new key confirmed after the record write, in this order; a failed record write that keeps it pending; the previous key that abandons it; both keys refused, which only notes the time and asks nothing more on its own, a retry within the wait that deletes nothing, and a key that authenticates in between, which ends the first refusal (also during the grace period), a first refusal older than a day, which starts the wait again, a round 10 minutes later that refuses both again, which deletes both keys and keeps the record, after which the real sign-in flow registers a new device with `previousDeviceId`; the count across a restart; a refused round followed by the new key or the previous key in a later round, which deletes nothing; the grace period of an uncertain sign-in (the previous key's token with both keys kept, a late commit of the new key confirmed, the abandon after it, across a restart, each outcome that starts it, a later outcome that keeps its time, and a pending replacement seen after a stop); the sign-out marker after a lost key; a network error, the timeout, a `5xx`, a `503`, an answer that is not the API's, an error body whose status does not fit, a `200` that is not a token, a body over the limit, and `rate_limited`, which change nothing, for the new and for the previous key and in either round; `sign_in_required` for either key; and no resolution while a sign-in runs. For the states: `device_revoked` (the state first, then the key, then the record, also during a replacement, and a key that cannot be deleted keeps the record), `sign_in_required`, `auth_failed`, `device_account_mismatch`, and close reasons of the WebSocket. ## Connection

The connection client ([`src/main/connection/`](src/main/connection/)) keeps the main process's connection to the cloud API's gateway (M2-02, #26; [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md), "Device key and authentication" and "Storage and transport on the device"; P-56). The Project Manager confirmed its scope and its client on 2026-11-02. It authenticates with the [device session](#session) through the [account service](#account), and the renderer sees only its status.

- **Client.** Electron's `net.WebSocket` in the main process, in Electron 45.0.0 (added in electron/electron#51593 and released in 42.7.0, 43.2.0, and 44.0.0), with the default session, `useSessionCookies: false`, and the `origin` option unset. It adds no dependency. It runs on Chromium's network stack, so it uses the same proxy resolution (system settings, PAC, and WPAD), proxy authentication cache, and TLS trust as the `net.fetch` calls of the session. It sends `Origin` with the http(s) form of the socket URL's origin, which is the API's own origin and which the API's `/ws` accepts since #154. The gateway path `/ws` is a desktop constant (`GATEWAY_PATH`, decided on #26). [`client.ts`](src/main/connection/client.ts) takes an injected socket factory, so the tests use a fake; [`system.ts`](src/main/connection/system.ts) passes `net.WebSocket` and the `powerMonitor` `resume` event, stays thin, and is only type-checked.
- **Options considered.**

  | Option                                                     | Why not                                                                                                                                                                            |
  | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Electron `net.WebSocket` (chosen)                          |                                                                                                                                                                                    |
  | Node's built-in `WebSocket`                                | No proxy support, and only the bundled root certificates, so a company root for TLS inspection is not trusted.                                                                     |
  | `undici` with a proxy agent, fed by `session.resolveProxy` | Resolves the proxy only indirectly (our own parsing of the PAC result, no SOCKS4), knows Basic proxy authentication only, and needs the trust store passed by hand.                |
  | `ws` with proxy agents, fed by `session.resolveProxy`      | The same as `undici`, and three to seven new packages.                                                                                                                             |
  | Chromium's WebSocket in a hidden window                    | The connection would leave the main process (P-56), the API refuses the renderer's origin, and the signature would have to cross IPC. A utility process has no Chromium WebSocket. |

- **Start and stop.** The client follows the account status: it connects while the device state is `signed_in`, the device key is `ready`, the installation holds an account, and the API origin is set. It closes with 1000 when that ends, on sign-out, removal, and revocation, and at quit (`will-quit`). Another device ID closes the socket first. There are never two sockets: after the client closed a socket, the next one opens only after its close event, or after 5 seconds without one (`CLOSE_WAIT_MS`).
- **Authentication.** The client waits for `auth.challenge` and sends exactly one `auth.response`, the frame that the account service's `signWebSocketChallenge` returns from the session; while a key replacement is pending, the service authenticates once first, which resolves it, and signs again. It then waits for `auth.ok` of the device that signed. The opening handshake may take 15 seconds (`HANDSHAKE_TIMEOUT_MS`), and the open socket gets 15 more until `auth.ok` (`AUTH_OK_TIMEOUT_MS`); on expiry the client closes with 1000 and backs off (`timeout`). A challenge with another protocol version stops the client with `update_required`; so does any first message whose `protocolVersion` differs, even one that is not a valid challenge, because the version is read before the type. A challenge that the session does not sign closes and backs off (`signature_failed`).
- **Messages.** The client accepts only text frames of at most 1 MiB in UTF-8 (`RECEIVE_LIMIT_BYTES`, decided on #26), checked after receipt, because `net.WebSocket` has no limit of its own; `MAX_FRAME_BYTES` (64 KiB) is the server's limit for the client's frames. Each message is parsed as JSON and decoded with `decodeServerMessage`. Before `auth.ok`, only the challenge and then `auth.ok` are accepted. A binary frame, invalid JSON, a decode failure, a message over the limit, or a frame out of order closes with 1000 and backs off (`invalid_message`). After `auth.ok`, decoded messages go to the `onMessage` listeners of the main process; the renderer never gets a frame. The client sends only after `auth.ok`, and only client events, through `sendAs` (see "Identity"), and the workspace frames, each checked with `decodeClientMessage` first; only the decoded copy is sent. A send is refused above `MAX_FRAME_BYTES` (`too_large`) and while more than 1 MiB waits in `bufferedAmount` (`backpressure`, `MAX_BUFFERED_SEND_BYTES`). `subscribeWorkspace` and `unsubscribeWorkspace` keep the set of requested workspace IDs, and every `auth.ok` sends `workspace.subscribe` for each of them again. The server's answers reach the listeners; the set changes only when main-process code asks.
- **Identity.** The client keeps the `userId` and `deviceId` of the current socket's `auth.ok`, the identity that the server binds every event of the connection to (ADR 0006, identity binding). It is cleared when the socket closes, when the client closes or replaces it, and at quit, and the next `auth.ok` sets it again. `sendAs(build)` calls `build` with that identity and sends the event on that socket in the same call, so that no await, and no other socket, comes between reading the identity and sending (decided on #27 and #28 on 2026-11-05). It is the only way to send an event, as decided on the same day; the client has no `send`. Without an authenticated socket it answers `not_connected` and does not call `build`; a `build` that throws gives `invalid`, and one that closed the socket gives `not_connected`. The send guards above apply, and an event whose `deviceId`, or whose `user` actor's `userId`, is not the identity's is refused as `invalid`, because the server would close the connection with 1008 `identity_mismatch`. The identity stays in the main process and in no status or log. `identity()` returns it, or null without an authenticated socket, for main-process code that keys its data by the account and the device: the [chat service](#chat-service) keys its waiting messages with it (decision 4 of 2026-11-05 on #27 and #28 keeps such a getter for the main process only). The chat service and the [development agent switch](#development-agent-switch) call `sendAs`.
- **Close reasons** (ADR 0014's table, the protocol package's `WS_CLOSE_CODES`, and the decisions on #26):

  | Code                                       | The client                                                                                                                                      |
  | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
  | 4000 `auth_failed`                         | Stops (`auth_failed`). The session's `deviceRefused` notes the refusal, and the account panel offers a sign-in.                                 |
  | 4002 `device_revoked`                      | Stops (`device_revoked`). `deviceRefused` deletes the key, and the account service calls its stop-local-execution hook.                         |
  | 4003 `sign_in_required`                    | Stops (`sign_in_required`). `deviceRefused` notes it; the browser opens only when the person clicks "Sign in with GitHub" in the account panel. |
  | 4004 `connection_replaced`                 | Stops (`connection_replaced`) and offers "Reconnect here once".                                                                                 |
  | 4005 `protocol_violation`                  | Stops (`protocol_violation`) and offers "Retry now".                                                                                            |
  | 4006 `key_replaced`                        | Reconnects at once, one time; when it repeats before the connection was stable, it backs off (`key_replaced`).                                  |
  | 1008 `unsupported_version`                 | Stops (`update_required`).                                                                                                                      |
  | 4001 `auth_timeout`                        | Backs off (`timeout`).                                                                                                                          |
  | 1011, 1013                                 | Backs off (`server_error`, `server_busy`).                                                                                                      |
  | 1003, 1007, 1008 with another reason, 1009 | Backs off (`message_refused`).                                                                                                                  |
  | 1001, 1006, any other code                 | Backs off (`connection_lost`, or `connection_failed` before the socket opened).                                                                 |

  The device ID of `deviceRefused` is the one of the signed `auth.response`, so that a late close of another device's connection changes nothing. After a stop, the client waits until the device is signed in again, for example after a new sign-in; after `connection_replaced` and `protocol_violation`, the person can also reconnect. `update_required` holds until the application is updated.

- **Backoff.** The client waits a random time between half of min(60 s, 1 s x 2^n) and all of it, where n counts the attempts; the count starts again after 60 seconds connected (`STABLE_CONNECTION_MS`). That stays well below the API's 60 handshakes per address in 10 minutes. When the system resumes (`powerMonitor` `resume`), a waiting connection starts at once, and an open one is replaced, because it may have died unnoticed during the sleep.
- **Status.** `{ state, reason?, retryAt?, revision }` (`ConnectionStatusSchema`): `offline` (with `not_signed_in` or `no_api_origin`, or without a reason while the session starts and at quit), `connecting`, `authenticating`, `connected`, `waiting` with a reason and `retryAt`, or `stopped` with a reason. `connection:reconnect` connects at once ("Retry now" while waiting, "Reconnect here once" after `connection_replaced`, and "Retry now" after `protocol_violation`). It is refused as `not_signed_in` without a signed-in device and after `auth_failed`, `device_revoked`, and `sign_in_required`, because the server would refuse the same key again and only a GitHub sign-in ends them; as `update_required`; as `already_open` while a socket is open or opening; and as `too_soon` within 3 seconds of the last reconnect (`RECONNECT_COOLDOWN_MS`) or after 10 reconnects within 10 minutes (`RECONNECT_BUDGET`). The backoff makes at most 25 handshakes in 10 minutes, when every wait is the shortest, so even a renderer that calls the reconnect in a loop keeps the client at 35, below the API's 60 per address. The shell header shows the state, a fixed sentence about the reason, and the action ([`src/renderer/connection-status.ts`](src/renderer/connection-status.ts)).
- **Secrets.** No status, result, or log holds a frame, a nonce, a signature, a connection ID, a user ID, or a key. The client's log messages are fixed text with a close code at most; the close reason's text, which may name a network error, is read only for 1008 and never logged. The signed frame goes only to the socket.
- **Known limits.** `net.WebSocket` answers the server's pings itself and shows none of them, so a connection that died without a close is noticed only when TCP or the system reports it, or at the next system resume; a protocol-level heartbeat is a later protocol change. A proxy that asks for Basic or Digest credentials is not prompted for them, the same as `net.fetch` today; cached credentials are used. A handshake that the API refused with `403` or `429` arrives as 1006, so it backs off like a dropped connection.
- **Manual test.** A connection to a locally running API, and one connection through a system proxy (PAC or a manual proxy), are part of the later manual test and are not recorded here. The proxy record holds the operating system and the Electron version, the proxy setting, the output of `session.resolveProxy` for the https form of the API URL, the proxy's `CONNECT` log line, the desktop status after `auth.ok`, and the API's log line of the authenticated connection. Chromium never sends `127.0.0.1` or `localhost` through a proxy unless the bypass list contains `<-loopback>`, so that record needs that setting or a hosted HTTPS API (#96).

## Agent activity

[`src/main/agents/activity.ts`](src/main/agents/activity.ts) holds the agent activity of one project (M2-04, #28): its agents from `GET /projects/:projectId/agents`, and its unfinished and recently finished runs from `GET /projects/:projectId/runs`, kept current with `agent.run.state_changed` events. It is a pure model, with no timers, no I/O, and no logging. Its functions return new frozen objects and never change their arguments: `activityFromSnapshot` reads both answers, `replaceAgents` takes a new answer of the agent route alone, and `applyRunEvent` applies one event.

- **Snapshot.** Every agent and every run must belong to the project in the path; otherwise the answers are refused as `wrong_project`. The server's order is kept and never sorted: the unfinished runs the most recently created first, the finished runs the most recently finished first. The model keeps 50 finished runs (`RECENT_FINISHED_RUNS`), or as many as the server sent when that is more.
- **The last event wins.** After `workspace.subscribed`, the buffered events are applied in order on top of the reload, which can be newer than some of them. An event sets the state and the reason that it reports; its `previousState` is never compared with the held state. An event that reports what the model already holds changes nothing (`unchanged`), so a repeated relay is harmless. A `repositoryId` in an event never changes the run's repository.
- **A finished run never changes.** An event for a run in the finished list is older than the snapshot and changes nothing.
- **Finishing and creation.** A terminal state moves the run to the front of the finished list, with the event's `occurredAt` as a provisional finish time that the next reload replaces with the server's; the oldest finished run beyond the limit is dropped. A creation (`previousState` null) of a run that the model does not hold adds it at the front of the unfinished list.
- **Reloads.** An event that changes a run of a listed agent that the model does not hold, or a held run of another agent, is `unknown_run`, and the caller reloads. An event for a run that the model does not hold, of an agent that the project does not list, is `unknown_agent`: most often its run belongs to another project of the workspace, because the event names no project, and the caller does not reload for it. An event for a held run applies also when the agent list does not hold the run's agent, for example an agent created between the two reads of the snapshot: the snapshot showed that the run belongs to this project. A server cancellation with a code of `RUN_CANCEL_REASONS` (`device_revoked` or `member_removed`) sets `agentsStale` whatever the outcome, because the revocation or removal also disabled agents and no event reports that; the caller then reloads the agents.

The [agent activity service](#agent-activity-service) uses it for the open project, and the [development agent switch](#development-agent-switch) reads that service; the panel follows (#28).

The tests ([`activity.test.ts`](src/main/agents/activity.test.ts)) build every answer through the protocol's schemas and every event through `decodeServerMessage`, as the connection client receives it, and freeze them. They cover the copy and the freeze of answers that are not frozen, the project check of both answers and of a new agent list, empty lists, the server's order, the finished limit (50, or the larger count of the snapshot) with the drop of the oldest finished run, an update in place that leaves its input unchanged, a reason that is replaced or cleared, the move to the finished list with the provisional finish time, events for finished runs, buffered events over a newer snapshot, unknown agents and runs, a held run of another agent, the events of a held run of an agent that the list does not hold, a creation at the front with and without a repository and with a reason, the stale agents after a server cancellation (also when the runs already show it, and for a run of another project), a repository in an event, and a repeated event.

## Workspace resync

The resync gate ([`src/main/workspace/resync.ts`](src/main/workspace/resync.ts); #27, #28) applies the protocol's rule for `workspace.subscribed` (the protocol package's [README](../../packages/protocol/README.md#workspace-subscriptions-presence-and-chat), decision 5): the device reloads the workspace over HTTP, buffers the workspace's events until the reload answers, and then applies them in order on top of the reloaded state. It is generic over the event type, does no I/O, and keeps no timers. Each service that holds workspace state (the workspace, chat, and agent services) owns one gate, so their reloads stay independent; the [workspace service](#workspaces), the [agent activity service](#agent-activity-service), and the [chat service](#chat-service) use one each.

- **Generations.** Every reload starts a new generation before its request is sent: `subscribed` after each `workspace.subscribed`, and `begin` for the others (a change of the open project, a reload that the service decides on, a retry, and the reload after an overflow). `reloaded(generation)` returns the buffered events in order and goes live; for a stale generation, or one that already answered, it returns `null` and the service drops the answer, for example one for the previous project. `reloadFailed(generation)` keeps the events buffered until the retry. `begin` during a reload keeps the buffered events, since applying an event again changes nothing. `generation()` lets a service drop the late answer of another request, such as an older page of the chat.
- **Scope.** A reload reads `all` of a service's state or a `part` of it, such as the agent list alone. `subscribed` always reads `all`. `begin(scope)` returns the generation and the scope that the service then requests: the scope asked for, or `all` while an earlier reload has not answered (it is open, it failed, or an overflow or `end` made it stale), because its dropped answer may have covered any part of the state. So a part reload never replaces the reload after `workspace.subscribed`, and `live` means that the whole state was reloaded since `subscribed`.
- **Events.** `push` returns `apply` while live, `buffered` during a reload, and `ignored` without a subscription. A reload begun without a subscription only gets a generation; the gate goes live only after `subscribed`.
- **Limits.** At most 1,000 events (`MAX_BUFFERED_EVENTS`) and 4 MiB (`MAX_BUFFERED_EVENT_BYTES`, measured with the service's `sizeOf`) wait for a reload. 4 MiB holds 64 of the largest chat messages and 4 of the largest messages that the connection client accepts, while 1,000 of the largest chat messages would hold about 64 MB in each gate. Above either limit, the buffer is cleared (`overflowed`), the open reload becomes stale, and later events are dropped until the service calls `begin`, whose reload then reads `all`. The gate never starts a reload itself, so the service's backoff decides when. Dropping is safe because the server relays an event only after its commit: a reload that begins after an event arrived contains it.
- **End.** `end`, for the end of the subscription, a change of the workspace, or a lost connection, drops the buffered events and changes the generation, so that the open reload and every request noted with `generation()` become stale. It does so also without a subscription, so that the answer of a reload for the previous workspace is dropped; a service that still needs that reload begins it again.

The tests ([`resync.test.ts`](src/main/workspace/resync.test.ts)) cover events without a subscription, while buffering, and while live; the order of the returned events; a second `workspace.subscribed` and a second `begin` during a reload; a failed reload and its retry; a stale failure; the overflow by count, by bytes, at the budget, with an invalid size, and after a failure; that the size is measured only for buffered events; the scope of a part reload while live, without a subscription, and after an open, a failed, an overflowed, or an ended reload; `end` in every state; a reload without a subscription; and two independent gates.

## Chat timeline

The chat timeline ([`src/main/chat/timeline.ts`](src/main/chat/timeline.ts); #27) is the model of one project's chat in the main process: the messages that the desktop holds, the oldest first, and the person's own messages that the server has not stored yet. It is pure: no I/O, no timers, and no IPC, and every result is frozen. The [chat service](#chat-service) calls it.

- **Body.** `prepareMessageBody` turns a carriage return, alone or before a line feed, into a line feed, and then applies the protocol's rules for a message body (`multilineText`): not blank, at most 16,000 code points (`LIMITS.messageBody`), and no other control, format, or invisible character.
- **Messages.** Each message ID and each `seq` is held once, in `seq` order. `applyNewestPage` replaces the held messages, so a reload never leaves a gap; held messages newer than the page stay, and so do the pending copies. While older pages exist, a newest page that ends below the held messages with a gap is stale, for example the answer to an earlier request that a later reload overtook. A reload that changes nothing returns the same timeline. `applyOlderPage` adds an older page only when the lowest held `seq` is still the `beforeSeq` that was sent, and drops it as stale otherwise. Both check what the schema cannot see: every message belongs to the project, the page holds at most the `limit` that was sent, and every `seq` of an older page is below its `beforeSeq`. `hasOlder` is true after a full page that does not reach `seq` 1; the server numbers a project's messages from 1 without gaps. `applyCreated` inserts a relayed message by `seq`, unless it is already held or lies below the held messages while older pages exist, and ignores another workspace or project.
- **Pending copies.** A timeline belongs to an account, a device, a workspace, and a project (the Project Manager's decision of 2026-11-05 on #27), and so do its pending copies. A copy is `waiting` for the connection, `sending`, or `refused` with the code of `event.refused`. `chat.message.created` removes the copy whose event ID is its `causationId`. `pendingForResend` lists the waiting copies only for the timeline's own key, and `keepForIdentity` drops the timeline after a sign-out or a change of account or device. A timeline holds at most 50 copies (`MAX_PENDING_CHAT_MESSAGES`). The retries after `rate_limited` and their timing belong to the [chat service](#chat-service).

The tests ([`timeline.test.ts`](src/main/chat/timeline.test.ts)) cover the body rules (line breaks, blank text, the limit counted with astral characters, and control, format, and invisible characters, written as escapes), duplicates, relays out of `seq` order, the page checks, `hasOlder`, stale older and newest pages, a reload that changes nothing, a reload that keeps the pending copies, the pending copy replaced through `causationId`, a duplicate created event, a refusal, the key checks, the limit on pending copies, and that every result is frozen and no argument changes.

## Workspaces

The workspace service ([`src/main/workspace/service.ts`](src/main/workspace/service.ts); #27, #28) holds the account's workspaces, the selected workspace's people and projects, and the open project in the main process, read with the account service's [workspace reads](#account) and kept current with the workspace's events. It is read-only: creating workspaces and projects stays with #95. [`index.ts`](src/main/index.ts) creates it after the [connection](#connection) and closes it at quit (`will-quit`). The renderer's sidebar ([Screens](#screens)) reads its IDs and names and selects a workspace or opens a project over IPC ([`src/main/workspace-ipc.ts`](src/main/workspace-ipc.ts); see [IPC contract](#ipc-contract)); the chat and agent services and the development switch read it in the main process.

- **List.** `GET /workspaces` loads whenever a signed-in device (the same condition under which the connection connects) reaches `connected`, because account frames sent while it was offline are lost. One load runs at a time; a trigger during a load drops its answer and loads again, so only an answer that was asked for after the last trigger applies. A failed load is retried after min(60 s, 2 s x 2^n), where n is the number of failures in a row before this one (2 s after the first); a `rate_limited` failure waits 60 s (`RATE_LIMITED_RETRY_MS`) and still counts toward n. A retry is scheduled only while connected: a lost connection cancels the retry, a load that fails while offline schedules none, and the next `connected` loads at once. A sign-out, or another device, resets everything and drops the answers on their way.
- **Selection.** Kept in memory only (decided on #27 on 2026-11-05). It defaults to the first workspace of the list, the most recently claimed, and stays while the list holds it. `select(workspaceId)` takes a workspace of the list, unsubscribes the previous one through the connection client, and subscribes the new one, so the client's set holds the selected workspace only. The open project closes with it.
- **Reload.** After every `workspace.subscribed` of the selected workspace, the service reloads its view (`GET /workspaces/:workspaceId`) and its projects through its own [resync gate](#workspace-resync), and applies the events that arrived meanwhile in order on top of the answers. Answers for another workspace are refused as `failed`. A failed reload is retried with the same rule as the list (min(60 s, 2 s x 2^n), where n is the number of failures in a row before this one, 2 s after the first; a `rate_limited` failure waits 60 s and still counts toward n), while the events keep waiting. A successful reload starts the count again. `not_found` also reloads the list. An overflow of the gate's buffer reloads after the same backoff and counts toward n. A lost connection ends the subscription until the next `workspace.subscribed`.
- **Events.** `workspace.member.defined`, `claimed`, `renamed`, `removed`, and `role_changed`, `workspace.ownership.transferred`, and `workspace.project.created` and `renamed` of the selected workspace. Each sets the state that it reports, so a repeated event changes nothing. A live event that names a person or a project that the service does not hold reloads the workspace; after a reload, such an event is skipped. The service keeps only each person's display name, which is all that `memberName` needs; a removed person keeps it, and a removal, a role change, and an ownership transfer change nothing that the service keeps. It never keeps the user ID, the identity, the role, or the removal time.
- **Membership.** After `workspace.subscribe_refused`, `workspace.unsubscribed` with `membership_ended`, and `account.removed_from_workspace`, the service calls the connection client's `unsubscribeWorkspace`, which otherwise sends the subscription again after every `auth.ok`, drops the workspace from the held list, selects the first remaining workspace or none, and reloads the list. A refused workspace is not selected by default while the lists hold it, so a list that still holds it does not subscribe to it in a loop; the person can still select it. Every list answer that applies forgets the refused workspaces that it does not hold, so a later listing, a new membership, is selected by default again. `account.join_request_decided` with `approved` forgets that the workspace was refused and reloads the list.
- **State.** `{ revision, status, problem?, workspaces, selectedWorkspaceId, projects, openProjectId }`, frozen, with `onChange` listeners. `status` is `signed_out`, `loading` until the list and the selected workspace loaded once, `ready`, or `unavailable` with the failure as `problem` while a retry waits, or until the next connection after a failure while offline; what was loaded before stays. `workspaces` holds `{ id, name }` in the server's order, and `projects` holds `{ id, name, createdByMemberId }`, the oldest first. `openProject(projectId)` opens a project of the selected workspace only, `openProject(null)` closes it, and a project that a reload no longer lists closes. The revision also grows when only `memberName` or `gateLive` would answer differently.
- **For the chat and agent services.** `memberName(memberId)` gives a person's display name, also of a former member, and `Unknown person` (`UNKNOWN_MEMBER_NAME`) for a person that the selected workspace does not hold. `gateLive(workspaceId)` is true only for the selected workspace while it is subscribed and reloaded with no reload open; those services and the development switch send events for a workspace only then. `selectedWorkspaceId()` gives the selected workspace. `ownMemberId(workspaceId)` gives the account's own person in a listed workspace, the `member` of the list's answer, and null for a workspace that the list does not hold; an ended membership and a sign-out forget it. The development switch checks an agent's owner with it.
- **Logs.** Fixed text with a failure code at most, never a name or an ID.

Not in this part: presence (`workspace.subscribed`'s `onlineMemberIds` and `presence.changed` are ignored, because no issue owns showing it yet), the question before a switch while chat messages wait to be sent (the chat service and screen, decided on #27 on 2026-11-05), the workspace's name from its view, and the ownership offer and the join request settings of the view.

## Agent activity service

The agent activity service ([`src/main/agents/service.ts`](src/main/agents/service.ts); #28) holds the agents and runs of the [workspace service](#workspaces)'s open project in the main process, in the model of [agent activity](#agent-activity). It reads them with the account service's [workspace reads](#account) and keeps them current with the run events of the selected workspace. It never sends an event. [`index.ts`](src/main/index.ts) creates it right after the workspace service and closes it at quit (`will-quit`). [`src/main/agent-ipc.ts`](src/main/agent-ipc.ts) sends its state to the renderer read-only as `window.desktop.agents`, with each owner's name resolved in the main process, the newest runs only, and at most one publish every 50 ms (see [IPC contract](#ipc-contract)). `gateLive()` is true only while the open project's activity was reloaded since the selected workspace's last `workspace.subscribed`, with no reload open; the development switch sends only then.

- **Gate.** The service owns its own [resync gate](#workspace-resync). After each `workspace.subscribed` of the selected workspace, it reloads the open project, if any. Opening another project begins a reload of everything. Closing the project, or another workspace, clears the state; another workspace also ends the gate until its own `workspace.subscribed`, and so do `workspace.unsubscribed`, `workspace.subscribe_refused`, and a lost connection. A project opened before the subscription loads at once, and its events apply only after the next `workspace.subscribed` and its reload.
- **Reload.** `GET /projects/:projectId/runs` first, then `GET /projects/:projectId/agents`, so that the agent list is never older than the runs. The answers go through the model, and the events that waited apply after them, in order. An answer for an earlier generation, another project, another workspace, or another device is dropped; answers that hold another project's agents or runs are refused as `failed`.
- **Events.** `agent.run.state_changed` of the selected workspace goes to the model. `unknown_agent` is ignored: most often the run belongs to another project, because the event names none. `unknown_run` reloads everything, once for each reload: an `unknown_run` after the reload that an `unknown_run` began reloads nothing more, so data that stays inconsistent, such as a run beyond the list's limit, does not reload in a loop. - **State.** `{ revision, status, problem?, workspaceId, projectId, agents, unfinishedRuns, finishedRuns }`, frozen, with `onChange` listeners. `status` is `no_project`, `loading` until the open project's activity loaded once, `ready`, or `unavailable` with the failure as `problem` until a reload succeeds (a retry waits, or the next `workspace.subscribed` reloads); what was loaded before stays. An agent's owner is a member ID: the IPC resolves names with the workspace service's `memberName`, so the state holds no person's name.
- **Logs.** Fixed text with a failure code at most, never a name or an ID.

Not in this part: the agent panel (PR 11a), the [development agent switch](#development-agent-switch) and every send, and agent events beyond the run state, which the protocol does not have yet. That is also a gap: disabling an agent has no event, so when another person's device with no unfinished run is revoked, the agent list stays stale until the next reload.

## Development agent switch

The development agent switch ([`src/main/agents/dev-switch.ts`](src/main/agents/dev-switch.ts); #28, decisions D2, D4, and D5 of 2026-11-02 and the Project Manager's decisions of 2026-11-05) is the test source of the [agent activity](#agent-activity) until #35 lets agents run. In an unpackaged development build, it moves the unfinished runs of the agent that `db:dev-seed` created through allowed transitions, as that agent, from its host device, over the real [connection](#connection). No production route is added.

**Use.**

1. Start the API with a local database and sign in on the desktop. Create a workspace and a project with `db:dev-workspace`, and the agent with its runs with `db:dev-seed`, both with this device's ID ([database README](../../packages/database/README.md#development-seed); "Find the device ID" tells where the desktop keeps it).
2. Start the desktop with the agent ID that `db:dev-seed` printed and the device ID that it was given:

   ```sh
   MYMANDEV_DEV_AGENT_SWITCH=<agent ID> MYMANDEV_DEV_AGENT_DEVICE=<device ID> npm run dev -w @mymandev/desktop
   ```

   In PowerShell, set `$env:MYMANDEV_DEV_AGENT_SWITCH` and `$env:MYMANDEV_DEV_AGENT_DEVICE` first. `MYMANDEV_API_ORIGIN` is set as for any local API.

3. Open the seeded project. The switch walks the agent's oldest unfinished run through `queued`, `running`, `awaiting_input`, `running`, and `completed`, one transition every 2 seconds, and then the next run. Its log lines in the terminal say what it does. `db:dev-seed` creates a new agent each time, so start the desktop again with the new agent ID.

**Guards.** Each one holds before every send, resends included.

- **Development build.** [`index.ts`](src/main/index.ts) creates the switch only when `app.isPackaged` is false, and `devAgentSwitchSettings` checks it again before it reads the environment. The switch has no IPC channel: the renderer cannot start it, stop it, or see it, and a packaged build sends nothing.
- **Variables.** `MYMANDEV_DEV_AGENT_SWITCH` must hold an agent ID and `MYMANDEV_DEV_AGENT_DEVICE` a device ID, each checked with the protocol's schema (`AgentIdSchema`, `DeviceIdSchema`: a lowercase UUIDv7). Without the first one, or with it empty, the switch stays off without a word. An invalid value logs a fixed line, and the switch stays off.
- **Host device.** The server closes the connection with `identity_mismatch` and audits it when an agent actor names an agent that another device hosts. The agent list shows the host device to no account, the owner included (#110), and no other route shows it, so `MYMANDEV_DEV_AGENT_DEVICE` names it: the device ID that `db:dev-seed` was given. The switch sends only while the signed-in device is that device, and the `build` that it passes to `sendAs` checks the socket's identity again and builds nothing for another device. The second variable is an addition to the decision of 2026-11-05, which names the agent ID only, because the desktop has no other way to know the host device.
- **Owner, and not disabled.** The open project's agent list, from the [agent activity service](#agent-activity-service), must hold the agent with `disabledAt` null and with `ownerMemberId` equal to the account's own person in the workspace, which the [workspace service](#workspaces)'s `ownMemberId` gives from `GET /workspaces`.
- **Live.** The workspace service's `gateLive(workspaceId)` and the agent activity service's `gateLive()` must both hold. Otherwise the switch waits: closing the project pauses it, and opening it again resumes it. A sign-out, a lost connection, and a reload pause it the same way.

**Sends.**

- Every send goes through the connection client's `sendAs`, with the agent actor (`{ kind: "agent", agentId }`) and the identity's device ID. A new transition gets a new UUIDv7 event ID and the wall clock as `occurredAt` when it is sent; it carries no reason, repository, correlation ID, or causation ID.
- One transition at a time: the next one waits for the acknowledgement of the last one, the relayed `agent.run.state_changed` with the same event ID, the agent actor, the same run, and the same workspace, which the sending connection gets also when it is not subscribed (D4). The acknowledgement's payload is the run's state from then on, also before the agent activity applies the relayed event, for example while its reload holds events back; a run without one has the agent activity's state. Nothing is taken from what was sent.
- Without an acknowledgement within 10 seconds (`DEV_SWITCH_ACK_TIMEOUT_MS`), it sends the same event again, with the same event ID and time, once the guards hold; the server never applies a recorded (device, event ID) twice and relays it again (D4). Without an acknowledgement of that resend within another 10 seconds, it stops. A connection that the server closes for a refused message while a transition waits, which the client reports as `waiting` with `message_refused`, stops the switch instead: it is most likely that transition, for example 1008 `identity_mismatch` when the database names another host device than `MYMANDEV_DEV_AGENT_DEVICE`, and a resend would only be refused again, closing the connection a second time. Any other loss, such as `connection_lost`, keeps the one resend.
- It stops at the first `event.refused` of its event: `conflict` for a stale `previousState` or a disabled agent, `not_found` for an unknown run, and `rate_limited` (D5). It also stops when the client does not send (`not_connected`, `backpressure`, `too_large`, or `invalid`), and on close at quit (`will-quit`). It stays stopped until the application starts again.
- At least 2 seconds pass between two sends, resends included (`DEV_SWITCH_STEP_MS`), so at most 5 go out in any 10 seconds, against the account's 30 (D5). At most 900 go out in any hour (`DEV_SWITCH_HOURLY_SENDS`), half of the account's 1,800, so that the account's other devices keep room.
- **Logs.** Fixed text with a refusal code or a send outcome at most: what the switch waits for, that it moves the runs, that no unfinished run is left, a resend, and why it stopped. Never an ID or a name.

**Never.** The switch never creates or cancels a run, sends for another agent or from another device, sends in a packaged build or while a gate is not live, sends a second transition before the first one's acknowledgement, retries after a refusal, keeps anything across restarts, or adds a route to the API.

They cover the settings in a packaged build and with an unset, empty, or invalid variable, another device (also only in the socket's identity), a sign-out, another owner, no own person, a disabled agent, both gates, the walk of two runs and of runs that are already further on, the 2-second pace, the wait for each acknowledgement and relays that are none (another event, agent, run, workspace, or event type), the one resend with the same event and the stop after it, the stop without a resend after `message_refused` and the resend after `connection_lost`, a resend that waits for the hourly budget, the account status checks during a walk (a key that is not ready, no API origin, a device that is not signed in), a log that throws, the stop at each refusal and each refused send, the pause and the resume with the project, an acknowledgement while paused, the run states from the acknowledgements' payloads, the budget over more than an hour of sends against both limits, `close`, that no log holds an ID or a name and the file does not log with `console`, and that only `index.ts` imports the switch. The tests of the [workspace service](#workspaces) and of the [agent activity service](#agent-activity-service) also cover `ownMemberId` and `gateLive()`.

## Chat service

The chat service ([`src/main/chat/service.ts`](src/main/chat/service.ts); #27) holds the chat of the open project in the main process: the project's [chat timeline](#chat-timeline), its history read with the account service's [workspace reads](#account), its `chat.message.created` events, and the person's messages, sent with the connection client's `sendAs`, the only way to send an event. It follows the [workspace service](#workspaces): the selected workspace and its open project. [`index.ts`](src/main/index.ts) creates it after the workspace service and closes it at quit (`will-quit`). It has no IPC channel yet.

- **Key.** A chat belongs to the account, the device, the workspace, and the project. The account and the device come from the connection client's `identity()` after `auth.ok` for the signed-in device, and are kept while the connection is down, so that messages can wait under their key. Without a signed-in device or such an identity the service holds nothing.
- **History.** The newest page (`GET /projects/:projectId/messages`, 50 messages) loads when a project opens and after every `workspace.subscribed` of the selected workspace, through the service's own [resync gate](#workspace-resync): `begin("all")` on a change of the open project, `subscribed()` on `workspace.subscribed`, and `end()` on a lost connection, an unsubscription, or another workspace. The project's `chat.message.created` events that arrive meanwhile wait and apply after the page; other projects' events are not held. An answer of an earlier generation, or for another project, is dropped. A failed page is retried with the workspace service's backoff (`workspaceRetryDelayMs`: min(60 s, 2 s x 2^n), and 60 seconds after `rate_limited`), and an overflow of the gate reloads after the same backoff. `loadOlder()` reads the page before the lowest held `seq`; its answer is dropped when the gate's `generation()` or the project changed meanwhile.
- **Sending.** `send(text)` makes the body with `prepareMessageBody`, so the limits are the protocol's, and a new UUIDv7 event ID (`newId`). A body that the protocol refuses, and a message beyond 50 that have not been stored (`too_many_pending`), are refused and nothing is kept. A message goes out at once when no other waits before it and the workspace service's `gateLive` holds for its workspace; otherwise it waits in line. Each event is built inside `sendAs` from the connection's identity, and only when that identity is the chat's own; another one drops the chat's waiting messages instead.
- **Waiting messages** (the Project Manager's decisions of 2026-11-05 on #27). They wait in memory, marked as waiting for the connection, and are sent again automatically with the same event ID and the same `occurredAt` while `gateLive` holds, at most one per second (`CHAT_RESEND_INTERVAL_MS`). The waiting messages go out in the order the person wrote them: only the first waiting message is sent, and while it waits for its retry after `rate_limited`, the messages behind it, a new one included, wait for it. Two limits remain. A message that shows as not sent no longer holds the line, so after a later `retry` the server stores it after the messages that were behind it. A message that is being sent does not hold the line either: in a narrow case the server's limit is reached within one round trip, the first message is then refused with `rate_limited`, and the next one is stored first. Waiting for each message's answer before the next is sent would cost a round trip per message and need its own way out for a lost answer, so the service does not. A message that was sent waits again when the connection drops. After an overflow of the gate, a message that was being sent at the overflow, or that was sent while the gate stayed overflowed, waits again once the reload has answered, because its `chat.message.created` may have been dropped; one sent after the reload began is not sent twice. The server answers a repeated event ID with the stored message. The waiting messages and their key outlive a lost connection, also when the workspace service changes its state while offline. `chat.message.created` removes the copy whose event ID is its `causationId`.
- **Refusals.** `not_found` and `conflict` show the message as not sent at once. After `rate_limited` it is tried again 10 seconds later (`CHAT_RATE_LIMITED_RETRY_MS`), up to 3 times (`CHAT_RATE_LIMITED_RETRIES`), so it is sent 4 times in all; after the third retry's refusal it shows as not sent. A late `rate_limited` for a message that is not being sent changes nothing: one that shows as not sent stays so, and a second answer for a message that an overflow had sent twice does not count against its retries. Discarding the first waiting message lets the next one go at once. A message that the connection client refuses as `too_large` or `invalid` shows as not sent as `not_sendable`. `retry(eventId)` sends a message that shows as not sent again, with the same event ID and new retries, and `discard(eventId)` drops a message that waits or shows as not sent.
- **Drops.** The waiting messages are dropped without asking on a sign-out, on a change of the account or the device, when the membership ends (`workspace.unsubscribed` with `membership_ended`, `account.removed_from_workspace`, or `workspace.subscribe_refused`), and whenever the workspace service selects another workspace or closes the project by itself. They are lost when the application quits; nothing is written to disk.
- **Switching.** When messages have not been stored yet and the person opens another project or selects another workspace, the application asks first. `switchProject(projectId | null, { discardWaiting })` and `selectWorkspace(workspaceId, { discardWaiting })` answer `{ kind: "waiting", count }` and change nothing while messages wait and `discardWaiting` is false; otherwise they drop the messages and call the workspace service, and answer `switched`, or `refused` for a project or a workspace that it does not hold. The IPC and the screens must switch through these wrappers, never through the workspace service's `openProject` and `select`.
- **State.** `{ revision, status, problem?, workspaceId, projectId, messages, hasOlder, loadingOlder, olderProblem?, pending }`, frozen, with `onChange` listeners. `status` is `no_project`, `loading` until the newest page loaded, `ready`, or `unavailable` with the failure as `problem`; what was loaded before stays. `messages` are the timeline's, the oldest first, so the IPC can drop the oldest ones to fit its byte budget. `pending` holds `{ eventId, body, status }` with `waiting`, `sending`, or `not_sent` with a `reason`. `authorName(author)` gives a person's name from the workspace service (`Unknown person` when it does not hold the person) and `Unknown agent` (`UNKNOWN_AGENT_NAME`) for an agent.
- **Logs.** Fixed text with a failure code at most, never a name, an ID, or a message body.

Not in this part: IPC, the renderer's snapshot with its byte budget, and the screen (parts 14 and 15), agent names (#28), and unread markers (none in M2).

The tests ([`service.test.ts`](src/main/chat/service.test.ts)) use a fake account service with reads that the test answers, a fake connection client whose `sendAs` builds each event from the socket's identity and checks it with `decodeClientMessage`, a fake workspace service with `gateLive`, and injected timers and clocks, and build every page through the protocol's schema and every frame and event through `decodeServerMessage`. They cover the load when a project opens and not without a signed-in device and its identity, the reload after every `workspace.subscribed` with the events that wait for it, the dropped answers of an earlier generation and of another project, the backoff with 60 seconds after `rate_limited`, older pages and their late answers, a send with the connection's identity and its replacement through `causationId`, the body rules, the limit of 50, sends only while `gateLive` holds with the same event IDs at one per second, a new message behind waiting ones and behind a message that waits after `rate_limited`, also after a reconnect, `sending` back to `waiting` on a lost connection, waiting messages kept through workspace changes while offline, `not_found` and `conflict`, the 3 retries after `rate_limited`, a late `rate_limited` for a message that shows as not sent and a second one for a message that was sent twice, and `retry`, the client's refusals, `discard`, also of the first waiting message, the drops on sign-out, another device, another account, and the end of the membership, the messages kept after a requested unsubscription, a sign-in again on the same device while offline, an identity that is not the chat's own, both switch wrappers in both directions, also with messages that are being sent or show as not sent, the overflow with only the messages whose answer may be lost sent again, also after a failed reload, for a message sent while overflowed whose answer was dropped, and across a lost connection, the reload failures (a stale one, a failure after `ready`, and the backoff reset after a success), `authorName`, a listener that throws, `close`, and that no log holds a name, an ID, or a body and the file does not log with `console`.

The runtime status is `{ state, revision }` (`RuntimeStatusSchema`). `subscribeStatus(listener, onError)` delivers the current status and every later one, drops a status older than the last one delivered, and returns a function that ends the subscription.

The repository list is `{ revision, repositories }` (`RepositoryListSchema`); each repository is `{ mountId, name, path, watching, state }`, and its state is `loading`, `ready` with the branch, the change summary, and the remotes, or `unavailable` with a problem. The mount result is `mounted` with the mount ID, `cancelled`, or `refused` with a reason (`MountResultSchema`); the renderer turns reasons and problems into messages ([`src/renderer/repository-view.ts`](src/renderer/repository-view.ts)). `subscribe` works like `subscribeStatus`. `unmount` passes on only a string, and the main process accepts only a UUID.

The account status is `{ revision, account, signIn, lastOutcome, deviceKey, replacementPending, apiOrigin, device }` (`AccountStatusSchema`): the account is `signed_out` or `signed_in` with `login`, `displayName`, and `deviceId`; the sign-in is `idle`, `starting`, `waiting` with `pairingCode` and `opened`, and with `authorizeUrl`, `warning`, and `browser` (`default` when the default browser could not be opened, `other` when the person asked for the address) when `opened` is false, or `completing` after the browser's post; `lastOutcome` is null or `{ code, deviceLogin? }`; `deviceKey` is a key state; `apiOrigin` is `set`, `unset`, or `invalid`; `device` is a device state code (`DEVICE_STATES`). The start takes no argument, which opens the default browser, or the option `{ browser }` with `default` or `other` (`StartSignInOptionsSchema`), a strict object that refuses any other key and value; `startSignIn` passes on its own `{ browser: "other" }` only when the renderer asks for another browser, and nothing from the renderer (#175). The start result is `started`, `refused` with `busy`, `key_not_ready`, or `too_soon`, or `failed` with an outcome code; the unlock result is `unlocked`, `refused` with `not_required`, `busy`, `wrong_passphrase`, `passphrase_invalid`, or `too_soon`, or `failed`; the forget result is `forgotten` with `removedAtServer`, `cancelled` when the person kept the account in the native confirmation, `refused` with `busy` or `not_signed_in`, or `failed`. The sign-out result is `signed_out` or `pending`, the removal result `removed`, `pending`, or `cancelled`, and the device list result `listed` with at most 1,000 devices of `{ id, label, platform, lastSeenAt, signInExpiresAt, revokedAt, current }`; each of them can also be `refused` with `busy`, `not_signed_in`, or (the list) `too_soon`, or `failed` with a code of `DEVICE_ACTION_FAILURES`. `unlockDeviceKey` passes on only a string, and the main process accepts 1 to 4,096 UTF-16 code units; the key store checks the rest. See [Account](#account).

The connection status is `{ state, reason?, retryAt?, revision }` (`ConnectionStatusSchema`): `offline` with an optional `not_signed_in` or `no_api_origin`, `connecting`, `authenticating`, `connected`, `waiting` with a reason of `CONNECTION_WAITING_REASONS` and `retryAt`, or `stopped` with a reason of `CONNECTION_STOP_REASONS`. The reconnect result is `reconnecting`, or `refused` with `not_signed_in`, `update_required`, `already_open`, or `too_soon`. Neither holds a frame, a nonce, a signature, or a key. See [Connection](#connection).

The workspace state is `{ revision, status, problem?, workspaces, selectedWorkspaceId, projects, openProjectId }` (`WorkspaceViewSchema`): `status` is `signed_out`, `loading`, `ready`, or `unavailable` with a `problem` of `WORKSPACE_PROBLEMS`; `workspaces` holds `{ id, name }` and `projects` `{ id, name }`, at most 1,000 of each (the protocol's `MAX_ANSWER_LIST_ITEMS`, the most that one answer of the API holds) with names of at most 100 characters (`LIMITS.name`), as `WORKSPACE_LIMITS` sets. The main process builds a frozen copy of the service's state for it ([`src/main/workspace-ipc.ts`](src/main/workspace-ipc.ts)): it sends no more than the limits and cuts a longer name, and a project's `createdByMemberId` stays in the main process, because no screen needs a member ID. The action result is `ok`, or `refused` with a reason of `WORKSPACE_ACTION_REFUSALS`: `not_found` for a workspace that the list does not hold, a project that the selected workspace does not hold, an ID that the protocol refuses, or no signed-in device, and `too_soon` for a switch to another workspace beyond the budget. The budget, like the reconnect's, counts accepted switches: at most 20 (`WORKSPACE_SWITCH_BUDGET`) within 60 seconds (`WORKSPACE_SWITCH_WINDOW_MS`), because each switch sends an unsubscribe and a subscribe frame and each subscription makes two reads of the API; it has no cooldown, so a person can click through a few workspaces quickly, and selecting the selected workspace or a refused select is not counted. `select` takes exactly one ID and `openProject` exactly one ID or null; an ID crosses as a lowercase UUIDv7 (`ProtocolIdSchema`, defined in the contract, which does not import the protocol package), and the contract refuses any other value, another UUID version, a longer string, a missing or an extra argument before the service is asked. The main process then checks the ID with the protocol's `WorkspaceIdSchema` or `ProjectIdSchema` as well. Both bridge functions pass on only a string (or null to close a project). The two actions, with the ID checks and the budget, sit in one place (`createWorkspaceActions`), so that the chat service can later route them through its own wrappers, which ask the person before a switch while chat messages wait to be sent, and keep the checks and the budget. The renderer shows that question at its one switch point ([Screens](#screens)). The main process closes the open project itself when the page that may have opened it is gone: a new document commits in the main frame (`did-navigate`, also on a reload), a load of the main frame fails other than with `ERR_ABORTED` (`did-fail-load` with `isMainFrame` and an `errorCode` other than -3), the render process is gone (`render-process-gone`), or the window closes (`closed`); the workspace selection stays. The start of a load alone (`did-start-loading`) changes nothing, because a dropped file, a blocked link, or a blocked download starts a navigation that is then cancelled while the page stays; such a cancelled navigation fails with -3, if at all. See [Workspaces](#workspaces).

The agent activity is `{ revision, status, problem?, workspaceId, projectId, agents, unfinishedRuns, moreUnfinishedRuns, finishedRuns }` (`AgentActivityViewSchema`): `status` is `no_project`, `loading`, `ready`, or `unavailable` with a problem of `AGENT_ACTIVITY_PROBLEMS`; each agent is `{ id, name, ownerName, disabledAt }`, and each run `{ id, agentId, state, reason, createdAt, finishedAt }` with a state of `AGENT_RUN_STATES`. The main process resolves each owner's display name with the workspace service's `memberName` (`Unknown person` for a person that the selected workspace does not hold), so no member ID crosses, and neither does a device ID, a run's project, or its repository. IDs are lowercase UUIDv7s (`ProtocolIdSchema`, decided on 2026-11-05). The main process sends at most 1,000 agents, the 200 newest unfinished runs (the model holds them the most recently created first) with the number of older ones that it leaves out as `moreUnfinishedRuns`, and the 50 most recently finished runs, and cuts an agent's name and an owner's name to 64 characters and a reason to 500 (`AGENT_LIMITS`); the view is a frozen copy. Both channels are read-only and take no argument. A change of the agent service, and a change of the workspace service, which reports a person's new name, raise the revision at once; the latest view then goes out once after 50 ms (`AGENT_PUBLISH_INTERVAL_MS`), so a burst sends one view with its last state, and the waiting publish is cancelled at quit. `subscribeState` works like `subscribeStatus`. See [Agent activity service](#agent-activity-service). The tests ([`agent-ipc.test.ts`](src/main/agent-ipc.test.ts), and the agent tests in [`ipc-contract.test.ts`](src/shared/ipc-contract.test.ts) and [`bridge.test.ts`](src/preload/bridge.test.ts)) use fake services and an injected timer. They cover the sender and argument check, the names (also of an unknown person), that no member ID, device ID, or repository ID crosses, the trim with its count and order, the cuts, the frozen copy, one publish for a burst with the last state, a publish after a new name, `close`, a view that the contract refuses, the closed lists and limits against the service and the protocol, the schema's limits, and the bridge's members.

- [`src/shared/ipc-channels.ts`](src/shared/ipc-channels.ts) names the channels. It imports nothing, so the preload script uses the names without bundling zod.
- [`src/shared/sign-in-timing.ts`](src/shared/sign-in-timing.ts) holds the sign-in start cooldown, which the main process enforces and the account panel's delay for "Use another browser" follows. It imports nothing, so the renderer may import its values, like `src/shared/product.ts`.
- [`src/shared/ipc-contract.ts`](src/shared/ipc-contract.ts) holds a zod schema for the arguments and the result of every invoke channel (`INVOKE_CONTRACT`) and for the payload of every event channel (`EVENT_CONTRACT`), and the types derived from them. The preload script and the renderer import only the types, so zod is bundled into the main process alone, and the renderer needs no `jitless` setting ([ADR 0003](../../docs/architecture/decisions/0003-zod-runtime-validation.md)).
- [`src/main/ipc.ts`](src/main/ipc.ts) registers the handlers. Each handler first checks the sender: the main frame, not a subframe, still attached, at the URL the window loaded, by the rules of the navigation guard (`isAppNavigation`): in a build only `app://renderer/index.html`, during development the development server's origin ([ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md)). It then validates the arguments against the contract, and parses its result with the contract, so unknown keys never reach the renderer. A refused call rejects in the renderer with a message that names the channel and the reason, never the arguments. Events go only to frames that subscribed and still show the application.
- [`src/preload/bridge.ts`](src/preload/bridge.ts) builds the frozen `window.desktop` object. Its functions call fixed channels and pass no argument from the renderer on, except four that take one string each, which the main process validates: the mount ID of `repositories.unmount`, the passphrase of `account.unlockDeviceKey`, the workspace ID of `workspaces.select`, and the project ID of `workspaces.openProject`, which also takes null to close the project. A value of another type is refused in the preload script without a call, and extra arguments are not passed on. `account.startSignIn` passes on a fixed option of its own when the renderer asks for another browser. The functions never hand the IPC event object, which holds `ipcRenderer`, to the renderer.

To add a channel:

1. Add its name to `INVOKE_CHANNELS` or `EVENT_CHANNELS` in `ipc-channels.ts`, with a `domain:action` name.
2. Add its schemas to `INVOKE_CONTRACT` or `EVENT_CONTRACT` in `ipc-contract.ts`. Every string and array has a maximum length, and objects use `z.object`, which strips unknown keys (ADR 0003). Never send a secret: the device key, tokens, and sign-in codes stay in the main process (ADR 0014).
3. Register an invoke handler with `createInvokeHandler` in `src/main/ipc.ts` (the implementation may return a promise), or send an event through `createEventPublisher`, which checks its receivers.
4. Add a function for it to `DesktopBridge` in `src/shared/desktop-bridge.ts` and to `createDesktopBridge`. Never expose `ipcRenderer`, a channel name parameter, or a generic `invoke` or `send`.
5. Add tests: the schemas accept and refuse, the handler refuses a foreign sender and invalid arguments, and the bridge keeps its exact shape (`ipc-contract.test.ts`, `ipc.test.ts`, `bridge.test.ts`).

## Security settings

- Every window runs its renderer sandboxed and with context isolation, without Node.js integration (also in workers and subframes), with web security on, and without webviews ([`src/main/window.ts`](src/main/window.ts)). Tests lock these values.
- Developer tools are available only when the application is not packaged.
- Every web contents gets the same guards ([`src/main/guards.ts`](src/main/guards.ts)): `window.open` is denied; a navigation (`will-navigate`, `will-frame-navigate`) or redirect (`will-redirect`) of any frame to a URL outside the application is prevented ([`src/main/navigation.ts`](src/main/navigation.ts)). With the built files, only `app://renderer/index.html` itself is navigable, not other `app://` paths; with the development server, any URL on its origin; attaching a webview is prevented; and Bluetooth device selection is cancelled.
- Every session, the default session and every session created later (`session-created`), gets the session guards once ([`src/main/guards.ts`](src/main/guards.ts)): permission requests are answered with false, permission checks (for example `Notification.permission`) and device permission checks return false, HID, serial, and USB device selection is cancelled, and every download is prevented.
- The main process sets the [data folder](#local-data) and then takes the single-instance lock in it, before anything else ([ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md)). A second start brings the existing window to the front.
- A built application loads its renderer from `app://renderer/`, a custom scheme registered as standard and secure before the application is ready, not from a `file:` URL ([`src/main/app-protocol.ts`](src/main/app-protocol.ts)). The scheme serves only files inside `out/renderer/`. It answers methods other than GET and HEAD with 405. It answers 404 for another host, credentials, a port, invalid percent-encoding, and a path segment that after decoding is empty, ends with a dot or a space (so also `.`, `..`, and `...`), is a Windows device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1` to `COM9`, `LPT1` to `LPT9`, with or without an extension, in any case), or contains `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`, or a control character. It also answers 404 for a missing file or a directory, and for a path whose real path, after symbolic links, is outside the real path of `out/renderer/`. Every response, errors included, carries the production Content Security Policy as a header and `X-Content-Type-Options: nosniff`; files also get their Content-Type.
- A packaged application always loads its built files. `ELECTRON_RENDERER_URL`, which electron-vite sets during development, is used only when the application is not packaged, and only for an http URL on `localhost`, `127.0.0.1`, or `[::1]`.
- The renderer reaches the main process only through `window.desktop`, which holds the Electron version, the runtime functions, the repository functions, the account functions, and the connection functions of the [IPC contract](#ipc-contract) ([`src/shared/desktop-bridge.ts`](src/shared/desktop-bridge.ts)). The main process checks the sender and the arguments of every IPC call.
- The device key stays in the main process, in a file outside the roaming profile that the system or a passphrase protects; only on Linux, after a warning and an explicit choice, can it be unprotected ([Device key](#device-key)). No IPC channel carries it, a sign-in code, a verifier, a signature, or a token, and the store never logs. The passphrase is the only secret that crosses IPC, from the renderer to the main process ([Account](#account)).
- The renderer has no file system access. It never sends a path: folders come from the main process's dialog, and Git runs in the main process with read-only commands, no shell, and no configured program ([Repositories](#repositories)).
- The Content Security Policy is defined once, in [`src/shared/content-security-policy.ts`](src/shared/content-security-policy.ts). It allows scripts, styles, images, and fonts only from the page's own origin, which in a build is `app://renderer` and serves only the built renderer files, and no network connection: no inline code, no `eval`, and no remote origin. The main process sends it as a header with every `app://` response, and [`config/csp.ts`](config/csp.ts) writes it into the meta element of [`src/renderer/index.html`](src/renderer/index.html), whose own value, `default-src 'none'`, blocks everything if that step is missing. During `npm run dev`, the plugin adds what the development server needs: a nonce for the inline scripts and styles it injects (the React Refresh preamble and reloaded styles), new for each start, and `connect-src 'self'` for its hot reload WebSocket.

## Tests

Vitest runs the tests in the Node.js environment, without DOM emulation. They cover the data folder (its name, the folder on Windows, macOS, and Linux, that it is created and set before the single-instance lock is taken in it, once on the real file system with a temporary directory, and that the entry point claims it before it uses `app` for anything else), the window options, the renderer URL and the navigation rules, the guards (with fake web contents and a fake session, so that a guard that allows or is missing fails a test), the path resolution and the handler of the `app://` scheme (with a fake file system, and once on the real file system with a temporary directory and a directory link that leads out of it), the screen state (every screen and side panel is reachable, invalid transitions are refused, and replaced projects keep the shown view or show the home screen when its project is gone), the markup of every screen with its landmarks, its placeholder content, and the marked navigation item, the text of every workspace state, the marked workspace, the one status paragraph with a problem and a switch text, a refused switch, no switch text while `signed_out`, and names as text, and the runtime status indicator (rendered with `react-dom/server`), the action that every navigation item and tab sends when it is clicked, the switch of every workspace item, and the keys of the tab list (the navigation components are called as functions with a fake `dispatch`), the workspace controller with a fake bridge ([`workspace-view.test.ts`](src/renderer/workspace-view.test.ts): every state replaces the projects, a refused subscription, the end of the subscription, the open project reported at the start and on each change, closed on `not_found`, and kept on a failed call, a refused null, a stale answer, or after the end, the switch text cleared first and then set, only by the latest switch, and cleared by a newer state, and the answer of every switch); `useWorkspaces` itself, its effects and their dependencies, needs a DOM to be tested, the renderer's imports (no Node.js, Electron, or network module, no file outside the renderer and the shared code, and only types from the shared code, except the product name) and its source (no network or Node.js API), the stylesheet (nothing loaded from another origin, colors only in tokens, the same dark tokens for both theme switches), the Content Security Policy, the IPC schemas, the sender check and the handlers, the preload bridge, the runtime lifecycle with its quit handling, and the repositories: the porcelain v2 parser (renames and copies, untracked and ignored paths, conflicts, a detached HEAD, a branch without commits, ahead and behind, paths with spaces, non-ASCII characters, and line breaks, and malformed records), the remote parser and the removal of credentials, the filter driver overrides, the environment and the lookup of Git (also with Windows paths through `path.win32`), the runner with a fake `execFile` (the arguments, no shell, the environment, the timeout and output limit, the failures, and a refused folder that is not a repository), the inspector with a fake runner, the watcher with a fake `fs.watch` (the Git directory filter, also with Windows separators, a linked worktree, the fallback without recursion, close, and errors), the service with fake timers (debouncing, no parallel status, unmount, limits, duplicates, and close), the repository IPC handlers (foreign senders, invalid arguments, the dialog, and busy), and the repository panel. A test with the real `git` builds a temporary repository with a staged rename, a staged and an unstaged change, an untracked file, a remote URL with a token, and programs that would leave marker files: a filter driver, one with an empty name, one from an `include` and one from an `includeIf` file, and a file system monitor from an included file. It checks that the inspection reads the expected state, leaves every file and folder unchanged (content, size, modification time, and inode, so a lock file that was created and deleted again shows too), and runs none of the programs, while a plain `git status` runs all of them. A partial clone with an SSH remote whose SSH command leaves a marker and with the object of HEAD missing shows that neither the inspection nor its environment without `GIT_NO_LAZY_FETCH` (as on Git before 2.44) fetches or writes anything, while a plain `git status` runs the SSH command. The partial clone also sets `protocol.ssh.allow=always`, and the inspection's command-line options alone, without either environment variable, still allow no transport. The test also covers a subfolder, a plain folder, the Git directory, a bare repository, and a linked worktree. The device key tests use temporary folders and a fake `safeStorage` with the asynchronous API only, which encrypts with a key of its own. They cover the atomic write (a failure at each step, also after half of the data was written, keeps the old file and leaves no temporary file; an existing file at the temporary name, and on Linux and macOS a symbolic link there, makes the write fail without touching it or the target; every rename is flushed, on Windows by opening the renamed file again), that a key file holds only the encrypted PKCS#8 key (neither the key in the clear nor the public key, in any encoding), the decryption once at startup and the rewrite after `shouldReEncrypt`, the passphrase format (a round trip, a wrong passphrase, a changed file, the normalization, a lone surrogate, and the default scrypt cost), every refused key file, the system protection on each platform and each Linux backend, the Linux probe and key writes whose ciphertext starts with `v10`, that Windows and macOS refuse a passphrase or an unprotected key and a key file planted with one, the explicit choice of an unprotected key and its renewal only with a fresh choice, the move up to the system on Linux, mode 0600 on Linux and macOS (skipped on Windows), the Windows folder through an injected environment and platform, signatures that verify with `node:crypto` for every input `deviceAuthInput` builds, the replacement that keeps the previous key until it is confirmed or abandoned, also across a restart, a stop between its two steps, and a failed write, `delete`, and that no file of the store names the synchronous `safeStorage` API or `console`, and no file of the renderer, the preload script, or the shared code reaches the store.
