# @mymandev/api

The cloud API: a Fastify application with a health endpoint, GitHub sign-in, device keys and access tokens, workspaces, GitHub's revocation webhook, and a WebSocket gateway that authenticates each connection with its device key, validates protocol events from [`@mymandev/protocol`](../../packages/protocol/README.md), and delivers workspace events and presence to the connections subscribed to a workspace. The decisions behind it are recorded in [ADR 0009](../../docs/architecture/decisions/0009-fastify-cloud-api.md), [ADR 0010](../../docs/architecture/decisions/0010-api-configuration-and-runtime.md), and [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md).

## Start locally

From the repository root, after `npm ci`:

```sh
npm run start -w @mymandev/api
```

The API listens on `http://127.0.0.1:3000` and writes JSON log lines to standard output. Check it with:

```sh
curl http://127.0.0.1:3000/health
```

Stop it with Ctrl+C. The API logs "shutting down", closes every WebSocket connection with code 1001, and exits with code 0. On Windows, SIGTERM is never delivered; Ctrl+C sends SIGINT, which runs the same shutdown. When npm runs through `npm.cmd` on Windows, `cmd.exe` may then ask "Terminate batch job (Y/N)?"; the API has already stopped at that point.

For development, `npm run dev -w @mymandev/api` restarts the API when a source file changes, including a file in `packages/protocol`, and reads `apps/api/.env` if it exists. On Windows, a restart by `--watch` stops the process without running the shutdown handler; on Linux and macOS, `--watch` sends SIGTERM, which runs it.

Node.js runs the TypeScript source directly. There is no build step.

Loopback only; widening it is part of the hosting decision (#96).                                                                                                                                                                                                                                           |
| `API_PORT`                           | `3000`        | A decimal integer from 0 to 65535, without sign, leading zero, or spaces.                                                                                                                                                                                                                                                                       |

With `NODE_ENV=production`, they and `DATABASE_URL` are required, and `DATABASE_URL` needs `sslmode=verify-full`; `API_GITHUB_WEBHOOK_SECRET_PREVIOUS` stays optional. In development and test the API also starts without them and logs a warning that GitHub sign-in, the webhook, or the database is disabled. The configuration keeps the client secret, the webhook secrets, and the database URL in an object that prints `[redacted]` in logs, JSON, and inspection.

## Endpoints

### `GET /health`

Returns `200` with `{"status":"ok","version":"<version>"}`, where the version is the `version` field of `apps/api/package.json`.

Errors use one body shape, `{"statusCode":<code>,"error":"<status text>","message":"<message>","code":"<code>"}`, where `code` is one of `API_ERROR_CODES` of [`@mymandev/protocol`](../../packages/protocol/README.md) (ADR 0014, P-66). A route raises a typed `ApiError` with a code; the answer then has the code's fixed status and the status text as the message. Every other error gets a generic code for its status (`genericApiErrorCode`). A server error (5xx) always has the generic message "Internal Server Error". A client error keeps the message only when Fastify produced it, for example a validation error or `413` for a body over `API_BODY_LIMIT_BYTES`. An unknown route gets `404` with the message "Not Found" and the code `not_found`, and does not echo the method or the path. A malformed URL, an over-long path parameter (`414`), a malformed request line, headers over the limit (`431`), a request timeout (`408`), and a request that arrives while the API closes (`503`) get the status text as the message and a generic code too. A message is at most 100 characters. GET routes get no automatic HEAD route, so a rate limit counts every request against one budget.

A route with a rate limit answers `429` with `rate_limited` and `Retry-After` when it is reached (`@fastify/rate-limit`, in-memory store, one instance). Routes that take a body validate it with the zod schema of `@mymandev/protocol` through `zodValidatorCompiler` (`src/validation.ts`), registered in their plugin scope: unknown keys are stripped, and a failure answers `400` with `bad_request` and a message that names the part, the path, and the issue, never an input value.

### Sign-in with GitHub

These routes exist only when GitHub sign-in is configured; otherwise they answer the generic `404`. They implement steps 2 to 5 of ADR 0014, "Sign-in". The API keeps every attempt, its PKCE verifier for GitHub, and the sign-in codes only in memory, and the codes and the cookie only as SHA-256 hashes. A timer drops expired entries every 15 seconds, and a restart drops them all. Every GitHub call refuses redirects, and a token in a failed exchange answer is deleted at once.

- `GET /auth/github/authorize`, opened by the desktop in the system browser with `code_challenge`, `code_challenge_method=S256`, `redirect_uri` (`http://127.0.0.1:<port>/callback`, ports 1024 to 65535), `state`, and optionally `login` and `prompt=select_account`. A malformed or repeated parameter gets an error page and never a redirect. Otherwise it starts an attempt that lives 10 minutes (at most 1,000 open attempts), sets the attempt cookie, and redirects to GitHub with the API's own state and PKCE pair. With an `https` origin the cookie is `__Host-mmd_signin` with `Secure`, `HttpOnly`, `SameSite=Lax`, and `Path=/`; with an `http` origin, which only development and test allow, it is `mmd_signin` without `Secure` (#99).
- `GET /auth/github/callback`, GitHub's redirect. It needs the cookie of the attempt that the state names and runs once. A request that names a live attempt without its cookie ends that attempt, so GitHub's code from another browser is never exchanged (the phishing scenario of ADR 0014, "Threats"). It exchanges the code with a form-encoded body and never retries; a token answer with an `error` field fails whatever its status. It reads `GET /user`, then deletes the user token at once and keeps no GitHub token. The attempt keeps the account and the time at which the API started the code exchange, the earliest moment at which GitHub can confirm the account, and the sign-in code carries both. It shows the confirmation page with the GitHub login and the pairing code.
- `POST /auth/github/confirm`, the form of the confirmation page, with `state` and `decision` (`continue` or `cancel`). It accepts only a form body and needs the attempt's cookie. It refuses a request whose `Sec-Fetch-Site` header is present and not `same-origin`; without that header, the `SameSite=Lax` cookie keeps a cross-site form from carrying the attempt. Continue creates a sign-in code (`mmdc_`, single use, 60 seconds) and answers with a page that posts `code` and `state` to the desktop's listener, by a script and a visible button. The code never appears in a URL.

- `POST /auth/sign-in`, sent by the desktop with the sign-in code, its PKCE verifier, `redirect_uri`, and the device registration (`SignInRequestSchema`). It needs the database too. It takes the code once, also when a later check fails, and answers `401` with `auth_failed` for an unknown, used, or expired code, a verifier whose S256 hash is not the bound challenge, another `redirect_uri`, or a signature that does not verify. A new device signs the `sign-in` input with its new key; an existing device signs it with its current key and with the new key. In one transaction the API then finds the account by GitHub's numeric ID, never by login, and refreshes the login, or creates the account with the GitHub name as its first display name, or the login when the name is not usable. It registers the device or replaces its key, keeping the device ID and clearing a sign-out, and revokes a named previous device of the same account as `replaced`. It refuses a disabled account (`auth_failed`), a GitHub identity whose revocation GitHub reported after the API read it (`sign_in_required`, below), a device of another account (`device_account_mismatch`), a revoked device (`device_revoked`), a new device while the registration lock is active (`device_registration_locked`), and more than 20 active or 10 new devices in 24 hours (`rate_limited`). It writes audit records for the sign-in and for the registration or key replacement, and answers with the user ID, the device ID, the display name, the login, and the sign-in expiry, 30 days later, without any credential. After the commit, the device's open connection, which used the replaced key, closes with `key_replaced`, and a replaced previous device's connection with `device_revoked`; the account's other connections get `account.device_registered` for a new device and `account.device_revoked` for the replaced one (see `GET /ws`).

A sign-in rests on the GitHub identity that the API read at GitHub's callback, but a device's last sign-in is the time of `POST /auth/sign-in`, up to 10 minutes for the attempt and 60 seconds for the code later. A revocation that GitHub reports in between (see `POST /auth/github/webhook`) would therefore not reach the device that this sign-in registers (#115). `POST /auth/sign-in` answers `401` with `sign_in_required` when a revocation of the identity was recorded later than the time that the code carries. Later means strictly later, as when the device state compares `sign_in_required_at` with a device's last sign-in: a revocation recorded at the same moment does not count. Two records are checked:

- The webhook keeps every verified revocation in a list in API memory, by GitHub's numeric ID, before its transaction starts, also for a sender without an account. An entry lives 13 minutes: an attempt and its code, and 2 minutes of margin for the check after the commit (below). The list holds at most 10,000 IDs and drops the oldest beyond that, a timer drops expired entries every 15 seconds, and a restart drops them all, as it drops the attempts. Nothing about a person without an account is stored in the database. `POST /auth/sign-in` checks the list before its transaction, so a first sign-in whose identity was read before the revocation creates no account.
- In the transaction that registers the device, the API reads `users.sign_in_required_at` under the account's row lock (`FOR NO KEY UPDATE`), which a revocation takes too. A revocation that committed first is seen there; one that waits for the sign-in then sets `sign_in_required_at` past the last sign-in of the device that the sign-in registered, so that device must sign in again. Which of the two requests took the earlier time before its transaction does not matter.

Both checks come before the device checks: a sign-in whose identity is too old answers `sign_in_required` also for a revoked device or a device of another account, and the next sign-in gets the device's own answer. A refused sign-in registers no device, replaces no key, and changes nothing in the database; the desktop starts a new sign-in.

After its commit, the sign-in checks the list again. A revocation that the webhook recorded while the transaction ran may have been missed by the webhook's own lookup, as for an account that this sign-in created, so the API then sets the account's `sign_in_required_at` as a revocation does, without an audit record (`requireSignIn` of `@mymandev/database`). The device is registered and its key replaced by then, so the answer stays `200` with the device, and the device's next authentication answers `sign_in_required`. Every order of the two requests is covered: a revocation recorded in memory before the first check refuses the sign-in, one recorded before the second check is marked there, and one recorded after it starts its transaction after the commit, so its lookup finds the account.

The opposite case is accepted: GitHub delivers the webhook about a minute after the revocation, and the delivery carries no time (#67), so a real new sign-in within that minute is required again when the delivery arrives. Another sign-in recovers from it. A replayed copy of a signed revocation, the risk accepted for #90 (see `POST /auth/github/webhook`), now also refuses the first sign-ins of that GitHub account that are in progress, for up to those 13 minutes; the remedy stays a new webhook secret. The list in memory, the lock, and the rule of the revocation are a decision for #115, applied on 2026-11-01 under the Project Manager's rule to apply the recommended option.

When an attempt ends without a code, the page posts `error` and `state` to the listener instead: `access_denied` (declined on GitHub or Cancel), `sign_in_failed` (GitHub did not confirm the code or the account), `unsupported_account` (a login outside the login rule), or `sign_in_unavailable` (GitHub's limit, with `Retry-After`). A request without a valid attempt gets an error page and posts nothing.

The pages load nothing from outside and send `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and a Content Security Policy with `default-src 'none'`, a hash for the one style and the one script, `frame-ancestors 'none'`, and a `form-action` that allows only the API itself or this attempt's listener. Each route allows 30 requests per address in 10 minutes. The API logs a warning above 1,500 token exchanges in an hour, below GitHub's limit of 2,000. No code, state, cookie, token, verifier, or GitHub response body is logged.

### Access tokens and devices

These routes need GitHub sign-in and the database (ADR 0014, "Device key and authentication" and "Revocation, sign-out, and recovery"). Challenges and access tokens live only in API memory, the tokens as SHA-256 hashes; a restart drops them, and the desktop fetches a new token.

- `POST /auth/challenge` returns a challenge ID and a nonce. The challenge is single use and valid for 60 seconds; at most 1,000 are open (`429` with `rate_limited` and `Retry-After`).
- `POST /auth/access-token` takes the device ID, the challenge ID, and a signature over the `http` input. The signature is checked first with the device's current key; an unknown device, a used or expired challenge, or a bad signature answers `auth_failed`. Only then does the device answer: `device_revoked`, `sign_in_required` (signed out, last sign-in 30 days ago or more, or a GitHub revocation after the last sign-in), or `auth_failed` for a disabled account. It returns an access token (`mmda_`, 15 minutes, never extended). A device may mint 30 tokens in 15 minutes and keeps at most 3 live tokens; a fourth ends the oldest. A token belongs to the device's sign-in: a new sign-in, which also replaces the key, ends the earlier tokens. Both routes answer with `Cache-Control: no-store`.
- Every other route below needs `Authorization: Bearer <access token>`, and so do the workspace routes. `src/auth/authenticate.ts` checks the token and the account's limit of 300 authenticated requests a minute, which counts every authenticated route together, when the headers arrive. The token, the device, and the account are checked again after the body arrived and before it is validated, so that a slow body cannot carry a request past a revocation; sign-out, revocation, lifting the lock, creating a workspace, changing its limit of unclaimed people, the people and invitation routes, and accepting an invitation check them a third time inside their transaction (`lockActor`). Every failure is `401` with `unauthorized`.
- `POST /auth/sign-out` signs the current device out: the device, its agents, and their grants stay, its tokens stop working, its WebSocket connection closes with `sign_in_required` after the commit, and the next token needs a GitHub sign-in (P-65).
- `GET /devices` lists the account's own devices, newest first, with the sign-in expiry and the current device.
- `POST /devices/:deviceId/revoke` with `reason` `removed` or `lost` revokes one of the account's own devices in one transaction: its agents are disabled, their grants revoked, and their unfinished runs cancelled (`revokeDevice`). After the commit, the device's WebSocket connection closes with `device_revoked`, the account's other connections get `account.device_revoked`, and each cancelled run reaches the connections subscribed to its workspace as `agent.run.state_changed` (see "Workspace subscriptions, presence, and delivery"). Another account's device answers `404` with `not_found`, also for the owner of a shared workspace; a revoked device answers `409` with `conflict`. `lost` also refuses new device registrations for 7 days; the current device cannot report itself `lost` (`409` with `conflict`), so that whoever holds it cannot lock the account's new devices.
- `POST /account/registration-lock/lift` lifts that lock from an active device.

Sign-out, revocations, and the lock write audit records. No `Authorization` header, token, nonce, or signature is logged.

The operator command (`db:account`) runs outside the API and cannot drop tokens from its memory: after disabling and enabling an account within 15 minutes, a token minted before the disable works again until it expires. Erasing an account (`db:account -- erase`, #93) revokes its devices, so its tokens stop working at once and its connections close at the next sweep; the API sends no membership or run events for an erasure, and the other members see it when they next load the workspace ([`@mymandev/database`](../../packages/database/README.md#operator-commands)).

### Workspaces

These routes need GitHub sign-in, the database, and an access token, like the device routes (ADR 0014, "People and roles", "Limits", and "What a workspace ID allows"; #91). Their bodies and answers are the schemas of `MEMBERSHIP_ROUTES` in [`@mymandev/protocol`](../../packages/protocol/README.md).

- `GET /workspaces` lists the workspaces that the account is an active member of, each with the account's own person, the most recently claimed first, at most 1,000 (`listWorkspaces`).
- `POST /workspaces` with `name`, `displayName`, and an optional `maxUnclaimedMembers` from 1 to 500 creates a workspace with the creator's person as its claimed `owner`, named `displayName`, and answers `200` with both. The workspace holds at most `maxUnclaimedMembers` active unclaimed people, 500 when it is omitted (Project Manager decision of 2026-11-02); a value outside 1 to 500 answers `400` with `bad_request`. `workspaces.created_by_user_id` stays a historical fact; ownership lives in the role. One transaction checks the account and the device again (`lockActor`), then `createWorkspace` locks the account, counts the workspaces it created in the last 24 hours, and refuses an 11th with `429`, `rate_limited`, and `Retry-After`: the seconds until the oldest of them is 24 hours old. It writes a `workspace.created` audit record. It sends no workspace event: the protocol has none for it, and the creator is the only member.
- `GET /workspaces/:workspaceId` answers with the workspace, all its people, the time join requests were paused, the limit of active unclaimed people as `maxUnclaimedMembers`, and the ownership offer unless it is 7 days old (`workspaceView`). Each person has its display name and role and, once claimed, the account's GitHub login with the time it was last verified, which is the account's last GitHub sign-in. Removed people stay in the list with `removedAt`, so that the desktop shows them as former members. The list holds at most 1,000 people: the owner, the target of the offer, the other claimed active people, then the unclaimed people, each the most recently created first, then the former members, the most recently removed first. So unclaimed people never push a claimed member out of the view, and with at most 500 of them they fill at most half of it.
- `POST /workspaces/:workspaceId/unclaimed-member-limit` with `maxUnclaimedMembers` from 1 to 500 changes how many active unclaimed people the workspace may hold and answers `204` (`setUnclaimedMemberLimit`; Project Manager decision of 2026-11-02). One transaction checks the account and the device again (`lockActor`), locks the caller's person, then the workspace row, and counts the active unclaimed people, people without an account who are not removed. Only the owner: an admin or a member gets `403` with `forbidden`, as on the other owner-only routes. A value below that count answers `409` with `conflict`, and a value outside 1 to 500 `400` with `bad_request`. It writes a `workspace.unclaimed_member_limit_changed` audit record without the value; sending the limit in force again answers `204` and writes nothing. No workspace event reports a change, because the protocol has none; the members read it from the workspace view.
- Every route under `/workspaces/:workspaceId` checks active membership first (`src/workspaces/access.ts`), right after the access token and before the path, the query, and the body are validated. An account without an active person in the workspace gets `404` with `not_found`, byte for byte the answer for a workspace that does not exist or a malformed workspace ID, whatever else the request holds.

The people routes (`src/workspaces/people-routes.ts`; ADR 0014, "People and roles" and "Removal and ownership") run each change in one transaction that checks the account and the device again (`lockActor`) and then locks the people it decides on, the caller's own person included, so that a caller removed or a person changed in the meantime is seen. A display name has 1 to 64 characters under the text rule of ADR 0005. A `role` in a body is stripped, as the protocol schemas strip every unknown field: an unclaimed person is always a `member`. For an active member, a body that breaks the protocol and a malformed person ID answer `400` with `bad_request`, and a person ID that the workspace does not have answers `404` with `not_found`; a non-member gets the membership check's `404` before any of them.

- `POST /workspaces/:workspaceId/members` with `displayName` defines an unclaimed person with the role `member` and answers `200` with it (`defineMember`). The owner and admins only; a member gets `403` with `forbidden`. After the caller's person it locks the workspace row and counts the active unclaimed people, so that concurrent definitions and a change of the limit are counted one after another; a workspace that already holds as many as its limit answers `429` with `rate_limited` and `Retry-After: 86400`, defines nobody, and sends no event. That is the code of every other limit of ADR 0014, also of those that count items, such as the 50 live invitations; no time frees a place, only removing or claiming an unclaimed person or a higher limit, so `Retry-After` is one day, as for the limit of 20 active devices. It writes a `member.defined` audit record and sends `workspace.member.defined`.
- `POST /workspaces/:workspaceId/members/:memberId/rename` with `displayName` renames a person and answers `204` (`renameMember`). Every member renames their own person, and the owner or an admin renames an unclaimed person; another claimed person answers `403` with `forbidden`, for the owner too, and so does an unclaimed person for a member. A removed person answers `409` with `conflict`. It writes a `member.renamed` audit record and sends `workspace.member.renamed`.
- `POST /workspaces/:workspaceId/members/:memberId/remove` removes a person and answers `204` (`removeMember`; ADR 0014, "Removal and ownership"). The owner removes any person except the owner; an admin removes unclaimed people and claimed people with the role `member`. Everything else answers `403` with `forbidden`: a member's removal, an admin's removal of the owner or of another admin, and anyone's removal of their own person, who leaves instead. A removed person answers `409` with `conflict`. It writes a `member.removed` audit record.
- `POST /workspaces/:workspaceId/leave` lets the caller's own person leave and answers `204` (`leaveWorkspace`). An admin or a member leaves; the owner gets `403` with `forbidden` and transfers ownership first. It writes a `member.left` audit record, and the leaving account is the remover.
- `POST /workspaces/:workspaceId/members/:memberId/promote` makes an active, claimed `member` an `admin` and answers `204` (`promoteMember`). Only the owner, from a device registered more than 72 hours earlier (`devices.created_at`); a device that is not older than 72 hours answers `403` with `device_too_new`. It writes a `member.promoted` audit record and sends `workspace.member.role_changed` with the role `admin`.
- `POST /workspaces/:workspaceId/members/:memberId/demote` makes an active `admin` a `member` and answers `204` (`demoteMember`), from any of the owner's devices. In the same transaction it revokes the invitations that the admin created in the workspace, each neither accepted nor revoked, also an expired one, as a removal does, with an `invitation.revoked` audit record with the reason `creator_demoted` for each, so that their codes answer `invitation_invalid`. It writes a `member.demoted` audit record and sends `workspace.member.role_changed` with the role `member`; the revoked invitations send no event.
- For both, a caller other than the owner, and the owner's own person, answers `403` with `forbidden`: the owner's role changes only by transfer, so nobody changes their own role. A removed person, an unclaimed person, who is always a member, promoting an admin, and demoting a member answer `409` with `conflict`. A role change ends no subscription; the person's devices see the event like every other subscriber.
- A removal and a departure are one transaction: it sets `removed_at` and `removed_by_user_id` and clears an ownership offer to the person; revokes the person's own invitation and the invitations that the person's account created in the workspace, each neither accepted nor revoked, also an expired one, with an `invitation.revoked` audit record with the reason `member_removed` for each; and, for a claimed person, disables the account's agents in the workspace's projects, revokes their active grants with the remover as `revoked_by_user_id`, and cancels with the reason `member_removed` the unfinished runs in the workspace that run on those agents or that the account requested on another member's agent. Nothing outside the workspace changes, and nothing is deleted: the view shows the person as a former member, and an account that rejoins with a new invitation claims a new person.
- After the commit, in this order: `workspace.member.removed` goes through the membership event delivery, which first ends the person's subscriptions to the workspace with `workspace.unsubscribed` and `membership_ended` and sends the person's `offline` to the other subscribers; every connection of the person's account that got `auth.ok` gets `account.removed_from_workspace` with the workspace and the time of the removal, also a connection that subscribed to nothing, through `onAccountFrame` as for a join request decision; and each cancelled run goes to the workspace's remaining subscribers as `agent.run.state_changed` through the connection registry, as after a device revocation (see "Workspace subscriptions, presence, and delivery"). `buildApp` connects both to the registry, which sends at once, so the order holds. An unclaimed person has no account, agents, or runs, so only the event is sent. The per-event membership check stays the backstop: the account's next event in the workspace closes its connection with `not_a_member`.
- The membership events have a `system` actor and `deviceId: null`, as the protocol requires of events that only the server originates. After the commit, a deeply frozen copy of each goes to the connections subscribed to the workspace (see "Workspace subscriptions, presence, and delivery") and then to the `onWorkspaceEvent` option of `buildApp`, which tests use to observe the events; the copy shares no object with the answer. The delivery logs the event type, the workspace ID, and the number of connections at debug level. The route does not wait for the option, so a hook that never returns cannot hold the answer. A failure of the hook is logged with the event type, the workspace ID, and the error's type, never its message, which may quote a display name; it does not change the answer, because the change is already committed. A refused request sends no event.

The ownership routes (`src/workspaces/ownership-routes.ts`; ADR 0014, "People and roles" and "Removal and ownership") run each change in one transaction that checks the account and the device again (`lockActor`) and then locks, in one statement and in the order of their IDs, the caller's own person, the owner, the person that holds the offer, and the person that a new offer names. A workspace has at most one offer, `ownership_offered_at` on the target's row, and an offer lives 7 days: from then on it is no offer, the view no longer shows it, and accepting or withdrawing it answers `409` with `conflict`. Each answers `204` without a body. The account frames below go to every connection of the target's account that got `auth.ok`, also one that subscribed to nothing, through `onAccountFrame`, as after a removal.

- `POST /workspaces/:workspaceId/ownership-offer` with `memberId` offers the ownership to another active, claimed person, an admin or a member (`offerOwnership`). Only the owner, from a device registered more than 72 hours earlier, as for a promotion; a device exactly 72 hours old or younger answers `403` with `device_too_new`, decided after the role and before the person's state. Anyone else, and an offer to the owner's own person, answer `403` with `forbidden`; an unclaimed or removed person, and a workspace with a live offer, to this person or another, answer `409` with `conflict`. It writes an `ownership.offered` audit record. After the commit every connection of the target's account gets `account.ownership_offered` with the offer, as the view shows it; nobody else is told, and no workspace event is sent, because the protocol has none for an offer.
- `POST /workspaces/:workspaceId/ownership-offer/accept` lets the target accept the live offer from any of its devices (`acceptOwnershipOffer`): one transaction makes the owner an `admin` and then the target the `owner`, so the unique index of one owner never sees two, and clears the offer. The owner answers `403` with `forbidden`, and so does any other person while the offer names someone else; without a live offer, also after a withdrawal, it answers `409` with `conflict`. It writes an `ownership.transferred` audit record and, after the commit, sends `workspace.ownership.transferred` with the former and the new owner's people through the membership event delivery, to the connections subscribed to the workspace. No account frame is sent: the protocol reports a transfer with this event only.
- `POST /workspaces/:workspaceId/ownership-offer/withdraw` lets the owner withdraw the live offer from any of the owner's devices (`withdrawOwnershipOffer`). Anyone else answers `403` with `forbidden`; without a live offer it answers `409` with `conflict`. It writes an `ownership.offer_withdrawn` audit record, and after the commit every connection of the target's account gets `account.ownership_offer_ended` with the reason `withdrawn` and the time of the withdrawal. An offer that another device of the owner makes while the withdrawal waits is not withdrawn: the withdrawal decides as if it came first.
- An expired offer is cleared by the owner's next offer or withdrawal, or by the target's acceptance, and only then; the reads skip it. The clearing writes no audit record, and after the commit every connection of the target's account gets `account.ownership_offer_ended` with the reason `expired` and the offer's expiry as `endedAt`: before `account.ownership_offered` of the new offer, and before the `409` of an acceptance or a withdrawal, whose transaction commits the clearing. Another person's acceptance of an expired offer answers `409` and clears nothing.
- For the desktop (#26, #95): an `account.ownership_offer_ended` frame names no offer, only the workspace. Its `endedAt` is never earlier than the `offeredAt` of the offer that it ends: the time of the withdrawal, or the offer's expiry. So a frame whose `endedAt` is earlier than the `offeredAt` of the offer that the desktop shows ends an older offer, for example one that the desktop missed and that the workspace view, read later, already replaced; the desktop ignores it and keeps showing the offer. When the two times are equal, the frame may end either offer, and the desktop reads the workspace view again.
- A removal or a departure of the target clears the offer in its transaction and sends no offer frame, since the account gets `account.removed_from_workspace`. A demotion of the target keeps the offer, because ADR 0014 lets the owner offer ownership to a member too. The owner can be neither removed nor demoted.

The invitation routes (`src/workspaces/invitation-routes.ts`; ADR 0014, "Invitations" and "Limits") are for the owner and admins only; a member gets `403` with `forbidden` on each of them. A change runs in one transaction that checks the account and the device again (`lockActor`) and then locks the caller's own person and the invited person, before it touches an invitation of that person. For an active member, a body that breaks the protocol and a malformed ID answer `400` with `bad_request`, and a person or invitation ID that the workspace does not have answers `404` with `not_found`; a non-member gets the membership check's `404` before any of them. Invitations send no membership event, because only the owner and admins see them.

- `POST /workspaces/:workspaceId/invitations` with `memberId` and an optional `lifetimeSeconds`, from 3,600 (1 hour) to 604,800 (7 days) and 7 days when omitted, creates an invitation for an unclaimed person and answers `200` with the invitation and its code, with `Cache-Control: no-store` (`createInvitation`). The code is `mmdi_` and 32 random bytes as base64url. This answer is the only place it appears: the database stores its SHA-256 hash, and the list, the logs, and the audit records never hold it. A claimed or removed person answers `409` with `conflict`. In the same transaction it revokes the person's earlier invitation that is neither accepted nor revoked, with an `invitation.revoked` audit record with the reason `replaced`, so that a lost code is replaced by a new invitation; it writes an `invitation.created` audit record. A workspace has at most 50 live invitations, not counting the one that the new invitation replaces, and at most 100 new invitations within 24 hours. Beyond either limit the route answers `429` with `rate_limited` and `Retry-After`: the seconds until the live invitation that expires first expires, or until the oldest invitation of the 24 hours leaves the window, the later of the two when both limits are reached.
- `GET /workspaces/:workspaceId/invitations` lists the live invitations, those neither accepted, revoked, nor expired, the most recently created first, each with `createdByMemberId`, the creator's person (`listInvitations`). It holds no code and no hash.
- `POST /workspaces/:workspaceId/invitations/:invitationId/revoke` revokes a live invitation and answers `204` (`revokeInvitation`), with an `invitation.revoked` audit record without a reason. An invitation that is already revoked, accepted, or expired answers `409` with `conflict`, so a second revocation changes nothing.

Previewing and accepting an invitation code (`src/workspaces/invitation-code-routes.ts`; ADR 0014, "Invitations", "Limits", and "Threats") needs only a signed-in device: the routes are not under `/workspaces/:workspaceId`, and the code travels only in the request body, never in a path or a query. Every answer of both routes, an error too, carries `Cache-Control: no-store`. A body without a well-formed code answers `400` with `bad_request`, and the message never quotes the code. The API looks the invitation up by the SHA-256 hash of the code.

- `POST /invitations/preview` with `code` answers `200` with the workspace's name, the display name of the person that the code claims, the inviter, and the expiry (`previewInvitation`). The inviter is the creator's person in the workspace, with its display name and its GitHub login and the time the login was last verified. A preview consumes nothing and writes nothing.
- `POST /invitations/accept` with `code` claims the person and answers `200` with the workspace and the claimed person, a `member` with the account's GitHub login (`acceptInvitation`). One transaction checks the account and the device again (`lockActor`), locks the invitation's person, consumes the invitation with a conditional update (only if the hash matches and the invitation is neither accepted, nor revoked, nor expired), records the accepting account and device, and claims the person only if it is still unclaimed and not removed. When either update changes nothing, the transaction rolls back. Of two acceptances of one code, only the first claims the person. It writes an `invitation.accepted` and a `member.claimed` audit record and, after the commit, sends `workspace.member.claimed` with the claimed person through `onWorkspaceEvent`, like the people routes.
- An account that is already an active member of the code's workspace gets `409` with `already_member` on both routes, whatever the state of the invitation, before anything is consumed: the invitation stays as it was. When the account claims another person of that workspace while its acceptance runs, the unique index of one active person per account and workspace refuses the claim, and the answer is `already_member` too.
- Every other refusal answers `404` with `invitation_invalid`, byte for byte the same: an unknown, used, expired, or revoked code, a removed person (whose invitation the removal revoked), and, in a preview, an inviter without a person or a GitHub identity in the workspace. The API logs `invitation code refused` at info level with the reason and the invitation's ID (none for an unknown code), never with the code or its hash.
- An account may fail 10 times within 15 minutes, previews and accepts together; only an `invitation_invalid` answer is a failure. An attempt counts from its start until its answer is known, so concurrent attempts count too. Beyond the limit both routes answer `429` with `rate_limited` and `Retry-After`, the seconds until the oldest counted attempt is 15 minutes old, for every code, a valid one too, so that the limit bounds guessing. The count lives in API memory, like the other limits of one instance.
- A claim always takes the person that the invitation names, a new person row: an account that was removed rejoins as a new person with a new invitation, and its earlier person stays as a former member.

Join requests (`src/workspaces/join-request-routes.ts`; ADR 0014, "Join requests", "Limits", "Lifetimes", and "What a workspace ID allows"; #92). A join request is the only action that a workspace ID allows a non-member, so the requester's routes are not under `/workspaces/:workspaceId`: `POST /join-requests` takes the ID in its body. A change runs in one transaction that checks the account and the device again (`lockActor`) first. A display name has 1 to 64 characters under the text rule of ADR 0005, and a body that breaks the protocol, or a malformed ID, answers `400` with `bad_request`; a `note` or any other unknown field is stripped.

- `POST /join-requests` with `workspaceId` and `displayName` answers `200` with the request as its requester sees it: its ID, the workspace ID, the requested name, and when it was created and expires, 7 days later, and nothing about the workspace (`createJoinRequest`). It stores the requesting device and writes a `join_request.created` audit record. A second request while one is pending answers with the pending request, unchanged, also while requests are paused (awaiting the Project Manager's confirmation). An unknown and an archived workspace answer the same `404` with `workspace_not_found`, byte for byte; a paused workspace and a block of the account answer the same `403` with `join_requests_closed`; an active member gets `409` with `already_member`. The limits of ADR 0014 answer `429` with `rate_limited` and `Retry-After`: 24 hours after a denial by the same workspace, 5 pending requests of the account, 10 requests of the account within 24 hours, and 50 pending requests in the workspace. The waits of the account's own limits are exact; the wait of the workspace's limit is rounded up to the next full hour, so that it does not tell when another account asked. A request past its expiry no longer counts as pending; the next request of the account in that workspace marks it `expired` before it is stored.
- `GET /join-requests` lists the account's own requests, the most recent first, at most 1,000, each with `decision` and `decidedAt`: null while pending, then `approved`, `denied`, `withdrawn`, or `expired`. A block is shown as `denied`, and a request past its expiry as `expired` before it is marked (`listOwnJoinRequests`).
- `POST /join-requests/:joinRequestId/withdraw` withdraws the account's own pending request and answers `204`, with a `join_request.withdrawn` audit record (`withdrawJoinRequest`). Another account's request answers the same `404` with `not_found` as one that does not exist; a request that is no longer pending answers `409` with `conflict`.

The approvers' routes lie under `/workspaces/:workspaceId`, behind the membership check, and are for the owner and admins only; a member gets `403` with `forbidden`. A change runs in one transaction that checks the account and the device again (`lockActor`), then locks the caller's own person, then the request, the pending requests in the order of their IDs, or the workspace row. A request ID that the workspace does not have answers `404` with `not_found`; a request that is decided, withdrawn, or past its expiry answers `409` with `conflict`, so a decision is made once.

- `GET /workspaces/:workspaceId/join-requests` lists the pending requests, then the blocks in force, each with the requested name, the requester's GitHub login with the time it was last verified, and the creation date of the GitHub account (`listJoinRequests`). A pending request of an account that is already an active member, for example after accepting an invitation, is left out, because approving it could only answer `already_member`.
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/approve` with an optional `displayName` answers `200` with the new person (`approveJoinRequest`): in the same transaction it creates a claimed person of the requester with the role `member`, named `displayName` or else the requested name. A requester who was removed earlier rejoins as a new person. A requester who is already an active member answers `409` with `already_member`, and the request stays pending. It writes a `join_request.approved` and a `member.claimed` audit record and, after the commit, sends `workspace.member.claimed` with the new person through `onWorkspaceEvent`, like the people routes.
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/deny` answers `204` and writes a `join_request.denied` audit record (`denyJoinRequest`). The requester can ask the workspace again 24 hours later; "deny and invite instead" is a denial followed by `POST /workspaces/:workspaceId/invitations`.
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/block` denies a pending request and blocks its account, answers `204`, and writes a `join_request.blocked` audit record (`blockJoinRequest`). Until the block is lifted, a new request of the account answers `403` with `join_requests_closed`, the same answer as for a pause; the requester sees the request as `denied`, and the approvers' list shows the block. A block needs a pending request, so a requester who withdraws the request before it is blocked escapes the block and can ask again at once; the approvers can pause join requests to keep such a requester out (for the screens of #95).
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/unblock` lifts a block in force, answers `204`, and writes a `join_request.unblocked` audit record (`unblockJoinRequest`). A request that is not blocked, or whose block was already lifted, answers `409` with `conflict`. The account can ask again at once; the 24-hour wait follows only a denial. The requester still sees `denied`, and nothing is sent to them.
- `POST /workspaces/:workspaceId/join-requests/deny-all` denies every pending request of the workspace, answers `204`, also when nothing is pending, and writes one `join_request.denied` audit record per request (`denyAllJoinRequests`). Each requester can ask again 24 hours later, as after a denial.
- `POST /workspaces/:workspaceId/join-requests/pause` and `POST /workspaces/:workspaceId/join-requests/resume` set and clear the time that the workspace view shows as `joinRequestsPausedAt`, answer `204`, and write a `join_requests.paused` or `join_requests.resumed` audit record (`pauseJoinRequests`, `resumeJoinRequests`). Pausing a paused workspace or resuming one that is not paused answers `204` and changes nothing. While paused, a new request answers `403` with `join_requests_closed`; the pending requests stay and can still be decided or withdrawn. A pause ends only with a resume. No workspace event reports a pause, because the protocol has none; the members read it from the workspace view.
- After an approval, a denial, a block, or denying all commits, `account.join_request_decided` with the request's ID, the workspace ID, the decision, and its time goes to every open connection of the requester's account that got `auth.ok`, through `ConnectionRegistry.sendToUser`, which `buildApp` passes to the workspace routes as `onAccountFrame`. A block is sent as `denied`, and denying all sends one frame per denied request. A failure is logged with the frame type and the error's type only and does not change the answer. A refused decision, unblocking, pausing, and resuming send nothing.

### `POST /auth/github/webhook`

GitHub sends `github_app_authorization` with the action `revoked` when a person revokes the app's authorization, also when they never installed it (ADR 0014, "Revocation, sign-out, and recovery"; P-54; #67). The route exists only with `API_GITHUB_WEBHOOK_SECRET` and the database; otherwise it answers the generic `404`.

- The body must be `application/json` (`415` otherwise) and at most 1 MiB (`413`), a limit of the route that replaces `API_BODY_LIMIT_BYTES`. The route keeps the raw bytes and checks `X-Hub-Signature-256` before it parses anything: `sha256=` and the lowercase hexadecimal HMAC-SHA256 of the body, compared with `timingSafeEqual`, under `API_GITHUB_WEBHOOK_SECRET` or, while it is set, `API_GITHUB_WEBHOOK_SECRET_PREVIOUS`. A missing or wrong signature answers `401` with `unauthorized` and changes nothing.
- With a valid signature, a body that is not a JSON object answers `400` with `bad_request`. `ping`, `installation`, `installation_repositories`, any other event, and `github_app_authorization` with another action answer `204` and change nothing; an installation grants nothing.
- A revocation needs `X-GitHub-Delivery` (letters, digits, and hyphens, at most 64) and `sender.id` (a positive integer); otherwise it answers `400` with `bad_request`. With GitHub sign-in configured, the route first records the sender's numeric ID and the time in the list of recent revocations in memory, also for a sender without an account (see "Sign-in with GitHub"). Then, in one transaction, `recordGitHubRevocation` of [`@mymandev/database`](../../packages/database/README.md) finds the account by the numeric sender ID in `user_identities`, never by the login, writes a `github.authorization_revoked` audit record with the delivery ID, locks the account's row as a sign-in does (`FOR NO KEY UPDATE`), and sets `users.sign_in_required_at` to the latest of its current value, now, and one millisecond after the last sign-in of each of the account's devices that are not revoked; it never moves backward. Each device counts at most 60 seconds past now, so a last sign-in in the future, after a jump of the clock, cannot keep the account from signing in for longer. A sign-in that committed before the revocation is therefore always covered, also one whose request took a later time than the webhook's (#115). Every device whose last sign-in is earlier must then sign in with GitHub again: `POST /auth/access-token` and the WebSocket authentication answer `sign_in_required`, and earlier access tokens stop working. The devices, their agents, and their grants stay. After the commit the API closes the account's sockets with `sign_in_required` (4003) and drops the access tokens of its devices from memory. It answers `204`.
- A delivery ID that is already recorded changes nothing and answers `204`. A redelivery keeps the ID of the original delivery (#67), and the unique `audit_events.github_delivery_id` recognizes it.
- A sender without an account, or whose identity was erased, gets `204` and one audit record without an actor or a subject, but with the delivery ID, so that a redelivery is recognized too.
- The route has no rate limit: GitHub delivers from shared addresses, a request without a valid signature costs one HMAC per configured secret, and the body limit bounds the work.
- Each delivery answered `204` logs one line with the event type (`githubEvent`) and the outcome: `revoked`, `no_account`, `already_processed`, or `ignored`. No body, signature, `X-GitHub-Delivery`, sender, or user ID is logged.

To rotate the secret, set the new one as `API_GITHUB_WEBHOOK_SECRET` and the old one as `API_GITHUB_WEBHOOK_SECRET_PREVIOUS`, restart the API, change the secret in the app's settings on GitHub, then remove the previous secret and restart again. GitHub does not redeliver a failed delivery on its own: after downtime or a rotation, the operator checks the app's recent deliveries and redelivers by hand (#96). [Development GitHub App](../../docs/development/GITHUB-APP.md#test-the-webhook-locally) describes local testing through a relay.

An accepted risk (ADR 0014, update of 2026-11-01): GitHub signs only the body, and a revocation's body carries no time. Whoever saw one signed delivery, on the app's recent deliveries, in a proxy log, or on a public development relay, can send it again with a new `X-GitHub-Delivery` and require that person to sign in again as often as they like. The API cannot tell such a copy from a real revocation. A copy deletes and grants nothing. A new webhook secret ends it.

Decisions that ADR 0014 leaves open, settled for #90 with the Project Manager's approval on 2026-11-01:

- A revocation whose sender has no account, or whose identity was erased, answers `204` and writes one audit record without a person that stores the delivery ID.
- The audit record has no actor, as for every action of the server; its subject is the account. `AUDIT_REASONS` does not change.
- Every other event type, and every other action, answers `204` without a change.
- A webhook secret is 32 to 256 printable ASCII characters without whitespace. The previous secret without the current one is a configuration error, and production requires the current secret, never the previous one.
- No per-address rate limit, a body limit of 1 MiB, and `application/json` only.
- A missing or wrong signature answers `401` with `unauthorized`; a signed delivery with a malformed body, a missing or invalid delivery ID, or a missing or invalid sender ID answers `400` with `bad_request`.

### `GET /ws` (WebSocket)

`/ws` is the only path that accepts a WebSocket handshake; a handshake on any other path gets `404` before the upgrade. `/ws` exists only with GitHub sign-in and the database, like the routes that need them (ADR 0014, "Configuration"); without them it answers the generic `404` as well, and no unauthenticated mode exists.

Before the upgrade:

1. A handshake with an `Origin` header that is not listed in `API_ALLOWED_ORIGINS` gets `403`. A handshake without `Origin` (Node.js, the Electron main process) is accepted. Browsers send `Origin` on every WebSocket handshake and apply no same-origin rule to WebSocket, so every browser origin that may connect must be listed. A renderer loaded from `file://` or a custom scheme sends the origin `null`, which cannot be listed.
2. One remote address may open 60 handshakes in 10 minutes, the limit of the other routes before a verified signature (P-63); the 61st gets `429` with `rate_limited` and `Retry-After`. Behind a proxy without `trustProxy` set to it, every client has the proxy's address, so the limit is valid only while the API is reached directly.
3. At most 200 connections may wait for authentication at once (ADR 0014, "Limits"). Above that, the handshake gets `429` with `rate_limited` and `Retry-After: 11`, the longest time a waiting connection holds its place: 10 seconds to authenticate and 1 second to close. No socket, timer, or nonce is created for it.

Authentication (ADR 0014, "Device key and authentication"):

1. After the upgrade the server sends `auth.challenge` with a nonce (32 random bytes), a new connection ID, and the protocol version, and starts a 10-second timer (`WS_AUTH_TIMEOUT_MS`). The nonce lives only in API memory and only for this connection.
2. The device answers with exactly one `auth.response`: its device ID and a signature over `deviceAuthInput` with the purpose `ws`, `API_PUBLIC_ORIGIN` as the audience, the nonce, the device ID, and the connection ID. The nonce is used once: the connection accepts no second response.
3. The server verifies the signature with the device's current key first and checks the device state second, like `POST /auth/access-token`: an unknown device, a bad signature, and a disabled account get `auth_failed`; a revoked device gets `device_revoked`; a signed-out device, a last sign-in 30 days ago or more, and a GitHub revocation after the last sign-in get `sign_in_required`.
4. On success the server writes `devices.last_seen_at`, builds a frozen `AuthenticatedConnectionContext` (the connection ID, the identity of user and device, which is never null, and the time of the device's last sign-in), and registers the connection as the device's live connection. It then reads the device again: a revocation, sign-out, disable, or new sign-in that committed after the first check closes the connection with its reason before `auth.ok`, and the connection leaves the registry; one that commits later finds the connection in the registry. Only then does the server send `auth.ok` with the user ID, the device ID, and the sign-in expiry (30 days after the last sign-in).
5. A device has one live connection. A newer authenticated connection closes the older one with `connection_replaced`. The server writes at most one `connection.replaced` audit record per device per hour and logs the other replacements with a count.

Before `auth.ok`, no frame reaches `decodeClientEvent` or the event handler: a binary frame, a frame over 1 KiB (`MAX_AUTH_FRAME_BYTES`, measured on the raw frame before the JSON is parsed), a frame that is not JSON or that `decodeClientFrame` refuses, any frame other than `auth.response`, and a second frame close the connection with `protocol_violation`. A frame over 64 KiB closes with 1009 at any time, because the WebSocket library refuses it first. A connection that is refused before `auth.ok`, or that times out, gets its close frame and is terminated 1 second later, so that it frees its place without waiting up to 30 seconds for the closing handshake.

Messages after `auth.ok`:

1. Each text frame must contain one JSON message, which the gateway decodes with `decodeClientMessage`: an event, with the rules of `decodeClientEvent`, or a workspace subscription frame (`workspace.subscribe` or `workspace.unsubscribe`), which the gateway answers itself (see "Workspace subscriptions, presence, and delivery"). A second `auth.response` is `unexpected_frame`, a frame that only the server sends is `not_allowed_from_device`, and an unknown frame is `unknown_type`.
2. `bindIdentity` then binds the event to the connection (ADR 0006, identity binding). The event's `deviceId`, and for a `user` actor its `actor.userId`, must be the connection's; a mismatch is refused and audited as `event.identity_mismatch`, with the event ID as the subject and no workspace, because the event's workspace is unverified. It is never overwritten. Like `connection.replaced`, at most one such record is written per device per hour, and the other mismatches are logged with a count. Every event also reads the device again: a revoked device gets `device_revoked`; a newer sign-in, which replaced the key that signed, gets `key_replaced`; a disabled account gets `auth_failed`; a sign-out and a GitHub revocation after the sign-in get `sign_in_required`. The 30-day sign-in is not checked per event: an open connection may continue for 24 hours more, which the sweep checks. Last, the user must be an active member of `event.workspaceId` at this moment: a claimed person whose `removed_at` is empty. A workspace that does not exist is refused like one without the user.
3. Only the result, a `VerifiedEvent` (a second brand next to `UnverifiedEvent`, defined in `src/gateway.ts`), reaches the event handler, together with the `AuthenticatedConnectionContext`. The handler's type accepts nothing else. The default handler logs the event ID, the event type, and the connection ID at `debug` level. No event from a device is routed, relayed, stored, or answered yet: the reference binding of runs, agents, projects, and repositories comes with the first event types that carry those references (#27, #28). This holds for `chat.message.send` too: it passes identity binding and reaches the event handler, and nothing is stored, relayed, or answered until #27 stores chat messages (Project Manager decision of 2026-11-01). How the server refuses a `chat.message.send` stays open with #27.
4. Messages are handled one after another, in the order they arrived; the gateway awaits the event handler, which may return a promise, and the answer to a subscription frame before the next message. While messages wait, the gateway stops reading from the socket, so a fast sender cannot queue without bound. An event whose connection closed or was replaced during its checks is not delivered. A handler that throws or rejects closes the connection with 1011, and its error is logged through the redacting error serializer.
5. Anything else closes the connection. Frames that arrive after the gateway has decided to close are ignored.

The codes 4000 to 4006 and their reasons are `WS_CLOSE_CODES` of `@mymandev/protocol`, whose README lists what the desktop does for each. The codes from 1003 to 1013 stay provisional (P-24).

No authentication frame, nonce, or signature is logged. A refused connection is logged with its connection ID and the close reason only (`protocol_violation` at `debug` level, with what broke the rule, and the others at `info`), and an authenticated connection with its connection ID, user ID, and device ID. A connection that a route or the sweep closes is logged at `info` as "connection closed", with its connection ID and the close reason; a failed sweep is logged at `error` with a `DatabaseError`, which carries the SQLSTATE code and no SQL or parameters. What a client sends wrong on its socket, such as a frame over 64 KiB, is logged at `debug` level with the connection ID; any other socket error at `error` level.

`ConnectionRegistry` (`src/gateway.ts`) holds the open connections of the instance: the unauthenticated ones, for their cap, and the live connection of each device. `closeDevice(deviceId, reason, log)` and `closeUser(userId, reason, log)` close live connections with a close reason of the protocol and log each close; `closeConnection(deviceId, connectionId, reason, log)` closes one only while it is still the device's live connection. `live()` lists the live connections without their sockets, and `sendToUser(userId, frame, exceptDeviceId)` sends an account frame. The registry also holds the workspace subscriptions of the live connections: `subscribe`, `unsubscribe`, `subscriptions()`, `endSubscription(subscription)`, `endMembership(workspaceId, memberId)`, and `sendToWorkspace(event)`; `heartbeat(log)` runs one heartbeat, and every send checks the backpressure limit. `buildApp` takes a registry as an option, so tests can count and close connections.

Connections after `auth.ok` (ADR 0014, "Revocation, sign-out, and recovery"):

1. After its transaction commits, a route closes the affected connection at once: a sign-out with `sign_in_required`, a revocation with `device_revoked`, a sign-in of an existing device, which replaced its key, with `key_replaced`, and a sign-in that replaced a previous device with `device_revoked` for that device.
2. The account frames go only to the account's own connections, never to another account's, and only to connections that got `auth.ok` and are still open. `account.device_registered` reports a new device with its device list item (`current: false`); the new device has no connection yet. `account.device_revoked` reports a revocation over HTTP and a device that a sign-in replaced, with the reason and the time; the revoked device itself never gets it, because its connection closes first. `account.join_request_decided` reports that an owner or admin approved or denied one of the account's join requests (see Workspaces). `account.ownership_offered` and `account.ownership_offer_ended` report an ownership offer to the account's person and its end without a transfer, after the ownership routes commit; the desktop ignores an `account.ownership_offer_ended` whose `endedAt` is earlier than the `offeredAt` of the offer it shows (see Workspaces). A frame is never repeated: after `auth.ok` the desktop reads its devices over HTTP.
3. Every 60 seconds (`CONNECTION_SWEEP_INTERVAL_MS`), `sweepConnections` re-checks the devices of all live connections with one batched query (`deviceRows`, at most 500 device IDs per query) and closes each connection that its device no longer accepts, with the reasons of the per-event check: `device_revoked`, `key_replaced`, `auth_failed`, or `sign_in_required`. It finds what no route of this API sees, such as the operator command `db:account`. The 30-day sign-in counts with a grace of 24 hours (`SIGN_IN_GRACE_MS`): a connection that is open when the sign-in expires stays open for 24 hours more, and the first sweep after that, up to 60 seconds later, closes it with `sign_in_required`. A sweep closes only the connection that it checked: a newer connection of the device that registered meanwhile stays open. Then the sweep re-checks the workspace subscriptions of the connections that stay open with one batched query (`activePeopleOf`, at most 500 pairs of a workspace and an account per query) and ends each subscription whose account is no longer an active member as the person it subscribed as, with `workspace.unsubscribed` and `membership_ended`. A tick while the previous sweep still runs is skipped, a failure of the database is logged and the next sweep tries again, and the interval stops when the API closes.
4. `devices.last_seen_at` is written at `auth.ok` and then by the sweep, at most every 5 minutes per device (`LAST_SEEN_INTERVAL_MS`), with one update for every device that is due (`markDevicesSeen`). A revoked device is left unchanged, also one revoked since the sweep read it. A device row that another transaction holds, such as a sign-in or a revocation, is skipped: the update never waits for a locked row, so it cannot deadlock with such a transaction. A skipped device is written at its next due time.
5. Every 30 seconds (`HEARTBEAT_INTERVAL_MS`) the heartbeat pings every live connection and terminates one that did not answer the previous ping with a pong, without a close frame, because its peer is gone. A half-open connection, whose device vanished without a close, therefore ends within 60 seconds instead of staying until its sign-in expires; its subscriptions end at once, so its person goes offline. Standard WebSocket clients, Node.js and Chromium among them, answer pings on their own. The termination is logged at `info` as "connection terminated" with the connection ID and the reason `no_pong`.
6. Backpressure: before the server queues a frame, a ping, or an event for a live connection, it checks how much still waits to be sent. Above 1 MiB (`MAX_BUFFERED_BYTES`) it queues nothing more and closes the connection with 1013 and `backpressure`; the connection leaves the registry with its subscriptions at once, so its person goes offline. The WebSocket library terminates the socket if the closing handshake does not end within 30 seconds.

Decisions that ADR 0014 leaves open, settled by the Project Manager on 2026-10-31 (#89):

- A frame that breaks the rules before authentication closes with the new code `protocol_violation` (4005). The desktop does not reconnect on its own and shows an error; when the protocol versions differ, it asks the person to update.
- A connection whose key a newer sign-in of the device has replaced closes with the new code `key_replaced` (4006); the desktop reconnects at once with its new key.
- Above the cap of 200 unauthenticated connections, the handshake gets `429` with `rate_limited` and `Retry-After` before the upgrade.
- `devices.last_seen_at` is written when a connection authenticates, and by the sweep at most every 5 minutes for an open connection.
- Without the sign-in configuration or without the database, `/ws` answers `404`; the unauthenticated mode of M1-02 is gone.

#### Workspace subscriptions, presence, and delivery

These rules follow #110, the protocol's "Workspace subscriptions, presence, and chat", and the Project Manager's decisions of 2026-11-01. The frames come from [`@mymandev/protocol`](../../packages/protocol/README.md).

1. A connection receives a workspace's events and presence only while it is subscribed to the workspace. `workspace.subscribe` first checks the cap: a connection holds at most 50 subscriptions (`MAX_SUBSCRIPTIONS_PER_CONNECTION`), and one more gets `workspace.subscribe_refused` with `too_many_subscriptions`, whatever the workspace, so the answer tells nothing about it; subscribing again to a held workspace still works. Then `subscriptionAccess` reads the device again, as for every event, and a device that may no longer act closes the connection with its reason; and it looks up the account's active person in the workspace. A workspace that does not exist and one without the account as an active member get the same `workspace.subscribe_refused` with `not_found`, and the connection stays open. Otherwise the gateway records the subscription as that person and answers `workspace.subscribed` with the people online. Subscribing again keeps one subscription and answers again.
2. `workspace.unsubscribe` ends the subscription and answers `workspace.unsubscribed` with `requested`, also when the connection was not subscribed.
3. Presence is per person and never stored: a person is online in a workspace while at least one live connection of the account is subscribed to it as that person. `workspace.subscribed` carries the snapshot (each online person once, at most 1,000, with the subscriber's own person first, so that a list cut at 1,000 keeps it), and the other subscribed connections get `presence.changed` only when a person's status changes: the first subscribed connection of a person brings it `online`, and the end of its last one `offline`. A second device of a person who is online changes nothing. No subscription or presence frame names a device.
4. A subscription ends when the device unsubscribes, when the connection closes or is replaced, and when the gateway or a route closes the connection: at that moment, before the closing handshake ends, so that the connection gets nothing more and its person goes offline at once.
5. After the commit, each membership event goes to the connections subscribed to its workspace, and to no one else. A connection whose socket the server is closing is skipped.
6. Membership ends: `workspace.member.removed`, after a removal or a departure, first ends the removed person's subscriptions, each with `workspace.unsubscribed` and `membership_ended`, so the removed account never gets the event, and the other subscribers see the person go offline before the event. Then every connection of the removed account gets `account.removed_from_workspace`, and the runs that the removal cancelled follow (item 7). The sweep ends a subscription whose account is no longer an active member, and so does an event that identity binding refuses with `not_a_member` for a subscribed workspace, before the connection closes as before; a new `workspace.subscribe` that finds the membership ended ends the held subscription the same way and answers `not_found`. A removal that the server processes in a workspace while a subscribe to that workspace checks the membership makes the subscribe check again, so the check cannot record a subscription for a person who was just removed; a removal in another workspace changes nothing. A subscribe checks again at most 3 times (`MAX_SUBSCRIBE_RECHECKS`): when the last check overlapped a removal too, it answers `not_found`, a subscription that the connection held to the workspace ends with it, and the device may subscribe again.
7. Cancelled runs: after a device revocation commits, through `POST /devices/:deviceId/revoke` or a sign-in that replaces a previous device, the route closes the device's connection, and after a removal or a departure commits, the route ends the person's subscriptions (item 6). Then it sends each run that the transaction cancelled as `agent.run.state_changed` to the connections subscribed to the run's workspace: a `system` actor, `deviceId: null`, the run's correlation ID when it has one, and a payload with the run and its agent, its repository when it has one, its state before, `cancelled`, and the reason code stored with the run, `device_revoked` or `member_removed` (ADR 0014, P-60). `revokeDevice`, `removeMember`, and `leaveWorkspace` return what these events need.
8. Events are not replayed and have no server sequence number: after every `workspace.subscribed`, also after a reconnect, the desktop reloads the workspace over HTTP and applies the events that arrived since that frame on top of it, as the protocol's README describes.

Decided by the Project Manager on 2026-11-01 (#110): subscribing is explicit; presence is per person, `online` or `offline`, never stored, a snapshot on subscribe and then the changes, with no device ID; a project event goes to every subscribed connection of the workspace; storing and relaying chat messages belongs to #27; M2 has no server sequence number; and the runs that a device revocation cancelled go to the workspace's subscribed connections as `agent.run.state_changed`.

Settled here: the cap of 50 subscriptions per connection, which the protocol leaves to the server (P-64); a subscribe re-checks the device as an event does; the subscriptions end when the server decides to close a connection, not when its closing handshake ends; a subscribe whose membership check keeps overlapping removals in its workspace answers `not_found` after 3 more checks, rather than closing the connection with 1011, so that the connection keeps its other subscriptions; a heartbeat every 30 seconds ends a connection that missed a ping; and a connection with more than 1 MiB waiting to be sent closes with 1013 and `backpressure`, a code of RFC 6455's registry that asks the client to try again later, because the protocol's codes from 4000 are for authentication and the device.

Still open: how the server refuses a `chat.message.send` (#27); relaying the events of devices, such as the run transitions that a host device reports, after their reference binding (#27, #28); and project lifecycle events, which wait for an issue about the projects API.

## Rules

- Credentials never appear in URLs, including the WebSocket URL. A browser `WebSocket` cannot set headers, which invites `/ws?token=...`; the query string would then reach proxies and browser history. WebSocket authentication uses the first message, `auth.response`.
- Logs contain the request method, the path without the query string, and the remote address. Errors are logged with their type, codes, message, and stack; an error that may carry query data (an own `query`, `params`, or `detail` property) is logged without message and stack.
- An event from a device stays `UnverifiedEvent` until `bindIdentity` has bound it to the authenticated connection. Never cast it to `ProtocolEvent` or to `VerifiedEvent`; only `bindIdentity` creates a `VerifiedEvent`, and the event handler accepts only that type with an `AuthenticatedConnectionContext`.
- `src/server.ts` is the only module with side effects. Tests build the application with `buildApp` from `src/app.ts` and use `inject` and `injectWS` without a network.

## Not included

Sessions, CORS, OpenAPI, TLS, the notice of a claim to the owner and admins (after #110), account erasure, permission enforcement, the reference binding of events (#27, #28), relaying and storing the events of devices, chat storage (#27), Docker, deployment configuration, clustering, a build step, pretty-printed logs, and a Fastify type provider.

Account erasure (#93) is the operator command `db:account -- erase` of [`@mymandev/database`](../../packages/database/README.md#operator-commands), not a route. It runs outside the API, so the API sends no `workspace.member.removed`, account frame, or `agent.run.state_changed` for an erasure: the sweep closes the account's connections, and the other members see the change when they next load the workspace.
