# @mymandev/api

The cloud API: a Fastify application with a health endpoint, GitHub sign-in, device keys and access tokens, GitHub's revocation webhook, and a WebSocket gateway that authenticates each connection with its device key and validates protocol events from [`@mymandev/protocol`](../../packages/protocol/README.md). The decisions behind it are recorded in [ADR 0009](../../docs/architecture/decisions/0009-fastify-cloud-api.md), [ADR 0010](../../docs/architecture/decisions/0010-api-configuration-and-runtime.md), and [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md).

## Start locally

From the repository root, after `npm ci`:

```sh
npm run start -w @mymandev/api
```

The API listens on `http://127.0.0.1:3000` and writes JSON log lines to standard output. Check it with:

```sh
curl http://127.0.0.1:3000/health
```

Stop it with Ctrl+C. The API logs "shutting down", closes every WebSocket connection with code 1001, and exits with code 0. On Windows, SIGTERM is never delivered; Ctrl+C sends SIGINT, which runs the same shutdown. When npm runs through `npm.cmd` on Windows, `cmd.exe` may then ask "Terminate batch job (Y/N)?"; the API has already stopped at that point.

For development, `npm run dev -w @mymandev/api` restarts the API when a source file changes, including a file in `packages/protocol`, and reads `apps/api/.env` if it exists. On Windows, a restart by `--watch` stops the process without running the shutdown handler; on Linux and macOS, `--watch` sends SIGTERM, which runs it.

Node.js runs the TypeScript source directly. There is no build step.

## Configuration

The API reads its configuration from environment variables once, at startup. An empty value counts as unset. Other variables are ignored. If a variable is invalid, the API prints one line per invalid variable, names the variable without printing its value, and exits with code 1.

| Variable                             | Default       | Accepted values                                                                                                                                                                                                                                                                                                                                 |
| ------------------------------------ | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `NODE_ENV`                           | `development` | `development`, `test`, `production`                                                                                                                                                                                                                                                                                                             |
| `API_HOST`                           | `127.0.0.1`   | `127.0.0.1`, `::1`, or `localhost`. Loopback only; widening it is part of the hosting decision (#96).                                                                                                                                                                                                                                           |
| `API_PORT`                           | `3000`        | A decimal integer from 0 to 65535, without sign, leading zero, or spaces.                                                                                                                                                                                                                                                                       |
| `API_LOG_LEVEL`                      | `info`        | `fatal`, `error`, `warn`, `info`, `debug`, `trace`, `silent`                                                                                                                                                                                                                                                                                    |
| `API_BODY_LIMIT_BYTES`               | `65536`       | A decimal integer from 1 to 10485760.                                                                                                                                                                                                                                                                                                           |
| `API_ALLOWED_ORIGINS`                | empty         | A comma-separated list of at most 20 browser origins that may open `/ws`, each exactly `http://host[:port]` or `https://host[:port]`: no path, no trailing slash, no `*`, no `null`.                                                                                                                                                            |
| `API_PUBLIC_ORIGIN`                  | empty         | The API's public origin, exactly `https://host[:port]` in lowercase without the default port; the host is a DNS name or a dotted IPv4 address. | `API_GITHUB_CLIENT_SECRET`           | empty         | A client secret of the GitHub App. A secret: never printed or logged.                                                                                                                                                                                                                                                                           |
| `API_GITHUB_WEBHOOK_SECRET`          | empty         | The webhook secret of the GitHub App: 32 to 256 printable ASCII characters without whitespace. A secret: never printed or logged.                                                                                                                                                                                                               |
| `API_GITHUB_WEBHOOK_SECRET_PREVIOUS` | empty         | The webhook secret before a rotation, in the same format, accepted too while it is set. It requires `API_GITHUB_WEBHOOK_SECRET`. A secret: never printed or logged.                                                                                                                                                                             |
| `DATABASE_URL`                       | empty         | A `postgres:` or `postgresql:` URL, percent-encoded, with `sslmode` unset, `disable`, or `verify-full` ([`@mymandev/database`](../../packages/database/README.md)). A secret: never printed or logged.                                                                                                                                          |

[`.env.example`](.env.example) lists every variable with its default. To change a value for `npm run dev`, copy it to `apps/api/.env`. `.env` is ignored by Git; never commit it.

`API_PUBLIC_ORIGIN`, `API_GITHUB_CLIENT_ID`, and `API_GITHUB_CLIENT_SECRET` enable GitHub sign-in together: set all three or none. `API_GITHUB_WEBHOOK_SECRET` enables the webhook. With `NODE_ENV=production`, they and `DATABASE_URL` are required, and `DATABASE_URL` needs `sslmode=verify-full`; `API_GITHUB_WEBHOOK_SECRET_PREVIOUS` stays optional. In development and test the API also starts without them and logs a warning that GitHub sign-in, the webhook, or the database is disabled. The configuration keeps the client secret, the webhook secrets, and the database URL in an object that prints `[redacted]` in logs, JSON, and inspection.

## Endpoints

### `GET /health`

Returns `200` with `{"status":"ok","version":"<version>"}`, where the version is the `version` field of `apps/api/package.json`.

Errors use one body shape, `{"statusCode":<code>,"error":"<status text>","message":"<message>","code":"<code>"}`, where `code` is one of `API_ERROR_CODES` of [`@mymandev/protocol`](../../packages/protocol/README.md) (ADR 0014, P-66). A route raises a typed `ApiError` with a code; the answer then has the code's fixed status and the status text as the message. Every other error gets a generic code for its status (`genericApiErrorCode`). A server error (5xx) always has the generic message "Internal Server Error". A client error keeps the message only when Fastify produced it, for example a validation error or `413` for a body over `API_BODY_LIMIT_BYTES`. An unknown route gets `404` with the message "Not Found" and the code `not_found`, and does not echo the method or the path. A malformed URL, an over-long path parameter (`414`), a malformed request line, headers over the limit (`431`), a request timeout (`408`), and a request that arrives while the API closes (`503`) get the status text as the message and a generic code too. A message is at most 100 characters. GET routes get no automatic HEAD route, so a rate limit counts every request against one budget.

A route with a rate limit answers `429` with `rate_limited` and `Retry-After` when it is reached (`@fastify/rate-limit`, in-memory store, one instance). Routes that take a body validate it with the zod schema of `@mymandev/protocol` through `zodValidatorCompiler` (`src/validation.ts`), registered in their plugin scope: unknown keys are stripped, and a failure answers `400` with `bad_request` and a message that names the part, the path, and the issue, never an input value.

### Sign-in with GitHub

These routes exist only when GitHub sign-in is configured; otherwise they answer the generic `404`. They implement steps 2 to 5 of ADR 0014, "Sign-in". The API keeps every attempt, its PKCE verifier for GitHub, and the sign-in codes only in memory, and the codes and the cookie only as SHA-256 hashes. A timer drops expired entries every 15 seconds, and a restart drops them all. Every GitHub call refuses redirects, and a token in a failed exchange answer is deleted at once.

- `GET /auth/github/authorize`, opened by the desktop in the system browser with `code_challenge`, `code_challenge_method=S256`, `redirect_uri` (`http://127.0.0.1:<port>/callback`, ports 1024 to 65535), `state`, and optionally `login` and `prompt=select_account`. A malformed or repeated parameter gets an error page and never a redirect. Otherwise it starts an attempt that lives 10 minutes (at most 1,000 open attempts), sets the attempt cookie, and redirects to GitHub with the API's own state and PKCE pair. With an `https` origin the cookie is `__Host-mmd_signin` with `Secure`, `HttpOnly`, `SameSite=Lax`, and `Path=/`; with an `http` origin, which only development and test allow, it is `mmd_signin` without `Secure` (#99).
- `GET /auth/github/callback`, GitHub's redirect. It needs the cookie of the attempt that the state names and runs once. A request that names a live attempt without its cookie ends that attempt, so GitHub's code from another browser is never exchanged (the phishing scenario of ADR 0014, "Threats"). It exchanges the code with a form-encoded body and never retries; a token answer with an `error` field fails whatever its status. It reads `GET /user`, then deletes the user token at once and keeps no GitHub token. It shows the confirmation page with the GitHub login and the pairing code.
- `POST /auth/github/confirm`, the form of the confirmation page, with `state` and `decision` (`continue` or `cancel`). It accepts only a form body and needs the attempt's cookie. It refuses a request whose `Sec-Fetch-Site` header is present and not `same-origin`; without that header, the `SameSite=Lax` cookie keeps a cross-site form from carrying the attempt. Continue creates a sign-in code (`mmdc_`, single use, 60 seconds) and answers with a page that posts `code` and `state` to the desktop's listener, by a script and a visible button. The code never appears in a URL.

- `POST /auth/sign-in`, sent by the desktop with the sign-in code, its PKCE verifier, `redirect_uri`, and the device registration (`SignInRequestSchema`). It needs the database too. It takes the code once, also when a later check fails, and answers `401` with `auth_failed` for an unknown, used, or expired code, a verifier whose S256 hash is not the bound challenge, another `redirect_uri`, or a signature that does not verify. A new device signs the `sign-in` input with its new key; an existing device signs it with its current key and with the new key. In one transaction the API then finds the account by GitHub's numeric ID, never by login, and refreshes the login, or creates the account with the GitHub name as its first display name, or the login when the name is not usable. It registers the device or replaces its key, keeping the device ID and clearing a sign-out, and revokes a named previous device of the same account as `replaced`. It refuses a disabled account (`auth_failed`), a device of another account (`device_account_mismatch`), a revoked device (`device_revoked`), a new device while the registration lock is active (`device_registration_locked`), and more than 20 active or 10 new devices in 24 hours (`rate_limited`). It writes audit records for the sign-in and for the registration or key replacement, and answers with the user ID, the device ID, the display name, the login, and the sign-in expiry, 30 days later, without any credential. After the commit, the device's open connection, which used the replaced key, closes with `key_replaced`, and a replaced previous device's connection with `device_revoked`; the account's other connections get `account.device_registered` for a new device and `account.device_revoked` for the replaced one (see `GET /ws`).

When an attempt ends without a code, the page posts `error` and `state` to the listener instead: `access_denied` (declined on GitHub or Cancel), `sign_in_failed` (GitHub did not confirm the code or the account), `unsupported_account` (a login outside the login rule), or `sign_in_unavailable` (GitHub's limit, with `Retry-After`). A request without a valid attempt gets an error page and posts nothing.

The pages load nothing from outside and send `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and a Content Security Policy with `default-src 'none'`, a hash for the one style and the one script, `frame-ancestors 'none'`, and a `form-action` that allows only the API itself or this attempt's listener. Each route allows 30 requests per address in 10 minutes. The API logs a warning above 1,500 token exchanges in an hour, below GitHub's limit of 2,000. No code, state, cookie, token, verifier, or GitHub response body is logged.

### Access tokens and devices

These routes need GitHub sign-in and the database (ADR 0014, "Device key and authentication" and "Revocation, sign-out, and recovery"). Challenges and access tokens live only in API memory, the tokens as SHA-256 hashes; a restart drops them, and the desktop fetches a new token.

- `POST /auth/challenge` returns a challenge ID and a nonce. The challenge is single use and valid for 60 seconds; at most 1,000 are open (`429` with `rate_limited` and `Retry-After`).
- `POST /auth/access-token` takes the device ID, the challenge ID, and a signature over the `http` input. The signature is checked first with the device's current key; an unknown device, a used or expired challenge, or a bad signature answers `auth_failed`. Only then does the device answer: `device_revoked`, `sign_in_required` (signed out, last sign-in 30 days ago or more, or a GitHub revocation after the last sign-in), or `auth_failed` for a disabled account. It returns an access token (`mmda_`, 15 minutes, never extended). A device may mint 30 tokens in 15 minutes and keeps at most 3 live tokens; a fourth ends the oldest. A token belongs to the device's sign-in: a new sign-in, which also replaces the key, ends the earlier tokens. Both routes answer with `Cache-Control: no-store`.
- Every other route below needs `Authorization: Bearer <access token>`. The token and the account's limit of 300 authenticated requests a minute are checked when the headers arrive. The token, the device, and the account are checked again after the body arrived and before it is validated, so that a slow body cannot carry a request past a revocation; sign-out, revocation, and lifting the lock check them a third time inside their transaction. Every failure is `401` with `unauthorized`.
- `POST /auth/sign-out` signs the current device out: the device, its agents, and their grants stay, its tokens stop working, its WebSocket connection closes with `sign_in_required` after the commit, and the next token needs a GitHub sign-in (P-65).
- `GET /devices` lists the account's own devices, newest first, with the sign-in expiry and the current device.
- `POST /devices/:deviceId/revoke` with `reason` `removed` or `lost` revokes one of the account's own devices in one transaction: its agents are disabled, their grants revoked, and their unfinished runs cancelled (`revokeDevice`). After the commit, the device's WebSocket connection closes with `device_revoked`, and the account's other connections get `account.device_revoked`. Another account's device answers `404` with `not_found`, also for the owner of a shared workspace; a revoked device answers `409` with `conflict`. `lost` also refuses new device registrations for 7 days; the current device cannot report itself `lost` (`409` with `conflict`), so that whoever holds it cannot lock the account's new devices.
- `POST /account/registration-lock/lift` lifts that lock from an active device.

Sign-out, revocations, and the lock write audit records. No `Authorization` header, token, nonce, or signature is logged.

The operator command (`db:account`) runs outside the API and cannot drop tokens from its memory: after disabling and enabling an account within 15 minutes, a token minted before the disable works again until it expires.

### `POST /auth/github/webhook`

GitHub sends `github_app_authorization` with the action `revoked` when a person revokes the app's authorization, also when they never installed it (ADR 0014, "Revocation, sign-out, and recovery"; P-54; #67). The route exists only with `API_GITHUB_WEBHOOK_SECRET` and the database; otherwise it answers the generic `404`.

- The body must be `application/json` (`415` otherwise) and at most 1 MiB (`413`), a limit of the route that replaces `API_BODY_LIMIT_BYTES`. The route keeps the raw bytes and checks `X-Hub-Signature-256` before it parses anything: `sha256=` and the lowercase hexadecimal HMAC-SHA256 of the body, compared with `timingSafeEqual`, under `API_GITHUB_WEBHOOK_SECRET` or, while it is set, `API_GITHUB_WEBHOOK_SECRET_PREVIOUS`. A missing or wrong signature answers `401` with `unauthorized` and changes nothing.
- With a valid signature, a body that is not a JSON object answers `400` with `bad_request`. `ping`, `installation`, `installation_repositories`, any other event, and `github_app_authorization` with another action answer `204` and change nothing; an installation grants nothing.
- A revocation needs `X-GitHub-Delivery` (letters, digits, and hyphens, at most 64) and `sender.id` (a positive integer); otherwise it answers `400` with `bad_request`. In one transaction, `recordGitHubRevocation` of [`@mymandev/database`](../../packages/database/README.md) finds the account by the numeric sender ID in `user_identities`, never by the login, writes a `github.authorization_revoked` audit record with the delivery ID, and sets `users.sign_in_required_at` to now, unless it is already later. Every device whose last sign-in is earlier must then sign in with GitHub again: `POST /auth/access-token` and the WebSocket authentication answer `sign_in_required`, and earlier access tokens stop working. The devices, their agents, and their grants stay. After the commit the API closes the account's sockets with `sign_in_required` (4003) and drops the access tokens of its devices from memory. It answers `204`.
- A delivery ID that is already recorded changes nothing and answers `204`. A redelivery keeps the ID of the original delivery (#67), and the unique `audit_events.github_delivery_id` recognizes it.
- A sender without an account, or whose identity was erased, gets `204` and one audit record without an actor or a subject, but with the delivery ID, so that a redelivery is recognized too.
- The route has no rate limit: GitHub delivers from shared addresses, a request without a valid signature costs one HMAC per configured secret, and the body limit bounds the work.
- Each delivery answered `204` logs one line with the event type (`githubEvent`) and the outcome: `revoked`, `no_account`, `already_processed`, or `ignored`. No body, signature, `X-GitHub-Delivery`, sender, or user ID is logged.

To rotate the secret, set the new one as `API_GITHUB_WEBHOOK_SECRET` and the old one as `API_GITHUB_WEBHOOK_SECRET_PREVIOUS`, restart the API, change the secret in the app's settings on GitHub, then remove the previous secret and restart again. GitHub does not redeliver a failed delivery on its own: after downtime or a rotation, the operator checks the app's recent deliveries and redelivers by hand (#96). [Development GitHub App](../../docs/development/GITHUB-APP.md#test-the-webhook-locally) describes local testing through a relay.

An accepted risk (ADR 0014, update of 2026-11-01): GitHub signs only the body, and a revocation's body carries no time. Whoever saw one signed delivery, on the app's recent deliveries, in a proxy log, or on a public development relay, can send it again with a new `X-GitHub-Delivery` and require that person to sign in again as often as they like. The API cannot tell such a copy from a real revocation. A copy deletes and grants nothing. A new webhook secret ends it.

Decisions that ADR 0014 leaves open, settled for #90 with the Project Manager's approval on 2026-11-01:

- A revocation whose sender has no account, or whose identity was erased, answers `204` and writes one audit record without a person that stores the delivery ID.
- The audit record has no actor, as for every action of the server; its subject is the account. `AUDIT_REASONS` does not change.
- Every other event type, and every other action, answers `204` without a change.
- A webhook secret is 32 to 256 printable ASCII characters without whitespace. The previous secret without the current one is a configuration error, and production requires the current secret, never the previous one.
- No per-address rate limit, a body limit of 1 MiB, and `application/json` only.
- A missing or wrong signature answers `401` with `unauthorized`; a signed delivery with a malformed body, a missing or invalid delivery ID, or a missing or invalid sender ID answers `400` with `bad_request`.

### `GET /ws` (WebSocket)

`/ws` is the only path that accepts a WebSocket handshake; a handshake on any other path gets `404` before the upgrade. `/ws` exists only with GitHub sign-in and the database, like the routes that need them (ADR 0014, "Configuration"); without them it answers the generic `404` as well, and no unauthenticated mode exists.

Before the upgrade:

1. A handshake with an `Origin` header that is not listed in `API_ALLOWED_ORIGINS` gets `403`. A handshake without `Origin` (Node.js, the Electron main process) is accepted. Browsers send `Origin` on every WebSocket handshake and apply no same-origin rule to WebSocket, so every browser origin that may connect must be listed. A renderer loaded from `file://` or a custom scheme sends the origin `null`, which cannot be listed.
2. One remote address may open 60 handshakes in 10 minutes, the limit of the other routes before a verified signature (P-63); the 61st gets `429` with `rate_limited` and `Retry-After`. Behind a proxy without `trustProxy` set to it, every client has the proxy's address, so the limit is valid only while the API is reached directly.
3. At most 200 connections may wait for authentication at once (ADR 0014, "Limits"). Above that, the handshake gets `429` with `rate_limited` and `Retry-After: 11`, the longest time a waiting connection holds its place: 10 seconds to authenticate and 1 second to close. No socket, timer, or nonce is created for it.

Authentication (ADR 0014, "Device key and authentication"):

1. After the upgrade the server sends `auth.challenge` with a nonce (32 random bytes), a new connection ID, and the protocol version, and starts a 10-second timer (`WS_AUTH_TIMEOUT_MS`). The nonce lives only in API memory and only for this connection.
2. The device answers with exactly one `auth.response`: its device ID and a signature over `deviceAuthInput` with the purpose `ws`, `API_PUBLIC_ORIGIN` as the audience, the nonce, the device ID, and the connection ID. The nonce is used once: the connection accepts no second response.
3. The server verifies the signature with the device's current key first and checks the device state second, like `POST /auth/access-token`: an unknown device, a bad signature, and a disabled account get `auth_failed`; a revoked device gets `device_revoked`; a signed-out device, a last sign-in 30 days ago or more, and a GitHub revocation after the last sign-in get `sign_in_required`.
4. On success the server writes `devices.last_seen_at`, builds a frozen `AuthenticatedConnectionContext` (the connection ID, the identity of user and device, which is never null, and the time of the device's last sign-in), and registers the connection as the device's live connection. It then reads the device again: a revocation, sign-out, disable, or new sign-in that committed after the first check closes the connection with its reason before `auth.ok`, and the connection leaves the registry; one that commits later finds the connection in the registry. Only then does the server send `auth.ok` with the user ID, the device ID, and the sign-in expiry (30 days after the last sign-in).
5. A device has one live connection. A newer authenticated connection closes the older one with `connection_replaced`. The server writes at most one `connection.replaced` audit record per device per hour and logs the other replacements with a count.

Before `auth.ok`, no frame reaches `decodeClientEvent` or the event handler: a binary frame, a frame over 1 KiB (`MAX_AUTH_FRAME_BYTES`, measured on the raw frame before the JSON is parsed), a frame that is not JSON or that `decodeClientFrame` refuses, any frame other than `auth.response`, and a second frame close the connection with `protocol_violation`. A frame over 64 KiB closes with 1009 at any time, because the WebSocket library refuses it first. A connection that is refused before `auth.ok`, or that times out, gets its close frame and is terminated 1 second later, so that it frees its place without waiting up to 30 seconds for the closing handshake.

Events after `auth.ok`:

1. Each text frame must contain one JSON event, which the gateway decodes with `decodeClientEvent`.
2. `bindIdentity` then binds the event to the connection (ADR 0006, identity binding). The event's `deviceId`, and for a `user` actor its `actor.userId`, must be the connection's; a mismatch is refused and audited as `event.identity_mismatch`, with the event ID as the subject and no workspace, because the event's workspace is unverified. It is never overwritten. Like `connection.replaced`, at most one such record is written per device per hour, and the other mismatches are logged with a count. Every event also reads the device again: a revoked device gets `device_revoked`; a newer sign-in, which replaced the key that signed, gets `key_replaced`; a disabled account gets `auth_failed`; a sign-out and a GitHub revocation after the sign-in get `sign_in_required`. The 30-day sign-in is not checked per event: an open connection may continue for 24 hours more, which the sweep checks. Last, the user must be an active member of `event.workspaceId` at this moment: a claimed person whose `removed_at` is empty. A workspace that does not exist is refused like one without the user.
3. Only the result, a `VerifiedEvent` (a second brand next to `UnverifiedEvent`, defined in `src/gateway.ts`), reaches the event handler, together with the `AuthenticatedConnectionContext`. The handler's type accepts nothing else. The default handler logs the event ID, the event type, and the connection ID at `debug` level. Nothing is routed, relayed, stored, or answered yet: the reference binding of runs, agents, projects, and repositories comes with the first event types that carry those references (#27, #28).
4. Events are handled one after another, in the order they arrived; the gateway awaits the event handler, which may return a promise, before the next event. While events wait, the gateway stops reading from the socket, so a fast sender cannot queue without bound. An event whose connection closed or was replaced during its checks is not delivered. A handler that throws or rejects closes the connection with 1011, and its error is logged through the redacting error serializer.
5. Anything else closes the connection. Frames that arrive after the gateway has decided to close are ignored.

| Close code | Reason                                                                                                            | When                                                                                                                                                                                                                                                |
| ---------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1001       | `server_shutdown`                                                                                                 | The API shuts down.                                                                                                                                                                                                                                 |
| 1003       | `binary_not_supported`                                                                                            | After authentication: a binary frame.                                                                                                                                                                                                               |
| 1007       | `invalid_json`                                                                                                    | After authentication: a text frame that is not JSON.                                                                                                                                                                                                |
| 1008       | `malformed`, `unsupported_version`, `unknown_type`, `invalid_payload`, `invalid_actor`, `not_allowed_from_device` | After authentication: `decodeClientEvent` refuses the event.                                                                                                                                                                                        |
| 1008       | `identity_mismatch`, `not_a_member`                                                                               | After authentication: `bindIdentity` refuses the event.                                                                                                                                                                                             |
| 1009       | (set by the WebSocket library)                                                                                    | A frame larger than 64 KiB.                                                                                                                                                                                                                         |
| 1011       | `internal_error`                                                                                                  | The server failed, for example its database or the event handler.                                                                                                                                                                                   |
| 4000       | `auth_failed`                                                                                                     | An unknown device, a bad signature, or a disabled account.                                                                                                                                                                                          |
| 4001       | `auth_timeout`                                                                                                    | No `auth.response` within 10 seconds.                                                                                                                                                                                                               |
| 4002       | `device_revoked`                                                                                                  | A valid signature from a revoked device, or after authentication a device that was revoked since.                                                                                                                                                   |
| 4003       | `sign_in_required`                                                                                                | A valid signature, but the device signed out, its last sign-in is 30 days old or older, or GitHub reported a revocation after it; after authentication, a sign-out or a GitHub revocation since, or the end of the 24-hour grace after the 30 days. |
| 4004       | `connection_replaced`                                                                                             | A newer connection of the same device authenticated.                                                                                                                                                                                                |
| 4005       | `protocol_violation`                                                                                              | Before authentication: a frame that breaks the rules above.                                                                                                                                                                                         |
| 4006       | `key_replaced`                                                                                                    | After authentication: a newer sign-in of the device replaced the key that signed.                                                                                                                                                                   |

The codes 4000 to 4006 and their reasons are `WS_CLOSE_CODES` of `@mymandev/protocol`, whose README lists what the desktop does for each. The codes from 1003 to 1011 stay provisional (P-24).

No authentication frame, nonce, or signature is logged. A refused connection is logged with its connection ID and the close reason only (`protocol_violation` at `debug` level, with what broke the rule, and the others at `info`), and an authenticated connection with its connection ID, user ID, and device ID. A connection that a route or the sweep closes is logged at `info` as "connection closed", with its connection ID and the close reason; a failed sweep is logged at `error` with a `DatabaseError`, which carries the SQLSTATE code and no SQL or parameters. What a client sends wrong on its socket, such as a frame over 64 KiB, is logged at `debug` level with the connection ID; any other socket error at `error` level.

`ConnectionRegistry` (`src/gateway.ts`) holds the open connections of the instance: the unauthenticated ones, for their cap, and the live connection of each device. `closeDevice(deviceId, reason, log)` and `closeUser(userId, reason, log)` close live connections with a close reason of the protocol and log each close; `closeConnection(deviceId, connectionId, reason, log)` closes one only while it is still the device's live connection. `live()` lists the live connections without their sockets, and `sendToUser(userId, frame, exceptDeviceId)` sends an account frame. `buildApp` takes a registry as an option, so tests can count and close connections.

Connections after `auth.ok` (ADR 0014, "Revocation, sign-out, and recovery"):

1. After its transaction commits, a route closes the affected connection at once: a sign-out with `sign_in_required`, a revocation with `device_revoked`, a sign-in of an existing device, which replaced its key, with `key_replaced`, and a sign-in that replaced a previous device with `device_revoked` for that device.
2. The account frames go only to the account's own connections, never to another account's, and only to connections that got `auth.ok` and are still open. `account.device_registered` reports a new device with its device list item (`current: false`); the new device has no connection yet. `account.device_revoked` reports a revocation over HTTP and a device that a sign-in replaced, with the reason and the time; the revoked device itself never gets it, because its connection closes first. A frame is never repeated: after `auth.ok` the desktop reads its devices over HTTP.
3. Every 60 seconds (`CONNECTION_SWEEP_INTERVAL_MS`), `sweepConnections` re-checks the devices of all live connections with one batched query (`deviceRows`, at most 500 device IDs per query) and closes each connection that its device no longer accepts, with the reasons of the per-event check: `device_revoked`, `key_replaced`, `auth_failed`, or `sign_in_required`. It finds what no route of this API sees, such as the operator command `db:account`. The 30-day sign-in counts with a grace of 24 hours (`SIGN_IN_GRACE_MS`): a connection that is open when the sign-in expires stays open for 24 hours more, and the first sweep after that, up to 60 seconds later, closes it with `sign_in_required`. A sweep closes only the connection that it checked: a newer connection of the device that registered meanwhile stays open. A tick while the previous sweep still runs is skipped, a failure of the database is logged and the next sweep tries again, and the interval stops when the API closes.
4. `devices.last_seen_at` is written at `auth.ok` and then by the sweep, at most every 5 minutes per device (`LAST_SEEN_INTERVAL_MS`), with one update for every device that is due (`markDevicesSeen`). A revoked device is left unchanged, also one revoked since the sweep read it. A device row that another transaction holds, such as a sign-in or a revocation, is skipped: the update never waits for a locked row, so it cannot deadlock with such a transaction. A skipped device is written at its next due time.

Decisions that ADR 0014 leaves open, settled by the Project Manager on 2026-10-31 (#89):

- A frame that breaks the rules before authentication closes with the new code `protocol_violation` (4005). The desktop does not reconnect on its own and shows an error; when the protocol versions differ, it asks the person to update.
- A connection whose key a newer sign-in of the device has replaced closes with the new code `key_replaced` (4006); the desktop reconnects at once with its new key.
- Above the cap of 200 unauthenticated connections, the handshake gets `429` with `rate_limited` and `Retry-After` before the upgrade.
- `devices.last_seen_at` is written when a connection authenticates, and by the sweep at most every 5 minutes for an open connection.
- Without the sign-in configuration or without the database, `/ws` answers `404`; the unauthenticated mode of M1-02 is gone.

Sending each run that a device revocation cancelled as `agent.run.state_changed`, with a `system` actor, `deviceId: null`, and the reason `device_revoked`, to the workspace's connections was moved to #110, where the workspace delivery lives, by the Project Manager on 2026-11-01. Until then, the revocation cancels those runs in the database, and the workspace's other connections are not told.

## Rules

- Credentials never appear in URLs, including the WebSocket URL. A browser `WebSocket` cannot set headers, which invites `/ws?token=...`; the query string would then reach proxies and browser history. WebSocket authentication uses the first message, `auth.response`.
- Logs contain the request method, the path without the query string, and the remote address. Errors are logged with their type, codes, message, and stack; an error that may carry query data (an own `query`, `params`, or `detail` property) is logged without message and stack.
- An event from a device stays `UnverifiedEvent` until `bindIdentity` has bound it to the authenticated connection. Never cast it to `ProtocolEvent` or to `VerifiedEvent`; only `bindIdentity` creates a `VerifiedEvent`, and the event handler accepts only that type with an `AuthenticatedConnectionContext`.
- `src/server.ts` is the only module with side effects. Tests build the application with `buildApp` from `src/app.ts` and use `inject` and `injectWS` without a network.

## Not included
