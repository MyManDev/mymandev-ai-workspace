# @mymandev/api

The cloud API: a Fastify application with a health endpoint, GitHub sign-in, device keys and access tokens, workspaces, GitHub's revocation webhook, and a WebSocket gateway that authenticates each connection with its device key, validates protocol events from [`@mymandev/protocol`](../../packages/protocol/README.md), and delivers workspace events and presence to the connections subscribed to a workspace. The decisions behind it are recorded in [ADR 0009](../../docs/architecture/decisions/0009-fastify-cloud-api.md), [ADR 0010](../../docs/architecture/decisions/0010-api-configuration-and-runtime.md), and [ADR 0014](../../docs/architecture/decisions/0014-accounts-devices-and-invitations.md).

## Start locally

From the repository root, after `npm ci`:

```sh
npm run start -w @mymandev/api
```

The API listens on `http://127.0.0.1:3000` and writes JSON log lines to standard output. Check it with:

```sh
curl http://127.0.0.1:3000/health
```

Stop it with Ctrl+C. The API logs "shutting down", closes every WebSocket connection with code 1001, and exits with code 0. On Windows, SIGTERM is never delivered; Ctrl+C sends SIGINT, which runs the same shutdown. When npm runs through `npm.cmd` on Windows, `cmd.exe` may then ask "Terminate batch job (Y/N)?"; the API has already stopped at that point.

For development, `npm run dev -w @mymandev/api` restarts the API when a source file changes, including a file in `packages/protocol`, and reads `apps/api/.env` if it exists. On Windows, a restart by `--watch` stops the process without running the shutdown handler; on Linux and macOS, `--watch` sends SIGTERM, which runs it.

Node.js runs the TypeScript source directly. There is no build step.

## Endpoints

### `GET /health`

Returns `200` with `{"status":"ok","version":"<version>"}`, where the version is the `version` field of `apps/api/package.json`.

Errors use one body shape, `{"statusCode":<code>,"error":"<status text>","message":"<message>","code":"<code>"}`, where `code` is one of `API_ERROR_CODES` of [`@mymandev/protocol`](../../packages/protocol/README.md) (ADR 0014, P-66). A route raises a typed `ApiError` with a code; the answer then has the code's fixed status and the status text as the message. Every other error gets a generic code for its status (`genericApiErrorCode`). A server error (5xx) always has the generic message "Internal Server Error". A client error keeps the message only when Fastify produced it, for example a validation error or `413` for a body over `API_BODY_LIMIT_BYTES`. An unknown route gets `404` with the message "Not Found" and the code `not_found`, and does not echo the method or the path. A malformed URL, an over-long path parameter (`414`), a malformed request line, headers over the limit (`431`), a request timeout (`408`), and a request that arrives while the API closes (`503`) get the status text as the message and a generic code too. A message is at most 100 characters. GET routes get no automatic HEAD route, so a rate limit counts every request against one budget.

A route with a rate limit answers `429` with `rate_limited` and `Retry-After` when it is reached (`@fastify/rate-limit`, in-memory store, one instance). A per-address limit counts an IPv6 client by its /64 network and an IPv4 client by its address; a request without an address shares one key. Routes that take a body validate it with the zod schema of `@mymandev/protocol` through `zodValidatorCompiler` (`src/validation.ts`), registered in their plugin scope: unknown keys are stripped, and a failure answers `400` with `bad_request` and a message that names the part, the path, and the issue, never an input value.

### Sign-in with GitHub

These routes exist only when GitHub sign-in is configured; otherwise they answer the generic `404`. They implement steps 2 to 5 of ADR 0014, "Sign-in". The API keeps every attempt, its PKCE verifier for GitHub, and the sign-in codes only in memory, and the codes and the cookie only as SHA-256 hashes. A timer drops expired entries every 15 seconds, and a restart drops them all. Every GitHub call refuses redirects, and a token in a failed exchange answer is deleted at once.

- `GET /auth/github/authorize`, opened by the desktop in the system browser with `code_challenge`, `code_challenge_method=S256`, `redirect_uri` (`http://127.0.0.1:<port>/callback`, ports 1024 to 65535), `state`, and optionally `login` and `prompt=select_account`. A malformed or repeated parameter gets an error page and never a redirect. A `code_challenge` or `state` that already started an attempt within the last 10 minutes, ended or not, also gets an error page and never reaches GitHub, because the authorize URL carries both and a second start could make another account's code acceptable to the desktop (#149); the desktop starts a new attempt instead. Otherwise it starts an attempt that lives 10 minutes (at most 1,000 open attempts), sets the attempt cookie, and redirects to GitHub with the API's own state and PKCE pair. With an `https` origin the cookie is `__Host-mmd_signin` with `Secure`, `HttpOnly`, `SameSite=Lax`, and `Path=/`; with an `http` origin, which only development and test allow, it is `mmd_signin` without `Secure` (#99).
- `GET /auth/github/callback`, GitHub's redirect. It needs the cookie of the attempt that the state names and runs once. A request that names a live attempt without its cookie ends that attempt, so GitHub's code from another browser is never exchanged (the phishing scenario of ADR 0014, "Threats"). It exchanges the code with a form-encoded body and never retries; a token answer with an `error` field fails whatever its status. It reads `GET /user`, then deletes the user token at once and keeps no GitHub token. The attempt keeps the account and the time at which the API started the code exchange, the earliest moment at which GitHub can confirm the account, and the sign-in code carries both. It shows the confirmation page with the GitHub login and the pairing code.
- `POST /auth/github/confirm`, the form of the confirmation page, with `state` and `decision` (`continue` or `cancel`). It accepts only a form body and needs the attempt's cookie. It refuses a request whose `Sec-Fetch-Site` header is present and not `same-origin`; without that header, the `SameSite=Lax` cookie keeps a cross-site form from carrying the attempt. Continue creates a sign-in code (`mmdc_`, single use, 60 seconds) and answers with a page that posts `code` and `state` to the desktop's listener, by a script and a visible button. The code never appears in a URL.

- `POST /auth/sign-in`, sent by the desktop with the sign-in code, its PKCE verifier, `redirect_uri`, and the device registration (`SignInRequestSchema`). It needs the database too. It takes the code once, also when a later check fails, and answers `401` with `auth_failed` for an unknown or expired code, a verifier whose S256 hash is not the bound challenge, another `redirect_uri`, or a signature that does not verify. A code that an earlier request with the verifier and `redirect_uri` of the code's attempt took answers `409` with `sign_in_code_used` to a request with the same two, and `auth_failed` to any other (below). A new device signs the `sign-in` input with its new key; an existing device signs it with its current key and with the new key. In one transaction the API then finds the account by GitHub's numeric ID, never by login, and refreshes the login, or creates the account with the GitHub name as its first display name, or the login when the name is not usable. It registers the device or replaces its key, keeping the device ID and clearing a sign-out, and revokes a named previous device of the same account as `replaced`. A new device whose key already belongs to an active device of the same account gets that device instead (below). It refuses a disabled account (`auth_failed`), a GitHub identity whose revocation GitHub reported after the API read it (`sign_in_required`, below), a device of another account (`device_account_mismatch`), a revoked device (`device_revoked`), a new device while the registration lock is active (`device_registration_locked`), a new device on an account that already has 20 active devices (`409` with `device_limit` and no `Retry-After`, Project Manager decision of 2026-11-10, #255: no time frees a place, only revoking a device does, so it is not `rate_limited`, which says to wait; a named previous device of the account does not count, because the new device replaces it), and more than 10 new devices in 24 hours (`429` with `device_daily_limit` and, as `Retry-After`, the seconds until the oldest of them is 24 hours old; Project Manager decision of 2026-11-14, #269, until then `rate_limited` with the same header). The limit of active devices is decided first, so a new device at both limits answers `device_limit`, for which no wait helps. The limit of new devices counts every device of the account that was created in the last 24 hours, also a revoked one and a named previous device, unlike the limit of active devices. It refuses inside the transaction, before anything is committed: it registers no device and no key, revokes no previous device, keeps the login as it was, and sends no frame (#269). That is why it has its own code: the answer is certain, so the desktop deletes the new key and shows the wait. The route's own limit of 30 requests per remote address in 10 minutes answers `429` with `rate_limited` and a `Retry-After` of at most 10 minutes, before the code is taken, so it can answer a resent copy of a request that committed too (#152). It is the only `rate_limited` of this route, and the desktop takes it as uncertain and keeps the new key. It writes audit records for the sign-in and for the registration or key replacement, and answers with the user ID, the device ID, the display name, the login, and the sign-in expiry, 30 days later, without any credential. After the commit, the device's open connection, which used the replaced key, closes with `key_replaced`, and a replaced previous device's connection with `device_revoked`; the account's other connections get `account.device_registered` for a new device and `account.device_revoked` for the replaced one (see `GET /ws`).

One sign-in request can arrive twice: when the connection breaks after the API committed but before the answer arrived, the desktop's network stack or a retrying proxy can send the same `POST` again (#152). So that the second copy does not read as "nothing was committed", the API records a code as used when a request with the code's verifier and `redirect_uri` takes it: the SHA-256 hash of the code, never the code, with its PKCE challenge and `redirect_uri`. The record is written before the request's first database query, so a copy that arrives while the request runs finds it, and its 60 seconds start again when the request ends, so a slow request still leaves its copies the full minute. A request with a recorded code answers `409` with `sign_in_code_used` when its verifier's S256 hash is the bound challenge and its `redirect_uri` the bound one, whether the earlier request committed or a later check refused it; without both, it answers `auth_failed`, so only the attempt's own desktop learns that the code was used. A code that a request without them consumed leaves no record, because that request committed nothing, so the attempt's own request then gets `auth_failed`. The records live in memory only, like the codes: a copy that reaches a restarted API gets `auth_failed`. The answer does not repeat the first answer and does not say whether the earlier request committed; the desktop treats it as uncertain. The status is `409` because the request conflicts with the state of the code, as `conflict` does with the state of a resource; the `401` codes say that a check of the request failed, and this request's verifier and `redirect_uri` match the code's attempt (its device signatures are not checked before this answer). A recorded code keeps a place under the cap until its record expires: at most 1,000 open codes, and at most 2,000 open codes and records together. A record is written right after its code left the open codes, so it always fits; one that expired during a request longer than a minute comes back at the request's end only within that cap.

A new device can also come again with the same key (#153): when the answer of its registration is lost, the desktop keeps the key and sends it once more with a new code, for at most 7 days, because it cannot learn whether the API registered it. In its transaction the API looks the key up before the registration lock and the limits, and locks the row that holds it as it locks an existing device's row. A key of an active device of the same account answers `200` with that device only while the device cannot have been used: it was registered less than 7 days earlier, and `devices.first_authenticated_at` is empty, so it never proved its key under its device ID. That column is set by the device's first access token (before the token is issued, waiting for a sign-in that holds the row), its first WebSocket authentication, and its first sign-in that replaced its key; migration `0014_device_first_authenticated` sets it to the creation time of every device that existed before. A copied key of a device in use therefore cannot renew itself without being replaced, as "Each GitHub sign-in replaces the key" of ADR 0014 requires for such a device. The `newKeySignature` proves the private key, so the repeat is a sign-in of that device like any other. It renews the device's sign-in expiry and clears a sign-out, keeps the label and the platform, writes only the `account.signed_in` audit record, and sends no `account.device_registered`. The device limits and the registration lock do not apply, because no device is added. The code is consumed as usual. The repeat ignores a named previous device: the first commit revoked it already, and the repeat revokes nothing. A key of a revoked device, of another account's device, of a device that authenticated, or of a device registered 7 days ago or earlier, and a request that names the key's own device as its previous device, answer `409` with `conflict` and change nothing. Two sign-ins of an existing account wait for each other at the account's identity row, so of two registrations with the same key the later one finds the device that the earlier one committed. When both create the account, the later one fails on the identity that the earlier one created; a sign-in whose transaction fails with a unique violation runs it once more, which finds the account and then the device, and a second unique violation, such as the same key registered for another account at the same time, answers `conflict`.

A sign-in rests on the GitHub identity that the API read at GitHub's callback, but a device's last sign-in is the time of `POST /auth/sign-in`, up to 10 minutes for the attempt and 60 seconds for the code later. A revocation that GitHub reports in between (see `POST /auth/github/webhook`) would therefore not reach the device that this sign-in registers (#115). `POST /auth/sign-in` answers `401` with `sign_in_required` when a revocation of the identity was recorded later than the time that the code carries. Later means strictly later, as when the device state compares `sign_in_required_at` with a device's last sign-in: a revocation recorded at the same moment does not count. Two records are checked:

- The webhook keeps every verified revocation in a list in API memory, by GitHub's numeric ID, before its transaction starts, also for a sender without an account. An entry lives 13 minutes: an attempt and its code, and 2 minutes of margin for the check after the commit (below). The list holds at most 10,000 IDs and drops the oldest beyond that, a timer drops expired entries every 15 seconds, and a restart drops them all, as it drops the attempts. Nothing about a person without an account is stored in the database. `POST /auth/sign-in` checks the list before its transaction, so a first sign-in whose identity was read before the revocation creates no account.
- In the transaction that registers the device, the API reads `users.sign_in_required_at` under the account's row lock (`FOR NO KEY UPDATE`), which a revocation takes too. A revocation that committed first is seen there; one that waits for the sign-in then sets `sign_in_required_at` past the last sign-in of the device that the sign-in registered, so that device must sign in again. Which of the two requests took the earlier time before its transaction does not matter.

Both checks come before the device checks: a sign-in whose identity is too old answers `sign_in_required` also for a revoked device or a device of another account, and the next sign-in gets the device's own answer. A refused sign-in registers no device, replaces no key, and changes nothing in the database; the desktop starts a new sign-in.

After its commit, the sign-in checks the list again. A revocation that the webhook recorded while the transaction ran may have been missed by the webhook's own lookup, as for an account that this sign-in created, so the API then sets the account's `sign_in_required_at` as a revocation does, without an audit record (`requireSignIn` of `@mymandev/database`). The device is registered and its key replaced by then, so the answer stays `200` with the device, and the device's next authentication answers `sign_in_required`. Every order of the two requests is covered: a revocation recorded in memory before the first check refuses the sign-in, one recorded before the second check is marked there, and one recorded after it starts its transaction after the commit, so its lookup finds the account.

The opposite case is accepted: GitHub delivers the webhook about a minute after the revocation, and the delivery carries no time (#67), so a real new sign-in within that minute is required again when the delivery arrives. Another sign-in recovers from it. A replayed copy of a signed revocation, the risk accepted for #90 (see `POST /auth/github/webhook`), now also refuses the first sign-ins of that GitHub account that are in progress, for up to those 13 minutes; the remedy stays a new webhook secret. The list in memory, the lock, and the rule of the revocation are a decision for #115, applied on 2026-11-01 under the Project Manager's rule to apply the recommended option.

When an attempt ends without a code, the page posts `error` and `state` to the listener instead: `access_denied` (declined on GitHub or Cancel), `sign_in_failed` (GitHub did not confirm the code or the account), `unsupported_account` (a login outside the login rule), or `sign_in_unavailable` (GitHub's limit, with `Retry-After` on the page, or the API's cap of open and recently used sign-in codes; the desktop gets only the error value). A request without a valid attempt gets an error page and posts nothing.

The pages load nothing from outside and send `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and a Content Security Policy with `default-src 'none'`, a hash for the one style and the one script, `frame-ancestors 'none'`, and a `form-action` that allows only the API itself or this attempt's listener. Each route allows 30 requests per address in 10 minutes. The API logs a warning above 1,500 token exchanges in an hour, below GitHub's limit of 2,000. No code, state, cookie, token, verifier, or GitHub response body is logged.

### Access tokens and devices

These routes need GitHub sign-in and the database (ADR 0014, "Device key and authentication" and "Revocation, sign-out, and recovery"). Challenges and access tokens live only in API memory, the tokens as SHA-256 hashes; a restart drops them, and the desktop fetches a new token.

- `POST /auth/challenge` returns a challenge ID and a nonce. The challenge is single use and valid for 60 seconds; at most 1,000 are open (`429` with `rate_limited` and `Retry-After`).
- `POST /auth/access-token` takes the device ID, the challenge ID, and a signature over the `http` input. The signature is checked first with the device's current key; an unknown device, a used or expired challenge, or a bad signature answers `auth_failed`. Only then does the device answer: `device_revoked`, `sign_in_required` (signed out, last sign-in 30 days ago or more, or a GitHub revocation after the last sign-in), or `auth_failed` for a disabled account. Before the first token it records `devices.first_authenticated_at`, which ends the repeat of the device's registration (#153, above). It returns an access token (`mmda_`, 15 minutes, never extended). A device may mint 30 tokens in 15 minutes and keeps at most 3 live tokens; a fourth ends the oldest. A token belongs to the device's sign-in: a new sign-in, which also replaces the key, ends the earlier tokens. Both routes answer with `Cache-Control: no-store`.
- Every other route below needs `Authorization: Bearer <access token>`, and so do the workspace routes. `src/auth/authenticate.ts` checks the token and the account's limit of 300 authenticated requests a minute, which counts every authenticated route together, when the headers arrive. The token, the device, and the account are checked again after the body arrived and before it is validated, so that a slow body cannot carry a request past a revocation; sign-out, revocation, lifting the lock, creating a workspace, changing its limit of unclaimed people, the people and invitation routes, and accepting an invitation check them a third time inside their transaction (`lockActor`). Every failure is `401` with `unauthorized`.
- `POST /auth/sign-out` signs the current device out: the device, its agents, and their grants stay, its tokens stop working, its WebSocket connection closes with `sign_in_required` after the commit, and the next token needs a GitHub sign-in (P-65).
- `GET /devices` lists the account's own devices, newest first, with the sign-in expiry and the current device. Its `registrationLockedUntil` is the end of the account's registration lock (below) while it is in force, otherwise null (#209). The lock is in force while its end is later than now, as the sign-in checks it, so an ended lock reads null although `users.device_registration_locked_until` keeps its end. The devices and the lock come from one read-only snapshot, so a revocation as `lost` never shows its lock without the revoked device.
- `POST /devices/:deviceId/revoke` with `reason` `removed` or `lost` revokes one of the account's own devices in one transaction: its agents are disabled, their grants revoked, and their unfinished runs cancelled (`revokeDevice`). After the commit, the device's WebSocket connection closes with `device_revoked`, the account's other connections get `account.device_revoked`, and each disabled agent, each revoked grant, and each cancelled run reach the connections subscribed to their workspace as `workspace.agent.disabled`, `agent.grant.revoked`, and `agent.run.state_changed`, in this order (see "Workspace subscriptions, presence, and delivery"). Another account's device answers `404` with `not_found`, also for the owner of a shared workspace; a revoked device answers `409` with `conflict`. `lost` also refuses new device registrations for 7 days; the current device cannot report itself `lost` (`409` with `conflict`), so that whoever holds it cannot lock the account's new devices.
- `POST /account/registration-lock/lift` lifts that lock from an active device. It answers `204` also when no lock is in force; the device list tells whether one is.

Sign-out, revocations, and the lock write audit records. No `Authorization` header, token, nonce, or signature is logged.

The operator command (`db:account`) runs outside the API and cannot drop tokens from its memory: after disabling and enabling an account within 15 minutes, a token minted before the disable works again until it expires. Erasing an account (`db:account -- erase`, #93) revokes its devices, so its tokens stop working at once and its connections close at the next sweep; the API sends no membership, agent, grant, or run events for an erasure, and the other members see it when they next load the workspace ([`@mymandev/database`](../../packages/database/README.md#operator-commands)).

### Workspaces

These routes need GitHub sign-in, the database, and an access token, like the device routes (ADR 0014, "People and roles", "Limits", and "What a workspace ID allows"; #91). Their bodies and answers are the schemas of `MEMBERSHIP_ROUTES` in [`@mymandev/protocol`](../../packages/protocol/README.md).

- `GET /workspaces` lists the workspaces that the account is an active member of, each with the account's own person, the most recently claimed first, at most 1,000 (`listWorkspaces`).
- `POST /workspaces` with `name`, `displayName`, and an optional `maxUnclaimedMembers` from 1 to 500 creates a workspace with the creator's person as its claimed `owner`, named `displayName`, and answers `200` with both. The workspace holds at most `maxUnclaimedMembers` active unclaimed people, 500 when it is omitted (Project Manager decision of 2026-11-02); a value outside 1 to 500 answers `400` with `bad_request`. `workspaces.created_by_user_id` stays a historical fact; ownership lives in the role. One transaction checks the account and the device again (`lockActor`), then `createWorkspace` locks the account, counts the workspaces it created in the last 24 hours, and refuses an 11th with `429`, `rate_limited`, and `Retry-After`: the seconds until the oldest of them is 24 hours old. It writes a `workspace.created` audit record. It sends no workspace event: the protocol has none for it, and the creator is the only member.
- `GET /workspaces/:workspaceId` answers with the workspace, all its people, the time join requests were paused, the limit of active unclaimed people as `maxUnclaimedMembers`, and the ownership offer unless it is 7 days old (`workspaceView`). Each person has its display name and role and, once claimed, the account's GitHub login with the time it was last verified, which is the account's last GitHub sign-in. Removed people stay in the list with `removedAt`, so that the desktop shows them as former members. The list holds at most 1,000 people: the owner, the target of the offer, the other claimed active people, then the unclaimed people, each the most recently created first, then the former members, the most recently removed first. So unclaimed people never push a claimed member out of the view, and with at most 500 of them they fill at most half of it.
- `POST /workspaces/:workspaceId/unclaimed-member-limit` with `maxUnclaimedMembers` from 1 to 500 changes how many active unclaimed people the workspace may hold and answers `204` (`setUnclaimedMemberLimit`; Project Manager decision of 2026-11-02). One transaction checks the account and the device again (`lockActor`), locks the caller's person, then the workspace row, and counts the active unclaimed people, people without an account who are not removed. Only the owner: an admin or a member gets `403` with `forbidden`, as on the other owner-only routes. A value below that count answers `409` with `conflict`, and a value outside 1 to 500 `400` with `bad_request`. It writes a `workspace.unclaimed_member_limit_changed` audit record without the value; sending the limit in force again answers `204` and writes nothing. No workspace event reports a change, because the protocol has none; the members read it from the workspace view.
- Every route under `/workspaces/:workspaceId` checks active membership first (`src/workspaces/access.ts`), right after the access token and before the path, the query, and the body are validated. An account without an active person in the workspace gets `404` with `not_found`, byte for byte the answer for a workspace that does not exist or a malformed workspace ID, whatever else the request holds.

The people routes (`src/workspaces/people-routes.ts`; ADR 0014, "People and roles" and "Removal and ownership") run each change in one transaction that checks the account and the device again (`lockActor`) and then locks the people it decides on, the caller's own person included, so that a caller removed or a person changed in the meantime is seen. A display name has 1 to 64 characters under the text rule of ADR 0005. A `role` in a body is stripped, as the protocol schemas strip every unknown field: an unclaimed person is always a `member`. For an active member, a body that breaks the protocol and a malformed person ID answer `400` with `bad_request`, and a person ID that the workspace does not have answers `404` with `not_found`; a non-member gets the membership check's `404` before any of them.

- `POST /workspaces/:workspaceId/members` with `displayName` defines an unclaimed person with the role `member` and answers `200` with it (`defineMember`). The owner and admins only; a member gets `403` with `forbidden`. After the caller's person it locks the workspace row and counts the active unclaimed people, so that concurrent definitions and a change of the limit are counted one after another; a workspace that already holds as many as its limit answers `409` with `unclaimed_limit` and no `Retry-After`, defines nobody, and sends no event (Project Manager decision of 2026-11-10, #242). No time frees a place, only removing or claiming an unclaimed person or a higher limit, so it is not `rate_limited`, which every other limit of ADR 0014 except the 20 active devices (`device_limit`, #255) answers and which says to wait. The account's limit of 300 requests a minute still answers this route with `rate_limited`. It writes a `member.defined` audit record and sends `workspace.member.defined`.
- `POST /workspaces/:workspaceId/members/:memberId/rename` with `displayName` renames a person and answers `204` (`renameMember`). Every member renames their own person, and the owner or an admin renames an unclaimed person; another claimed person answers `403` with `forbidden`, for the owner too, and so does an unclaimed person for a member. A removed person answers `409` with `conflict`. It writes a `member.renamed` audit record and sends `workspace.member.renamed`.
- `POST /workspaces/:workspaceId/members/:memberId/remove` removes a person and answers `204` (`removeMember`; ADR 0014, "Removal and ownership"). The owner removes any person except the owner; an admin removes unclaimed people and claimed people with the role `member`. Everything else answers `403` with `forbidden`: a member's removal, an admin's removal of the owner or of another admin, and anyone's removal of their own person, who leaves instead. A removed person answers `409` with `conflict`. It writes a `member.removed` audit record.
- `POST /workspaces/:workspaceId/leave` lets the caller's own person leave and answers `204` (`leaveWorkspace`). An admin or a member leaves; the owner gets `403` with `forbidden` and transfers ownership first. It writes a `member.left` audit record, and the leaving account is the remover.
- `POST /workspaces/:workspaceId/members/:memberId/promote` makes an active, claimed `member` an `admin` and answers `204` (`promoteMember`). Only the owner, from a device registered more than 72 hours earlier (`devices.created_at`); a device that is not older than 72 hours answers `403` with `device_too_new`. It writes a `member.promoted` audit record and sends `workspace.member.role_changed` with the role `admin`.
- `POST /workspaces/:workspaceId/members/:memberId/demote` makes an active `admin` a `member` and answers `204` (`demoteMember`), from any of the owner's devices. In the same transaction it revokes the invitations that the admin created in the workspace, each neither accepted nor revoked, also an expired one, as a removal does, with an `invitation.revoked` audit record with the reason `creator_demoted` for each, so that their codes answer `invitation_invalid`. It writes a `member.demoted` audit record and sends `workspace.member.role_changed` with the role `member`; the revoked invitations send no event.
- For both, a caller other than the owner, and the owner's own person, answers `403` with `forbidden`: the owner's role changes only by transfer, so nobody changes their own role. A removed person, an unclaimed person, who is always a member, promoting an admin, and demoting a member answer `409` with `conflict`. A role change ends no subscription; the person's devices see the event like every other subscriber.
- A removal and a departure are one transaction: it sets `removed_at` and `removed_by_user_id` and clears an ownership offer to the person; revokes the person's own invitation and the invitations that the person's account created in the workspace, each neither accepted nor revoked, also an expired one, with an `invitation.revoked` audit record with the reason `member_removed` for each; and, for a claimed person, disables the account's agents in the workspace's projects, revokes their active grants with the remover as `revoked_by_user_id`, and cancels with the reason `member_removed` the unfinished runs in the workspace that run on those agents or that the account requested on another member's agent. Nothing outside the workspace changes, and nothing is deleted: the view shows the person as a former member, and an account that rejoins with a new invitation claims a new person.
- After the commit, in this order: `workspace.member.removed` goes through the membership event delivery, which first ends the person's subscriptions to the workspace with `workspace.unsubscribed` and `membership_ended` and sends the person's `offline` to the other subscribers; every connection of the person's account that got `auth.ok` gets `account.removed_from_workspace` with the workspace and the time of the removal, also a connection that subscribed to nothing, through `onAccountFrame` as for a join request decision; and each cancelled run goes to the workspace's remaining subscribers as `agent.run.state_changed` through the connection registry, as after a device revocation (see "Workspace subscriptions, presence, and delivery"). `buildApp` connects both to the registry, which sends at once, so the order holds. An unclaimed person has no account, agents, or runs, so only the event is sent. The per-event membership check stays the backstop: the account's next event in the workspace closes its connection with `not_a_member`.
- The membership events have a `system` actor and `deviceId: null`, as the protocol requires of events that only the server originates. After the commit, a deeply frozen copy of each goes to the connections subscribed to the workspace (see "Workspace subscriptions, presence, and delivery") and then to the `onWorkspaceEvent` option of `buildApp`, which tests use to observe the events; the copy shares no object with the answer. The delivery logs the event type, the workspace ID, and the number of connections at debug level. The route does not wait for the option, so a hook that never returns cannot hold the answer. A failure of the hook is logged with the event type, the workspace ID, and the error's type, never its message, which may quote a display name; it does not change the answer, because the change is already committed. A refused request sends no event.

The ownership routes (`src/workspaces/ownership-routes.ts`; ADR 0014, "People and roles" and "Removal and ownership") run each change in one transaction that checks the account and the device again (`lockActor`) and then locks, in one statement and in the order of their IDs, the caller's own person, the owner, the person that holds the offer, and the person that a new offer names. A workspace has at most one offer, `ownership_offered_at` on the target's row, and an offer lives 7 days: from then on it is no offer, the view no longer shows it, and accepting or withdrawing it answers `409` with `conflict`. Each answers `204` without a body. The offer frames below, `account.ownership_offered` and `account.ownership_offer_ended`, go to every connection of the target's account and then of the owner's account that got `auth.ok`, also one that subscribed to nothing, through `onAccountFrame`, as after a removal, so that every device of both people reads the offer again (#241). They are two accounts, because a person of the workspace belongs to one account and the target is never the owner. No other member is told: no workspace event reports an offer or its end.

- `POST /workspaces/:workspaceId/ownership-offer` with `memberId` offers the ownership to another active, claimed person, an admin or a member (`offerOwnership`). Only the owner, from a device registered more than 72 hours earlier, as for a promotion; a device exactly 72 hours old or younger answers `403` with `device_too_new`, decided after the role and before the person's state. Anyone else, and an offer to the owner's own person, answer `403` with `forbidden`; an unclaimed or removed person, and a workspace with a live offer, to this person or another, answer `409` with `conflict`. It writes an `ownership.offered` audit record. After the commit every connection of the target's account and then of the owner's account, the offering device's included, gets `account.ownership_offered` with the offer, as the view shows it; no other member is told, and no workspace event is sent, because the protocol has none for an offer. A refusal writes nothing and sends nothing.
- `POST /workspaces/:workspaceId/ownership-offer/accept` lets the target accept the live offer from any of its devices (`acceptOwnershipOffer`): one transaction makes the owner an `admin` and then the target the `owner`, so the unique index of one owner never sees two, and clears the offer. The owner answers `403` with `forbidden`, and so does any other person while the offer names someone else; without a live offer, also after a withdrawal, it answers `409` with `conflict`. It writes an `ownership.transferred` audit record and, after the commit, sends `workspace.ownership.transferred` with the former and the new owner's people through the membership event delivery, to the connections subscribed to the workspace. Then every connection of the former owner's account and of the new owner's account gets `account.ownership_transferred` with the workspace, both people, and the time of the acceptance as `transferredAt`, also a connection that subscribed to nothing, so every device of both people learns of the transfer (ADR 0014, "Removal and ownership"). A subscribed connection of either account gets the event first and then the frame. A refused acceptance sends neither the event nor this frame.
- `POST /workspaces/:workspaceId/ownership-offer/withdraw` lets the owner withdraw the live offer from any of the owner's devices (`withdrawOwnershipOffer`). Anyone else answers `403` with `forbidden`; without a live offer it answers `409` with `conflict`. It writes an `ownership.offer_withdrawn` audit record, and after the commit every connection of the target's account and then of the owner's account, the withdrawing device's included, gets `account.ownership_offer_ended` with the reason `withdrawn` and the time of the withdrawal. An offer that another device of the owner makes while the withdrawal waits is not withdrawn: the withdrawal decides as if it came first.
- An expired offer is cleared by the owner's next offer or withdrawal, or by the target's acceptance, and only then; the reads skip it. The clearing writes no audit record, and after the commit every connection of the target's account and then of the owner's account gets `account.ownership_offer_ended` with the reason `expired` and the offer's expiry as `endedAt`, also when the target's acceptance cleared it: before `account.ownership_offered` of the new offer, which then reaches the new target's and the owner's accounts, and before the `409` of an acceptance or a withdrawal, whose transaction commits the clearing. A transaction that rolls back sends nothing. Another person's acceptance of an expired offer answers `409` and clears nothing.
- For the desktop (#26, #95): an `account.ownership_offer_ended` frame names no offer, only the workspace. Its `endedAt` is never earlier than the `offeredAt` of the offer that it ends: the time of the withdrawal, or the offer's expiry. The desktop reads the workspace view again on every `account.ownership_offer_ended`, whichever offer it ends.
- A removal or a departure of the target clears the offer in its transaction and sends no offer frame to either account, since the target's account gets `account.removed_from_workspace` and the owner's subscribed devices get `workspace.member.removed`. An acceptance sends no offer frame either: `account.ownership_transferred` tells both accounts. A demotion of the target keeps the offer, because ADR 0014 lets the owner offer ownership to a member too. The owner can be neither removed nor demoted.

The invitation routes (`src/workspaces/invitation-routes.ts`; ADR 0014, "Invitations" and "Limits") are for the owner and admins only; a member gets `403` with `forbidden` on each of them. A change runs in one transaction that checks the account and the device again (`lockActor`) and then locks the caller's own person and the invited person, before it touches an invitation of that person. For an active member, a body that breaks the protocol and a malformed ID answer `400` with `bad_request`, and a person or invitation ID that the workspace does not have answers `404` with `not_found`; a non-member gets the membership check's `404` before any of them. Invitations send no membership event, because only the owner and admins see them.

- `POST /workspaces/:workspaceId/invitations` with `memberId` and an optional `lifetimeSeconds`, from 3,600 (1 hour) to 604,800 (7 days) and 7 days when omitted, creates an invitation for an unclaimed person and answers `200` with the invitation and its code, with `Cache-Control: no-store` (`createInvitation`). The code is `mmdi_` and 32 random bytes as base64url. This answer is the only place it appears: the database stores its SHA-256 hash, and the list, the logs, and the audit records never hold it. A claimed or removed person answers `409` with `conflict`. In the same transaction it revokes the person's earlier invitation that is neither accepted nor revoked, with an `invitation.revoked` audit record with the reason `replaced`, so that a lost code is replaced by a new invitation; it writes an `invitation.created` audit record. A workspace has at most 50 live invitations, not counting the one that the new invitation replaces, and at most 100 new invitations within 24 hours. Beyond either limit the route answers `429` with `rate_limited` and `Retry-After`: the seconds until the live invitation that expires first expires, or until the oldest invitation of the 24 hours leaves the window, the later of the two when both limits are reached.
- `GET /workspaces/:workspaceId/invitations` lists the live invitations, those neither accepted, revoked, nor expired, the most recently created first, each with `createdByMemberId`, the creator's person (`listInvitations`). It holds no code and no hash.
- `POST /workspaces/:workspaceId/invitations/:invitationId/revoke` revokes a live invitation and answers `204` (`revokeInvitation`), with an `invitation.revoked` audit record without a reason. An invitation that is already revoked, accepted, or expired answers `409` with `conflict`, so a second revocation changes nothing.

Previewing and accepting an invitation code (`src/workspaces/invitation-code-routes.ts`; ADR 0014, "Invitations", "Limits", and "Threats") needs only a signed-in device: the routes are not under `/workspaces/:workspaceId`, and the code travels only in the request body, never in a path or a query. Every answer of both routes, an error too, carries `Cache-Control: no-store`. A body without a well-formed code answers `400` with `bad_request`, and the message never quotes the code. The API looks the invitation up by the SHA-256 hash of the code.

- `POST /invitations/preview` with `code` answers `200` with the workspace's name, the display name of the person that the code claims, the inviter, and the expiry (`previewInvitation`). The inviter is the creator's person in the workspace, with its display name and its GitHub login and the time the login was last verified. A preview consumes nothing and writes nothing.
- `POST /invitations/accept` with `code` claims the person and answers `200` with the workspace and the claimed person, a `member` with the account's GitHub login (`acceptInvitation`). One transaction checks the account and the device again (`lockActor`), locks the invitation's person, consumes the invitation with a conditional update (only if the hash matches and the invitation is neither accepted, nor revoked, nor expired), records the accepting account and device, and claims the person only if it is still unclaimed and not removed. When either update changes nothing, the transaction rolls back. Of two acceptances of one code, only the first claims the person. It writes an `invitation.accepted` and a `member.claimed` audit record and, after the commit, sends `workspace.member.claimed` with the claimed person through `onWorkspaceEvent`, like the people routes.
- An account that is already an active member of the code's workspace gets `409` with `already_member` on both routes, whatever the state of the invitation, before anything is consumed: the invitation stays as it was. When the account claims another person of that workspace while its acceptance runs, the unique index of one active person per account and workspace refuses the claim, and the answer is `already_member` too.
- Every other refusal answers `404` with `invitation_invalid`, byte for byte the same: an unknown, used, expired, or revoked code, a removed person (whose invitation the removal revoked), a code of an archived workspace (reason `workspace_archived`, whatever the invitation's state; the erasure that archives a workspace revokes its codes too), and, in a preview, an inviter without a person or a GitHub identity in the workspace. The API logs `invitation code refused` at info level with the reason and the invitation's ID (none for an unknown code), never with the code or its hash.
- An account may fail 10 times within 15 minutes, previews and accepts together; only an `invitation_invalid` answer is a failure. An attempt counts from its start until its answer is known, so concurrent attempts count too. Beyond the limit both routes answer `429` with `rate_limited` and `Retry-After`, the seconds until the oldest counted attempt is 15 minutes old, for every code, a valid one too, so that the limit bounds guessing. The count lives in API memory, like the other limits of one instance.
- A claim always takes the person that the invitation names, a new person row: an account that was removed rejoins as a new person with a new invitation, and its earlier person stays as a former member.

Join requests (`src/workspaces/join-request-routes.ts`; ADR 0014, "Join requests", "Limits", "Lifetimes", and "What a workspace ID allows"; #92). A join request is the only action that a workspace ID allows a non-member, so the requester's routes are not under `/workspaces/:workspaceId`: `POST /join-requests` takes the ID in its body. A change runs in one transaction that checks the account and the device again (`lockActor`) first. A display name has 1 to 64 characters under the text rule of ADR 0005, and a body that breaks the protocol, or a malformed ID, answers `400` with `bad_request`; a `note` or any other unknown field is stripped.

- `POST /join-requests` with `workspaceId` and `displayName` answers `200` with the request as its requester sees it: its ID, the workspace ID, the requested name, and when it was created and expires, 7 days later, and nothing about the workspace (`createJoinRequest`). It stores the requesting device and writes a `join_request.created` audit record. A second request while one is pending answers with the pending request, unchanged, also while requests are paused (awaiting the Project Manager's confirmation). An unknown and an archived workspace answer the same `404` with `workspace_not_found`, byte for byte; a paused workspace and a block of the account answer the same `403` with `join_requests_closed`; an active member gets `409` with `already_member`. The limits of ADR 0014 answer `429` with `rate_limited` and `Retry-After`: 24 hours after a denial by the same workspace, 5 pending requests of the account, 10 requests of the account within 24 hours, and 50 pending requests in the workspace. The waits of the account's own limits are exact; the wait of the workspace's limit is rounded up to the next full hour, so that it does not tell when another account asked. A request past its expiry no longer counts as pending; the next request of the account in that workspace marks it `expired` before it is stored.
- `GET /join-requests` lists the account's own requests, the most recent first, at most 1,000, each with `decision` and `decidedAt`: null while pending, then `approved`, `denied`, `withdrawn`, or `expired`. A block is shown as `denied`, and a request past its expiry as `expired` before it is marked (`listOwnJoinRequests`).
- `POST /join-requests/:joinRequestId/withdraw` withdraws the account's own pending request and answers `204`, with a `join_request.withdrawn` audit record (`withdrawJoinRequest`). Another account's request answers the same `404` with `not_found` as one that does not exist; a request that is no longer pending answers `409` with `conflict`.

The approvers' routes lie under `/workspaces/:workspaceId`, behind the membership check, and are for the owner and admins only; a member gets `403` with `forbidden`. A change runs in one transaction that checks the account and the device again (`lockActor`), then locks the caller's own person, then the request, the pending requests in the order of their IDs, or the workspace row. A request ID that the workspace does not have answers `404` with `not_found`; a request that is decided, withdrawn, or past its expiry answers `409` with `conflict`, so a decision is made once.

- `GET /workspaces/:workspaceId/join-requests` lists the pending requests, then the blocks in force, each with the requested name, the requester's GitHub login with the time it was last verified, and the creation date of the GitHub account (`listJoinRequests`). A pending request of an account that is already an active member, for example after accepting an invitation, is left out, because approving it could only answer `already_member`.
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/approve` with an optional `displayName` answers `200` with the new person (`approveJoinRequest`): in the same transaction it creates a claimed person of the requester with the role `member`, named `displayName` or else the requested name. A requester who was removed earlier rejoins as a new person. A requester who is already an active member answers `409` with `already_member`, and the request stays pending. It writes a `join_request.approved` and a `member.claimed` audit record and, after the commit, sends `workspace.member.claimed` with the new person through `onWorkspaceEvent`, like the people routes.
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/deny` answers `204` and writes a `join_request.denied` audit record (`denyJoinRequest`). The requester can ask the workspace again 24 hours later; "deny and invite instead" is a denial followed by `POST /workspaces/:workspaceId/invitations`.
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/block` denies a pending request and blocks its account, answers `204`, and writes a `join_request.blocked` audit record (`blockJoinRequest`). Until the block is lifted, a new request of the account answers `403` with `join_requests_closed`, the same answer as for a pause; the requester sees the request as `denied`, and the approvers' list shows the block. A block needs a pending request, so a requester who withdraws the request before it is blocked escapes the block and can ask again at once; the approvers can pause join requests to keep such a requester out (for the screens of #95).
- `POST /workspaces/:workspaceId/join-requests/:joinRequestId/unblock` lifts a block in force, answers `204`, and writes a `join_request.unblocked` audit record (`unblockJoinRequest`). A request that is not blocked, or whose block was already lifted, answers `409` with `conflict`. The account can ask again at once; the 24-hour wait follows only a denial. The requester still sees `denied`, and nothing is sent to them; the owner and admins get `workspace.join_request.unblocked` (below). The desktop may still reload the list when an unblock answers `conflict`.
- `POST /workspaces/:workspaceId/join-requests/deny-all` denies every pending request of the workspace, answers `204`, also when nothing is pending, and writes one `join_request.denied` audit record per request (`denyAllJoinRequests`). Each requester can ask again 24 hours later, as after a denial.
- `POST /workspaces/:workspaceId/join-requests/pause` and `POST /workspaces/:workspaceId/join-requests/resume` set and clear the time that the workspace view shows as `joinRequestsPausedAt`, answer `204`, and write a `join_requests.paused` or `join_requests.resumed` audit record (`pauseJoinRequests`, `resumeJoinRequests`). Pausing a paused workspace or resuming one that is not paused answers `204` and changes nothing. While paused, a new request answers `403` with `join_requests_closed`; the pending requests stay and can still be decided or withdrawn. A pause ends only with a resume. No workspace event reports a pause, because the protocol has none; the members read it from the workspace view.
- After an approval, a denial, a block, or denying all commits, `account.join_request_decided` with the request's ID, the workspace ID, the decision, and its time goes to every open connection of the requester's account that got `auth.ok`, through `ConnectionRegistry.sendToUser`, which `buildApp` passes to the workspace routes as `onAccountFrame`. A block is sent as `denied`, and denying all sends one frame per denied request. A failure is logged with the frame type and the error's type only and does not change the answer. A refused decision, unblocking, pausing, and resuming send no account frame.
- The join request events (#210; Project Manager decision of 2026-11-09) go only to the connections subscribed to the workspace as its owner or an admin, never to the requester or to members, with a `system` actor and `deviceId: null`. After a new request commits, `workspace.join_request.created` carries the request as `GET /workspaces/:workspaceId/join-requests` shows it (`joinRequestForApprovers`); a pending request returned again sends nothing. After a withdrawal, an approval, a denial, or a block commits, `workspace.join_request.resolved` carries the request ID and the outcome, `withdrawn`, `approved`, `denied`, or `blocked`, and denying all sends one per denied request. After a lifted block commits, `workspace.join_request.unblocked` carries the request ID (#227; Project Manager decision of 2026-11-09); it is not a `resolved`, because the request was not pending. An expiry, pausing, and resuming send none. After an approval, `workspace.member.claimed` goes first, then this event, then the requester's frame.
- Every route that sends a join request event runs its change through one helper, `changeThenReadApprovers`: one transaction checks the account and the device (`lockActor`), runs the change, and reads the workspace's active owner and admins last, after every lock that the change took, without a lock of its own (`joinRequestApprovers`). After the commit, `buildApp`'s `onApproverEvent` hands the event to `ConnectionRegistry.sendToPeople` with those people. The registry keeps no role: a demotion or a removal that committed before that read leaves the person out, and one that commits after the read but before the change commits does not, so that person can get that one event. A promotion that commits after the read but before the change commits leaves the new admin out of that one event; the new admin's own reload of the list after `workspace.member.role_changed` usually covers it. Locking the people `FOR SHARE` would close that window, but two decisions that each hold their own person `FOR NO KEY UPDATE` would then wait for each other; the Project Manager accepted the window on 2026-11-09. `sendToWorkspace` and `sendEvent` take no event of the protocol's `APPROVER_EVENT_TYPES` (`SubscriberEvent`), whatever its name, so the type checker refuses a join request event there, and both send nothing and log `approver event refused` at error level if a cast still gets one there (#232). The events for the owner and admins are `ApproverEvent`, and the membership events, `WorkspaceEvent`, leave them out, both derived from the same list. A failure after the commit is logged with the event type, the workspace ID, and the error's type only, and does not change the answer; a refused or rolled-back change sends nothing.
- Known gaps, decided by the Project Manager on 2026-11-09: a requester who joins by an invitation while the request is pending gets no event, so the desktop of an owner or admin reloads the pending list on `workspace.member.claimed` and `workspace.member.removed`; and the operator command that erases an account withdraws its pending requests outside the API process, so no event goes out and the list catches up at its next reload, and the desktop treats `conflict` or `not_found` on a decision as a reason to reload the list.

Recent claims (`src/workspaces/claim-routes.ts`; ADR 0014, "Invitations"; #208). ADR 0014 asks that the owner and admins see every claim with the claimer's GitHub login and the creation date of that GitHub account, so that a freshly made account stands out. The live event `workspace.member.claimed` carries no creation date, reaches only the connections subscribed to the workspace, and is never replayed, so the Project Manager decided on 2026-11-06 (#95, D5a) to add a read route for the owner and admins.

- `GET /workspaces/:workspaceId/claims` answers `200` with the workspace's most recent claims, the most recent first, ties to the higher person ID, at most 50 (`RECENT_CLAIMS`), whatever their age (`listClaims`). Each claim has the workspace, the claimed person (`memberId`), the claiming account's GitHub identity as `claimer` (the login, the time it was last verified, which is the account's last GitHub sign-in, and the creation date of the GitHub account as `accountCreatedAt`), how the person was claimed as `via` (`invitation` or `join_request`), and the time of the claim as `claimedAt` (`workspace_members.claimed_at`). The desktop shows the person through the workspace view.
- A claim is a person claimed by an accepted invitation or through an approved join request, the two actions that send `workspace.member.claimed`. The creator's own person, which `POST /workspaces` creates as the claimed `owner`, is no claim. A claim stays listed after its person was removed, and its `claimer` is null after the account's data was erased. Nobody vetted the account of an invitation claim before it joined, while an owner or admin approved a join-request claim after seeing the account's GitHub login and its creation date, so the desktop can make an invitation claim of a freshly made account stand out, against the leaked invitation code of ADR 0014 ("Threats"). The list of values is closed (`CLAIM_VIAS`): a third way of claiming a person needs a protocol change, because an older client refuses an unknown value.

### Projects

The project routes (`src/workspaces/project-routes.ts`; #155 and the Project Manager's decisions of 2026-11-02) lie under `/workspaces/:workspaceId`, in the scope of the membership check, so a non-member, a removed member, and an unknown or malformed workspace ID get the same `404` with `not_found` before anything else, and the account's request limit of every authenticated route applies, as on the other workspace routes. For an active member, a body that breaks the protocol and a malformed project ID answer `400` with `bad_request`, and a project ID that the workspace does not have, also one of another workspace, answers `404` with `not_found`. A name is normalized to Unicode NFC and trimmed of white space at the start and the end (Project Manager decision of 2026-11-02), and then has 1 to 100 characters under the text rule of ADR 0005; the route stores and compares only the normalized name, so names that look the same clash, and a name of only white space answers `400`. Unknown fields in a body are stripped. A project in an answer or an event carries its creator, `createdByMemberId`: the creating account's active person in the workspace, or its most recently removed person while it has none.

- `GET /workspaces/:workspaceId/projects` answers `200` with the workspace's projects that are not archived, the oldest first (`listProjects`). Any active member.
- `POST /workspaces/:workspaceId/projects` with `name` creates a project and answers `200` with it (`createProject`). Any active member. One transaction checks the account and the device again (`lockActor`), locks the account, the caller's person, and the workspace row, and inserts the project and its `project` conversation, the project's chat, so it creates both or neither. A workspace with 100 projects that are not archived answers `409` with `project_limit` and no `Retry-After` (Project Manager decision of 2026-11-10, #255), as the limits of unclaimed people and of active devices answer with their own codes: no time frees a place, only archiving a project does, so it is not `rate_limited`, which says to wait. That limit is decided first, so a creation at both limits answers `project_limit`; an account that created 20 projects in the last 24 hours, in all its workspaces together, answers `429` with `rate_limited` and the seconds until the oldest of them is 24 hours old. A name that a project of the workspace that is not archived already has, compared without regard to case, answers `409` with `conflict`; the unique index of the database decides it, so of two concurrent creations with the same name one succeeds and the other gets `409`.
- `POST /workspaces/:workspaceId/projects/:projectId/rename` with `name` renames a project and answers `204` (`renameProject`). The account that created the project, also after it left and joined again as a new person, the owner, and admins; any other member gets `403` with `forbidden`. One transaction checks the account and the device again, then locks the caller's person, the workspace row, as a creation does, and the project, so that the name changes of one workspace happen one after another; two renames that swap two names therefore both answer `409` instead of failing with a deadlock. A name of another project answers `409` with `conflict`, as for a creation, and so does an archived project. The name in force, after normalization, answers `204`, changes nothing, and sends no event; a change of case alone renames.
- After the commit, `workspace.project.created` with the project, and `workspace.project.renamed` with the project ID and the new name, go through the membership event delivery to the connections subscribed to the workspace and then to `onWorkspaceEvent`, with a `system` actor and `deviceId: null`, as the membership events do. A refused request sends no event.
- Neither route writes an audit record: creating and renaming a project are not administrative actions of ADR 0014, and its audit vocabulary has no project action.

### Repositories

The repository routes (`src/workspaces/repository-routes.ts`; #286 and the Project Manager's decision of 2026-11-14) lie under `/projects/:projectId`, in the scope of the chat history and the agent activity, under the same check (`requireProjectMember`): a project that does not exist, a project of a workspace that the account is not an active member of, also after a removal, and a malformed project ID get the same `404` with `not_found` before anything else, and the account's request limit of every authenticated route applies. For an active member, a body that breaks the protocol and a malformed repository ID answer `400` with `bad_request`, and a repository ID that the project does not have, also one of another project, answers `404` with `not_found`. A repository is an identity and a name: no route takes or answers a path or a remote URL, because the folder's path stays on the device (ADR 0005, ADR 0013). The body's schema strips every field but `name`, and it refuses a name that holds a slash or a backslash, which a folder's full path and a remote URL do, with `400`. A name has 1 to 100 characters under the text rule of ADR 0005 and is stored as sent; it is a label, so two repositories of a project may share it. A repository in an answer or an event carries who registered it, `createdByMemberId`: the registering account's active person in the workspace, or its most recently removed person while it has none. Who may register and remove, and the code `repository_limit`, follow the Project Manager's decisions of 2026-11-14 (#286), and the limits, the rule of the name, and what a removal does follow the Project Manager's decision of 2026-11-17 on #286 ([protocol README](../../packages/protocol/README.md#repository-routes)).

- `GET /projects/:projectId/repositories` answers `200` with the project's repositories that are not removed, the oldest first (`listRepositories`), also of an archived project. Any active member.
- `POST /projects/:projectId/repositories` with `name` registers a repository and answers `200` with it (`registerRepository`). Any active member. One transaction checks the account and the device again (`lockActor`), locks the account, the caller's person, and the project row, and inserts the repository. An archived project answers `409` with `conflict`. A project with 20 repositories that are not removed answers `409` with `repository_limit` and no `Retry-After`, as a workspace at its limit of projects answers `project_limit`: no time frees a place, only a removal does. That limit is decided first, so a registration at both limits answers `repository_limit`; an account that registered 20 repositories in the last 24 hours, in all its projects together and removed ones included, answers `429` with `rate_limited` and the seconds until the oldest of them is 24 hours old.
- `POST /projects/:projectId/repositories/:repositoryId/remove` removes a repository and answers `204` (`removeRepository`). The account that registered it, also after it left and joined again as a new person, the owner, and admins; any other member gets `403` with `forbidden`. One transaction checks the account and the device again, locks the caller's person, the project, and the repository, sets the time of the removal, and revokes every grant scoped to the repository that is not revoked yet, with the caller's account as the revoker (ADR 0015, P-77). Nothing is deleted, and nothing restores the grants. The removal cancels no run. After the commit it sends one `agent.grant.revoked` for each revoked grant (#75; see "Grants"). A repository that is already removed and a repository of an archived project answer `409` with `conflict`.
- After the commit, `workspace.repository.registered` with the repository, and `workspace.repository.removed` with the project ID and the repository ID, go through the membership event delivery to the connections subscribed to the project's workspace and then to `onWorkspaceEvent`, with a `system` actor and `deviceId: null`, as the project events do. Their audience is every member (`SERVER_EVENT_AUDIENCES`). A removal then sends one `agent.grant.revoked` for each grant that it revoked, in the order of the grant IDs, to the same connections (`sendRevokedGrants`). A refused request and a change whose commit fails send no event.
- Neither route writes an audit record: registering and removing a repository are not administrative actions of ADR 0014, and its audit vocabulary has no repository action.

### Project chat

A project's chat (#27; the Project Manager's decisions of 2026-11-02 on #27 and #28) is read over HTTP and written over the connection. The refusal table of the [protocol README](../../packages/protocol/README.md#chat-history-refused-events-and-agent-activity) lists what the server answers to an event that it does not accept.

- `GET /projects/:projectId/messages` (`CHAT_ROUTES.listMessages`, `src/workspaces/chat-routes.ts`) answers `200` with one page of the history, `ChatHistoryResponseSchema`: the newest messages first by `seq`, with `beforeSeq` only those with a lower `seq`, `limit` from 1 to 100 and 50 without it (`ChatHistoryQuerySchema`; a query that breaks it answers `400` with `bad_request`). Any active member of the project's workspace reads it, also the history of an archived project (`listChatMessages`, called outside any other transaction, so that its membership check and its page read share one snapshot). The route lies under `/projects/:projectId`, in a scope whose check (`requireProjectMember`, `src/workspaces/access.ts`) runs right after authentication and before the path and the query are validated: a project that does not exist, a project of a workspace that the account is not an active member of, also after a removal, and a malformed project ID get the same `404` with `not_found`, whatever the query holds. The account's request limit of every authenticated route applies.
- `GET /projects/:projectId/messages/:messageId` (`CHAT_ROUTES.getMessage`, same file; #34, Project Manager decision of 2026-11-25) answers `200` with one message, `ChatMessageResponseSchema`: `{ message }`, the message exactly as it is an item of a page of the history, with no other field. It lies in the same scope as the history, so it has the same readers, the same request limit, and the same refusals in the same order: `401` without a usable access token; then the `404` of the membership check for a project that does not exist, a project of a workspace that the account is not an active member of, also after a removal, and a malformed project ID, whatever the message ID; then `400` with `bad_request` for a member's message ID that is not a lowercase UUIDv7; then the same `404` for a message ID that the project's chat does not have, also a message of another project or of another workspace. It never answers `forbidden`. `getChatMessage` reads the message in one statement that locks nothing and checks the account's active person in the same statement, so an account removed after the scope's check gets the same `404`. Like the history, it does not filter on `deleted_at`, which no writer sets yet.
- `chat.message.send` (`chatSendHandler`, `src/workspaces/chat-events.ts`), after identity binding: first the account's send limit (below); then one transaction locks the account and the device again (`lockConnection`, in the order of `lockActor`) and posts the message with `postChatMessage` in the event's workspace, which identity binding verified. The project must be a project of that workspace before anything is stored (ADR 0006, reference binding), so a project of another workspace answers as an unknown one, also for an account that is a member of both.
- A new message goes as `chat.message.created` to every connection subscribed to the workspace and to the sending connection, also when it is not subscribed: a `system` actor, `deviceId: null`, a new event ID, `occurredAt` set to the message's `createdAt`, `causationId` set to the ID of the `chat.message.send`, no `correlationId`, and the message with its `seq` and its author's person.
- A resent event ID that the database returns as stored gets that message again in a new `chat.message.created`, with the same `causationId`, sent only to the sending connection, also when the body differs.
- `not_found` (a project that the event's workspace does not have) and `conflict` (an archived project or workspace, or an event ID that the device used in another workspace) get `event.refused` with the event ID and the code, sent only to the sending connection, which stays open; nothing is stored or sent to others.
- An account that is not an active member of the event's workspace closes the connection with `not_a_member`, at identity binding or, when the removal commits after it, inside the transaction; a device or an account that may no longer act closes it with its reason. Nothing is stored.

The send limit (`CHAT_SEND_LIMIT`), settled with this part under the Project Manager's rule of 2026-11-02 to apply the recommended values and record them:

- At most 15 messages in any 10 seconds, a sliding window, and at most 600 in an hour, a fixed window that starts with the account's first accepted message after the previous one ended; a send that the burst refuses starts no window. Every device and every workspace of the account count together. A send above either gets `event.refused` with `rate_limited`, and the connection stays open; a refused send is not counted, and the device may send the same event ID again later. Every send below the limit counts, also one that is then refused with `not_found` or `conflict` or answered as a duplicate, because each costs a transaction.
- Why 15: the largest `chat.message.created` is about 64,600 bytes, just under `MAX_FRAME_BYTES` (64 KiB), and a connection with more than 1 MiB (`MAX_BUFFERED_BYTES`) waiting to be sent closes with `backpressure`. 15 of the largest messages are about 969,000 bytes, so the chat messages of one account alone can never push a subscriber that reads nothing for 10 seconds over that limit, with about 79,000 bytes left for presence and the messages of others; 16 would leave about 15,000 bytes, and the suggested 30 could close a slow reader with one burst of long messages. A person who types sends far fewer than 15 messages in 10 seconds.
- Why 600: a message every 6 seconds for a whole hour is beyond a person who chats, and still lets a long log be pasted in many messages; it bounds what one account adds to each subscriber to about 39 MB an hour, about 11 KB a second, and to the database to 600 rows an hour.
- The counts live in the memory of the API instance, like the request limits (ADR 0014 assumes one instance); a restart starts them empty. An account's count is kept while its hourly window lasts, with at most 15 times, and a sweep every minute forgets the accounts whose window ended and whose last accepted send is 10 seconds old or more.
- The limit counts `chat.message.send` only. The run transitions of #28 have their own limit (see "Agent activity").

Residual risks, accepted for M2:

- Backpressure: several accounts together can still exceed a slow reader's 1 MiB, and so can one account that toggles `workspace.subscribe` and `workspace.unsubscribe`, which no limit counts: each toggle that changes the person's presence sends `presence.changed` to every subscriber of the workspace. The reader then closes with `backpressure`, reconnects, and reloads the history after `workspace.subscribed`.
- Delivery after a membership or an account ends: `chat.message.created` and the relayed `agent.run.state_changed` (#28) go to the subscriptions held in memory. A removal or a departure through the API ends the person's subscriptions only when its `workspace.member.removed` is delivered after the commit (`endMembership`), so a message posted or a transition recorded between that commit and the delivery can still reach the removed account. A disable or an erasure through the operator command `db:account` runs outside the API, so the account's connections and subscriptions stay until the next sweep, up to 60 seconds, and receive the messages and the transitions of that time. The account itself can no longer post or report a transition in either case, because the transaction locks and checks the person, the account, and the device.

### Agent activity

A project's agent activity (#28; the Project Manager's decisions of 2026-11-02) is read over HTTP and reported over the connection. In M2 it is `agent.run.state_changed` only; a development-only seed creates an agent hosted on the developer's device with runs in `queued` (`db:dev-seed`), an agent is created and disabled with the routes of #294 (see "Agent creation and disabling"), and a run is created with `POST /projects/:projectId/runs` since #35 (see "Run creation"). The refusal table of the [protocol README](../../packages/protocol/README.md#chat-history-refused-events-and-agent-activity) lists what the server answers to an event that it does not accept.

- `GET /projects/:projectId/agents` (`AGENT_ROUTES.listAgents`, `src/workspaces/agent-routes.ts`) answers `200` with `AgentListResponseSchema`: the project's agents, the oldest first, disabled ones included, each with its owner's person, and with its host device (`hostDeviceId`) only for the agents that the caller's account owns (`listProjectAgents`; #342, update of 2026-11-24): every other agent leaves the field out, as a run leaves out its provider connection (#35). `GET /projects/:projectId/runs` (`AGENT_ROUTES.listRuns`) answers `200` with `AgentRunListResponseSchema`: every unfinished run, the most recently created first, and the 50 most recently finished runs, the most recently finished first (`listProjectRuns`). Any active member of the project's workspace reads them, also of an archived project; each list is read from one snapshot. Both routes lie in the scope of the chat history, under the same check (`requireProjectMember`): a project that does not exist, a project of a workspace that the account is not an active member of, also after a removal, and a malformed project ID get the same `404` with `not_found`, and the account's request limit of every authenticated route applies. The desktop reloads both after each `workspace.subscribed`.
- `agent.run.state_changed` from a device (`runTransitionHandler`, `src/workspaces/agent-events.ts`), after identity binding: first the account's run transition limit (below); then a `reason` that only the server gives, a code of `RUN_CANCEL_REASONS` (`runReasonAllowed`, #201), gets `event.refused` with `conflict` before anything is read. Like the limit, this comes before the agent is checked, so it also answers an event ID that the device already recorded, and an agent that another device hosts or another account owns; then one transaction locks the account and the device again (`lockConnection`) and records the transition with `recordRunTransition` in the event's workspace, which identity binding verified. The agent must be an agent of that workspace, hosted by the sending device and owned by its account, and the run must be the agent's, before anything is stored (ADR 0006, reference binding); the run moves only while it is still in `previousState`.
- A new transition is relayed as it was recorded: the same event ID, `occurredAt`, agent actor, `correlationId`, `causationId`, and payload, with `deviceId: null`, so that other members never see the host device. It goes to every connection subscribed to the workspace and to the sending connection, also when it is not subscribed, as its acknowledgement.
- A transition whose device and event ID are already recorded gets the stored relayed event, sent only to the sending connection, also when the event sent again differs or the run moved on since; it is never applied twice. A resend whose `reason` is a code of `RUN_CANCEL_REASONS` gets `event.refused` with `conflict` instead (#201).
- `not_found` (an agent or a run that the event's workspace does not have, a run of another agent, a repository that is not the run's) and `conflict` (a disabled agent, an archived project or workspace, a run that is no longer in `previousState`, an event ID that the device used in another workspace, or an agent's `reason` of `RUN_CANCEL_REASONS`) get `event.refused` with the event ID and the code, sent only to the sending connection, which stays open; nothing is stored or sent to others. A disabled agent is a race with the person who disabled it, not an attack.
- An agent of the workspace that another device hosts or another account owns closes the connection with `identity_mismatch`, and the gateway audits it as `event.identity_mismatch`, as for a mismatch that identity binding finds: at most once per device per hour, with the event ID as its subject. A transition that the run transition limit or a code of `RUN_CANCEL_REASONS` refused first gets that refusal instead, and nothing is audited. An account that is not an active member closes it with `not_a_member`, and a device or an account that may no longer act with its reason. Nothing is stored.
- Order: the gateway handles one connection's messages one after another, in the order they arrived, and awaits the handler, with its transaction and its delivery, before the next; reading pauses while messages wait. So one connection's run transitions are recorded and relayed in the order they arrived, as `recordRunTransition` requires, and a transition sent right after another starts from the state that the other left.

The run transition limit (`RUN_TRANSITION_LIMIT`), settled with this part under the Project Manager's rule of 2026-11-02 to apply the recommended option and record it:

- Run transitions do not count toward the chat send limit. They have their own limit per account, with its own counts: at most 30 in any 10 seconds, a sliding window, and at most 1,800 in an hour, a fixed window, counted as the chat send limit counts (`AccountSendLimit`, `src/workspaces/send-limit.ts`). Every device and every workspace of the account count together. A transition above either gets `event.refused` with `rate_limited`, and the connection stays open; a refused transition is not counted, and the device may send the same event ID again later. Every transition below the limit counts, also one that is then refused or answered as a duplicate. Counted apart, an agent that reports its runs never takes a person's room to chat, and a full chat burst never holds up an agent.
- Why 30: the largest relayed `agent.run.state_changed`, with a reason of 500 code points of 4 bytes each and every optional field, is about 2,600 bytes, so 30 are about 78,500 bytes, under the about 79,000 bytes that 15 of the largest chat messages leave below the 1 MiB (`MAX_BUFFERED_BYTES`) of a connection. One account's chat burst and transition burst, as the limits count them, fit together under that limit; a test holds the sum to it. The limits count an event when it arrives, before its transaction, and the relay follows the commit, so when transactions wait for locks, the relays of two bursts can reach a subscriber close together. A subscriber that reads nothing then can still close with `backpressure`, reconnect, and reload; that is the accepted worst case, as for several accounts together (see "Residual risks" under "Project chat"). A run moves a few times in its life, so 30 in 10 seconds lets the development switch walk several runs at once and lets an agent report every state change of its runs.
- Why 1,800: a transition every 2 seconds for a whole hour; it bounds what one account adds to each subscriber to about 4.7 MB of run events an hour, and to the transition log to 1,800 rows an hour.
- The counts live in the memory of the API instance and start empty after a restart, as the chat send limit's do, and the same sweep every minute forgets the accounts whose window ended.
- Relayed transitions reach the subscriptions held in memory, so a removed account, or one that an operator disabled, can still receive the transitions recorded until its subscriptions end, as chat messages do (see "Residual risks" under "Project chat").

### Agent creation and disabling

An agent is created and disabled over HTTP (#294; the Project Manager's decisions of 2026-11-20, whose defaults the Project Manager accepted on 2026-11-23). The [protocol README](../../packages/protocol/README.md#agent-creation-and-disabling) holds the contract.

- `POST /projects/:projectId/agents` (`AGENT_ROUTES.createAgent`, `src/workspaces/agent-routes.ts`) with `name` (`CreateAgentRequestSchema`) creates an agent and answers `200` with it (`CreateAgentResponseSchema`), as the agent list shows it to its owner: enabled, owned by the caller's person, and with its host device, the calling device (`hostDeviceId`; #342, update of 2026-11-24). Any active member. It lies in the scope of the agent activity routes, under the same check (`requireProjectMember`): a project that does not exist, a project of a workspace that the account is not an active member of, also after a removal, and a malformed project ID get the same `404` with `not_found` before anything else, and the account's request limit of every authenticated route applies. The body's schema strips every field but the name, so a host device, an owner, or a provider kind in the body changes nothing.
- One transaction checks the account and the device again (`lockActor`), so a device that was revoked after the request was authenticated creates nothing, and then creates the agent with `createAgent`, which locks the account, the device, the caller's person, and the project row. An archived project or workspace answers `409` with `conflict`. A project with 20 enabled agents, or with 500 agents, disabled ones included, answers `409` with `agent_limit` and no `Retry-After`, as a project at its limit of repositories answers `repository_limit`: no time frees a place, only disabling an agent frees one of the first limit. An account that created 20 agents within 24 hours, in any project and disabled ones included, gets `429` with `rate_limited` and `Retry-After`, the wait until the oldest of them is 24 hours old. A creation at a project's limit and the account's limit answers `agent_limit`. The limits are `AGENT_COUNT_LIMITS` and are counted in the database, inside the creation's transaction, so they hold across restarts and for concurrent requests.
- `POST /projects/:projectId/agents/:agentId/disable` (`AGENT_ROUTES.disableAgent`) disables an agent and answers `204` (`disableAgent`). The agent's owner, from any of the owner's devices, the workspace's owner, and admins; any other member gets `403` with `forbidden`. An agent ID that the project does not have, also one of another project, answers `404` with `not_found`, and an agent that is already disabled, or one of an archived project or workspace, `409` with `conflict`. One transaction checks the account and the device again, locks the caller's person, the project, and the agent, sets the time of the disabling, revokes every grant of the agent that is not revoked yet with the caller as the revoker (ADR 0015, P-77), and cancels the agent's unfinished runs with the reason `agent_disabled`. Disabling is final: no route enables an agent again.
- After the commit, `workspace.agent.created` and `workspace.agent.disabled`, each with the agent as the agent list shows it, go through the membership event delivery to the connections subscribed to the project's workspace and then to `onWorkspaceEvent`, with a `system` actor and `deviceId: null`, as the repository events do. Their audience is every member (`SERVER_EVENT_AUDIENCES`). The payload is built field by field (`workspaceAgent`), so it never holds the host device, which only the creation's answer and the agent list give to the agent's own account (#342). A disable then sends one `agent.grant.revoked` for each grant that it revoked, in the order of the grant IDs (#75; `sendRevokedGrants`), and one `agent.run.state_changed` for each run that it cancelled, from its state before to `cancelled`, with a `system` actor, `deviceId: null`, and the reason `agent_disabled`, to the same connections, as a device revocation and a removal of a person send theirs (`sendCancelledRuns`). A refused request and a change whose commit fails send no event.
- The cascades that disable agents send the same `workspace.agent.disabled` for each agent that they disabled, after the commit, to the connections subscribed to the agent's own workspace (#326): a device revocation and a sign-in that replaces a device, after the revoked device's connection closed, and a removal of a person and a departure, after the removed person's subscriptions ended (see "Workspace subscriptions, presence, and delivery", item 7). The route reads the disabled agents inside its transaction (`disabledAgentsOf` of `@mymandev/database`), so a change whose commit fails sends none, and builds the payload with the agent route's own function (`agentDisabledEvent`), so it never holds the host device. A failure to send one is logged with the event type, the workspace ID, and the error's type, as for every membership event, and keeps neither the answer nor the events after it from going out. The erasure of an account, an operator command outside the API, sends none, as it sends no `agent.grant.revoked` (recommendation 5 of #75): the other members see its disabled agents when they next load the agent list.
- One `workspace.agent.disabled` is at most about 710 bytes, with a name of 64 characters of 4 bytes each. A cascade that disables more than about 1,400 agents at once, fewer together with its grant and run events, sends more than the 1 MiB that a connection may hold unsent. Only a removal of a person who owns that many enabled agents in one workspace, or a revocation of a device that hosts them, reaches it: a project holds at most 20 enabled agents, and an account creates at most 20 agents in 24 hours. A subscriber that does not read fast enough then closes with `backpressure` and reloads, the accepted worst case of every burst (see "Workspace subscriptions, presence, and delivery").
- Neither route writes an audit record: creating and disabling an agent are not administrative actions of ADR 0014, and its audit vocabulary has no agent action.

### Run creation

A run is created over HTTP (#35; the Project Manager's decision of 2026-11-14; ADR 0007, updates of 2026-11-14), and moved over the connection by its agent's host device (see "Agent activity"). The [protocol README](../../packages/protocol/README.md#run-creation) holds the contract and the choices that are still open.

- `POST /projects/:projectId/runs` (`RUN_ROUTES.createRun`, `src/workspaces/run-routes.ts`) with `agentId`, `providerConnectionId`, `inputMessageId`, and an optional `repositoryId` (`CreateRunRequestSchema`) answers `200` with the new run in `queued`, with its input message and its provider connection (`CreateRunResponseSchema`). It lies in the scope of the agent activity routes, under the same check (`requireProjectMember`): a project that does not exist, a project of a workspace that the account is not an active member of, also after a removal, and a malformed project ID get the same `404` with `not_found` before the body is validated, and the account's request limit of every authenticated route applies. A malformed body is `400`.
- One transaction locks the account and the device again (`lockActor`), so a device that was revoked after the request was authenticated creates nothing, and then creates the run with `createRun`, which decides in this order: `not_found` for an agent that the project does not have; `forbidden` for an agent that the account does not own or that the asking device does not host, before anything about the other IDs is read; `not_found` for a repository that the project does not have, a provider connection that the agent's host device does not have, and a message that the project's chat does not have from the account or that is deleted, all with one answer; `conflict` for an archived project or workspace, a disabled agent, an archived repository, and a removed provider connection; and then the two limits below. An account that stopped being an active member after the membership check gets the check's `404`. Nothing is written when it refuses.
- Only the account that owns the agent asks, and only from the agent's host device, as only that device grants (#75): another device of the account, for example one that a taken-over GitHub account registered, gets `403` with `forbidden` and cannot start a run with the grants that the agent already holds. The provider connection is always one of that device. A role gives no right to another member's agent.
- The input is a message that the account wrote: another member's or an agent's message is the same `404` as an unknown one, so that the chat shows the instruction as the requester's own words.
- After the commit, the run goes to every connection subscribed to the project's workspace as `agent.run.state_changed` from no state to `queued`, with a `system` actor, `deviceId: null`, the run's creation time as `occurredAt`, and `run`, the new run as every member reads it in the run list (`createdRunEvent`). The event is built field by field and never holds the run's provider connection, the host device, or the asking account. A connection that is not subscribed gets nothing, also one of the asking account; the asking device reads the run from the answer. A creation whose commit fails sends nothing, and a failure to send is logged with the event type, the workspace ID, and the error's type and does not fail the answer.
- `GET /projects/:projectId/runs` shows a run's `inputMessageId` to every member and its `providerConnectionId` only to the account that owns the run's agent (`listProjectRuns`).
- A creation writes no audit record: it is not an administrative action of ADR 0014.

The limits of a creation, each with its own code. Provisional (#35): both values, applied as defaults until the Project Manager decides:

- An agent has at most 10 unfinished runs (`queued`, `running`, or `awaiting_input`; `MAX_UNFINISHED_RUNS_PER_AGENT`), the runs of the development seed included. A creation above it answers `409` with `run_limit` and no `Retry-After`, because no time frees a place: only a run of the agent that finishes does. 10 keeps what one host device has to work through small, and keeps a project's unfinished runs, which the run list returns whole, far below `MAX_ANSWER_LIST_ITEMS`.
- An agent gets at most 100 runs within 24 hours (`MAX_NEW_RUNS_PER_AGENT_PER_DAY`), however they ended. A creation above it answers `429` with `run_daily_limit` and `Retry-After`, the time until the oldest of those runs leaves the 24 hours. It bounds what one agent adds to the run tables and what it can spend of its owner's provider in a day. The account's request limit on the route stays `rate_limited`.
- An agent at both limits answers `run_limit`: the limit that no wait frees is decided first.
- Both are counted in the database, inside the creation's transaction, after it locked the agent, so they hold across restarts and for concurrent requests.

An agent is created with `POST /projects/:projectId/agents` since #294, and the host device registers a provider connection with `POST /provider-connections` since #295 (see "Provider connections"), so an account can create a run in production once its desktop sends these requests; the desktop does not send them yet.

### Provider connections

A host device registers, lists, and removes its own provider connections over HTTP (#295; the Project Manager's decisions of 2026-11-20, whose defaults the Project Manager accepted on 2026-11-23). The [protocol README](../../packages/protocol/README.md#provider-connections) holds the contract.

- `GET /provider-connections` (`PROVIDER_CONNECTION_ROUTES.listProviderConnections`, `src/providers/provider-connection-routes.ts`) answers `200` with `ProviderConnectionListResponseSchema`: the calling device's connections that are not removed, the oldest first (`listProviderConnections`).
- `POST /provider-connections` (`PROVIDER_CONNECTION_ROUTES.registerProviderConnection`) with `kind` and `label` (`RegisterProviderConnectionRequestSchema`) registers a connection hosted on the calling device and answers `200` with it (`RegisterProviderConnectionResponseSchema`). The body's schema strips every field but the kind and the label, so an API key, a token, a provider account, or a host device in the body never reaches the database, and the answer is built field by field. A kind outside `PROVIDER_KINDS` and a label outside the text rule answer `400` with `bad_request`.
- `POST /provider-connections/:providerConnectionId/remove` (`PROVIDER_CONNECTION_ROUTES.removeProviderConnection`) removes a connection of the calling device and answers `204` (`removeProviderConnection`). A connection that the calling device does not host, also one of another device of the same account, answers `404` with `not_found`, as an unknown one does, and one that is already removed `409` with `conflict`. A malformed ID answers `400`.
- The paths name no device, as `GET /grant-records` names none: the calling device, from the access token, is the host device of every connection that a route reads or changes, so no device reaches another device's connection. The routes need an access token, and the account's request limit of every authenticated route applies.
- Each change runs in one transaction that checks the account and the device again (`lockActor`), so a device that was revoked after the request was authenticated changes nothing, and then calls the database function, which locks the account and the device again and decides on them.
- A device holds at most 10 connections that are not removed: a registration over it answers `409` with `provider_connection_limit` and no `Retry-After`, because only a removal frees a place. An account registers at most 20 connections within 24 hours, on all its devices and removed ones included: a registration over it answers `429` with `rate_limited` and `Retry-After`, the wait until the oldest of them is 24 hours old. A registration at both limits answers `provider_connection_limit`. The limits are `PROVIDER_CONNECTION_COUNT_LIMITS` and are counted in the database, inside the registration's transaction, after it locked the account, so they hold across restarts and for concurrent requests.
- A removal sets the connection's `removed_at` and revokes its `provider.use` grants that are not revoked yet, with the removing account as the revoker, in the same transaction (ADR 0015, P-77). It deletes nothing and cancels no run, as a repository removal cancels none. A device revocation does not mark the device's connections removed.
- No change sends a workspace event: a connection is device data (#110). After the commit, a removal sends one `agent.grant.revoked` for each grant that it revoked to the connections subscribed to the grant's workspace (#75; see "Grants"), which may be several workspaces: the event names the grant and its agent, never the connection.
- Neither change writes an audit record: they are not administrative actions of ADR 0014, and its audit vocabulary has no provider connection action.

### Grants

The agent's owner grants capabilities to an agent and revokes grants over HTTP, the agent's host device reads its grant records, and the agent's owner reads one agent's grants on any of its devices (#75, #345; ADR 0015, P-74 to P-80; the Project Manager's decisions of 2026-11-02, 2026-11-14, 2026-11-19, and 2026-11-24). The [protocol README](../../packages/protocol/README.md#grant-routes-and-events) holds the contract and the choices that are still open.

| Route                                          | Who                                           | Body                                                                          | Answer                                                           | Codes beyond the common ones                        |
| ---------------------------------------------- | --------------------------------------------- | ----------------------------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------- |
| `GET /grant-records`                           | any signed-in device                          |                                                                               | the grant records of the agents that the device hosts            |                                                     |
| `GET /agents/:agentId/grants`                  | the agent's owner, on any of its devices      |                                                                               | the agent's grants that are not revoked, as its owner reads them | `not_found`, `forbidden`                            |
| `POST /agents/:agentId/grants`                 | the agent's owner, on the agent's host device | `capability`, `repositoryId` or `providerConnectionId`, and `lifetimeSeconds` | the new grant, whole                                             | `not_found`, `forbidden`, `conflict`, `grant_limit` |
| `POST /agents/:agentId/grants/:grantId/revoke` | the agent's owner                             |                                                                               |                                                                  | `not_found`, `forbidden`, `conflict`                |

- The routes are `GRANT_ROUTES` (`src/grants/grant-routes.ts`). They need an access token, and the account's request limit of every authenticated route applies; beyond it, only a grant has a rate limit, the account's grants in 24 hours (below). No path names a workspace or a project: an agent ID names both, and the database decides on the agent.
- `GET /grant-records` answers `200` with `GrantRecordListResponseSchema` (`listGrantRecords`): every grant of the agents that the calling device hosts that is not revoked, an expired one included, each with the facts that the check needs (the agent, the host device, the project, the granting account's membership, and the provider connection of a `provider.use` grant), read in one statement, so from one snapshot (P-76), in the order of the grant IDs. Revoked grants are left out, and a record has no repository fact (#75, decisions of 2026-11-14). The path names no device: a device can only read its own records, a device of another account and a device that hosts no agent get an empty list, and the list is never cut (`GRANT_COUNT_LIMITS`).
- `POST /agents/:agentId/grants` with `capability`, `repositoryId` or `providerConnectionId`, and `lifetimeSeconds` (`GrantCapabilityRequestSchema`) answers `200` with the new grant (`GrantCapabilityResponseSchema`), as `grantCapability` returns it: `grantedByUserId` is the caller's own account, `createdAt` the server's time, and `expiresAt` that time plus the lifetime, or null. The body is the parsed JSON body itself, validated by the request schema (#290, review): Fastify's JSON parser refuses a `__proto__` or `constructor.prototype` key with `400`, so no inherited `lifetimeSeconds` counts, and unknown fields are stripped, so the body sets neither the grant's ID, its agent, its granting account, nor its times. A grant of `terminal.execute` without a lifetime or with one over 30 days (`SHELL_GRANT_MAX_LIFETIME_SECONDS`), and any other malformed body, answers `400` with `bad_request`; the other capabilities accept `null` for a grant without an expiry.
- Only the agent's owner grants, and only from the agent's host device (#75, decision of 2026-11-14): another device of the owner, for example one that a taken-over GitHub account registered, and another member, the workspace's owner and admins included, get `403` with `forbidden`. An agent that does not exist and an agent of a workspace that the account is not an active member of, also after a removal, get the same `404` with `not_found`, and so do a repository that is not in the agent's project and a provider connection that is not on the agent's host device. A disabled agent, an archived repository, project, or workspace, a removed provider connection, and a grant of the same capability on the same scope that is neither revoked nor expired answer `409` with `conflict`. An agent with 100 grants that are not revoked, or a host device whose agents hold 1,000, answers `409` with `grant_limit` and no `Retry-After` (`GRANT_COUNT_LIMITS`; #75, decision of 2026-11-14): no time frees a place, only a revocation does. An expired grant counts until it is revoked; one of the same capability on the same scope is revoked and replaced in the same transaction (P-77).
- An account makes at most 200 grants within 24 hours, on all its agents and devices, revoked ones included, and the renewal of an expired grant counts as a grant (`GRANT_COUNT_LIMITS.perDay`; #75, decision of 2026-11-23): a grant over it answers `429` with `rate_limited` and `Retry-After`, the wait until the oldest of them is 24 hours old, because time frees a place. It is decided after every other refusal, so a grant that is also a `conflict` or over `grant_limit` answers that code. The limit is counted in the database, inside the grant's transaction, after it locked the account, so it holds across restarts and for concurrent requests. It keeps one member who grants and revokes in a loop from making every other member's devices read their grant records without end, because each grant sends `agent.grant.created` to every subscribed member.
- `POST /agents/:agentId/grants/:grantId/revoke` revokes a grant of the agent, also an expired one, and answers `204` (`revokeGrant`). The agent's owner, from any of its devices (#75, recommendation 4 and decision of 2026-11-14); any other member gets `403` with `forbidden`. An agent that the account cannot see, a grant ID that the agent does not have, also one of another agent, and an unknown grant answer the same `404` with `not_found`, and a grant that is already revoked `409` with `conflict`. A malformed ID answers `400`.
- `GET /agents/:agentId/grants` answers `200` with `AgentGrantListResponseSchema` (`listAgentGrants`; #345, Project Manager decision of 2026-11-24): the agent's grants that are not revoked, an expired one included, because a revocation also takes an expired grant, in the order of the grant IDs, at most `GRANT_COUNT_LIMITS.perAgent` (100). It lets the owner revoke from a device that does not host the agent, for example while the host device is lost. Each grant carries its ID, its agent, its capability, its scope (`repositoryId`, or `providerConnectionId` for `provider.use`), and its creation and expiry times: no host device, no account, no project, and no record fact, which stay with the host device's `GET /grant-records` (#110). The agent's owner reads it from the host device and from every other device of the owner; it refuses as a revocation does: another member, the workspace's owner and admins included, gets `403` with `forbidden`, and an agent that the account cannot see, also after the owner's removal, the same `404` with `not_found` as an unknown agent. A malformed ID answers `400`. The database checks the owner and the membership in the statement that reads the grants, and the read locks nothing, so it needs no `lockActor`; the account's request limit applies as for every read.
- Each change runs in one transaction that checks the account and the device again (`lockActor`), so a device that was revoked after the request was authenticated changes nothing, and then calls the database function, which locks the account, the device, the owner's person, the project, the scope, the agent, and the grant in the order of `src/grants.ts` of `@mymandev/database`. A refusal of the database maps to the code of the same name. Its `forbidden` also covers a disabled account, which `lockActor` already refuses with `401` before the database is asked.
- After the commit, the change's events go to every connection subscribed to the agent's workspace, and to no one else (`members` in `SERVER_EVENT_AUDIENCES`), with a `system` actor and `deviceId: null`: a grant sends `agent.grant.created`, with the grant as members see it (`WorkspaceGrant`, built field by field, so that it never names the granting account, the host device, or the provider connection of a `provider.use` grant); a revocation sends `agent.grant.revoked`, with the grant, its agent, and the time stored as `revoked_at`. A grant that replaced an expired grant sends `agent.grant.revoked` for the expired one first, then `agent.grant.created`. A refused request and a change whose commit fails send nothing, and a failure to send is logged with the event type, the workspace ID, and the error's type and does not fail the answer. A committed change whose grant comes back without its revocation time, which the database never does, still answers as committed; the missing event is logged as a broken invariant.
- Every other change that revokes grants in its own transaction (ADR 0015, P-77) sends one `agent.grant.revoked` for each grant after its commit, in the order of the grant IDs, to the connections subscribed to the grant's own workspace (ADR 0015, update of 2026-11-14; `sendRevokedGrants`): an agent's disable, a repository removal, a provider connection removal, a removal of a person and a departure, a device revocation, and a sign-in that replaces a device. A change that spans workspaces, such as a device revocation, tells each workspace of its own grants only. The route reads the revoked grants inside its transaction (`revokedGrantsOf` of `@mymandev/database`), so a change whose commit fails sends none. These events are sent as the grant routes send theirs (`sendGrantEvents`): a failure to send one is logged and fails neither the committed change's answer nor the events after it, such as the cancelled runs. The operator commands that revoke grants, disabling and erasing an account, run outside the API and send none (recommendation 5 of #75): a device learns of those revocations at its next read of `GET /grant-records`.
- One event is about 400 bytes. A change that revokes more than about 2,500 grants at once, which only a removal of a person who owns many agents in a workspace can reach, sends more than the 1 MiB that a connection may hold unsent, so a subscriber that does not read fast enough closes with `backpressure` and reloads, the accepted worst case of every burst (see "Workspace subscriptions, presence, and delivery").
- Neither change writes an audit record: they are not administrative actions of ADR 0014, and its audit vocabulary has no grant action.

### `POST /auth/github/webhook`

GitHub sends `github_app_authorization` with the action `revoked` when a person revokes the app's authorization, also when they never installed it (ADR 0014, "Revocation, sign-out, and recovery"; P-54; #67). The route exists only with `API_GITHUB_WEBHOOK_SECRET` and the database; otherwise it answers the generic `404`.

- The body must be `application/json` (`415` otherwise) and at most 1 MiB (`413`), a limit of the route that replaces `API_BODY_LIMIT_BYTES`. The route keeps the raw bytes and checks `X-Hub-Signature-256` before it parses anything: `sha256=` and the lowercase hexadecimal HMAC-SHA256 of the body, compared with `timingSafeEqual`, under `API_GITHUB_WEBHOOK_SECRET` or, while it is set, `API_GITHUB_WEBHOOK_SECRET_PREVIOUS`. A missing or wrong signature answers `401` with `unauthorized` and changes nothing.
- With a valid signature, a body that is not a JSON object answers `400` with `bad_request`. `ping`, `installation`, `installation_repositories`, any other event, and `github_app_authorization` with another action answer `204` and change nothing; an installation grants nothing.
- A revocation needs `X-GitHub-Delivery` (letters, digits, and hyphens, at most 64) and `sender.id` (a positive integer); otherwise it answers `400` with `bad_request`. With GitHub sign-in configured, the route first records the sender's numeric ID and the time in the list of recent revocations in memory, also for a sender without an account (see "Sign-in with GitHub"). Then, in one transaction, `recordGitHubRevocation` of [`@mymandev/database`](../../packages/database/README.md) finds the account by the numeric sender ID in `user_identities`, never by the login, writes a `github.authorization_revoked` audit record with the delivery ID, locks the account's row as a sign-in does (`FOR NO KEY UPDATE`), and sets `users.sign_in_required_at` to the latest of its current value, now, and one millisecond after the last sign-in of each of the account's devices that are not revoked; it never moves backward. Each device counts at most 60 seconds past now, so a last sign-in in the future, after a jump of the clock, cannot keep the account from signing in for longer. A sign-in that committed before the revocation is therefore always covered, also one whose request took a later time than the webhook's (#115). Every device whose last sign-in is earlier must then sign in with GitHub again: `POST /auth/access-token` and the WebSocket authentication answer `sign_in_required`, and earlier access tokens stop working. The devices, their agents, and their grants stay. After the commit the API closes the account's sockets with `sign_in_required` (4003) and drops the access tokens of its devices from memory. It answers `204`.
- A delivery ID that is already recorded changes nothing and answers `204`. A redelivery keeps the ID of the original delivery (#67), and the unique `audit_events.github_delivery_id` recognizes it.
- A sender without an account, or whose identity was erased, gets `204` and one audit record without an actor or a subject, but with the delivery ID, so that a redelivery is recognized too.
- The route has no rate limit: GitHub delivers from shared addresses, a request without a valid signature costs one HMAC per configured secret, and the body limit bounds the work.
- Each delivery answered `204` logs one line with the event type (`githubEvent`) and the outcome: `revoked`, `no_account`, `already_processed`, or `ignored`. No body, signature, `X-GitHub-Delivery`, sender, or user ID is logged.

To rotate the secret, set the new one as `API_GITHUB_WEBHOOK_SECRET` and the old one as `API_GITHUB_WEBHOOK_SECRET_PREVIOUS`, restart the API, change the secret in the app's settings on GitHub, then remove the previous secret and restart again. GitHub does not redeliver a failed delivery on its own: after downtime or a rotation, the operator checks the app's recent deliveries and redelivers by hand (#96). [Development GitHub App](../../docs/development/GITHUB-APP.md#test-the-webhook-locally) describes local testing through a relay.

An accepted risk (ADR 0014, update of 2026-11-01): GitHub signs only the body, and a revocation's body carries no time. Whoever saw one signed delivery, on the app's recent deliveries, in a proxy log, or on a public development relay, can send it again with a new `X-GitHub-Delivery` and require that person to sign in again as often as they like. The API cannot tell such a copy from a real revocation. A copy deletes and grants nothing. A new webhook secret ends it.

Decisions that ADR 0014 leaves open, settled for #90 with the Project Manager's approval on 2026-11-01:

- A revocation whose sender has no account, or whose identity was erased, answers `204` and writes one audit record without a person that stores the delivery ID.
- The audit record has no actor, as for every action of the server; its subject is the account. `AUDIT_REASONS` does not change.
- Every other event type, and every other action, answers `204` without a change.
- A webhook secret is 32 to 256 printable ASCII characters without whitespace. The previous secret without the current one is a configuration error, and production requires the current secret, never the previous one.
- No per-address rate limit, a body limit of 1 MiB, and `application/json` only.
- A missing or wrong signature answers `401` with `unauthorized`; a signed delivery with a malformed body, a missing or invalid delivery ID, or a missing or invalid sender ID answers `400` with `bad_request`.

### `GET /ws` (WebSocket)

`/ws` is the only path that accepts a WebSocket handshake; a handshake on any other path gets `404` before the upgrade. `/ws` exists only with GitHub sign-in and the database, like the routes that need them (ADR 0014, "Configuration"); without them it answers the generic `404` as well, and no unauthenticated mode exists.

Before the upgrade:

1. A handshake with an `Origin` header that is neither `API_PUBLIC_ORIGIN` nor listed in `API_ALLOWED_ORIGINS` gets `403`. A handshake without `Origin` (Node.js) is accepted. Origins are compared as exact strings: another scheme, host, port, or case, a subdomain, a path, or a trailing dot is a different origin. The API's own origin is accepted because the desktop's client, Electron's `net.WebSocket` in the main process, sends by default the http(s) form of the WebSocket URL's origin, which is the API's origin (#154); this is safe because the socket carries no cookie or other ambient credential, and the device signature below authenticates the connection. The exception is safe only while `API_PUBLIC_ORIGIN` serves nothing but the API, with no website or web app on that origin, and `/ws` uses no ambient credential; either change would require removing the exception. Browsers send `Origin` on every WebSocket handshake and apply no same-origin rule to WebSocket, so every other browser origin that may connect must be listed. A renderer loaded from `file://` or a custom scheme sends the origin `null`, which cannot be listed.
2. One remote address may open 60 handshakes in 10 minutes, the limit of the other routes before a verified signature (P-63); the 61st gets `429` with `rate_limited` and `Retry-After`. Behind a proxy without `trustProxy` set to it, every client has the proxy's address, so the limit is valid only while the API is reached directly.
3. At most 200 connections may wait for authentication at once (ADR 0014, "Limits"). Above that, the handshake gets `429` with `rate_limited` and `Retry-After: 11`, the longest time a waiting connection holds its place: 10 seconds to authenticate and 1 second to close. No socket, timer, or nonce is created for it.

Authentication (ADR 0014, "Device key and authentication"):

1. After the upgrade the server sends `auth.challenge` with a nonce (32 random bytes), a new connection ID, and the protocol version, and starts a 10-second timer (`WS_AUTH_TIMEOUT_MS`). The nonce lives only in API memory and only for this connection.
2. The device answers with exactly one `auth.response`: its device ID and a signature over `deviceAuthInput` with the purpose `ws`, `API_PUBLIC_ORIGIN` as the audience, the nonce, the device ID, and the connection ID. The nonce is used once: the connection accepts no second response.
3. The server verifies the signature with the device's current key first and checks the device state second, like `POST /auth/access-token`: an unknown device, a bad signature, and a disabled account get `auth_failed`; a revoked device gets `device_revoked`; a signed-out device, a last sign-in 30 days ago or more, and a GitHub revocation after the last sign-in get `sign_in_required`.
4. On success the server writes `devices.last_seen_at`, builds a frozen `AuthenticatedConnectionContext` (the connection ID, the identity of user and device, which is never null, and the time of the device's last sign-in), and registers the connection as the device's live connection. It then reads the device again: a revocation, sign-out, disable, or new sign-in that committed after the first check closes the connection with its reason before `auth.ok`, and the connection leaves the registry; one that commits later finds the connection in the registry. Only then does the server send `auth.ok` with the user ID, the device ID, and the sign-in expiry (30 days after the last sign-in).
5. A device has one live connection. A newer authenticated connection closes the older one with `connection_replaced`. The server writes at most one `connection.replaced` audit record per device per hour and logs the other replacements with a count.

Before `auth.ok`, no frame reaches `decodeClientEvent` or the event handler: a binary frame, a frame over 1 KiB (`MAX_AUTH_FRAME_BYTES`, measured on the raw frame before the JSON is parsed), a frame that is not JSON or that `decodeClientFrame` refuses, any frame other than `auth.response`, and a second frame close the connection with `protocol_violation`. A frame over 64 KiB closes with 1009 at any time, because the WebSocket library refuses it first. A connection that is refused before `auth.ok`, or that times out, gets its close frame and is terminated 1 second later, so that it frees its place without waiting up to 30 seconds for the closing handshake.

Messages after `auth.ok`:

1. Each text frame must contain one JSON message, which the gateway decodes with `decodeClientMessage`: an event, with the rules of `decodeClientEvent`, or a workspace subscription frame (`workspace.subscribe` or `workspace.unsubscribe`), which the gateway answers itself (see "Workspace subscriptions, presence, and delivery"). A second `auth.response` is `unexpected_frame`, a frame that only the server sends is `not_allowed_from_device`, and an unknown frame is `unknown_type`.
2. `bindIdentity` then binds the event to the connection (ADR 0006, identity binding). The event's `deviceId`, and for a `user` actor its `actor.userId`, must be the connection's; a mismatch is refused and audited as `event.identity_mismatch`, with the event ID as the subject and no workspace, because the event's workspace is unverified. It is never overwritten. Like `connection.replaced`, at most one such record is written per device per hour, and the other mismatches are logged with a count. Every event also reads the device again: a revoked device gets `device_revoked`; a newer sign-in, which replaced the key that signed, gets `key_replaced`; a disabled account gets `auth_failed`; a sign-out and a GitHub revocation after the sign-in get `sign_in_required`. The 30-day sign-in is not checked per event: an open connection may continue for 24 hours more, which the sweep checks. Last, the user must be an active member of `event.workspaceId` at this moment: a claimed person whose `removed_at` is empty. A workspace that does not exist is refused like one without the user.
3. Only the result, a `VerifiedEvent` (a second brand next to `UnverifiedEvent`, defined in `src/gateway.ts`), reaches the event handler, together with the `AuthenticatedConnectionContext`. The handler's type accepts nothing else. The default handler (`dispatchDeviceEvents`, `src/device-events.ts`) logs the event ID, the event type, and the connection ID at `debug` level and hands the event to the handler of its type: `chat.message.send` is stored and delivered (see "Project chat"), and `agent.run.state_changed` is recorded and relayed (see "Agent activity"). A type without a handler is only logged and answered with nothing; adding a type is one entry in the handler map. A handler may return an `EventRejection` when it finds, inside the transaction that would store the event, that the account is no longer an active member, that the device or the account may no longer act, or an identity mismatch that only the stored data shows, such as an agent that another device hosts; the gateway then closes the connection as it does after `bindIdentity`, and audits an identity mismatch with the same throttle (`auditIdentityMismatch`). How the server refuses an event that it does not accept, with `event.refused` or by closing the connection, is in the refusal table of the [protocol README](../../packages/protocol/README.md#chat-history-refused-events-and-agent-activity) (#27, #28).
4. Messages are handled one after another, in the order they arrived; the gateway awaits the event handler, which may return a promise, and the answer to a subscription frame before the next message. While messages wait, the gateway stops reading from the socket, so a fast sender cannot queue without bound. An event whose connection closed or was replaced during its checks is not delivered. A handler that throws or rejects closes the connection with 1011, and its error is logged through the redacting error serializer.
5. Anything else closes the connection. Frames that arrive after the gateway has decided to close are ignored.

The codes 4000 to 4006 and their reasons are `WS_CLOSE_CODES` of `@mymandev/protocol`, whose README lists what the desktop does for each. The codes from 1003 to 1013 stay provisional (P-24).

No authentication frame, nonce, or signature is logged. A refused connection is logged with its connection ID and the close reason only (`protocol_violation` at `debug` level, with what broke the rule, and the others at `info`), and an authenticated connection with its connection ID, user ID, and device ID. A connection that a route or the sweep closes is logged at `info` as "connection closed", with its connection ID and the close reason; a failed sweep is logged at `error` with a `DatabaseError`, which carries the SQLSTATE code and no SQL or parameters. What a client sends wrong on its socket, such as a frame over 64 KiB, is logged at `debug` level with the connection ID; any other socket error at `error` level.

`ConnectionRegistry` (`src/gateway.ts`) holds the open connections of the instance: the unauthenticated ones, for their cap, and the live connection of each device. `closeDevice(deviceId, reason, log)` and `closeUser(userId, reason, log)` close live connections with a close reason of the protocol and log each close; `closeConnection(deviceId, connectionId, reason, log)` closes one only while it is still the device's live connection. `live()` lists the live connections without their sockets, and `sendToUser(userId, frame, exceptDeviceId)` sends an account frame. The registry also holds the workspace subscriptions of the live connections: `subscribe`, `unsubscribe`, `subscriptions()`, `endSubscription(subscription)`, `endMembership(workspaceId, memberId)`, `sendToWorkspace(event, sender)`, which also reaches the sending connection when it is not subscribed, `sendToPeople(event, memberIds)`, which reaches only the connections subscribed as one of these people and is the only one that takes an event of `APPROVER_EVENT_TYPES`, such as a join request event, and `sendEvent(context, event)`, which reaches one connection only; `heartbeat(log)` runs one heartbeat of pings, `sendHeartbeats()` sends one round of `connection.heartbeat`, and every send checks the backpressure limit. `buildApp` takes a registry as an option, so tests can count and close connections.

Connections after `auth.ok` (ADR 0014, "Revocation, sign-out, and recovery"):

1. After its transaction commits, a route closes the affected connection at once: a sign-out with `sign_in_required`, a revocation with `device_revoked`, a sign-in of an existing device, which replaced its key, with `key_replaced`, and a sign-in that replaced a previous device with `device_revoked` for that device.
2. The account frames go only to the account's own connections, never to another account's, and only to connections that got `auth.ok` and are still open. `account.device_registered` reports a new device with its device list item (`current: false`); the new device has no connection yet. `account.device_revoked` reports a revocation over HTTP and a device that a sign-in replaced, with the reason and the time; the revoked device itself never gets it, because its connection closes first. `account.join_request_decided` reports that an owner or admin approved or denied one of the account's join requests (see Workspaces). `account.ownership_offered` and `account.ownership_offer_ended` report an ownership offer and its end without a transfer to the target's account and to the owner's account (#241), after the ownership routes commit; the desktop reloads the workspace view on both frames (see Workspaces). `account.ownership_transferred` reports to the former owner's account and to the new owner's account that an acceptance moved a workspace's ownership, with both people and the time. A frame is never repeated: after `auth.ok` the desktop reads its devices over HTTP.
3. Every 60 seconds (`CONNECTION_SWEEP_INTERVAL_MS`), `sweepConnections` re-checks the devices of all live connections with one batched query (`deviceRows`, at most 500 device IDs per query) and closes each connection that its device no longer accepts, with the reasons of the per-event check: `device_revoked`, `key_replaced`, `auth_failed`, or `sign_in_required`. It finds what no route of this API sees, such as the operator command `db:account`. The 30-day sign-in counts with a grace of 24 hours (`SIGN_IN_GRACE_MS`): a connection that is open when the sign-in expires stays open for 24 hours more, and the first sweep after that, up to 60 seconds later, closes it with `sign_in_required`. A sweep closes only the connection that it checked: a newer connection of the device that registered meanwhile stays open. Then the sweep re-checks the workspace subscriptions of the connections that stay open with one batched query (`activePeopleOf`, at most 500 pairs of a workspace and an account per query) and ends each subscription whose account is no longer an active member as the person it subscribed as, with `workspace.unsubscribed` and `membership_ended`. A tick while the previous sweep still runs is skipped, a failure of the database is logged and the next sweep tries again, and the interval stops when the API closes.
4. `devices.last_seen_at` is written at `auth.ok` and then by the sweep, at most every 5 minutes per device (`LAST_SEEN_INTERVAL_MS`), with one update for every device that is due (`markDevicesSeen`). A revoked device is left unchanged, also one revoked since the sweep read it. A device row that another transaction holds, such as a sign-in or a revocation, is skipped: the update never waits for a locked row, so it cannot deadlock with such a transaction. A skipped device is written at its next due time.
5. Every 30 seconds (`HEARTBEAT_INTERVAL_MS`) the heartbeat pings every live connection and terminates one that did not answer the previous ping with a pong, without a close frame, because its peer is gone. A half-open connection, whose device vanished without a close, therefore ends within 60 seconds instead of staying until its sign-in expires; its subscriptions end at once, so its person goes offline. Standard WebSocket clients, Node.js and Chromium among them, answer pings on their own. The termination is logged at `info` as "connection terminated" with the connection ID and the reason `no_pong`.
6. Every 15 seconds (`CONNECTION_HEARTBEAT_INTERVAL_MS` of the protocol) `sendHeartbeats` sends the frame `connection.heartbeat` to every live connection that got `auth.ok` and is still open, never before `auth.ok` and never after the connection closed or left the registry (the Project Manager's decision of 2026-11-23, #316). A desktop cannot see the pings of item 5, which `net.WebSocket` answers on its own, so it closes and reconnects when no message of any kind arrived for 45 seconds (`CONNECTION_LIVENESS_BOUND_MS`), before the pings end the connection here. One interval serves every connection, so no timer belongs to a connection and none outlives it; it stops when the API closes. `buildApp` turns it on; the test apps turn it off with its option `connectionHeartbeat: false`, so that a test client never reads a heartbeat in place of the frame it waits for, and only the heartbeat tests turn it on. A desktop built before this change refuses the unknown frame and reconnects in a loop, so it is rebuilt: protocol version 0 requires both sides to run the same version (ADR 0006).
7. Backpressure: before the server queues a frame, a ping, or an event for a live connection, it checks how much still waits to be sent; a `connection.heartbeat` counts as a frame. Above 1 MiB (`MAX_BUFFERED_BYTES`) it queues nothing more and closes the connection with 1013 and `backpressure`; the connection leaves the registry with its subscriptions at once, so its person goes offline. The WebSocket library terminates the socket if the closing handshake does not end within 30 seconds.

Decisions that ADR 0014 leaves open, settled by the Project Manager on 2026-10-31 (#89):

- A frame that breaks the rules before authentication closes with the new code `protocol_violation` (4005). The desktop does not reconnect on its own and shows an error; when the protocol versions differ, it asks the person to update.
- A connection whose key a newer sign-in of the device has replaced closes with the new code `key_replaced` (4006); the desktop reconnects at once with its new key.
- Above the cap of 200 unauthenticated connections, the handshake gets `429` with `rate_limited` and `Retry-After` before the upgrade.
- `devices.last_seen_at` is written when a connection authenticates, and by the sweep at most every 5 minutes for an open connection.
- Without the sign-in configuration or without the database, `/ws` answers `404`; the unauthenticated mode of M1-02 is gone.

#### Workspace subscriptions, presence, and delivery

These rules follow #110, the protocol's "Workspace subscriptions, presence, and chat", and the Project Manager's decisions of 2026-11-01. The frames come from [`@mymandev/protocol`](../../packages/protocol/README.md).

1. A connection receives a workspace's events and presence only while it is subscribed to the workspace. `workspace.subscribe` first checks the cap: a connection holds at most 50 subscriptions (`MAX_SUBSCRIPTIONS_PER_CONNECTION`), and one more gets `workspace.subscribe_refused` with `too_many_subscriptions`, whatever the workspace, so the answer tells nothing about it; subscribing again to a held workspace still works. Then `subscriptionAccess` reads the device again, as for every event, and a device that may no longer act closes the connection with its reason; and it looks up the account's active person in the workspace. A workspace that does not exist and one without the account as an active member get the same `workspace.subscribe_refused` with `not_found`, and the connection stays open. Otherwise the gateway records the subscription as that person and answers `workspace.subscribed` with the people online. Subscribing again keeps one subscription and answers again.
2. `workspace.unsubscribe` ends the subscription and answers `workspace.unsubscribed` with `requested`, also when the connection was not subscribed.
3. Presence is per person and never stored: a person is online in a workspace while at least one live connection of the account is subscribed to it as that person. `workspace.subscribed` carries the snapshot (each online person once, at most 1,000, with the subscriber's own person first, so that a list cut at 1,000 keeps it), and the other subscribed connections get `presence.changed` only when a person's status changes: the first subscribed connection of a person brings it `online`, and the end of its last one `offline`. A second device of a person who is online changes nothing. No subscription or presence frame names a device.
4. A subscription ends when the device unsubscribes, when the connection closes or is replaced, and when the gateway or a route closes the connection: at that moment, before the closing handshake ends, so that the connection gets nothing more and its person goes offline at once.
5. After the commit, each membership event and each project event goes to the connections subscribed to its workspace, and to no one else. A join request event goes only to those of them subscribed as the workspace's owner or an admin (#210, see Workspaces). A connection whose socket the server is closing is skipped.
6. Membership ends: `workspace.member.removed`, after a removal or a departure, first ends the removed person's subscriptions, each with `workspace.unsubscribed` and `membership_ended`, so the removed account never gets the event, and the other subscribers see the person go offline before the event. Then every connection of the removed account gets `account.removed_from_workspace`, and the runs that the removal cancelled follow (item 7). The sweep ends a subscription whose account is no longer an active member, and so does an event that identity binding refuses with `not_a_member` for a subscribed workspace, before the connection closes as before; a new `workspace.subscribe` that finds the membership ended ends the held subscription the same way and answers `not_found`. A removal that the server processes in a workspace while a subscribe to that workspace checks the membership makes the subscribe check again, so the check cannot record a subscription for a person who was just removed; a removal in another workspace changes nothing. A subscribe checks again at most 3 times (`MAX_SUBSCRIBE_RECHECKS`): when the last check overlapped a removal too, it answers `not_found`, a subscription that the connection held to the workspace ends with it, and the device may subscribe again.
7. Disabled agents, revoked grants, and cancelled runs: after a device revocation commits, through `POST /devices/:deviceId/revoke` or a sign-in that replaces a previous device, the route closes the device's connection, and after a removal or a departure commits, the route ends the person's subscriptions (item 6). Then it sends each agent that the transaction disabled as `workspace.agent.disabled` through the membership event delivery to the connections subscribed to the agent's workspace, in the order of the agent IDs, with the agent as the agent list shows it and never its host device, as the agent route sends it (#326). Then it sends each grant that the transaction revoked as `agent.grant.revoked` to the connections subscribed to the grant's workspace (#75), and then each run that the transaction cancelled as `agent.run.state_changed` to the connections subscribed to the run's workspace: a `system` actor, `deviceId: null`, the run's correlation ID when it has one, and a payload with the run and its agent, its repository when it has one, its state before, `cancelled`, and the reason code stored with the run, `device_revoked` or `member_removed` (ADR 0014, P-60). `revokeDevice`, `removeMember`, and `leaveWorkspace` return what the run events need, and the IDs of the disabled agents and of the revoked grants, which the route reads again with `disabledAgentsOf` and `revokedGrantsOf` inside its transaction for the agent and grant events. The order is the agent route's: the agents, then the grants, then the runs.
8. Events are not replayed and have no server sequence number: after every `workspace.subscribed`, also after a reconnect, the desktop reloads the workspace over HTTP and applies the events that arrived since that frame on top of it, as the protocol's README describes.

Decided by the Project Manager on 2026-11-01 (#110): subscribing is explicit; presence is per person, `online` or `offline`, never stored, a snapshot on subscribe and then the changes, with no device ID; a project event goes to every subscribed connection of the workspace; storing and relaying chat messages belongs to #27; M2 has no server sequence number; and the runs that a device revocation cancelled go to the workspace's subscribed connections as `agent.run.state_changed`.

Settled here: the cap of 50 subscriptions per connection, which the protocol leaves to the server (P-64); a subscribe re-checks the device as an event does; the subscriptions end when the server decides to close a connection, not when its closing handshake ends; a subscribe whose membership check keeps overlapping removals in its workspace answers `not_found` after 3 more checks, rather than closing the connection with 1011, so that the connection keeps its other subscriptions; a heartbeat every 30 seconds ends a connection that missed a ping; and a connection with more than 1 MiB waiting to be sent closes with 1013 and `backpressure`, a code of RFC 6455's registry that asks the client to try again later, because the protocol's codes from 4000 are for authentication and the device.

`chat.message.send` is stored and delivered since #27 (see "Project chat"), the project events since #155, and the run transitions that a host device reports since #28 (see "Agent activity").

## Rules

- Credentials never appear in URLs, including the WebSocket URL. A browser `WebSocket` cannot set headers, which invites `/ws?token=...`; the query string would then reach proxies and browser history. WebSocket authentication uses the first message, `auth.response`.
- Logs contain the request method, the path without the query string, and the remote address. Errors are logged with their type, codes, message, and stack; an error that may carry query data (an own `query`, `params`, or `detail` property) is logged without message and stack.
- An event from a device stays `UnverifiedEvent` until `bindIdentity` has bound it to the authenticated connection. Never cast it to `ProtocolEvent` or to `VerifiedEvent`; only `bindIdentity` creates a `VerifiedEvent`, and the event handler accepts only that type with an `AuthenticatedConnectionContext`.
- `src/server.ts` is the only module with side effects. Tests build the application with `buildApp` from `src/app.ts` and use `inject` and `injectWS` without a network.

## Not included

Sessions, CORS, OpenAPI, TLS, account erasure, permission enforcement, Docker, deployment configuration, clustering, a build step, pretty-printed logs, and a Fastify type provider.

Account erasure (#93) is the operator command `db:account -- erase` of [`@mymandev/database`](../../packages/database/README.md#operator-commands), not a route. It runs outside the API, so the API sends no `workspace.member.removed`, account frame, `workspace.agent.disabled`, `agent.grant.revoked`, or `agent.run.state_changed` for an erasure (recommendation 5 of #75, which #326 follows for the disabled agents): the sweep closes the account's connections, and the other members see the change when they next load the workspace. An erasure of an owner archives each workspace in which no other active member with an account remains, and replaces the names of the workspace, its projects and repositories, and its unclaimed people with fixed placeholders (the Project Manager's decisions of 2026-11-02): nobody with an account is active in it afterwards, so `GET /workspaces` lists it for nobody, every route under `/workspaces/:workspaceId` answers as for a non-member, a join request answers `workspace_not_found`, and its invitation codes `invitation_invalid`. There is no route that archives a workspace.
